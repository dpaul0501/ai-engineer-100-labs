DAY 2 · THE TOP KDSA

The top k: from a thousand counts to the ten on screen

Where we are. Day 1 ended with a dictionary for every user: each candidate, and how many mutual friends they share. On the week's data that dictionary is big. The smallest has 5 candidates, the median 888, the mean 1,191, and the largest 8,271. One user in ten has at least 2,478, and one in a hundred at least 4,607. The app shows ten. Today is about picking those ten: first from a dictionary that sits still while you look at it, then from counts that keep changing as friendships arrive, and finally, as an advanced part, from counts spread over many machines.

By hand. You's dictionary is Esha 2, Dev 1, Farid 1. The top 2 is Esha, then one of Dev and Farid, who tie on 1. The rule from the reading settles it: on a tie, the smaller id goes first. Dev is 3 and Farid is 5, so the answer is Esha, Dev. Every method on this page must return exactly that list, and the tie rule turns out to matter far more than this tiny example suggests.

DSA · the static top k: the list is fixed when you ask

1 · The obvious attempt: sort everything

The situation. A request for You arrives. Day 1's counting pass has built the dictionary; nothing changes while we pick. Write n for the number of candidates and k for how many we show (10).

The obvious attempt. Sort every candidate by (most mutual friends, then smaller id) and keep the first ten. It is one line, obviously correct, and it is the oracle every faster method is tested against.

code/day_2/topk.py · sort
def topk_sort(count, k):
    """O(n log n): sort every candidate, keep the first k."""
    return sorted(count, key=lambda v: (-count[v], v))[:k]

Where it breaks. Sorting costs about \(n\log_2 n\) comparisons, so the work per candidate grows with n. Measured on a sample of 1,000 users (mean 1,195 candidates), Python's sort made 9.41 comparisons per candidate. Nearly all of them put candidate 412 before candidate 413 in an order nobody will ever see.

2 · Keep the ten best so far, with the worst of them on top

The idea in plain words. Walk through the candidates once and keep only the best ten seen so far. Arrange them so the worst of the ten is always the one you can see. Each new candidate is compared with that one. If it is not better, it is thrown away after one comparison. If it is better, it replaces the worst, and the pile reorders itself. The structure that keeps the smallest item on top and reorders in about \(\log_2 k\) steps is a binary min-heap; Python's is heapq.

The tie rule goes into the key: store (count, −id), so a larger tuple is a better candidate, and the root of the min-heap is the worst one kept.

code/day_2/topk.py · size-k heap
def topk_heap(count, k):
    """O(n log k) time, O(k) memory: keep the k best seen so far; the worst of them sits on top."""
    if k <= 0:
        return []
    heap = []                                   # items (m, -v): the root is the worst one kept
    for v, m in count.items():
        item = (m, -v)                          # bigger is better: more friends, then smaller id
        if len(heap) < k:
            heapq.heappush(heap, item)
        elif item > heap[0]:                    # beats the worst kept: replace it
            heapq.heapreplace(heap, item)
    return [-nv for m, nv in sorted(heap, reverse=True)]

Measured. 1.17 comparisons per candidate on the same 1,000 users, eight times fewer than sorting. Most candidates lose to the root and leave. For the user with the most candidates (8,271), the heap changed only 78.1 times on average over 20 random orders of the candidates; the math below predicts \(k(1+\ln(n/k)) = 10(1 + \ln 827.1) = 77.2\).

3 · Quickselect: throw away the half that cannot hold the answer

The idea in plain words. Pick a random candidate as a pivot and split the others into "better than the pivot" and "worse". If ten or more are better, the answer is among them: repeat there and forget the rest. If fewer, they all belong to the answer, together with the pivot: keep them and look for the remainder among the worse ones. Each round discards a large share of what is left. At the end, sort just the ten.

code/day_2/topk.py · quickselect
def topk_quickselect(count, k, seed=0):
    """O(n) on average: split around a random pivot, keep only the side that holds the answer."""
    rng = random.Random(seed)
    keys = [(-m, v) for v, m in count.items()]  # distinct keys; smaller is better
    best = []
    while k > 0 and keys:
        p = rng.choice(keys)
        better = [x for x in keys if x < p]
        if len(better) >= k:
            keys = better                       # all k answers are better than the pivot
        else:
            best += better + [p]                # all of these are answers
            k -= len(better) + 1
            keys = [x for x in keys if x > p]
    return [v for _, v in sorted(best)]

Measured. 2.18 comparisons per candidate, counting every element of every pass. That is the best guarantee on paper, O(n) on average whatever k is, but for k = 10 it loses to the heap: quickselect makes a couple of full passes and builds new lists, while the heap makes one pass and rarely does anything but compare.

4 · Bucket counting: the counts are small whole numbers

The situation, looked at again. A mutual-friend count is a whole number between 1 and the number of friends you have. On the week's data the 11,908,610 (user, candidate) counts are tiny: 86.6% equal 1 and 99.0% are at most 3. The largest count anywhere is 67, and the largest count in a typical user's dictionary is 5.

The idea. Do not compare candidates at all. Make one bucket per possible count, drop each candidate into the bucket of its count, then walk the buckets from the top down, taking candidates until you have ten. Only the last bucket you take from needs ordering, and only by id. For You: bucket 2 holds Esha, bucket 1 holds Dev and Farid. Take Esha; one more is needed, and the smallest id in bucket 1 is Dev.

code/day_2/topk.py · bucket counting
def topk_bucket(count, k):
    """O(n + max count): counts are small whole numbers, so drop each candidate in the bucket of
    its count and walk the buckets from the top. Only the last bucket touched needs ordering."""
    if not count:
        return []
    buckets = [[] for _ in range(max(count.values()) + 1)]
    for v, m in count.items():
        buckets[m].append(v)
    out = []
    for m in range(len(buckets) - 1, 0, -1):
        need = k - len(out)
        if need == 0:
            break
        out += heapq.nsmallest(need, buckets[m])   # smallest ids first inside a bucket
    return out

Measured. 1.06 steps per candidate: one to drop each candidate in its bucket, one per bucket visited, plus the comparisons inside the last bucket. This is 347's trick, and it is the day's first live problem.

6 · Ties, and why the list must be the same every time

The situation. With counts this small, ties are not a corner case. Of the 9,998 users with more than ten candidates, 9,271 (92.7%) have a tie between their 10th and 11th candidate. Without a tie rule, "the top 10" is not one list but many, and which one you get depends on the order a dictionary happens to iterate in, or which machine answered first.

  • Tests. The sort is the oracle. If two correct methods may return different lists, an exact comparison fails at random and the test gets loosened until it no longer catches real bugs.
  • Caching. A cached list that differs from a fresh one with no change in the data looks like a change to every system downstream: the user sees the list reshuffle on refresh, and anything that compares old and new lists does useless work.
  • Experiments. On Day 4, two versions of the ranker are compared on real users. Random reshuffling at the cutoff adds noise to both arms that has nothing to do with either version.

So the rule is part of the key, in every method: (count, −id) in the heap, (−count, id) in quickselect, and smallest ids first inside a bucket. Each key is unique because ids are, so every method has exactly one right answer.

Interview takeaway
  • "Top k of n: sort is O(n log n); a size-k min-heap whose root is the worst kept is O(n log k) time and O(k) memory and works on a stream; quickselect is O(n) on average; if the scores are small integers, bucket them in O(n + max)."
  • Say the tie rule before you code, and put it in the key.
  • Follow-ups to expect. k close to n? Quickselect, or select the n − k to drop. Output in order? Pop the heap: k log k more. Data too big for memory? The heap reads it once and keeps k. Worst case matters? Quickselect with a median-of-medians pivot is O(n) always, rarely worth it in practice.

In one line. Compare each candidate with the worst of the ten kept, and most are rejected in one comparison; when the scores are small whole numbers, do not compare at all.

The math, step by step: the cost of sorting, why the heap is correct and how often it changes, quickselect's average

Order candidates by the key (−count, id): smaller is better, and no two keys are equal because ids differ.

Sorting needs about n log₂ n comparisons. A comparison sort must be able to produce any of the n! orders, and each comparison has two outcomes, so it needs at least \(\log_2 n!\) comparisons in the worst case. Stirling's formula gives

\[ \log_2 n! \;\approx\; n\log_2 n - n\log_2 e \;\approx\; n\log_2 n - 1.44\,n . \]

For n = 1,195, \(\log_2 1{,}195 \approx 10.2\), so about 10.2 − 1.44 ≈ 8.8 comparisons per candidate. Python's sort made 9.41 on average over the sampled users, close to this floor.

The heap is correct. Claim: after the first i candidates, the heap holds exactly the best \(\min(i,k)\) of them. True while it fills. Suppose it is true and the heap is full; its root r is the k-th best so far. A new candidate x worse than r is beaten by k candidates already seen, so it cannot be in the top k, and leaving the heap alone is right. If x beats r, the new top k is the old one with r swapped for x, which is what heapreplace does.

How often the heap changes. In a random order, the i-th candidate goes in exactly when it is among the best k of the first i. Each of those i is equally likely to hold any rank, so for i > k the chance is \(k/i\). Try k = 10: the 20th candidate goes in with chance 1/2, the 1,000th with chance 1/100. Adding up,

\[ E[\text{insertions}] \;=\; k + \sum_{i=k+1}^{n}\frac{k}{i} \;\approx\; k\Big(1 + \ln\frac{n}{k}\Big). \]

Each insertion costs O(log k); every other candidate costs one comparison. So the total is about n + (a few dozen) × log₂ k, which is why 1.17 per candidate was measured.

Quickselect averages a constant per candidate. A round over s keys costs at most 2s comparisons (two passes). Call a round good if the pivot lands in the middle half of the ranks; a random pivot is good with probability 1/2, so on average two rounds bring one good one, and after it at most 3s/4 keys remain. Shrinking from s to 3s/4 therefore costs at most 4s on average, and

\[ E[\text{comparisons}] \;\le\; 4n\Big(1 + \tfrac34 + \big(\tfrac34\big)^2 + \cdots\Big) \;=\; \frac{4n}{1 - 3/4} \;=\; 16\,n . \]

The bound is loose: 2.18 per candidate was measured. The worst case, a bad pivot every round, is \(n^2\), and random pivots make it vanishingly unlikely.

Bucket counting. Dropping n candidates costs n; the walk visits at most M buckets, where M is the largest count; choosing the smallest ids from the buckets taken costs O(b log k) for a bucket of size b. In total O(n + M), and here M ≤ 67.

DAY 2 · THE TOP KDSAML

The top k when the data keeps arriving

The situation. The dictionary does not sit still. The week's 100,000 friendships are stored in the order they formed (column t of edges.csv), and every new one changes someone's counts. Replaying them in that order turns the static question into three stream questions: keep every user's ten fresh as friendships arrive; track a statistic of the stream, such as the median; and find the items that occur most often when there are too many items to count them all.

DSA · counts that change: keeping every top 10 fresh

7 · What one new friendship changes

By hand. Suppose Dev and Chloe become friends. Chloe is now a mutual friend of Dev and of each of Chloe's other friends: You, Esha and Farid (Ben is already Dev's friend, so nothing changes there). That is three pairs, each counted from both sides: six count changes. And Chloe stops being Dev's candidate, because she is now his friend. For You, Dev goes from 1 to 2 and ties with Esha; Dev has the smaller id, so You's top 2 becomes Dev, Esha.

The idea. Keep the counts and the top 10 for every user, and update them in place. A count that goes up is easy: the candidate either is already in the ten (move it up) or must beat the worst of the ten to enter, the same one comparison as the size-k heap. A candidate that disappears (because the two just became friends) is the hard case: if it was in the ten, the eleventh best has to be found again, from the full dictionary.

code/day_2/fresh.py · exact top k under new friendships
class FreshTopK:
    def __init__(self, k=10):
        self.k = k
        self.friends = defaultdict(set)
        self.count = defaultdict(dict)   # user -> {candidate: mutual friends}, always exact
        self.top = defaultdict(list)     # user -> sorted (-count, id), at most k long
        self.changes = self.top_changes = self.recomputes = 0

    def bump(self, x, y):
        """y gained one mutual friend with x. Counts only grow here, so x's top k changes
        only if y is already in it or now beats the worst of it."""
        self.changes += 1
        c = self.count[x][y] = self.count[x].get(y, 0) + 1
        t = self.top[x]
        for i, (_, v) in enumerate(t):
            if v == y:
                t[i] = (-c, y)
                if i > 0 and t[i] < t[i - 1]:
                    t.sort(); self.top_changes += 1
                return
        if len(t) < self.k or (-c, y) < t[-1]:
            t.append((-c, y)); t.sort(); del t[self.k:]; self.top_changes += 1

    def unlink(self, x, y):
        """x and y just became friends, so y stops being x's candidate. If y was in x's top k,
        the next best must be found again from the full dict."""
        if self.count[x].pop(y, None) is not None and any(v == y for _, v in self.top[x]):
            self.recomputes += 1
            self.top[x] = sorted(heapq.nsmallest(self.k, ((-c, v) for v, c in self.count[x].items())))

    def add_friendship(self, a, b):
        self.unlink(a, b); self.unlink(b, a)
        for f in self.friends[b]:            # b becomes a mutual friend of a and each f
            if f != a and f not in self.friends[a]:
                self.bump(a, f); self.bump(f, a)
        for f in self.friends[a]:            # a becomes a mutual friend of b and each f
            if f != b and f not in self.friends[b]:
                self.bump(b, f); self.bump(f, b)
        self.friends[a].add(b); self.friends[b].add(a)

    def suggest(self, u):
        return [v for _, v in self.top[u]]

    s.add_friendship(a, b)
assert s.count[YOU] == {DEV: 1, ESHA: 2, FARID: 1} and s.suggest(YOU) == [ESHA, DEV]
before = s.changes
s.add_friendship(DEV, CHLOE)                 # Chloe now vouches for Dev with You, Esha and Farid
assert s.changes - before == 6               # Dev-You, Dev-Esha, Dev-Farid, both directions

assert s.count[YOU] == {DEV: 2, ESHA: 2, FARID: 1}
assert s.suggest(YOU) == [DEV, ESHA]         # a tie at 2; Dev has the smaller id

Measured, replaying all 100,000 friendships. The friendships caused 14,280,420 count changes: 143 per new friendship on average and 3,308 for the most expensive one (a friendship involving a user with very many friends touches all their friends). Only 5.2% of those changes altered anybody's top 10; the rest stopped at the one comparison with the worst of the ten. Removals forced 16,795 recomputes from the full dictionary, 16.8 per 100 friendships: each one is a new friend who had been in the other person's top 10 when the friendship formed. At the end, every user's counts and top 10 were checked against a fresh recount.

The takeaway for design: per new friendship, the work is proportional to how many friends the two people have, and almost none of it changes what anyone sees. That is the case for updating stored lists incrementally rather than recomputing them; Day 5 builds that pipeline.

8 · A stream of numbers: the k-th largest so far (LeetCode 703)

The size-k heap needs nothing from the future: it reads each item once and keeps k. That makes it the standard answer for "top k of a stream" and for 703, the day's second live problem: after each new number, report the k-th largest seen so far. The root of a size-k min-heap is exactly that number.

code/day_2/stream.py · LeetCode 703
class KthLargest:
    """703: a size-k min-heap; its root is the k-th largest number seen so far."""

    def __init__(self, k, nums):
        self.k, self.heap = k, []
        for x in nums:
            self.add(x)

    def add(self, val):
        if len(self.heap) < self.k:
            heapq.heappush(self.heap, val)
        elif val > self.heap[0]:
            heapq.heapreplace(self.heap, val)
        return self.heap[0]

O(log k) per number and O(k) memory, however long the stream runs.

9 · A statistic of a stream: the running median with two heaps (LeetCode 295)

The situation. A useful health number for any friend-suggestion product: when a friendship forms, how many mutual friends did the two people already have? If most new friendships close a triangle through a mutual friend, mutual-friend counting is aimed at the right people. We want this as a running number, without storing every value.

The idea. Keep the smaller half of the values in a max-heap and the larger half in a min-heap. The median sits at the top of one or between the two tops. Each new value goes through the lower heap into the upper one, and one value moves back if the halves become uneven: O(log n) per value. Moving the boundary from the half to 90% gives any percentile with the same two heaps.

code/day_2/stream.py · LeetCode 295, and any percentile
class MedianFinder:
    """295: lower half in a max-heap (stored negated), upper half in a min-heap; len(lo) - len(hi) is 0 or 1."""

    def __init__(self):
        self.lo, self.hi = [], []

    def addNum(self, num):
        heapq.heappush(self.lo, -num)
        heapq.heappush(self.hi, -heapq.heappop(self.lo))   # the largest of the lower half moves up
        if len(self.hi) > len(self.lo):
            heapq.heappush(self.lo, -heapq.heappop(self.hi))

    def findMedian(self):
        if len(self.lo) > len(self.hi):
            return float(-self.lo[0])
        return (-self.lo[0] + self.hi[0]) / 2


class QuantileFinder:
    """Any running percentile with the same two heaps: lo keeps the ceil(q*n) smallest numbers,
    so its largest one is the nearest-rank q-quantile. q = 0.5 gives the lower median."""

    def __init__(self, q):
        self.q, self.n, self.lo, self.hi = q, 0, [], []

    def add(self, num):
        self.n += 1
        heapq.heappush(self.lo, -num)
        heapq.heappush(self.hi, -heapq.heappop(self.lo))
        while len(self.lo) < math.ceil(self.q * self.n):
            heapq.heappush(self.lo, -heapq.heappop(self.hi))

    def value(self):
        return -self.lo[0]

ML · heavy hitters: too many items to count them all

10 · Who gained the most friends this hour?

The situation. A "trending" feature, or a check for accounts adding friends suspiciously fast, needs the users who gained the most friends in the last hour. Each new friendship is two arrivals, one per person. In the last hour of the replay there are 20,000 arrivals from 7,819 different users; the exact top 10 gained 142, 109, 102, 99, 70, 52, 52, 45, 40 and 39 friends.

The obvious attempt is a dictionary with a counter per user and a top-k at the end. It is exact, and its memory grows with the number of distinct users. Suppose 100 million users each gain a friend in an hour: at 16 bytes per entry that is 1.6 GB per window, per machine that counts. We want memory set by how many winners we need, not by how many users there are.

Misra–Gries: m counters, and everyone pays when there is no room. Keep at most m counters. An arrival with a counter adds one. An arrival with no counter takes a free one. If none is free, every counter drops by one, the newcomer's arrival included, and counters at zero are freed. Each estimate is an undercount, by at most N/(m+1) after N arrivals.

Space-Saving: the newcomer takes over the smallest counter. Same m counters, one change: with no room, the newcomer replaces the item with the smallest counter and inherits its count plus one. Each estimate is now an overcount, by at most N/m, and the counter remembers how much of it may be inherited.

code/day_2/stream.py · Space-Saving
class SpaceSaving:
    """m counters. A new item takes over the smallest counter and inherits its count + 1,
    so each estimate is an overcount by at most N/m; the item's error is stored with it."""

    def __init__(self, m):
        self.m, self.c, self.err = m, {}, {}
        self.heap = []                          # (count, item), with stale entries skipped lazily

    def add(self, x):
        if x in self.c:
            self.c[x] += 1
        elif len(self.c) < self.m:
            self.c[x], self.err[x] = 1, 0
        else:
            while True:                         # find the current smallest counter
                cnt, y = heapq.heappop(self.heap)
                if self.c.get(y) == cnt:
                    break
            del self.c[y], self.err[y]
            self.c[x], self.err[x] = cnt + 1, cnt   # x may have been seen up to cnt times before
        heapq.heappush(self.heap, (self.c[x], x))
        if len(self.heap) > 4 * self.m:         # drop stale entries now and then
            self.heap = [(c, y) for y, c in self.c.items()]
            heapq.heapify(self.heap)

    def estimate(self, x):
        return self.c.get(x, 0)

    def top(self, k):
        return heapq.nsmallest(k, self.c, key=lambda y: (-self.c[y], y))

Read it through the bound. The guarantee covers only items that occur more than N/m times. The leader gained 142 friends, so it is guaranteed only once 20,000/m < 142, that is m ≥ 141. At m = 200 the bound is 100, so the three users above 100 are safe, and recall is 0.6. The math, step by step: why Misra–Gries undercounts by at most N/(m+1), and Space-Saving overcounts by at most N/m

Misra–Gries. Call an arrival that finds no free counter a decrement step. It lowers m counters by one and throws away its own arrival: m + 1 units of count disappear. Counts never go below zero, and the total that ever went in is N, so there are at most N/(m+1) decrement steps. An item's counter misses one of its arrivals only in a decrement step (its own counter dropped, or it was the newcomer thrown away), so

\[ \text{true}(x) - \frac{N}{m+1} \;\le\; \text{estimate}(x) \;\le\; \text{true}(x). \]

Any item with more than N/(m+1) arrivals therefore still has a positive counter at the end: it cannot be lost.

Space-Saving. Every arrival raises the sum of the counters by exactly one (a takeover replaces a count c by c + 1). So once the counters are full, they add up to N, and the smallest of the m is at most N/m. A newcomer inherits the smallest count, and that inheritance is the only error it ever carries:

\[ \text{true}(x) \;\le\; \text{estimate}(x) \;\le\; \text{true}(x) + \text{err}(x), \qquad \text{err}(x) \le \min \text{counter} \le \frac{N}{m}. \]

An item without a counter at the end has been seen at most as often as the current smallest counter, at most N/m, so any item above N/m is kept. The tests in stream.py check all four inequalities on 30 random skewed streams. Because each estimate comes with its error, an item whose (estimate − err) beats the next item's estimate is certainly in the top k.

11 · Count-Min: counts without storing ids

The idea. Keep d rows of w counters and one hash function per row. An arrival adds one to its cell in every row. To estimate an item's count, read its d cells and take the smallest. Other items that land in the same cell can only add to it, so the estimate never undercounts, and taking the minimum over rows keeps the excess small. The sketch stores no ids, so for a top k it is paired with a size-k heap of the items with the largest estimates so far.

code/day_2/stream.py · Count-Min, with a small top-k on the side
class CountMin:
    """d rows of w counters. An estimate never undercounts, and overcounts by more than
    (e/w)·N with probability at most e^-d. It stores no ids, so a size-k heap keeps the candidates."""

    P = (1 << 61) - 1

    def __init__(self, w, d, k, seed=0):
        rng = random.Random(seed)
        self.w, self.k = w, k
        self.ab = [(rng.randrange(1, self.P), rng.randrange(self.P)) for _ in range(d)]
        self.rows = [[0] * w for _ in range(d)]
        self.best = {}                          # the k items with the largest estimates so far

    def _cells(self, x):
        return [((a * x + b) % self.P) % self.w for a, b in self.ab]

    def add(self, x):
        est = None
        for row, j in zip(self.rows, self._cells(x)):
            row[j] += 1
            est = row[j] if est is None else min(est, row[j])
        if x in self.best or len(self.best) < self.k:
            self.best[x] = est
        else:
            worst = min(self.best, key=lambda y: (self.best[y], -y))
            if (est, -x) > (self.best[worst], -worst):
                del self.best[worst]
                self.best[x] = est

    def estimate(self, x):
        return min(row[j] for row, j in zip(self.rows, self._cells(x)))

    def top(self, k):
        return sorted(self.best, key=lambda y: (-self.estimate(y), y))[:k]

The math, step by step: the Count-Min error bound

Fix an item x and one row. Its cell holds true(x) plus the arrivals of every other item hashed to the same cell. With a hash family where two different items collide with probability 1/w, the expected excess is

\[ E[\text{excess}] \;=\; \sum_{y \ne x} \text{true}(y)\cdot\frac1w \;\le\; \frac{N}{w}. \]

The excess is never negative, so Markov's inequality applies: the chance it exceeds e times its mean is at most 1/e.

\[ P\Big(\text{excess} > \frac{e}{w}N\Big) \;\le\; \frac1e . \]

The estimate is the minimum over d rows with independent hashes, and it is too large only if every row is: probability at most \(e^{-d}\). So with \(w = \lceil e/\varepsilon \rceil\) and \(d = \lceil \ln(1/\delta) \rceil\), every estimate is within \(\varepsilon N\) with probability at least \(1 - \delta\). With d = 4 that probability is \(1 - e^{-4} \approx 98.2\%\) per item; with w = 500 and N = 20,000 the bound is \(2.718 \times 20{,}000 / 500 \approx 109\), and the largest overcount measured was 51.

12 · Windows: "this hour" in three ways

  • Tumbling. Start fresh summaries every hour, as the medians above did. Cheap; the answer jumps at the hour boundary.
  • Sliding, exact. Keep the last W arrivals in a queue: count the newcomer, uncount the one that fell out. Exact, with memory proportional to W.
  • Sliding, approximate. Split the hour into, say, six ten-minute pieces, keep one sketch per piece, and add the six when asked. Count-Min sketches with the same hashes add cell by cell; every ten minutes the oldest piece is dropped. Memory is six sketches, whatever the traffic.
code/day_2/stream.py · exact counts over the last W arrivals
class WindowCounts:
    """Exact counts over the last W arrivals: add the newcomer, forget the one that fell out."""

    def __init__(self, W):
        self.W, self.q, self.c = W, deque(), Counter()

    def add(self, x):
        self.q.append(x)
        self.c[x] += 1
        if len(self.q) > self.W:
            old = self.q.popleft()
            self.c[old] -= 1
            if self.c[old] == 0:
                del self.c[old]

Advanced · at scale: the top k when the counts live on many machines

The situation. At a billion users, neither the friend lists nor the candidate counts fit on one machine. They are split into shards, and a request for You asks s shards for their part and combines the answers at a coordinator. Systems · local top k, then merge

14 · Each shard sends its top k; a heap of heads merges them

When each candidate lives on exactly one shard, for example when candidates are split by id, each shard holds complete counts for its candidates and returns its ten best, best first. The best item overall must be the head of one of these lists. So keep the heads in a heap ordered best-first, pop the best, and push the next item from the same list: LeetCode 23's merge, stopped after k pops.

code/day_2/distributed.py · merge the shards' lists
def local_top(count, k):
    """What one shard sends: its k best (count, id) pairs, best first."""
    return [(v, count[v]) for v in topk_sort(count, k)]


def merge_topk(lists, k):
    """lists: one best-first list of (id, count) per shard. Returns the k best ids overall.
    Exact when every id lives on exactly one shard. O(s + k log s) for s shards."""
    heap = [(-lst[0][1], lst[0][0], s, 0) for s, lst in enumerate(lists) if lst]
    heapq.heapify(heap)                          # one entry per shard: its best unsent item
    out = []
    while heap and len(out) < k:
        _, v, s, i = heapq.heappop(heap)         # the best head is the best item left anywhere
        out.append(v)
        if i + 1 < len(lists[s]):
            w, c = lists[s][i + 1]
            heapq.heappush(heap, (-c, w, s, i + 1))
    return out

Cost. The heap never holds more than one entry per shard, so each pop costs about log₂ s, and the merge reads at most s + k items, however many candidates each shard has. Measured: with each user's candidates split by id mod s, the merged top 10 equalled the single-machine top 10 for all 10,000 users at s = 2, 4, 8 and 16, and each shard sent at most 10 pairs.

15 · The trap: one candidate's count split across shards

How it happens. Day 1's counting pass reads each friend's list. Friend lists are naturally stored with their owner, so friend f's list lives on shard f mod s. A shard can then count only the mutual friends it stores: it computes a partial count for each candidate, and the true count is the sum over shards. Esha's two mutual friends, Ben and Chloe, can live on different shards.

A tiny counterexample (hypothetical counts, k = 1). Shard 1 counts Dev 3, Esha 2. Shard 2 counts Farid 3, Esha 2. Each sends its top 1: Dev 3 and Farid 3. The coordinator picks Dev. But Esha's true count is 2 + 2 = 4, more than anyone's, and neither shard ever mentioned her.

16 · Two fixes: aggregate first, or prune with a threshold

Aggregate by candidate first (shuffle by key). Each shard sends every partial count to the machine that owns that candidate (candidate id mod s). The owner adds them up, and now each candidate lives on exactly one machine with its full count: section 14's merge is exact again. This is the reduce step of Day 1's MapReduce job. The price is shipping every partial count: 1,284 pairs per user at s = 2, rising to 1,394 at s = 16, more than the 1,191 candidates because a candidate appears on several shards.

A threshold algorithm (TPUT). Ship only what could matter, in three rounds:

  1. Each shard sends its top k. The coordinator adds up what it has: a lower bound on each total. Call the k-th best of these τ.
  2. Any item whose total reaches τ must have a partial of at least τ/s on some shard (if every share were below τ/s, the sum would be below τ). So each shard sends every item with a partial of at least τ/s.
  3. Now every unsent partial is known to be below τ/s, which caps each item's total from above. Items whose cap falls short of the k-th best lower bound are out; for the few left, fetch their missing partials and rank exactly.

On the counterexample: round 1 gives τ = 3 (Dev 3, Farid 3), so the cut is ⌈3/2⌉ = 2; round 2 brings Esha 2 from both shards, total 4; round 3 confirms Esha, 4.

code/day_2/distributed.py · TPUT, exact in three rounds
def tput_topk(partials, k):
    """Three rounds, exact. Round 1: each shard sends its top k; tau1 = the k-th best partial sum.
    Round 2: each shard sends every candidate whose partial count is >= tau1/s. A candidate it does
    not send has a partial below tau1/s there, which bounds its total from above. Round 3: fetch the
    missing partials of the candidates whose upper bound still reaches the k-th best lower bound."""
    s = len(partials)
    known = [dict() for _ in range(s)]           # what the coordinator has received from each shard
    for j, p in enumerate(partials):
        for v, c in local_top(p, k):
            known[j][v] = c
    shipped = sum(len(x) for x in known)

    def lower():
        lo = Counter()
        for x in known:
            lo.update(x)
        return lo

    lo = lower()
    tau1 = sorted(lo.values(), reverse=True)[k - 1] if len(lo) >= k else 0
    cut = math.ceil(tau1 / s)                    # a shard sends every partial >= tau1/s
    for j, p in enumerate(partials):
        for v, c in p.items():
            if c >= cut and v not in known[j]:
                known[j][v] = c
                shipped += 1
    lo = lower()
    tau2 = sorted(lo.values(), reverse=True)[k - 1] if len(lo) >= k else 0
    hidden = max(cut - 1, 0)                     # the most an unsent partial can be
    keep = [v for v in lo if lo[v] + hidden * sum(v not in x for x in known) >= tau2]
    total = {}
    for v in keep:                               # round 3: exact totals for the survivors
        for j, p in enumerate(partials):
            if v not in known[j] and v in p:
                shipped += 1
        total[v] = sum(p.get(v, 0) for p in partials)
    return topk_sort(total, k), shipped

TPUT halves the traffic at two shards and then fades. The reason is in round 2: the median user's 10th-best count is only 2, so the cut ⌈τ/s⌉ falls to 1 as soon as s ≥ τ, and "send every partial of at least 1" means send everything. For the 149 users whose 10th-best count is at least 8, TPUT sends 3% of the shuffle's pairs at two shards. A threshold algorithm pays off when the winners' scores are large compared with the number of shards; mutual-friend counts are not, which is one reason to aggregate by candidate in a batch job instead (Day 5).

The idea behind it, plainly. TPUT is the network version of Fagin's threshold algorithm: read every shard's sorted list in step, and keep a threshold equal to the sum of the current heads, the best total any unread item could still have. Stop as soon as the k-th best total you know is at least the threshold. Nothing unread can win.

The math, step by step: why the merge needs only each shard's top k, and why TPUT is exact

Merge, one shard per item. Suppose candidate v is in the overall top k and lives on shard j. Fewer than k candidates anywhere beat v, so fewer than k on shard j do: v is in shard j's own top k and is sent. The heap of heads then outputs items best first: the top of the heap is the best head, and every unsent item is no better than its own shard's head.

Why split counts break it. The argument needs "fewer than k items beat v on shard j". With partial counts, shard j ranks by its partial, and v's partial can be beaten by k items whose totals are smaller than v's. That is the counterexample.

TPUT is exact. Let τ₁ be the k-th best lower bound after round 1, and \(c = \lceil \tau_1 / s \rceil\). In round 2 each shard sends every partial ≥ c, so an unsent partial is at most c − 1 (counts are integers).

  • An item sent by no shard has total at most \(s(c-1) < s\cdot\tau_1/s = \tau_1\).
  • After round 2, let τ₂ be the k-th best lower bound; τ₂ ≥ τ₁ because lower bounds only grow. An item with known partials summing to L and u unsent shards has total at most \(L + u(c-1)\). Keep it if this reaches τ₂.
  • The k items behind τ₂ have totals ≥ τ₂ and are kept. Every dropped item has total < τ₂, strictly worse than all k of them, ties included. So the exact top k of the kept items, after round 3, is the exact top k overall.

distributed.py checks TPUT and the merge against the brute force on 3,000 random cases.

17 · Fan-out: a request is as slow as its slowest shard

Every plan above asks s shards and waits for all of them. The coordinator cannot answer until the last reply arrives, so the request takes as long as the slowest of s replies, and the more shards a request touches, the more likely one of them is having a slow moment. This is the strongest argument for laying data out so that the common request touches as few shards as possible: store each user's precomputed suggestions together on one shard, and do the cross-shard aggregation in a batch job, away from the request. Day 5 does the tail-latency arithmetic and builds that layout.

Interview takeaway
  • "Local top k + merge with a heap is exact only if each item's whole score lives on one shard. If scores are sums of partial scores across shards, local top k can miss the winner; aggregate by key first, or use a threshold algorithm like TPUT."
  • "Merging s sorted lists of which we need k: a heap of heads, O(s + k log s)."
  • "Fan-out to s shards makes latency the maximum of s latencies; keep the request path on one shard when you can."

In one line. Before you merge local winners, ask whether any item's score is split across machines; if it is, add first and rank second.

def topKFrequent(nums, k):                           # 347: bucket by count, O(n)
    count = Counter(nums)
    buckets = [[] for _ in range(len(nums) + 1)]      # a count is at most n
    for x, c in count.items():
        buckets[c].append(x)
    out = []
    for c in range(len(nums), 0, -1):
        for x in buckets[c]:
            out.append(x)
            if len(out) == k:
                return out
    return out

def findKthLargest(nums, k, seed=0):                  # 215: quickselect, O(n) expected
    rng = random.Random(seed)
    while True:
        p = rng.choice(nums)
        hi = [x for x in nums if x > p]
        eq = sum(1 for x in nums if x == p)
        if k <= len(hi):
            nums = hi
        elif k <= len(hi) + eq:
            return p
        else:
            k -= len(hi) + eq
            nums = [x for x in nums if x < p]

def kClosest(points, k):                              # 973: keep the k closest in a max-heap of size k
    heap = []

        elif d > heap[0][0]:
            heapq.heapreplace(heap, (d, x, y))
    return [[x, y] for _, x, y in heap]
