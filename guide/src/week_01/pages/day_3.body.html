1 · Dots and lines, and three ways to write them down

The situation. Here are the six people of the running example again, this time drawn instead of listed. Each person is a dot. Each friendship is a line between two dots.

The six people. Ids in code: You = 0, Ben = 1, Chloe = 2, Dev = 3, Esha = 4, Farid = 5. Esha can be reached in two steps by two routes (through Ben, through Chloe): those are her two mutual friends with you.

Now put your finger on Ben's dot and follow every line that leaves it. You reach You, Chloe, Dev and Esha. That is exactly Ben's friend list from Day 1. A friend list is the list of lines leaving a dot. And Day 1's "friends of friends" is a walk: from your dot, take one step along a line to a friend, then a second step to one of their friends. Each two-step route that ends at someone is one mutual friend. Esha has two routes, so two mutual friends; Dev and Farid one each.

The words that go with the picture, each something you can point at:

  • A dot is a node or vertex; a line is an edge. Six nodes, seven edges here. Friendship goes both ways, so the lines have no arrows: the graph is undirected. A follow graph, where you can follow someone who does not follow you back, has arrows: it is directed.
  • The nodes one line away are the neighbours; \(N(u)\) is the set of neighbours of \(u\), its friend list.
  • The number of lines at a dot is its degree, the friend count: You 2, Ben 4, Chloe 4, Dev 1, Esha 2, Farid 1.
  • A sequence of steps along lines is a path; the fewest steps between two people is their distance. Esha is at distance 2 from you, Farid is at distance 3 from Dev (Dev → Ben → Chloe → Farid).

The obvious way to store the picture: a table. One row and one column per person, a 1 where two people are friends. That is the adjacency matrix. "Are Dev and Esha friends?" is one look at one cell. "Who are Farid's friends?" means reading his whole row to find one 1. On the week's graph a row has 10,000 cells and about 20 ones: you scan 500 cells for each friend you find, and only 0.2% of the table's cells are ones.

The idea: write down only the lines. Two layouts do that.

  • An adjacency list: for each person, the list of their neighbours. This is what Days 1 and 2 used. Each line appears twice, once in each person's list, so the six people need 14 entries.
  • An edge list: one row per line, (smaller id, larger id), seven rows here. It is how friendships arrive (the week's edges.csv is an edge list in the order they formed) and how batch jobs ship them around. But "who are Farid's friends?" means scanning every row, unless you sort it, and a sorted edge list is an adjacency list in disguise.

In code: a dict of dicts. The first adjacency list most people write is a dictionary from each person to their friends. Make the inner one a dictionary too, and each friendship can carry a value: here, when it formed.

code/day_3/representations.py
def dict_of_dicts(pairs):
    """u -> {friend: when they became friends}, with pairs given in the order they formed."""
    G = {}
    for t, (u, v, *_) in enumerate(pairs):
        G.setdefault(u, {})[v] = t      # each friendship is written twice,
        G.setdefault(v, {})[u] = t      # once in each person's dict
    return G

For the six people, Ben's entry is {0: 0, 2: 2, 3: 3, 4: 4}: You, Chloe, Dev and Esha, and the order each friendship arrived in. What it gives you:

  • Friends of Ben: read his inner dict, four entries. No scanning 10,000 cells as in a matrix row.
  • Are Ben and Esha friends? 4 in G[1]: one hash lookup, as fast as a matrix cell.
  • A new friendship: two assignments. Nothing else moves.
  • A value per friendship: when it formed, how often the two interact. Day 4 needs the formation time: its features may only look at friendships that formed before a cut.

When there is no value to keep, the inner dict becomes a set, and that is what this week's code uses: adjacency() returns one set per person (a list of sets, since ids run 0 to \(n-1\)). The price of both is memory. Every entry is a full Python integer object plus a table slot holding its hash and pointers, and each table keeps empty slots spare so lookups stay fast.

Packing the lists: CSR. Once the graph stops changing for a while (a nightly snapshot), the same lists fit in a much tighter layout called compressed sparse row, or CSR. The name comes from sparse matrices: it stores only the 1s of the adjacency matrix, row by row. It is two plain arrays:

  • indices: every friend list written end to end, each list sorted.
  • indptr ("index pointer"): where each person's list starts. Person \(u\)'s friends are indices[indptr[u]:indptr[u+1]].

Each list sits in one contiguous run of memory and is already sorted, so Day 1's merge and binary-search intersections work on it directly. A value per friendship, like the formation time, goes in a third array lined up with indices. The catch: adding a friend shifts everything after that person's run.

code/day_3/representations.py
def csr(n, pairs):
    """Adjacency lists packed into two arrays: u's friends are indices[indptr[u]:indptr[u+1]]."""
    deg = np.zeros(n, dtype=np.int64)
    for u, v in pairs:
        deg[u] += 1; deg[v] += 1
    indptr = np.zeros(n + 1, dtype=np.int64)
    np.cumsum(deg, out=indptr[1:])                  # where each list starts
    fill, indices = indptr[:-1].copy(), np.empty(indptr[-1], dtype=np.int32)
    for u, v in pairs:                              # write each friendship into both lists
        indices[fill[u]] = v; fill[u] += 1
        indices[fill[v]] = u; fill[v] += 1
    for u in range(n):
        indices[indptr[u]:indptr[u + 1]].sort()
    return indptr, indices

Two things stand out. The hash layouts take 19 to 22 times the bytes of CSR for the same lists (Python sets keep more spare room than dicts, which is why the set version is the larger one here). And at 10,000 users they are even larger than the bit matrix. That flips as the graph grows: the matrix grows with the square of the users, the lists with the friendships.

At a billion users. Suppose a billion users with 300 friends each. That is \(10^9 \times 300 / 2 = 1.5 \times 10^{11}\) friendships and \(3 \times 10^{11}\) list entries. The bit matrix needs \(10^{18}/8\) bytes, 125 petabytes, almost all of it zeros. CSR with 4-byte ids (enough, since \(10^9 < 2^{32} \approx 4.29 \times 10^9\)) needs \(3 \times 10^{11} \times 4 = 1.2 \times 10^{12}\) bytes for indices plus 8 GB for indptr: about 1.2 TB. An edge list with 8-byte ids needs \(1.5 \times 10^{11} \times 16 = 2.4\) TB. A dict of dicts at the measured 84 bytes per entry (16,790,644 / 200,000) would need about \(3 \times 10^{11} \times 84 \approx 25\) TB: twenty times CSR, still thousands of times less than the matrix. The matrix grows with the square of the users; the lists grow with the friendships.

Trade-off, and what to say. Adjacency lists (a dict of dicts or of sets while the graph changes, CSR for a read-mostly snapshot) for anything social: sparse, and "friends of u" costs only the friends. An edge list for logs, streams and batch shuffles. A matrix only when the graph is small and dense, or as a slow, obviously correct reference in tests. In an interview: "it is a sparse graph; I store adjacency lists; the matrix would be \(n^2\) bits, 125 PB at a billion users."

In one line. People are nodes, friendships are edges, a friend list is the list of edges leaving a node, and friends of friends are the nodes two steps away.

The math, step by step: how many entries, and how many bytes

Step 1: count list entries. The six degrees are 2, 4, 4, 1, 2, 1; they add up to 14, twice the 7 edges. Each edge puts one entry in each of its two people's lists, so for any undirected graph with \(m\) edges

\[ \sum_u \deg(u) = 2m . \]

This is the handshake lemma. Week's graph: \(2 \times 100{,}000 = 200{,}000\) entries, so the average degree is \(200{,}000 / 10{,}000 = 20\).

Step 2: the matrix. It has one cell per ordered pair, \(n^2\) cells, whatever \(m\) is. Only \(2m\) of them are 1: \(200{,}000 / 10^8 = 0.2\%\). A row has \(n\) cells and \(\deg(u)\) ones, so listing a friend costs \(n / \bar d = 10{,}000 / 20 = 500\) cells on average.

Step 3: CSR. \(n + 1\) offsets of 8 bytes and \(2m\) ids of \(b\) bytes: \(8(n+1) + 2mb\). Week's graph with \(b = 4\): \(80{,}008 + 800{,}000 = 880{,}008\) bytes. indptr is a running total of degrees, \(\texttt{indptr}[u+1] = \texttt{indptr}[u] + \deg(u)\): for the six people 0, 2, 6, 10, 11, 13, 14, which the code's asserts check.

Step 4: the ratio. The bit matrix has \(n^2\) bits; CSR has \(2m\) ids of 32 bits each. At a billion users with 300 friends: \(10^{18}\) bits against \(3 \times 10^{11} \times 32 \approx 10^{13}\) bits, so the matrix is about 100,000 times larger, even though each of its cells is a single bit.

What this shows. A list layout costs memory in proportion to friendships, a matrix in proportion to the square of the people, and social graphs have far fewer friendships than pairs.

2 · Friends of friends is a two-step breadth-first search

The situation. Day 1's double loop, "for each friend, for each of their friends", is a walk of exactly two steps. Other questions the product asks are walks too: is this person reachable from you at all? How far away are they? Who is within three steps?

The obvious attempt: follow every route. From You, step to Ben and Chloe, then to all their friends: 8 two-step routes, and You is reached twice, Esha twice. Keep going further and the walk never ends, because Ben → Chloe → Ben → Chloe goes round forever. To walk further than two steps, you must remember whom you have already seen.

The idea: visit in rings, mark on first sight. Ring 0 is you. Ring 1 is everyone one step away. Ring 2 is everyone one step from ring 1 who has not been seen yet, and so on. A first-in, first-out queue keeps the rings in order. Each person gets their ring number when first seen and never enters the queue again. This is breadth-first search (BFS), and the ring number is the distance.

code/day_3/bfs.py
def friends_of_friends(adj, u):
    """Walk two steps from u. Count how many routes reach each person who is
    not u and not already u's friend: that count is the number of mutual friends."""
    count = Counter()
    for f in adj[u]:                 # step 1: a friend
        for v in adj[f]:             # step 2: a friend of that friend
            if v != u and v not in adj[u]:
                count[v] += 1
    return count

def bfs(adj, s, max_depth=None):
    """dist[v] = fewest steps from s to v, for everyone reachable (within max_depth)."""
    dist = {s: 0}
    queue = deque([s])
    while queue:
        x = queue.popleft()
        if max_depth is not None and dist[x] == max_depth:
            continue                 # at the limit: do not look further out
        for y in adj[x]:
            if y not in dist:        # mark on first sight, so y enters the queue once
                dist[y] = dist[x] + 1
                queue.append(y)
    return dist

Trade-off and interview takeaway. BFS gives distances in steps and costs time proportional to people plus friendships: a full walk of the week's graph reads all 200,000 list entries once. A depth-limited BFS (max_depth) reads only the rings it needs. Depth-first search reaches the same people but not their distances. Say out loud: "mark on discovery, not on removal, or a person enters the queue many times."

In one line. BFS visits people in rings of distance; friends-of-friends is its second ring, counted with repeats.

The math, step by step: why BFS ring numbers are true distances, and what two steps cost

Write \(\ell(v)\) for the ring number BFS gives \(v\), and \(\mathrm{dist}(s, v)\) for the true fewest steps.

Step 1: the queue stays sorted. At every moment the labels in the queue, front to back, never go down, and the back is at most the front plus 1. True at the start (only \(s\)). Each step removes the front, label \(\ell\), and appends people labelled \(\ell + 1\); the order and the "spread at most 1" survive. So people leave the queue in order of their labels. Check on the trace: after taking Ben the queue is Chloe (1), Dev (2), Esha (2).

Step 2: a label is never too small. Each label is the length of a real path (follow who discovered whom back to \(s\)), and no path is shorter than the shortest one: \(\ell(v) \ge \mathrm{dist}(s, v)\).

Step 3: a label is never too large. Suppose some labels are too large, and take such a \(v\) closest to \(s\), at true distance \(k\). The person \(x\) just before \(v\) on a shortest path is closer, so \(\ell(x) = k - 1\). When \(x\) left the queue, either \(v\) was new and got label \(k\), or \(v\) had been seen from some \(x'\) that left earlier, so \(\ell(x') \le k - 1\) by Step 1 and \(\ell(v) \le k\). Either way, not too large: a contradiction. With Step 2, \(\ell(v) = \mathrm{dist}(s, v)\).

Step 4: cost. Each person enters and leaves the queue once, and their list is read once when they leave. The lists hold \(2m\) entries (the handshake lemma), so BFS is \(O(n + m)\).

Step 5: two steps. Stopping after ring 2 reads your own list (\(\deg u\) entries) and each friend's list:

\[ \text{entries read} = \deg(u) + \sum_{f \in N(u)} \deg(f) . \]

For You: \(2 + (4 + 4) = 10\). The sum over friends is the quantity the next section is about.

The situation. The two-step walk reads the whole list of every friend. So its cost is not your friend count; it is the sum of your friends' friend counts. For You: Ben 4 + Chloe 4 = 8 entries. What does that sum look like across 10,000 people?

A user's list is read once by each of their friends, so a user with degree d causes d × d reads. The single largest hub, 1,480 friends, causes 14.8% of all two-step work on its own.

Why squared: Ben's list has 4 entries and 4 people read it (each of his friends), so Ben causes 4 × 4 = 16 reads. A hub with 1,480 friends causes 1,480 × 1,480 = 2,190,400. Summed over everyone, the work is \(\sum_v \deg(v)^2 = 14{,}768{,}324\) entries, an average of 1,477 per request. It is also why your friends are, on average, more popular than you: a friend reached along a random line has 73.8 friends, not 20.

Capping hubs. The cheapest fix: skip any friend with more than cap friends. A request then reads at most cap × (your degree) entries.

code/day_3/degrees.py
def work(adj, u):
    """List entries a two-step walk from u reads: the sum of u's friends' degrees."""
    return sum(len(adj[f]) for f in adj[u])

def suggest_capped(adj, u, k=10, cap=None):
    """Top k by mutual friends, but skip any friend with more than `cap` friends.
    Returns (top k, entries read). Ties: smaller id first."""
    count, read = Counter(), 0
    for f in adj[u]:
        if cap is not None and len(adj[f]) > cap:
            continue                          # a hub: the longest list, the weakest hint
        read += len(adj[f])
        for v in adj[f]:
            if v != u and v not in adj[u]:
                count[v] += 1
    return heapq.nsmallest(k, count, key=lambda v: (-count[v], v)), read

In one line. The two-step cost is the sum of your friends' degrees; summed over everyone it is the sum of squared degrees, so the top 1% of users cause 69% of the work, and capping them buys a 60% cut at no measured loss.

The math, step by step: total work is the sum of squared degrees

Step 1: write the work. \(W(u) = \sum_{f \in N(u)} \deg(f)\). Six people: You 8, Ben 9 (2 + 4 + 1 + 2), Chloe 9, Dev 4, Esha 8, Farid 4. Total 42.

Step 2: count the same pairs the other way. \(\sum_u W(u)\) adds \(\deg(f)\) once for every (user, friend) pair \((u, f)\). Fix \(f\): it appears as the friend in \(\deg(f)\) pairs, each adding \(\deg(f)\). So

\[ \sum_u W(u) = \sum_f \deg(f)^2 . \]

Six people: \(4 + 16 + 16 + 1 + 4 + 1 = 42\). Week's graph: both sides are 14,768,324, which the script asserts. Counting one set of pairs in two orders like this is double counting.

Step 3: why it beats 400. Divide by \(n\): the mean work is \(E[d^2]\), the average of squared degrees, and

\[ E[d^2] = E[d]^2 + \operatorname{Var}(d) = 400 + 1{,}076.8 = 1{,}476.8 . \]

The naive 400 squared the average; the true cost averages the squares, and the gap is the variance, which a heavy tail makes large.

Step 4: a friend's degree. Pick a random line and a random end of it: you land on person \(f\) with probability \(\deg(f)/2m\), so the expected degree there is \(\sum_f \deg(f)^2 / 2m = 14{,}768{,}324 / 200{,}000 = 73.8\). Popular people sit at the end of many lines; this is the friendship paradox.

Step 5: the cap's bound. With a cap \(c\), every list read has at most \(c\) entries and there are at most \(\deg(u)\) of them, so \(W_c(u) \le c \cdot \deg(u)\), whatever the graph.

def findJudge(n, trust):
    score = [0] * (n + 1)
    for a, b in trust:
        score[a] -= 1                         # an arrow out disqualifies a
        score[b] += 1                         # an arrow in counts for b
    return next((p for p in range(1, n + 1) if score[p] == n - 1), -1)

In-degree minus out-degree reaches \(n - 1\) only for someone trusted by everyone else and trusting nobody, so one number per person suffices: \(O(n + |\text{trust}|)\).

4 · Triadic closure: why mutual friends work at all

The situation. Days 1 and 2 ranked by mutual friends because it sounded right. Why should a shared friend predict a friendship? Because friends introduce friends. If Ben knows you and Esha, you two are likely to meet at Ben's party. When you and Esha become friends, the three of you form a triangle: three people, all friends. The tendency of an open "two lines with a shared corner" to close into a triangle is triadic closure.

The obvious attempt: count triangles. The week's graph has 71,976. Is that many? On its own the number cannot say; it has to be compared with the chances to form one.

The idea: of all pairs of your friends, what share are friends with each other? That share is your clustering coefficient. Ben has four friends (You, Chloe, Dev, Esha), so six pairs; two of them are friends (You–Chloe, Chloe–Esha): Ben's clustering is 2/6 = 1/3. Your two friends, Ben and Chloe, are friends: yours is 1.

code/day_3/triangles.py
def count_triangles(adj):
    """Each triangle once, at its least popular corner (rank by degree, ties by id)."""
    rank = {v: (len(adj[v]), v) for v in range(len(adj))}
    up = [{w for w in adj[v] if rank[w] > rank[v]} for v in range(len(adj))]
    return sum(len(up[u] & up[v]) for u in range(len(adj)) for v in up[u])

def closed_at_birth(edges, n):
    """For each friendship in formation order: how many mutual friends its two people
    had just before it formed (each one is a triangle the new line closes)."""
    adj, out = [set() for _ in range(n)], []
    for u, v, _ in edges:
        out.append(len(adj[u] & adj[v]))
        adj[u].add(v); adj[v].add(u)
    return out

The math, step by step: wedges, triangles, and what a random graph would give

Step 1: wedges. A pair of \(v\)'s friends \(\{x, y\}\) is a path \(x - v - y\), a wedge at \(v\). With \(\deg(v) = d\) there are \(\binom{d}{2} = d(d-1)/2\) wedges. A wedge is closed when \(x\) and \(y\) are friends. If \(T_v\) is the number of closed wedges at \(v\), then \(C_v = T_v / \binom{d}{2}\).

Step 2: each triangle is three closed wedges. The six people have two triangles, {You, Ben, Chloe} and {Ben, Chloe, Esha}; closed wedges: You 1, Ben 2, Chloe 2, Esha 1, total 6 = 3 × 2. In general \(\sum_v T_v = 3 \times (\text{triangles})\).

Step 3: averaged against pooled. The average of \(C_v\) gives each person one vote: (1 + 1/3 + 1/3 + 1)/4 = 0.67 for the six. The pooled share \(\sum T_v / \sum \binom{d_v}{2} = 6/14 = 0.43\) weights each person by \(\binom{d_v}{2}\), roughly degree squared, so hubs dominate it. That is why 0.0296 sits far below 0.1104 on the week's graph.

Step 4: a random graph. If each pair is a friendship independently with probability \(p\), a wedge is closed with probability \(p\), so expected clustering is \(p\). Same number of friendships:

\[ p = \frac{m}{\binom{n}{2}} = \frac{100{,}000}{49{,}995{,}000} \approx 0.0020, \qquad \frac{0.1104}{0.0020} \approx 55 . \]

Step 5: every triangle is closed by its last line. A triangle exists from the moment its third line appears, and at that moment its two other lines already exist, so its third corner is a mutual friend of the new line's ends. Each triangle is counted once this way, so the mutual counts at formation add up to the number of triangles: 71,976, which triangles.py asserts.

Step 6: why the upward count is fast. count_triangles points each line from the less popular end to the more popular end and looks only upward, so each triangle is found once, at its least popular corner. A person with \(k\) friends above them has \(k\) people each with at least \(k\) friends, so \(k^2 \le 2m\) and \(k \le \sqrt{2m}\); the total work is at most \(m\sqrt{2m}\), however skewed the degrees (a result of Chiba and Nishizeki, 1985).

5 · Better pair scores: Jaccard, Adamic–Adar, resource allocation

The situation. Section 3 showed that a hub is an expensive mutual friend; the cap table hinted it is also a weak one. Can the score itself know that, instead of a hard cut?

The obvious score and where it breaks. Mutual friends gives every shared friend one vote. Look at a small graph where that is clearly wrong. You have three friends: A, who has 2 friends; B, who has 3; and H, a hub with 6. X and Y both share two friends with you, so counting ties them.

X and Y both have two mutual friends with you. X's come from small circles; one of Y's is H, who knows everyone.

Think about how an introduction happens. A has only one other friend, so if A introduces you to anyone, it is X. H has five others to choose from, so H vouching for Y is weaker news. A mutual friend who knows everyone says little about any one pair. Three classic scores act on that, each computed from the same two-step walk:

  • Jaccard: mutual friends divided by everyone either of you knows, \(|N(u) \cap N(v)| / |N(u) \cup N(v)|\). How similar are your two circles?
  • Adamic–Adar (AA): each mutual friend \(z\) votes \(1/\ln \deg(z)\) instead of 1. A popular mutual friend votes a little less.
  • Resource allocation (RA): each mutual friend votes \(1/\deg(z)\). A popular mutual friend votes much less.

def two_hop_scores(adj, u):
    """One two-step walk from u fills all four scores for every candidate v.
    z is a mutual friend of u and v; its degree d_z sets its weight."""
    cn, aa, ra = Counter(), Counter(), Counter()
    for z in adj[u]:
        dz = len(adj[z])                   # dz >= 2: z knows u and v
        for v in adj[z]:
            if v != u and v not in adj[u]:
                cn[v] += 1                 # mutual friends: every z votes 1
                aa[v] += 1 / math.log(dz)  # Adamic-Adar: a popular z votes less
                ra[v] += 1 / dz            # resource allocation: much less
    du = len(adj[u])
    jac = {v: c / (du + len(adj[v]) - c) for v, c in cn.items()}   # |N(u) ∪ N(v)| = du + dv - cn
    return {"mutual": cn, "jaccard": jac, "adamic_adar": aa, "resource": ra}

def top_k(score, k=10):
    """Highest score first; ties go to the smaller id."""
    return sorted(score, key=lambda v: (-score[v], v))[:k]

    """Mean over evaluated users of |top k ∩ future friends| / |future friends|.
    ranked[u] is u's list (best first); a user with no list scores 0."""
    total = 0.0
    for u, fut in truth.items():
        top = ranked.get(u, [])[:k]
        total += len(fut.intersection(top)) / len(fut)
    return total / len(truth)

The math, step by step: where the 1/degree weight comes from

The story. User \(u\) picks one of their \(\deg(u)\) friends \(z\) at random, and \(z\) introduces \(u\) to one of \(z\)'s other \(\deg(z) - 1\) friends at random.

Numbers first. In the hub picture, You have 3 friends. Through A (1 other friend): X with probability \(\tfrac13 \cdot 1\). Through B (2 others): X with \(\tfrac13 \cdot \tfrac12\). The two routes are different first picks, so they add: X gets \(\tfrac13(1 + \tfrac12) = 0.50\). Y: through B or H (5 others), \(\tfrac13(\tfrac12 + \tfrac15) = 0.23\). Z, P, Q, R: \(\tfrac13 \cdot \tfrac15 = 0.067\) each. Check: \(0.50 + 0.23 + 4 \times 0.067 = 1\).

In symbols. The introduction reaches \(v\) through \(z\) only when \(z\) is a mutual friend:

\[ P(u \text{ meets } v) = \frac{1}{\deg u} \sum_{z \in N(u) \cap N(v)} \frac{1}{\deg(z) - 1} . \]

For one user \(u\), the factor \(1/\deg u\) is the same for every candidate, so the ranking is by \(\sum_z 1/(\deg z - 1)\): resource allocation, up to the −1.

Where 1/log comes from. Adamic and Adar built their score for web pages: two pages sharing a rare feature are more likely related than two sharing a common one, so each shared feature is weighted by one over the log of how common it is. On a graph the feature is a mutual friend and its commonness is its degree. \(1/\ln d\) falls much more slowly than \(1/d\): from \(d = 5\) to \(d = 500\), \(1/d\) shrinks 100 times, \(1/\ln d\) only \(\ln 500 / \ln 5 = 6.21/1.61 \approx 3.9\) times. Which discount fits best is an empirical question; here the gentler one won by a little.

Jaccard in symbols. \(|N(u) \cup N(v)| = \deg u + \deg v - |N(u) \cap N(v)|\), so Jaccard is the count divided by something that grows with the candidate's degree: it is a penalty on popular candidates, not on popular mutual friends.

6 · Random walks: a score that looks beyond two steps

The situation. Every score so far stops at two steps, and on the time split 51.6% of a user's future friends (mean per user) are further away. Can one score add up evidence along all routes from you, favour short ones, and still discount hubs?

The obvious attempt: count routes of every length. Through a hub the counts explode: a hub with 1,480 friends creates 1,480 routes to each of its friends' friends. Raw route counts reward being near a hub, the opposite of what we want.

The idea: a walker who keeps going home. Put a walker on your dot. At every step, with probability α the walker jumps back to you; otherwise it moves along a random line from where it stands. Let it walk for a long time and record the share of time it spends at each person. That share is the person's personalised PageRank from you, also called a random walk with restart. Short routes count most, because the walker keeps going home. A hub splits the walker over all its friends, so a route through a hub delivers only a sliver to each.

code/day_3/ppr.py
def ppr(src, dst, deg, u, alpha=0.3, rounds=30):
    """Share of time a walker spends at each person when, at every step, it goes
    home to u with probability alpha and otherwise moves to a random friend."""
    n = len(deg)
    home = np.zeros(n); home[u] = 1.0
    share = np.divide(1.0, deg, out=np.zeros(n), where=deg > 0)   # 1 / degree
    x = home.copy()
    for _ in range(rounds):
        moved = np.bincount(dst, weights=x[src] * share[src], minlength=n)  # one step for everyone
        x = alpha * home + (1 - alpha) * moved
    return x

def ppr_top_k(adj, x, u, k=10):
    """Best k non-friends by walk share; ties go to the smaller id."""
    x = x.copy()
    x[u] = -1.0
    x[list(adj[u])] = -1.0                       # yourself and your friends are not candidates
    order = np.lexsort((np.arange(len(x)), -x))  # by -share, then by id
    return [int(v) for v in order[:k] if x[v] > 0]

The math, step by step: restart, the settled shares, and why 30 rounds are enough

Step 1: one step as a table. Let \(P_{fv} = 1/\deg(f)\) when \(f\) and \(v\) are friends, 0 otherwise; each row adds to 1. If the row vector \(x_t\) holds the walker's chances after \(t\) steps, one more step gives \(x_t P\). Ben's row on the six people has 1/4 at You, Chloe, Dev and Esha.

Step 2: add the restart. With \(e_u\) the vector with 1 at you, one round is

\[ x_{t+1} = \alpha\, e_u + (1-\alpha)\, x_t P . \]

The settled shares \(\pi_u\) are the vector that this round leaves unchanged, \(\pi_u = \alpha e_u + (1-\alpha)\pi_u P\): the stationary distribution of the walk with restart. Without restart (α = 0) the walker would wander off and the shares would forget where it started; the restart is what makes the score about you.

Step 3: unroll it. Substitute the equation into itself again and again:

\[ \pi_u = \alpha \sum_{t=0}^{\infty} (1-\alpha)^t\, e_u P^t . \]

In words: the score of \(v\) adds the chance of reaching \(v\) in exactly \(t\) steps, for every \(t\), with longer routes discounted by \((1-\alpha)^t\).

Step 4: the two-step term is resource allocation. Reaching \(v\) in two steps means going to a friend \(f\) (chance \(1/\deg u\)) and then to \(v\) (chance \(1/\deg f\)), with \(f\) a mutual friend:

\[ (e_u P^2)_v = \frac{1}{\deg u} \sum_{f \in N(u) \cap N(v)} \frac{1}{\deg f} . \]

Six people: Esha \(\tfrac12(\tfrac14 + \tfrac14) = \tfrac14\), Dev and Farid \(\tfrac18\). With Ben at 24 friends Dev falls to \(\tfrac12 \cdot \tfrac1{24} = \tfrac1{48}\). So the walk contains section 5's resource allocation as its two-step part, plus longer routes.

Step 5: the error shrinks every round. Measure a vector by \(\|y\|_1 = \sum_v |y_v|\). Because each row of \(P\) adds to 1, \(\|yP\|_1 \le \|y\|_1\). Subtracting the settled equation from a round gives \(x_{t+1} - \pi_u = (1-\alpha)(x_t - \pi_u)P\), so the error shrinks by at least \(1 - \alpha\) per round. Two probability vectors are at most 2 apart, so

\[ \|x_t - \pi_u\|_1 \le 2(1-\alpha)^t . \]

For α = 0.3 and an error of \(10^{-4}\): \(t \ge \ln(2/10^{-4}) / \ln(1/0.7) = 9.90 / 0.357 \approx 28\) rounds, whatever the size of the graph. The same shrinking argument shows the settled shares exist and are unique.

DSA · islands: connected components and union-find

7 · Are there islands? Union-find

The situation. A person in an island of their own, with no route to anyone else, can never be reached by friends of friends or by a walk. How many islands does the graph have, and how do you keep that answer up to date as friendships stream in?

The obvious attempt. Run BFS from every unlabelled person; each run labels one island. That is exact, \(O(n + m)\), and fine for one snapshot. But a new friendship arrives every moment, and re-running BFS over the whole graph for each one is far too much.

The idea: give every island a representative. Each person points to someone in their island; follow the pointers and you reach the island's root. Two people are in the same island exactly when they reach the same root. A new friendship \((a, b)\) joins two islands by pointing one root at the other. Two tricks keep the pointer chains short: union by rank (hang the shorter tree under the taller one) and path compression (after finding a root, point everyone you passed straight at it). This is union-find, also called disjoint-set union.

code/day_3/components.py
class UnionFind:
    def __init__(self, n):
        self.parent = list(range(n))       # everyone starts as their own island
        self.rank = [0] * n                # an upper bound on each tree's height
        self.count = n                     # number of islands

    def find(self, x):
        root = x
        while self.parent[root] != root:
            root = self.parent[root]
        while self.parent[x] != root:      # path compression: point everyone on the way at the root
            self.parent[x], x = root, self.parent[x]
        return root

    def union(self, a, b):
        """Join a's island and b's island. False if they were already one."""
        ra, rb = self.find(a), self.find(b)
        if ra == rb:
            return False
        if self.rank[ra] < self.rank[rb]:
            ra, rb = rb, ra                # union by rank: hang the shorter tree under the taller
        self.parent[rb] = ra
        if self.rank[ra] == self.rank[rb]:
            self.rank[ra] += 1
        self.count -= 1
        return True

# Merging duplicate accounts: two accounts are the same person if they share an email or phone.
def merge_accounts(accounts):
    """accounts[i] = set of contact strings. Returns groups of account ids that belong together."""
    uf, owner = UnionFind(len(accounts)), {}
    for i, contacts in enumerate(accounts):
        for c in contacts:
            if c in owner:
                uf.union(i, owner[c])      # shared contact: same person
            else:
                owner[c] = i
    groups = {}
    for i in range(len(accounts)):
        groups.setdefault(uf.find(i), []).append(i)
    return sorted(groups.values())

Trade-off and interview takeaway. BFS for a one-off snapshot, union-find when pairs stream in and you only need "same island or not". Union-find cannot delete a friendship: once two islands are joined, there is no cheap way to split them, so unfriending needs a periodic rebuild. Say: "union by rank plus path compression, near-constant time per operation."

In one line. Union-find keeps islands as pointer trees with a root each; joining and asking cost almost nothing, so it handles a stream of friendships or contact matches.

The math, step by step: why the trees stay short

Step 1: rank bounds size. A root's rank only grows when two trees of equal rank \(r\) join, and then the new tree has at least twice the nodes of each. By induction, a tree whose root has rank \(r\) has at least \(2^r\) nodes. Start: rank 0, one node, \(2^0 = 1\). Join two rank-\(r\) trees: at least \(2^r + 2^r = 2^{r+1}\) nodes, rank \(r + 1\).

Step 2: height is at most log n. Height never exceeds rank, and \(2^r \le n\), so \(r \le \log_2 n\). With 10,000 users, no chain is longer than \(\log_2 10{,}000 \approx 13.3\), so 13 steps, even without path compression.

Step 3: with path compression too. Each find flattens the path it walked, so later finds are shorter. Tarjan proved that \(m\) operations on \(n\) items take \(O(m\,\alpha(n))\) time, where \(\alpha\) is the inverse Ackermann function, at most 4 for any \(n\) that fits in the universe. In practice: constant.

Step 4: why 9,999 joins. Each successful join reduces the number of islands by one. Starting from 10,000 islands and ending with 1 takes exactly 9,999 joins, whatever the order.

                uf.union(i, j)
    return uf.count

# LeetCode 684 · Redundant Connection: the first edge whose ends are already joined
def findRedundantConnection(edges):
    uf = UnionFind(len(edges) + 1)
    for a, b in edges:
        if not uf.union(a, b):
            return [a, b]

547 is \(O(n^2)\) because the input is a matrix; 684 is near-linear in the number of edges. 684 is exactly the "inside an island already" count above, stopped at the first one.

System Design · advanced · at scale

At scale. This block is advanced: it assumes the graph no longer fits on one machine. Day 5 builds the full system; here we measure the two graph-specific questions it rests on.

8 · Partitioning the graph across machines

The situation. At a billion users the adjacency lists are about 1.2 TB (section 1), so they are split across \(p\) machines. A friends-of-friends request runs on the machine that holds your list and must read each friend's list. Every friend who lives elsewhere is a network round trip.

The obvious attempt: hash partitioning. Put user \(u\) on machine \(\text{hash}(u) \bmod p\). Load is even and lookups need no directory. But a hash knows nothing about who is friends with whom, so a friend is on your machine with probability only \(1/p\). The share of friendships that cross machines is the edge cut.

code/day_3/partition.py
def hash_partition(n, p):
    """Machine of user u: a hash of the id, so users spread evenly and at random."""
    return [(u * 2654435761 % 2**32) * p >> 32 for u in range(n)]   # multiplicative hash, top bits

def remote_read_share(adj, part, replicated=frozenset()):
    """A two-step walk for u runs on u's machine and reads each friend f's list (deg f entries).
    Share of those entries that live on another machine. Lists in `replicated` are on every machine."""
    remote = total = 0
    for u in range(len(adj)):
        for f in adj[u]:
            total += len(adj[f])
            if part[f] != part[u] and f not in replicated:
                remote += len(adj[f])
    return remote / total

Two ideas to do better. Locality: place friends together. A simple version (balanced label propagation) starts from the hash and repeatedly moves each user to the machine where most of their friends live, as long as that machine stays within 3% of an even share. Copy the hubs: section 3 showed the top 1% of lists cause 69% of the reads, so keep a copy of those 100 lists on every machine.

The math, step by step: why hashing gives (p − 1)/p, and what copying hubs leaves

Step 1. With a hash that spreads ids evenly and ignores friendships, the machine of a friend \(f\) is independent of yours, so \(P(\text{different}) = 1 - 1/p\). That holds for every friend, popular or not, so both the edge cut and the work-weighted remote share are \((p-1)/p\) in expectation.

Step 2. Copying the hub lists makes their reads local. What remains is the non-hub part of the work, still remote with probability \((p-1)/p\):

\[ \text{remote share} \approx \frac{p-1}{p}\,(1 - 0.691) = 0.875 \times 0.309 = 0.270 \quad (p = 8), \]

matching the measured 0.271.

Step 3: storage. Each extra copy of the hub lists adds their 11.1% share; \(p - 1 = 7\) copies add \(7 \times 11.1\% \approx 78\%\).

9 · Think like a vertex: BFS and PageRank in rounds

The situation. BFS and PageRank were written above as loops over one big in-memory graph. On a partitioned graph, no machine can see it all. How do you run them?

The idea: every vertex runs the same tiny program, in rounds. In each round (a superstep), a vertex reads the messages sent to it in the previous round, updates its own value, and sends messages along its own lines. Then everyone waits at a barrier and the next round begins. This is the vertex-centric model, often called Pregel-style after the paper that named it. BFS becomes: in round \(r\), vertices first reached in round \(r - 1\) message their friends, and a vertex hearing for the first time sets its distance to \(r\). PageRank becomes: every vertex sends value / degree to each friend, then sets value = α·[it is the start] + (1 − α)·(sum received).

code/day_3/partition.py
# --- Pregel-style rounds: every vertex runs the same small program, talking only to neighbours.
def pregel_bfs(adj, s, part=None):
    """Round r: vertices reached in round r - 1 message their friends; a vertex that hears
    for the first time sets dist = r. Returns dist, rounds, messages, cross-machine messages."""
    dist, frontier, r, msgs, cross = {s: 0}, [s], 0, 0, 0
    while frontier:
        r += 1
        inbox = set()
        for x in frontier:                          # each active vertex sends to all its friends
            for y in adj[x]:
                msgs += 1
                cross += part is not None and part[x] != part[y]
                inbox.add(y)
        frontier = [y for y in inbox if y not in dist]
        for y in frontier:
            dist[y] = r
    return dist, r - 1, msgs, cross

Measured (partition.py): BFS from user 8604 on the week's graph finishes in 4 rounds (its farthest user is 4 steps away) and sends 200,000 messages, one per list entry, the same count the in-memory BFS reads. With hash partitioning on 8 machines, 175,130 of them (87.6%) cross machines. Personalised PageRank sends 200,000 messages every round, 6,000,000 for 30 rounds, and the vertex-centric version gives the same shares as ppr on the six people (asserted).

Trade-off and interview takeaway. Rounds are simple to reason about and fault-tolerant (checkpoint at the barrier), but each round waits for the slowest machine, and the machine holding a hub sends a hub-sized burst every round: the same skew as section 3, now in network traffic. Combine messages per destination machine, copy or split hubs, and prefer few rounds: friends-of-friends is 2 rounds, BFS is as many rounds as the farthest distance, PageRank about 30. Say: "vertex-centric supersteps; cost per round is messages, and messages are list entries."

In one line. On a partitioned graph, BFS and PageRank run as rounds of messages along edges; each round costs one message per list entry, and hubs set the slowest machine.

# LeetCode 785 · Is Graph Bipartite? Colour by BFS layer; an edge inside a layer breaks it.
def isBipartite(graph):
    colour = [-1] * len(graph)
    for s in range(len(graph)):              # the graph may have several islands
        if colour[s] != -1:
            continue
        colour[s] = 0
        queue = deque([s])
        while queue:
            x = queue.popleft()
            for y in graph[x]:
                if colour[y] == -1:
                    colour[y] = 1 - colour[x]
                    queue.append(y)
                elif colour[y] == colour[x]:
                    return False             # an odd cycle, for example a triangle
    return True

# LeetCode 133 · Clone Graph: BFS with a map from old node to its copy (the "seen" set).
class Node:
    def __init__(self, val=0, neighbors=None):
        self.val = val
        self.neighbors = neighbors if neighbors is not None else []

def cloneGraph(node):
    if node is None:
        return None
    copy = {node: Node(node.val)}
    queue = deque([node])
    while queue:
        x = queue.popleft()
        for y in x.neighbors:
            if y not in copy:                # first sight: make the copy, visit later
                copy[y] = Node(y.val)
                queue.append(y)
            copy[x].neighbors.append(copy[y])
    return copy[node]

Both are BFS with one extra job per first sight: give a colour (785) or make a copy (133). Both are \(O(n + m)\).
