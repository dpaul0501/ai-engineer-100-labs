Read less, and still find almost the same people

Where we are. Day 2 ended with a bill. To suggest people for one user, the exact count reads the friend list of every one of their friends. On the week's graph that is 1,477 entries for an average request, 7,284 for the slowest request in a hundred, and 51,806 for the user whose friends are the most popular. A request that has to answer quickly cannot promise to read all of that. Today each request gets a fixed read budget, and we measure how much of the exact answer survives. Then we look for good candidates by other routes, check cheaply who must never be shown, and put the routes together under one budget.

The route through the day: read a random handful of friends and scale up (is the guess fair, and how noisy is it?); a yardstick for "almost the same people"; a different way to find candidates, through people whose friend sets look like yours; a tiny structure that answers "already friends, already shown, blocked?"; random walks as a third source; and finally the design that combines them.

ML · read some friends, and scale up

Try the obvious thing: read the first lists that fit

Take the six-person example. You have two friends, Ben and Chloe, and each has four friends, so the exact count reads 8 entries. Give the request a budget of 4: it can read one list. The obvious rule is to read friends in the order they are stored, say by id, until the budget runs out. That reads Ben's list every time. You learn about Dev and Esha, and Farid, who is only reachable through Chloe, never shows up.

Two things are wrong with this, and both get worse on a real graph.

  • The mistake repeats. Storage order is the same on every request, so the same friends are skipped every time. Someone known only through the skipped friends is never seen, and asking again does not help.
  • One popular friend eats the budget. User 570 has only 9 friends, but two of them have 1,480 and 1,108 friends. If one of those comes first, a budget of 700 reads stops before it has read anything, and the user gets an empty list.

The idea: a random handful of friends, scaled up

Pick the friends to read at random, so that no friend is favoured. Count, for each candidate, how many of the friends you read know them. Then scale up: if you read 1 friend out of 2, multiply the count by 2. If you read 10 out of 100, multiply by 10. With the user's number of friends written d (their degree, from Day 1), the number of friends read s, and the count among them c, the guess for the mutual-friend count is

\[ \hat m \;=\; \frac{d}{s}\, c . \]

By hand. You have d = 2 friends and the budget lets you read s = 1, chosen at random, so the scale is 2.

EshaBenorChloeboth of your friends know her, so whichever you read counts 1 · guess 2 either way (true count 2)
DevBenorChloeread Ben: count 1, guess 2 · read Chloe: count 0, guess 0 · average 1 (true count 1)
FaridBenorChloethe mirror image of Dev: guess 0 or 2 · average 1 (true count 1)
Averaged over the two equally likely choices, every guess equals the true count. For Esha the guess is exact every time; for Dev and Farid it is off by 1 every time.

The example shows the two questions to ask of any estimate. Is it fair? Yes: averaged over the random choice, the guess is the true count. A statistician calls such a guess unbiased. How noisy is it? That depends: no noise for Esha, who is known through all your friends, and the most noise for the weak candidates, known through few. The noise is measured by the variance, the average squared distance of the guess from its mean: 0 for Esha, 1 for Dev and Farid.

Use it

A budget counts entries read, not friends: reading friend f's list costs as many reads as f has friends. The function shuffles the friends, reads lists until the next one would not fit, and optionally skips very popular friends first (Day 2's hub cap; it gets its own section below).

sampled.py · two-hop counts under a read budget, with an optional hub cap
def sampled_suggest(adj, u, k=10, budget=500, cap=None, rng=random):
    """Approximate top-k by mutual friends, reading at most `budget` adjacency entries.

    Friends are read in a uniformly random order; a friend whose degree exceeds `cap`
    (a hub) is skipped before sampling. Returns (top, estimate, reads)."""
    friends = sorted(f for f in adj[u] if cap is None or len(adj[f]) <= cap)
    rng.shuffle(friends)                          # uniform random order
    count, reads, s = Counter(), 0, 0
    for f in friends:
        if reads + len(adj[f]) > budget:          # the next list does not fit: stop
            break
        reads += len(adj[f]); s += 1
        for v in adj[f]:
            if v != u and v not in adj[u]:
                count[v] += 1
    scale = len(friends) / s if s else 0.0        # d / s: scale the sample count up
    estimate = {v: scale * c for v, c in count.items()}
    top = heapq.nsmallest(k, count, key=lambda v: (-count[v], v))
    return top, estimate, reads

For checking the noise, a simpler version reads exactly s friends, fixed in advance, and comes with the variance formula derived in the math section below.

estimator.py · the fixed-s estimate and its variance
def estimate_mutual(adj, u, v, s, rng=random):
    """Unbiased estimate of m(u, v) from s friends of u drawn without replacement."""
    sample = rng.sample(sorted(adj[u]), s)
    c = sum(1 for f in sample if v in adj[f])     # c ~ Hypergeometric(d, m, s)
    return len(adj[u]) / s * c

def estimator_variance(d, m, s):
    """Var(m_hat) = m (d - m) (d - s) / (s (d - 1)), derived on the page."""
    return m * (d - m) * (d - s) / (s * (d - 1)) if d > 1 else 0.0

When it is enough, and what to say in an interview

  • Ranking needs less than fairness. Within one request the scale d/s is the same for every candidate, so ranking by the guess is ranking by the raw count c. Fairness matters when the number leaves the request: as an input to Day 4's model, against a threshold ("show only with at least 3 mutual friends"), or as the "12 mutual friends" text on a profile. Then send s along with the guess, so whoever uses it knows how noisy it is.
  • The hard part is near tenth place. Top candidates have many mutual friends and are estimated well. The ones that decide the bottom of the top 10 have 2 or 3 (that is the exact tenth-best count for 72.7% of a sample of 1,000 users), and those are the noisiest.
  • Use a seeded random order. Seeding the shuffle with the user and the day makes a refresh give the same list, while different users still get independent errors.
  • The budgeted version is a little different. In sampled_suggest the number of friends read depends on which friends came first, so the scaled count is no longer exactly fair. For ranking that does not matter. When the count is exported, use estimate_mutual with an s fixed before sampling, for example the budget divided by the average friend list length.
The math, step by step: the scaled count is fair, and how noisy it is

A slightly bigger example first. Say you have d = 6 friends, f1 to f6, and a candidate knows f1 and f2, so the true count is m = 2. Read s = 3 friends at random; the scale is 6/3 = 2. There are \(\binom63 = 20\) equally likely sets of 3 friends. Sort them by how many of f1, f2 they contain:

c = 0f3f4f5…three of the other four: \(\binom43 = 4\) sets · guess 0
c = 1f1f3f4…one of f1, f2 and two of the other four: \(2 \cdot \binom42 = 12\) sets · guess 2
c = 2f1f2f3…both, plus one of four: \(\binom41 = 4\) sets · guess 4
Average guess \((0 \cdot 4 + 2 \cdot 12 + 4 \cdot 4)/20 = 2\). Average squared guess \((0 + 4 \cdot 12 + 16 \cdot 4)/20 = 5.6\), so the variance is \(5.6 - 2^2 = 1.6\).

We now prove that the average is always m, and find a formula that gives 1.6 here.

Step 1: name the pieces. For each friend f of the user, let \(X_f = 1\) if f is in the sample and 0 if not; this is the random part. Let \(Y_f = 1\) if f also knows the candidate and 0 if not; this is fixed, and \(\sum_f Y_f = m\). The count in the sample is \(c = \sum_f X_f Y_f\): it adds 1 for every sampled friend who knows the candidate.

Step 2: the chance that one friend is sampled. Of the \(\binom ds\) possible samples, those that contain a given friend f are made by choosing the other \(s-1\) members from the remaining \(d-1\) friends. So

\[ P(X_f = 1) = \frac{\binom{d-1}{s-1}}{\binom{d}{s}} = \frac{s}{d} . \]

In the example, \(\binom52/\binom63 = 10/20 = 1/2 = 3/6\). Similarly, a given pair of friends f and g are both in the sample with probability \(\binom{d-2}{s-2}/\binom ds = \frac{s(s-1)}{d(d-1)}\) (in the example \(4/20 = (3 \cdot 2)/(6 \cdot 5)\)).

Step 3: the average of the guess. The average of a sum is the sum of the averages, whether or not the terms depend on each other (linearity of expectation). Each \(X_f\) averages \(s/d\), so

\[ \mathbb E[c] = \sum_f Y_f\, \mathbb E[X_f] = m \cdot \frac{s}{d}, \qquad \mathbb E[\hat m] = \frac{d}{s}\cdot m \cdot \frac{s}{d} = m . \]

That is fairness: the scale d/s exactly undoes the fraction of friends read.

Step 4: why the variance needs care. The \(X_f\) are not independent: if f took one of the s places, there is one place fewer for g. So we need each term's variance and the covariance of each pair (how much two terms move together). For a 0/1 variable with probability p, the variance is \(p(1-p)\):

\[ \operatorname{Var}(X_f) = \frac{s}{d}\Big(1 - \frac{s}{d}\Big) = \frac{s(d-s)}{d^2}, \qquad \operatorname{Cov}(X_f, X_g) = \frac{s(s-1)}{d(d-1)} - \frac{s^2}{d^2} = -\frac{s(d-s)}{d^2(d-1)} . \]

The covariance is the chance both are in, minus the product of the separate chances; it comes out negative, as expected.

Step 5: add them up. The variance of a sum is the sum of the variances plus the covariances of all ordered pairs. Only the m friends with \(Y_f = 1\) appear in c, so there are m variance terms and \(m(m-1)\) covariance terms:

\[ \operatorname{Var}(c) = m\,\frac{s(d-s)}{d^2} - m(m-1)\,\frac{s(d-s)}{d^2(d-1)} = \frac{m\,s(d-s)}{d^2}\Big(1 - \frac{m-1}{d-1}\Big) = \frac{m\,s\,(d-s)(d-m)}{d^2(d-1)} . \]

This is the variance of the hypergeometric distribution: the number of marked items in a sample of s drawn without replacement from d, of which m are marked.

Step 6: scale up. Multiplying a random number by d/s multiplies its variance by \((d/s)^2\):

\[ \operatorname{Var}(\hat m) = \frac{d^2}{s^2}\cdot\frac{m\,s\,(d-s)(d-m)}{d^2(d-1)} = \frac{m\,(d-m)\,(d-s)}{s\,(d-1)} . \]

Check. The example: \(2 \cdot 4 \cdot 3/(3 \cdot 5) = 1.6\), as counted. The six-person graph: Dev has \(m = 1\), \(d = 2\), \(s = 1\): \(1 \cdot 1 \cdot 1/(1 \cdot 1) = 1\); Esha has \(m = d = 2\): the factor \(d - m\) is 0, so no noise.

Step 7: read the formula.

  • The factor \((d-s)/(d-1)\) is 0 when \(s = d\): reading every friend is exact. It is called the finite population correction. Drawing with replacement would replace it by 1 (the count becomes binomial, with variance \(m(d-m)/s\)), which is worse by the ratio \((d-1)/(d-s)\).
  • When m and s are much smaller than d, the variance is about \(m d/s\), so the typical error divided by m is about \(\sqrt{md/s}/m = \sqrt{d/(ms)} = 1/\sqrt{ms/d}\). And \(ms/d = \mathbb E[c]\) is the number of mutual friends you expect to see. That is the rule used above.

What was proved. Reading s friends chosen uniformly without replacement and scaling the count by d/s gives the right answer on average, with variance \(m(d-m)(d-s)/(s(d-1))\); the noise relative to the true count falls as one over the square root of the expected number of mutual friends seen.

ML · the yardstick: recall@10 against the exact answer

What "almost the same people" means

We need one number that says how close the budgeted top 10 came. Compare it with the thing it approximates: the exact top 10 from Day 1. Recall@10 is the share of the exact top 10 that the budgeted top 10 recovers. (Both lists have 10 entries, so the share of the budgeted list that is right is the same number.)

Why not compare with the friendships that actually formed later? Because that mixes two errors: "the budget lost candidates" and "mutual-friend count is an imperfect predictor". Day 4 deals with the second. Comparing with the exact answer isolates the first, which is the one a budget changes.

Ties need a rule

Back to the six-person example, top 2 this time. The exact top 2 is Esha (2) and Dev (1); Farid also has 1 and loses to Dev only because Day 1 breaks ties by smaller id. With a budget of 4 reads, suppose the random order reads Chloe's list: the budgeted top 2 is Esha and Farid. Counted strictly, it got 1 of 2 right. But Farid is exactly as good as Dev; the budget did nothing wrong. So a pick counts as a hit when its exact count is at least the exact tenth-best (here, second-best) count. By that rule the answer is 2 of 2.

On the real graph this matters a lot, because the tenth-best count is usually small and shared by many candidates. At a budget of 400 reads, strict overlap is 0.470 and tie-aware recall is 0.585. The rest of the day reports tie-aware recall.

recall.py · tie-aware recall@k
def recall_at_k(approx_top, exact_count, k=10):
    """Tie-aware recall@k: an approximate pick counts if its exact mutual count is at
    least the exact k-th best count. Denominator: min(k, number of candidates)."""
    if not exact_count:
        return 1.0
    best = sorted(exact_count.values(), reverse=True)
    need = min(k, len(best))
    threshold = best[need - 1]
    hits = sum(1 for v in approx_top[:k] if exact_count.get(v, 0) >= threshold)
    return hits / need

Skipping popular friends: a trade

Day 2 capped hubs: skip any friend with more than C friends. Here that does two things at once.

  • It changes the question. The capped count only counts mutual friends who are not hubs. However many reads you allow, it cannot recover the hub's votes. A fixed error that more data does not remove is called bias.
  • It buys many more votes per read. A hub with 1,480 friends costs as many reads as 74 friends with 20 each. The hub is one vote in the mutual count; the 74 friends are 74 votes. At a fixed budget, skipping hubs lowers the noise (the variance).

The math, step by step: what capping does to the estimate

Step 1: what the capped sample sees. With a cap, the random friends are drawn only from the user's non-hub friends; call their number \(d_C\). Of the m mutual friends, say \(m_C\) are non-hubs and \(m - m_C\) are hubs.

Step 2: rerun the fairness proof. The proof above never used anything about the friends except that the sample is uniform among them. So, with \(d_C\) in place of d and \(m_C\) in place of m, the scaled count \((d_C/s)\,c\) averages \(m_C\).

Step 3: the bias. Its average misses the true count by \(m_C - m = -(\text{number of hubs among the mutual friends})\). No budget fixes that.

Step 4: why the variance drops. At a budget of B reads, the number of friends read is about B divided by the average list length among the friends eligible to be read. The hubs dominate that average (it is 73.8 against a typical 20, Day 2), so removing them raises s, and by the variance formula a larger s lowers the noise.

What was shown. Capping turns a fair, noisy estimate of m into a fair, less noisy estimate of a slightly different number, \(m_C\). The recall table measures which error matters more at each budget.

Solution

s = 2. 15 samples: 6 contain neither f1 nor f2, 8 contain one, 1 contains both. The scale is 3: average \((3 \cdot 8 + 6 \cdot 1)/15 = 2\); average square \((9 \cdot 8 + 36)/15 = 7.2\); variance \(7.2 - 4 = 3.2\). Formula: \(2 \cdot 4 \cdot 4/(2 \cdot 5) = 3.2\).

Capped bias. \(-1\) for each hub among the mutual friends, as in step 3 of the capping math.

With replacement. The count is binomial with s trials and success chance \(m/d\): \(\operatorname{Var}(c) = s\,(m/d)(1 - m/d)\), so \(\operatorname{Var}(\hat m) = m(d-m)/s\). The ratio to the without-replacement variance is \((d-1)/(d-s) \ge 1\), equal to 1 only at \(s = 1\).

Horvitz–Thompson. \(\hat m = \sum_f X_f Y_f / \pi_f\) with \(\mathbb E[X_f] = \pi_f\), so \(\mathbb E[\hat m] = \sum_f Y_f = m\), by linearity again. The uniform case is \(\pi_f = s/d\).

DSA · people with similar friend sets: Jaccard, MinHash, LSH

A different route

The two-hop scan finds candidates by walking through your friends, so its cost is set by how popular they are. Here is another way to think about a good suggestion: someone whose circle of friends looks like yours. If we could find, for every user, the people with the most similar friend sets, without walking through hubs, we would have a second source of candidates whose cost does not depend on the hubs.

Measuring "looks like yours". Take the friends two people share and divide by everyone either of them knows. This share is the Jaccard similarity, a number from 0 (nothing shared) to 1 (identical friend sets). In the six-person example your friends are Ben and Chloe. Esha's friends are also Ben and Chloe: Jaccard 1. Dev knows only Ben: 1 shared out of 2 people in all, Jaccard 0.5. Dividing by everyone either knows is what makes this different from the mutual count: a hub shares a few friends with nearly everyone, but they know so many people that their Jaccard with you stays small.

Try the obvious thing. Compare every pair of users: about 50 million pairs at 10,000 users, and the number grows with the square of the user count. Or compare only pairs two hops apart, which costs the sum of squared degrees, 14,768,324 counter updates on the week's graph, dominated by hubs (Day 2). Both are the costs we want to escape.

MinHash: a short signature that remembers similarity

The idea. Shuffle all users into one random order. For each person, note which of their friends comes first in that order. Two people get the same "first friend" exactly when the first person in the order, among everyone either of them knows, is someone they both know.

By hand. You (Ben, Chloe) and Dev (Ben). Among the people either of you knows, Ben and Chloe, one comes first in the random order, each with chance one half. If Ben comes first, both your first friend and Dev's are Ben: they agree. If Chloe comes first, yours is Chloe and Dev's is still Ben: they differ. They agree half the time, and the Jaccard similarity is one half. That is not a coincidence: the chance that the first friends agree is exactly the Jaccard similarity.

Repeat with k independent orders. Each person's k first friends form their signature: k numbers, however many friends they have. The share of positions where two signatures agree estimates their Jaccard similarity, and the estimate gets better as k grows, with the same one-over-square-root law as the friend sample.

Hash functions play the shuffles. Storing random orders of every user is impossible at scale, so a hash function stands in for each order: friend x's position is mix64(x ^ seed), a 64-bit function that sends nearby ids to unrelated values. The proof needs every element to be equally likely to come first, and cheap hashes can fail that badly. The textbook hash \((a x + b) \bmod p\), fine for hash tables, sends consecutive ids to evenly spaced values, so the minimum lands near the ends of a run of ids rather than at a random member. On two sets of ids {0…59} and {30…89} (Jaccard 1/3), with 400 hashes and five seeds, it estimated 0.282, 0.237, 0.270, 0.285 and 0.268, all low. The mixing hash gave 0.347, 0.320, 0.335, 0.310 and 0.340.

minhash.py · signatures and the Jaccard estimate
MASK = (1 << 64) - 1

def mix64(x):
    """A 64-bit mixing function (the splitmix64 finalizer): nearby inputs give unrelated outputs."""
    x = (x + 0x9E3779B97F4A7C15) & MASK
    x = ((x ^ (x >> 30)) * 0xBF58476D1CE4E5B9) & MASK
    x = ((x ^ (x >> 27)) * 0x94D049BB133111EB) & MASK
    return x ^ (x >> 31)

def make_hashes(k, seed=0):
    """k random seeds; h_i(x) = mix64(x XOR seed_i) stands in for k random permutations."""
    rng = random.Random(seed)
    return [rng.getrandbits(64) for _ in range(k)]

def minhash(items, hashes):
    """Signature: for each hash function, the smallest hash value over the set."""
    return [min(mix64(x ^ h) for x in items) for h in hashes]

def jaccard(a, b):
    return len(a & b) / len(a | b) if a or b else 1.0

def estimate_jaccard(sig_a, sig_b):
    """Fraction of positions where the two signatures agree."""
    return sum(x == y for x, y in zip(sig_a, sig_b)) / len(sig_a)

Cost. One signature costs k hashes per friend, so all signatures cost k times the number of friend-list entries: linear in the friendships, with no sum-of-squares term. Each user stores k numbers; comparing two users costs k steps. A new friendship updates a signature in k steps (keep the smaller of the old value and the new friend's hash). An ended friendship cannot be removed that way; the signature is recomputed from the list.

In one line. The first friend of two people under a random order agrees with probability equal to their Jaccard similarity, so k random orders give a fixed-size signature whose agreements estimate it.

The math, step by step: why the first friends agree with probability J, and how noisy the estimate is

Step 1: list it out once. Take two small sets, A = {1, 2, 3} and B = {2, 3, 4}. They share 2 and 3, and together contain 1, 2, 3, 4, so \(J = 2/4\). Order 1, 2, 3, 4 at random. If 2 or 3 comes first among them, it is the first member of both sets: agree. If 1 comes first, A's first is 1 and B's is not: differ. If 4 comes first, the same the other way. Each of the four is first with chance 1/4, so they agree with chance 2/4 = J.

Step 2: the general argument. Write the min-hash of a set as \(h_\pi(A) = \min_{x \in A} \pi(x)\), the position of its earliest member under the order π. Let \(x^{*}\) be the earliest element of \(A \cup B\) (everyone either set contains). By symmetry, each element of \(A \cup B\) is equally likely to be \(x^{*}\), with chance \(1/|A \cup B|\).

  • If \(x^{*}\) is in both sets, it comes before every other member of each set, so both min-hashes equal \(\pi(x^{*})\): they agree.
  • If \(x^{*}\) is only in A, then \(h_\pi(A) = \pi(x^{*})\), which is smaller than the position of every member of B, so \(h_\pi(A) < h_\pi(B)\): they differ. The case "only in B" is the same.

So they agree exactly when \(x^{*} \in A \cap B\), which has probability \(|A \cap B|/|A \cup B| = J(A, B)\).

Step 3: the estimate and its noise. With k independent orders, let \(Z_i = 1\) if the i-th min-hashes agree. Each \(Z_i\) is 1 with probability J, independently, so its variance is \(J(1-J)\). The estimate is the average of the \(Z_i\):

\[ \hat J = \frac1k \sum_{i=1}^k Z_i, \qquad \mathbb E[\hat J] = J, \qquad \operatorname{Var}(\hat J) = \frac{1}{k^2}\cdot k \cdot J(1-J) = \frac{J(1-J)}{k} . \]

At J = 0.1 and k = 100 the typical error is \(\sqrt{0.09/100} = 0.03\). Halving it costs four times the hashes.

Step 4: what a hash must do. Step 2 used only one property of the order: every element of any set is equally likely to come first. A hash family with that property is called min-wise independent. A well-mixed 64-bit hash behaves like one in practice; \((ax+b) \bmod p\) does not, as the measurement above shows.

What was proved. One random order makes two min-hashes agree with probability exactly J; averaging over k independent orders gives a fair estimate of J with variance \(J(1-J)/k\).

LSH: find the similar pairs without comparing every pair

The situation. Signatures make one comparison cheap, but there are still 50 million pairs. We want only the similar ones, and we want to find them by sorting people into buckets, not by comparing.

The idea. Cut each signature of k numbers into b bands of r numbers each. For each band, put every user into a bucket labelled by that band's r numbers. Two users become a candidate pair if they land in the same bucket in at least one band. Matching a whole band is unlikely unless two people are similar (a narrow door), and b bands give them many chances (many doors). This is locality-sensitive hashing, LSH for short.

The S-curve. A pair agrees on one band with probability \(J^r\), so the chance of becoming a candidate rises with J in an S shape: near 0 for dissimilar pairs, near 1 for similar ones, with the step at about \((1/b)^{1/r}\). More rows per band make the step sharper and move it right; more bands move it left.

lsh.py · banding and the S-curve
def lsh_pairs(sigs, r, b):
    """Banding: split each signature into b bands of r values; two users become a
    candidate pair if they agree on every value of at least one band.
    Returns (set of pairs u < v, work = pairs emitted before deduplication)."""
    pairs, work = set(), 0
    for j in range(b):
        buckets = defaultdict(list)
        for u, sig in sigs.items():
            buckets[tuple(sig[j * r:(j + 1) * r])].append(u)
        for members in buckets.values():
            work += len(members) * (len(members) - 1) // 2
            for i, x in enumerate(members):
                for y in members[i + 1:]:
                    pairs.add((min(x, y), max(x, y)))
    return pairs, work

def s_curve(s, r, b):
    """P(a pair with Jaccard s becomes a candidate) = 1 - (1 - s^r)^b."""
    return 1 - (1 - s ** r) ** b

The math, step by step: the S-curve and where its step is

Step 1: one position. By the MinHash result, one signature position agrees with probability J, and positions use independent hashes, so they agree independently.

Step 2: one band. A band agrees only if all r of its positions agree: probability \(J^r\). With r = 2 and J = 0.1, that is 0.01.

Step 3: all bands. The pair is missed only if every one of the b bands fails, each with probability \(1 - J^r\), independently. So

\[ P(\text{candidate}) = 1 - (1 - J^r)^b . \]

With r = 2, b = 50, J = 0.1: \(1 - 0.99^{50} = 1 - 0.605 = 0.395\), the value in the chart.

Step 4: where the step is. Try \(J^r = 1/b\): the probability is \(1 - (1 - 1/b)^b\), and since \((1 - 1/b)^b\) is close to \(e^{-1}\) for large b, that is about \(1 - 1/e \approx 0.63\). So at \(J = (1/b)^{1/r}\) the curve is already most of the way up. To find the steepest point, differentiate \(f(J) = 1 - (1 - J^r)^b\):

\[ f'(J) = b\,r\,J^{r-1}(1 - J^r)^{b-1} . \]

The steepest point is where \(f'\) is largest, so set the derivative of \(\ln f'\) to zero:

\[ \frac{r-1}{J} - \frac{(b-1)\,r\,J^{r-1}}{1 - J^r} = 0 \;\Rightarrow\; (r-1)(1 - J^r) = (b-1)\,r\,J^r \;\Rightarrow\; J^r = \frac{r-1}{rb-1} . \]

For large b, \((r-1)/(rb-1) \approx (1 - 1/r)/b\), the same size as \(1/b\). Hence the rule of thumb: the step is near \((1/b)^{1/r}\).

Step 5: the two errors. A pair well below the step becomes a candidate with probability about \(b\,J^r\) (a false positive; for small \(J^r\), \(1 - (1-x)^b \approx bx\)). A pair above it is missed with probability \((1 - J^r)^b\) (a false negative). With r = 2, b = 50: a pair at J = 0.02 slips through with chance about \(50 \cdot 0.0004 = 0.02\), and a pair at J = 0.3 is missed with chance \(0.91^{50} \approx 0.009\).

What was proved. Banding catches a pair of similarity J with probability \(1 - (1 - J^r)^b\), an S-curve whose step sits near \((1/b)^{1/r}\); rows sharpen it, bands shift it left.

DSA · Bloom filters: who must not be shown

The situation

Before a list goes back to the app, every candidate is checked: not already a friend, not blocked in either direction, not already shown many times. Candidates now come from several sources, in the hundreds per request, and each check must be fast and small enough to keep next to the candidate lists.

Try the obvious thing. Keep an exact hash set of all such pairs (LeetCode 705 at the end of the day builds one). It stores the keys themselves. The week's 100,000 friendships, stored in both directions as 8-byte numbers, are 1.6 MB before any table overhead, and the size grows with every key.

The idea: a few bits per key, and an error that only goes one way

A Bloom filter is a row of m bits, all 0, and k hash functions that each pick a position. To add a key, set its k bits to 1. To ask about a key, look at its k bits: if any is 0, the key was never added, for certain. If all are 1, the answer is "probably yes". Bits only ever go from 0 to 1, so a key that was added always finds its bits set: a Bloom filter never says "no" to a key it holds. It can say "yes" wrongly, when other keys happen to have set all of a key's bits between them.

By hand. m = 10 bits, k = 2. Add "You–Ben", whose hashes land, say, on bits 1 and 4, and "You–Chloe" on bits 4 and 8. Ask about "You–Esha", whose hashes land on 1 and 8: both bits are 1, set by two different keys, so the filter says "yes": a false positive. Ask about "You–Dev" on 2 and 4: bit 2 is 0, so a certain "no".

bloom.py · a Bloom filter and its false-positive rate
class Bloom:
    """m bits; k positions per integer key from two base hashes (Kirsch-Mitzenmacher).
    A pair (u, v) is stored as the integer u * N + v. Uses mix64 from the MinHash block."""
    def __init__(self, m, k):
        self.m, self.k, self.bits = m, k, bytearray((m + 7) // 8)

    def _positions(self, key):
        h = mix64(key)
        h1, h2 = h & 0xFFFFFFFF, (h >> 32) | 1    # h2 odd, so the k positions differ
        return [(h1 + i * h2) % self.m for i in range(self.k)]

    def add(self, key):
        for p in self._positions(key):
            self.bits[p >> 3] |= 1 << (p & 7)

    def __contains__(self, key):                  # False is certain; True may be wrong
        return all(self.bits[p >> 3] >> (p & 7) & 1 for p in self._positions(key))

def bloom_fpr(n, m, k):
    """False-positive rate after n insertions: (1 - e^{-kn/m})^k."""
    return (1 - math.exp(-k * n / m)) ** k

def bloom_best_k(n, m):
    return max(1, round(m / n * math.log(2)))

The code gets its k positions from two base hashes as \(h_1 + i\,h_2\), a trick (Kirsch and Mitzenmacher, 2006) that keeps the same false-positive rate as k independent hashes.

Why the one-way error fits, and two cautions

These checks guard exclusions. A false "yes" drops a good candidate: a small loss of relevance, at a rate we choose. A false "no" would show someone the user blocked, a trust failure, and the filter never gives one for a key it holds. Two cautions follow:

  • A filter is a snapshot. A block made after it was built is not in it. So the final, exact check against the stored data still runs on every response (Day 5 covers where that data lives).
  • A Bloom filter cannot delete. Clearing an unblocked pair's bits could clear bits other keys share. Rebuild periodically, or use a counting filter (small counters instead of bits).

Why a Bloom filter cannot count mutual friends. Counting needs the candidates, and a filter cannot list what it holds; it stores bits, not keys. Given a candidate from elsewhere, you could ask "is f–v a friendship?" for each of the user's friends, but each friend who does not know v adds a false "yes" at the false-positive rate. Measured with the 8-bits-per-key filter on 200 users and up to 20 candidates each, the count came out too high by 0.381 on average (predicted 0.396) and was never too low. The error grows with the user's number of friends and hits hardest the weak candidates that a threshold has to separate.

Where it goes. Small per-user filters kept next to the candidate lists: "already shown" (a user who has seen 2,000 suggestions needs 2,000 × 9.6 bits ≈ 2.4 KB at 1%), "blocked by or blocking", and a global "recently dismissed". They run when sources are merged, before ranking, to cut the list cheaply. The exact checks run after ranking, on the 10 that are shown.

In one line. A Bloom filter answers "have I seen this?" in about 10 bits per key with a false "yes" now and then and never a false "no", which is the right error for "do not show" lists, as long as an exact check runs last.

The math, step by step: the false-positive rate, and the best number of hashes

Step 1: one bit stays 0. Assume each hash position is uniform and independent. One position of one key misses a given bit with probability \(1 - 1/m\). Adding n keys sets kn positions, so

\[ P(\text{a given bit is still } 0) = \Big(1 - \frac1m\Big)^{kn} \approx e^{-kn/m} . \]

The approximation uses \((1 - 1/m)^m \approx e^{-1}\) for large m. With 10 bits per key (\(m/n = 10\)) and \(k = 7\): \(e^{-0.7} = 0.497\), so about half the bits are still 0.

Step 2: a false positive. A key that was never added is a false positive when all its k bits are 1. Treating the bits as independent (very nearly true for large m), the rate is

\[ f = \big(1 - e^{-kn/m}\big)^{k} . \]

With the numbers above: \((1 - 0.497)^7 = 0.503^7 \approx 0.0082\), the 0.82% in the table.

Step 3: the tug of war in k. More hashes check more bits (fewer false positives) but set more bits (more false positives). Let \(p = e^{-kn/m}\), the share of bits still 0. Then \(k = -(m/n)\ln p\), and taking logs of f,

\[ \ln f = k \ln(1 - p) = -\frac{m}{n}\,\ln p\,\ln(1-p) . \]

For a fixed number of bits per key \(m/n\), making f small means making \(g(p) = \ln p \cdot \ln(1-p)\) large. Both logs are negative, so \(g > 0\); and \(g \to 0\) as p goes to 0 or 1.

Step 4: find the top of g. Differentiate and put it over one denominator:

\[ g'(p) = \frac{\ln(1-p)}{p} - \frac{\ln p}{1-p} = \frac{(1-p)\ln(1-p) - p \ln p}{p(1-p)} . \]

Call the numerator \(-D(p)\), so \(D(p) = p\ln p - (1-p)\ln(1-p)\). D is 0 at \(p = 0\), \(\tfrac12\) and 1. Its derivative is \(D'(p) = \ln p + 1 + \ln(1-p) + 1 = \ln\big(p(1-p)\big) + 2\), negative for small p (below about 0.161) and positive from there to ½. So on \((0, \tfrac12)\), D dips below 0 and climbs back to 0 at ½: \(D < 0\), hence \(g' > 0\) and g increases. Since \(D(1-p) = -D(p)\), g decreases on \((\tfrac12, 1)\). The maximum is at \(p = \tfrac12\): the best filter is half full.

Step 5: translate back. \(p = e^{-kn/m} = \tfrac12\) gives

\[ k^{*} = \frac{m}{n}\ln 2, \qquad f^{*} = \Big(\frac12\Big)^{k^{*}} \approx 0.6185^{\,m/n}, \qquad \frac{m}{n} = \frac{\log_2(1/f)}{\ln 2} \approx 1.44 \log_2\frac1f . \]

For 1%: \(\log_2 100 = 6.64\), times 1.44 is 9.6 bits per key, and \(k^{*} = 9.6 \times 0.693 \approx 7\).

What was proved. A Bloom filter with m bits, n keys and k hashes has false-positive rate about \((1 - e^{-kn/m})^k\); it is smallest when half the bits are set, at \(k = (m/n)\ln 2\), and then 1.44 log2(1/f) bits per key buy a false-positive rate f.

DSA · random walks: personalized PageRank

The situation

Counting mutual friends gives every mutual friend the same vote, popular or not, and it cannot see anyone three steps away. The reading found that 53% of new friendships had a mutual friend; the other 47% are invisible to the count. Can one score add up evidence over all routes from you to someone, favour short routes, and discount routes that pass through hubs?

Try the obvious thing. Count routes of length 2, 3, 4 and so on from you to each person. Through a hub the counts explode: a hub with 1,480 friends creates 1,480 routes to each of its friends' friends. Raw route counts reward being near a hub, the opposite of what we want.

The idea: a walker who keeps going home

Put a walker on you. At each step, with probability α (say 0.3) the walker jumps back to you; otherwise they move to a friend of where they stand, chosen at random. Run this for a long time and note the share of time the walker spends at each person. That share is the person's personalized PageRank from you. Short routes count most, because the walker keeps going home. A hub splits the walker's next step among all its friends, so a route through a hub delivers only a sliver to each of them.

Now give Ben 20 more friends, so he has 24 and Chloe still has 4. Dev and Farid each still have exactly one mutual friend with you. But the walker reaches Dev only through Ben, who now sends each step to one of 24 people:

ppr.py · personalized PageRank by repeated spreading, and by random walks
def to_arrays(adj):
    """Edge arrays for vectorized walks: an edge f -> v for every friendship, both ways."""
    src = np.array([f for f in range(len(adj)) for _ in adj[f]], dtype=np.int64)
    dst = np.array([v for f in range(len(adj)) for v in adj[f]], dtype=np.int64)
    deg = np.array([len(a) for a in adj], dtype=np.float64)
    return src, dst, deg

def ppr(src, dst, deg, u, alpha=0.3, iters=30):
    """Personalized PageRank of every user for walks that restart at u with prob. alpha.
    Power iteration on x = alpha e_u + (1 - alpha) x P, P[f, v] = 1/deg(f) per edge."""
    n = len(deg)
    e = np.zeros(n); e[u] = 1.0
    inv = np.divide(1.0, deg, out=np.zeros(n), where=deg > 0)
    x = e.copy()
    for _ in range(iters):
        spread = np.bincount(dst, weights=x[src] * inv[src], minlength=n)   # x P
        x = alpha * e + (1 - alpha) * spread
    return x

def ppr_suggest(adj, src, dst, deg, u, k=10, alpha=0.3, iters=30):
    x = ppr(src, dst, deg, u, alpha, iters)
    x[u] = -1.0
    for f in adj[u]:
        x[f] = -1.0                               # self and friends are not candidates
    top = np.argsort(-x, kind="stable")[:k]
    return [int(v) for v in top if x[v] > 0]

def ppr_walks(adj_lists, u, walks=1000, alpha=0.3, rng=random):
    """Monte Carlo PPR: a walk stops with probability alpha before each step; the share of
    walks that stop at v estimates ppr(u)[v] without bias. Returns (stop counts, steps)."""
    stops, steps = Counter(), 0
    for _ in range(walks):
        x = u
        while rng.random() >= alpha and adj_lists[x]:
            x = rng.choice(adj_lists[x]); steps += 1   # one random read: O(1), as in LC 380
        stops[x] += 1
    return stops, steps

ppr computes the shares exactly by spreading: start with all the walker's weight on you, and on each round keep a share α at home and spread the rest evenly over each person's friends. This is called power iteration. ppr_walks estimates the same shares by actually running walks and counting where they stop, with no matrix at all.

In an interview, this is the "random walk with restart" source behind follow recommendations; say what it adds (discounted hubs, reach beyond two hops), that it runs offline, and how it is computed at scale (walks for all users at once in a batch job, or local "push" methods).

In one line. A walk that keeps returning home scores everyone by all short routes from you, with each route through a hub diluted, and on this graph it ranks future friends better than the mutual count; it is computed offline.

The math, step by step: what the walk adds up, and why spreading settles

Step 1: one step as a table. Write P for the table of step chances: \(P_{fv} = 1/\deg(f)\) if f and v are friends, and 0 otherwise. Each row adds to 1. If the row vector \(x_t\) holds the walker's chances of being at each person after t steps, one more step gives \(x_t P\). In the six-person graph, Ben's row has 1/4 for each of You, Chloe, Dev and Esha.

Step 2: the walk with restarts. With \(e_u\) the vector with 1 at you and 0 elsewhere, one round is "go home with chance α, otherwise step":

\[ x_{t+1} = \alpha\, e_u + (1 - \alpha)\, x_t P, \qquad \text{and the settled shares satisfy} \qquad \pi_u = \alpha\, e_u + (1 - \alpha)\, \pi_u P . \]

Step 3: unroll it. Substitute the right-hand side into itself once: \(\pi_u = \alpha e_u + (1-\alpha)\alpha\, e_u P + (1-\alpha)^2 \pi_u P^2\). Keep going T times:

\[ \pi_u = \alpha \sum_{t=0}^{T-1} (1-\alpha)^t\, e_u P^t \;+\; (1-\alpha)^T \pi_u P^T \;\xrightarrow{T \to \infty}\; \alpha \sum_{t=0}^{\infty} (1-\alpha)^t\, e_u P^t . \]

The last term vanishes because \(\pi_u P^T\) has total weight at most 1 and \((1-\alpha)^T \to 0\). In words: the score of v adds up the chance of reaching v in exactly t steps, for every t, with longer routes discounted by \((1-\alpha)^t\).

Step 4: the two-step term is a discounted mutual count. To reach v in two steps, the walker goes to a friend f of yours (chance \(1/\deg(u)\)) and then to v (chance \(1/\deg(f)\)), and f must be a mutual friend:

\[ (e_u P^2)_v = \sum_{f \in N(u) \cap N(v)} \frac{1}{\deg(u)}\cdot\frac{1}{\deg(f)} . \]

Each mutual friend votes \(1/\deg(f)\). Six-person graph: Esha \(\tfrac12(\tfrac14 + \tfrac14) = \tfrac14\), Dev and Farid \(\tfrac12 \cdot \tfrac14 = \tfrac18\). With Ben at 24 friends: Dev \(\tfrac12 \cdot \tfrac1{24} = \tfrac1{48}\), Farid still \(\tfrac18\). Day 4 meets this same sum as the resource allocation score.

Step 5: a step never increases the total error. Measure the size of a vector y by \(\|y\|_1 = \sum_v |y_v|\). Then

\[ \|yP\|_1 = \sum_v \Big|\sum_f y_f P_{fv}\Big| \le \sum_f |y_f| \sum_v P_{fv} = \|y\|_1 , \]

using that the absolute value of a sum is at most the sum of absolute values, and that each row of P adds to 1 (or 0 for someone with no friends).

Step 6: the error shrinks every round. Subtract the settled equation from the round: \(x_{t+1} - \pi_u = (1-\alpha)(x_t - \pi_u)P\). By step 5, \(\|x_{t+1} - \pi_u\|_1 \le (1-\alpha)\|x_t - \pi_u\|_1\). Both start as probability vectors, so their distance is at most 2, and after t rounds

\[ \|x_t - \pi_u\|_1 \le 2\,(1-\alpha)^t \qquad\Rightarrow\qquad t \ge \frac{\ln(2/\varepsilon)}{\ln\!\big(1/(1-\alpha)\big)} \text{ rounds reach error } \varepsilon . \]

For α = 0.3 and ε = 10−4: \(\ln 20{,}000 / \ln(1/0.7) = 9.90/0.357 \approx 28\) rounds, whatever the size of the graph. The same shrinking shows the settled shares exist and are unique: two different fixed points would have to be closer to each other than they are.

Step 7: walks are a fair estimate. In ppr_walks, a walk stops before each step with chance α, so it makes exactly t moves with chance \(\alpha(1-\alpha)^t\), and is then at v with chance \((e_u P^t)_v\). Adding over t gives the series of step 3, so the share of walks that stop at v averages \(\pi_u(v)\), with variance \(\pi_u(v)(1 - \pi_u(v))/R\) for R walks. A walk makes \((1-\alpha)/\alpha\) moves on average (2.33 at α = 0.3, matching 2,330 reads per 1,000 walks).

What was proved. Personalized PageRank adds up all routes from you, shorter ones weighted more and each route through a friend f divided by deg(f); spreading reaches it with error at most \(2(1-\alpha)^t\) after t rounds, and random walks estimate it fairly.

DSA · three small structures behind sampling and filtering

Each idea today rests on a small structure an interviewer may ask for on its own: a random friend in constant time (walks and friend sampling), a weighted random pick (sampling with unequal chances), and the exact set that a Bloom filter approximates.

380 Insert Delete GetRandom O(1)

The situation. A walk step needs "a random friend" from a list that changes as friendships form and end. Try the obvious thing. A hash set adds and removes in constant time but has no positions, so picking a random element means walking it; a list has positions but removing from the middle shifts everything. The idea. Keep both: a gap-free array of the elements, and a map from each element to its position. To remove, move the last element into the hole, update its position, and drop the last slot. Why it is right. Two facts hold after every operation: the array holds exactly the set with no gaps, and the map gives each element's true position. Insert appends and records the position; remove overwrites the hole with the last element, records the new position and drops the duplicate at the end. A random position in a gap-free array is a random element. Cost. Constant time per operation on average, linear space.

randomized_set.py · 380
class RandomizedSet:                              # 380: insert, remove, getRandom in O(1)
    def __init__(self):
        self.pos, self.items = {}, []             # value -> index, and a dense array

    def insert(self, val):
        if val in self.pos:
            return False
        self.pos[val] = len(self.items); self.items.append(val)
        return True

    def remove(self, val):
        if val not in self.pos:
            return False
        i, last = self.pos[val], self.items[-1]
        self.items[i], self.pos[last] = last, i   # move the last element into the hole
        self.items.pop(); del self.pos[val]
        return True

    def getRandom(self):
        return random.choice(self.items)

528 Random Pick with Weight

The situation. Return index i with chance proportional to its weight. Weighted walks and the unequal-chance friend sample need it. Try the obvious thing. Repeat each index as many times as its weight and pick uniformly: memory grows with the total weight, and real-valued weights do not work. The idea. Lay the weights end to end on a line: running totals cut the line into pieces, piece i as long as weight i. Throw a point uniformly on the line and return the piece it lands in, found by binary search on the running totals. Why it is right. The point lands in a piece with chance (piece length) / (line length) = weight / total; bisect_right returns the first running total above the point, which is that piece, and a weight-0 piece has no length and is never returned. Cost. Linear to build, logarithmic per pick.

import bisect
import itertools

class Solution528:                                # 528: pick index i with prob. w[i] / sum(w)
    def __init__(self, w):
        self.prefix = list(itertools.accumulate(w))

    def pickIndex(self):
        x = random.random() * self.prefix[-1]     # uniform point on [0, total)
        return bisect.bisect_right(self.prefix, x)

705 Design HashSet

The situation. Build the exact set that the Bloom filter approximates. The idea. An array of buckets; key x lives in bucket \(h(x) \bmod M\), in a short list. Why it is fast. If the hash spreads keys evenly, a bucket holds on average (keys / buckets) of them, the load factor. Doubling the buckets whenever keys outnumber them keeps the load at most 1, so a lookup checks a constant number of keys on average. A doubling copies every key, but the copies add up to at most 8 + 16 + … + n ≤ 2n over n inserts, so each insert costs constant time on average. Against the Bloom filter. The hash set keeps the keys, so it is exact and can delete; the filter throws the keys away and keeps a few bits each.

hash_set.py · 705
class MyHashSet:                                  # 705: separate chaining, resize at load 1
    def __init__(self):
        self.size, self.buckets = 0, [[] for _ in range(8)]

    def _b(self, key):
        return self.buckets[hash(key) % len(self.buckets)]

    def add(self, key):
        b = self._b(key)
        if key not in b:
            b.append(key); self.size += 1
            if self.size > len(self.buckets):     # keep chains O(1) long on average
                old = [x for bucket in self.buckets for x in bucket]
                self.buckets = [[] for _ in range(2 * len(self.buckets))]
                for x in old:
                    self._b(x).append(x)

    def remove(self, key):
        b = self._b(key)
        if key in b:
            b.remove(key); self.size -= 1

    def contains(self, key):
        return key in self._b(key)

System Design · several sources under one budget

The situation

We now have several ways to find candidates: the sampled two-hop scan, which runs per request under its read budget; PageRank and LSH partners, computed offline and stored per user; and, cheapest of all, members of the user's groups, which works even for someone with few friends. The ranker after them can score a few hundred candidates. How should the sources share that space?

Try the obvious thing: one source, best effort

Run the two-hop scan with a timeout and return whatever it has by then. Three problems: the output changes with machine load, so tests and experiments cannot be repeated; nobody downstream knows how complete the list is; and the 47% of new friendships with no mutual friend can never appear.

The next idea: give each source a fixed share

Each source returns a list, best first. Merge them by taking each source's first candidate, then each source's second, and so on (round-robin), skipping anyone already taken or excluded, until the list is full. Every source gets an equal share.

merge.py · merge ranked sources, deduplicate, filter
def merge_sources(sources, k, exclude):
    """Round-robin merge of ranked candidate lists, deduplicated, hard filters applied.
    Each source is a list of user ids, best first. Returns at most k ids."""
    out, seen = [], set(exclude)
    for rank in range(max((len(s) for s in sources), default=0)):
        for s in sources:
            if rank < len(s) and s[rank] not in seen:
                seen.add(s[rank]); out.append(s[rank])
                if len(out) == k:
                    return out
    return out

Why it is right. seen starts as the excluded ids, and an id is added to the output only if it is not in seen, after which it joins seen: so no duplicates and no excluded ids. Ranks are visited in order, so every source's r-th candidate is considered before any source's (r+1)-th, and the loop stops at k. Cost. One set lookup per input entry. The exclude set may be the cheap Bloom-filter check, since it errs only by dropping.
