System Design · how big is a billion users?

The situation

An interviewer says: "There are a billion users." Before drawing any boxes, find out what that number does to the code you already have. Which resource runs out first: memory, network, or machines?

Try the obvious thing

"Run the same suggest on a bigger machine." To judge that, you need the size of the graph and the work per request at a billion users. Nobody will hand you those numbers. You estimate them.

The idea: estimate on paper, with every assumption labelled

A back-of-envelope estimate is a calculation from round numbers that is right to within a factor of a few. Its job is to tell you which resource breaks first. It has three steps.

  1. Write every assumption down, with a label. Then anyone can change one and redo the arithmetic.
  2. Compute with round numbers. A day is 86,400 seconds, close to 10⁵.
  3. Sanity-check against something known, and say which assumption the answer is most sensitive to.

Now the arithmetic, one line at a time.

  • Friendships. Each friendship gives two people one friend each. So a billion people with 200 friends each hold 10⁹ × 200 / 2 = 100 billion friendships.
  • Storage. Each friendship is stored twice, once in each person's list: 200 billion stored ids. At 8 bytes each, 1.6 TB. One large server with 256 GB of memory holds a seventh of it, so it takes 7 servers just to hold one copy, before replicas.
  • Traffic. 500 million active users × 2 loads = 10⁹ requests a day, or 10⁹ / 86,400 = 11,574 requests per second on average and 34,722 in the busiest hour.
  • Work per request. The two-hop scan reads every friend's friend list. With 200 friends of 200 friends each: 40,000 ids per request. But friends are more popular than average (Day 2's friendship paradox), and on the week's graph that makes the real work 3.69 times larger: about 148,000 ids, or 1.2 MB per request.
  • Bandwidth. 34,722 requests per second × 148,000 ids × 8 bytes = 41 GB of friend lists read every second at peak.

What breaks first. Not storage: 1.6 TB across a handful of machines is ordinary. What breaks is the reading: a hundred thousand ids per request, from many machines, tens of thousands of times a second, with a heavy tail. The rest of today attacks it from three sides: spread the reads well and cache the hot ones, keep the slowest machine from setting everyone's latency, and do the work before the request arrives.

In one line. Label every assumption, compute in round numbers, and let the estimate tell you which resource to design around; here it is reads per request, not storage.

The math, step by step: why the work per request grows with the square of the degree

We want the average number of ids a request reads, and why it is 3.69 times the "200 × 200" guess.

Small numbers first. In the six-person example, You have friends Ben (4 friends) and Chloe (4 friends). Your request reads 4 + 4 = 8 ids. Your own degree is 2, so "degree × degree" would guess 4. The guess is low because your friends are better connected than you.

The work of one request. For user u, the request reads the list of every friend f, and that list has \(\deg(f)\) entries. Write \(W(u) = \sum_{f \in N(u)} \deg(f)\), where \(N(u)\) is the set of u's friends.

Average over all users. Sum \(W(u)\) over every u. Each person f appears in that double sum once for each of their friends, that is \(\deg(f)\) times, and each time contributes \(\deg(f)\). So \(\sum_u W(u) = \sum_f \deg(f)^2\). Dividing by the number of users n:

\[ \text{mean } W = \frac{1}{n}\sum_f \deg(f)^2 = E[d^2], \]

where \(E[d^2]\) is the average squared degree. It is not \(E[d]^2\), the squared average degree.

Compare the two. On the week's graph \(E[d] = 20.0\) and \(E[d^2] = 1{,}476.8\) (Day 2), so

\[ \frac{E[d^2]}{E[d]^2} = \frac{1476.8}{400} = 3.69 . \]

The ratio is \(1 + \mathrm{Var}(d)/E[d]^2\): it is 1 only when everyone has the same degree, and it grows with the spread of degrees. Assuming the same shape at a billion users with \(E[d] = 200\): \(E[d^2] \approx 3.69 \times 40{,}000 \approx 147{,}600\) ids per request (147,683 with the unrounded ratio 3.692).

What this shows. The mean work is the average squared degree. Storage grows with the degree, reads grow with its square, and a heavy tail multiplies the reads again. That is why reading, not storage, breaks first.

Algorithms · split the graph across machines

1 · The situation

The friend lists need several machines (call each one a shard). Every server that handles a request must work out, from a user id alone, which shard holds that user's list, without asking anyone. When we add machines, as few lists as possible should move, because every moved list is copied over the network while the service runs. And every shard should hold about the same amount.

2 · Try the obvious thing: hash mod N

A hash function turns a user id into a large number that looks random: change the id a little and the number changes completely. The code below uses one called splitmix64. Mod-N sharding puts user k on shard "hash of k, modulo N". It needs no stored state and balances well: with 16 shards on the week's graph, the fullest holds 1.08 times the average.

The math, step by step: why mod N moves N/(N+1) of the keys

We want the share of keys whose shard changes when we go from N to N+1 shards.

Small numbers first. With N = 3, look at hash values 0 to 11, a block of 3 × 4 = 12 values. A key stays when "value mod 3" equals "value mod 4". That happens for 0, 1, 2 only: 3 of 12, a quarter. So three quarters move, which is N/(N+1) = 3/4.

In general. Take any block of N(N+1) consecutive hash values. Because N and N+1 share no common factor, the Chinese remainder theorem says each pair (a, b), with a = value mod N and b = value mod (N+1), appears exactly once in the block. A key stays exactly when a = b. The possible equal pairs are (0, 0), (1, 1), …, (N−1, N−1): N of them (b = N matches no a). So N of the N(N+1) values stay, a share of 1/(N+1), and N/(N+1) move. A 64-bit hash spans so many blocks that the partial last block does not matter.

Doubling. Going from N to 2N, "value mod 2N" equals "value mod N" exactly when value mod 2N is below N: half the time. So half the keys move.

What this shows. With mod N, nearly every key moves on every resize, because the shard of a key depends on N itself.

3 · Consistent hashing

The idea in plain words. Bend the range of hash values into a circle, the ring. Hash the servers onto the ring too. Each key walks clockwise from its own position and belongs to the first server it meets. Adding a server only takes over the stretch of ring just before it; every other key still meets the same server first.

Servers A, B, C at positions 10, 45, 75 (filled). Keys (squares) go clockwise to the next server: k1 (5) → A, k2 (20) → B, k3 (50) and k4 (60) → C, k5 (90) wraps to A. Add server D at 30 (hollow). Only the shaded arc (10, 30] changes owner: k2 moves from B to D. Nothing else moves.

One point per server balances badly, because the gaps between random points vary a lot. The fix is to give each server many points, its virtual nodes; a server's share is then the sum of many small gaps, which evens out. Looking up a key is a binary search in the sorted list of points.

consistent_hash.py · splitmix64, mod N, a ring with virtual nodes, rendezvous
import bisect

MASK = (1 << 64) - 1

def h64(x):
    """splitmix64: a fast, well-mixed 64-bit hash of a non-negative integer."""
    z = (x + 0x9E3779B97F4A7C15) & MASK
    z = ((z ^ (z >> 30)) * 0xBF58476D1CE4E5B9) & MASK
    z = ((z ^ (z >> 27)) * 0x94D049BB133111EB) & MASK
    return z ^ (z >> 31)

def mod_shard(key, n):
    return h64(key) % n                       # the shard of a key among n shards

class Ring:
    """Consistent hashing with v virtual nodes per server."""
    def __init__(self, servers, v=100, salt=0):
        self.v, self.salt = v, salt
        self.points = []                      # sorted list of (position, server)
        for s in servers:
            self.add(s)

    def _positions(self, s):
        # salt the server id: hashing raw (s, i) like a key would put key i exactly on a point
        base = h64(s ^ (self.salt << 32) ^ 0x632BE59BD9B4E019)
        return [h64((base + i) & MASK) for i in range(self.v)]

    def add(self, s):
        for p in self._positions(s):
            bisect.insort(self.points, (p, s))

    def remove(self, s):
        self.points = [(p, t) for p, t in self.points if t != s]

    def lookup(self, key):
        i = bisect.bisect_left(self.points, (h64(key), -1))
        return self.points[i % len(self.points)][1]   # first point clockwise; wrap at the end

def rendezvous(key, servers):
    """Highest-random-weight hashing: the server with the largest h(key, server) wins."""
    return max(servers, key=lambda s: h64(h64(key) ^ (s * 0xD6E8FEB86659FD93 & MASK)))

The math, step by step: only the new server gains keys, about K/(N+1) of them, and virtual nodes cut the spread to about 1/√V

Claim 1: every key that moves, moves to the new server. The old server points stay where they were. A key's owner is the first point clockwise from it. After the addition, that first point is either an old point, and then it is the same old point as before (no old point appeared in between), or it is one of the new server's points. So a key either keeps its owner or goes to the new server. Removing a server is the same argument in reverse: only its own keys move, each to the next point clockwise.

Claim 2: about K/(N+1) of K keys move. Treat the N+1 servers' points as independent random positions. Fix one key. It moves exactly when the first point clockwise from it belongs to the new server. All N+1 servers are placed by the same random rule, so each is equally likely to own that first point: the chance is 1/(N+1). Add this up over K keys (the expected count of a sum is the sum of the expected counts): K/(N+1) keys move on average. For 10,000 users and 17 servers, that is 588.

Why one point per server is uneven. Put M random points on a ring of length 1. A server's share is the gap before its point. That gap is longer than x exactly when the other M−1 points all miss the stretch of length x before it, which has probability \((1-x)^{M-1}\). Averaging over x:

\[ E[\text{gap}] = \int_0^1 (1-x)^{M-1}\,dx = \frac{1}{M}, \qquad E[\text{gap}^2] = \int_0^1 2x(1-x)^{M-1}\,dx = \frac{2}{M(M+1)} . \]

So the variance is \( \frac{2}{M(M+1)} - \frac{1}{M^2} = \frac{M-1}{M^2(M+1)} \) and the standard deviation divided by the mean is \(\sqrt{(M-1)/(M+1)}\), almost 1: the spread is as large as the share itself.

With V virtual nodes. Now there are M = NV points and a server's load L is the sum of its V gaps. The gaps always add to 1, so the variance of their total is 0. Writing that out, \(M\,\mathrm{Var} + M(M-1)\,\mathrm{Cov} = 0\), fixes the covariance between two gaps: \(\mathrm{Cov} = -\mathrm{Var}/(M-1)\). For one server's V gaps:

\[ \mathrm{Var}(L) = V\,\mathrm{Var} + V(V-1)\,\mathrm{Cov} = \frac{V(M-V)}{M^2(M+1)} = \frac{N-1}{N^2(NV+1)} . \]

Divide its square root by the mean load 1/N: \(\text{std}/\text{mean} = \sqrt{(N-1)/(NV+1)} \approx 1/\sqrt{V}\). With N = 16 and V = 100 that is \(\sqrt{15/1601} = 0.097\), the "predicted" column of the table.

What was shown. Adding a server moves only keys that go to it, about K/(N+1) on average, and V virtual nodes shrink the unevenness of shares by a factor of about √V.

4 · Rendezvous hashing

The idea. For each key, score every server with a hash of the pair (key, server) and pick the highest score. There is no ring and nothing to store except the list of servers. When a server joins, a key moves only if the new server's score is the new maximum, which happens for about 1/(N+1) of keys, and then it moves to the new server. Measured: adding a 17th server moved 0.0577 of users, and the fullest of 16 servers held 1.05 times the average.

When to use which. A rendezvous lookup computes one hash per server, so it is ideal for a few dozen servers or for choosing among replicas and caches, and easy to weight. The ring's binary search wins when there are thousands of servers.

5 · Scatter-gather: how many machines one request touches

The situation. Your request reads every friend's list, and those lists now live on different shards. One call per friend means one network round trip per friend.

The idea. Group your friends' ids by shard and send one call per shard, all at once (the scatter); then add up the answers (the gather). For example, friends 3, 8, 11, 14 and 21 on 4 shards (shard = id mod 4) fall on shards 3, 0, 3, 2, 1: four calls instead of five.

fanout.py · shards touched, batching, cross-shard edges
from collections import defaultdict

def shards_touched(adj, u, shard_of):
    """The distinct shards a two-hop request must read: one per shard holding a friend's list."""
    return {shard_of(f) for f in adj[u]}

def batch_by_shard(friends, shard_of):
    """Group the keys to read by shard: one RPC per shard instead of one per friend."""
    batches = defaultdict(list)
    for f in friends:
        batches[shard_of(f)].append(f)
    return batches

def expected_shards(d, s):
    """E[distinct shards] when d keys land uniformly on s shards."""
    return s * (1 - (1 - 1 / s) ** d)

def cross_shard_fraction(edges, part):
    return sum(part[u] != part[v] for u, v, *_ in edges) / len(edges)

The math, step by step: expected shards touched

We want the average number of distinct shards among d friends placed independently and uniformly on S shards.

One shard at a time. A given shard holds none of the d friends when each friend independently lands elsewhere, with probability \(1 - 1/S\) each: \((1-1/S)^d\) in all. So it is touched with probability \(1 - (1-1/S)^d\).

Add over shards. The expected number of touched shards is the sum of these probabilities over the S shards:

\[ E[\text{shards touched}] = S\Big(1 - \big(1 - \tfrac{1}{S}\big)^{d}\Big). \]

Plug in. d = 20, S = 16: \(16(1 - (15/16)^{20}) = 11.6\). d = 200, S = 1,000: \(1000(1 - 0.999^{200}) = 181.4\). When d is small compared with S, \((1-1/S)^d \approx 1 - d/S\) and the answer is close to d: one shard per friend. When d is much larger than S, it approaches S: every shard. The table's "predicted" column averages this formula over the real degrees, and it is lower than the value at the mean degree because the curve bends downward.

What was shown. Under hashing, a request touches about one shard per friend until the friend count approaches the number of shards.

6 · Hash or locality: placing friends together

A friendship crosses shards when the two friends live on different shards. Hashing places people independently, so a friendship crosses with probability 1 − 1/S: 93.8% with 16 shards, and measured 0.937. The alternative is locality: try to put friends on the same shard. A simple heuristic packs each user's main group onto a shard, then moves users towards the shard holding most of their friends while that shard has room.

7 · Caching the hot lists

The situation. Your request reads the list of each of your friends. So a person's list is read once for each of their friends: a list is read as often as its owner has friends. That is Day 2's friendship paradox, seen from the storage side. Popular people's lists are read most often, and they are also the longest.

The obvious cache is LRU (least recently used): keep the most recently read lists and throw out the one unused for longest. It needs a hash map from key to entry, for finding an entry at once, and a list in order of use, for moving an entry to the front and dropping the last one, also at once.

lru.py · LeetCode 146 with OrderedDict (a hash map plus a recency order)
from collections import OrderedDict

class LRUCache:
    """LeetCode 146. get/put in O(1): a hash map plus a recency order."""
    def __init__(self, capacity):
        self.cap = capacity
        self.d = OrderedDict()                 # least recent first

    def get(self, key):
        if key not in self.d:
            return -1
        self.d.move_to_end(key)                # now the most recent
        return self.d[key]

    def put(self, key, value):
        if key in self.d:
            self.d.move_to_end(key)
        self.d[key] = value
        if len(self.d) > self.cap:
            self.d.popitem(last=False)         # evict the least recent

It also protects a shard when a hot list falls out of the cache and a crowd of requests misses at the same moment.

In one line. A list is read as often as its owner has friends, so pin the hub lists in cache and coalesce concurrent reads of the same list.

    def __init__(self, capacity):

        x.prev.next, x.next.prev = x.next, x.prev

    def _push_front(self, x):
        x.prev, x.next = self.head, self.head.next
        self.head.next.prev = x
        self.head.next = x

    def get(self, key):
        x = self.map.get(key)
        if x is None:
            return -1
        self._unlink(x); self._push_front(x)
        return x.val

    def put(self, key, value):
        x = self.map.get(key)
        if x:
            x.val = value
            self._unlink(x); self._push_front(x)
            return
        if len(self.map) == self.cap:
            lru = self.tail.prev
            self._unlink(lru); del self.map[lru.key]
        x = Node(key, value)
        self.map[key] = x; self._push_front(x)

Why the map stores the node. Moving a key to the front needs its place in the list. Storing the node gives that place at once; storing only the value would force a search through the list.

System Design · fast at the tail, fresh, and consistent enough

1 · Fast: fan-out makes the slow machine everyone's problem

The situation. A request sends calls to many shards in parallel and must wait for all of them. Any single call is occasionally slow: a garbage-collection pause, a busy disk. Say each call is slow 1% of the time. How often is the request slow?

Try the obvious answer. "1%." That is right only for one call. A request that waits for all its calls is as slow as the slowest one.

The idea. The request is fast only if every call is fast. With 10 calls the chance that all ten are fast is 0.99 × 0.99 × … ten times, 0.904, so the request is slow 9.6% of the time. With 100 calls, all fast has probability 0.366, so 63% of requests are slow although each machine is fine 99% of the time. As a formula: with n calls each slow with probability p,

\[ P(\text{request slow}) = 1 - (1-p)^n . \]

def p_any_slow(p, n):
    """A request waits for n independent calls, each slow with probability p."""
    return 1 - (1 - p) ** n

def per_call_quantile(target, n):
    """How often each call must be fast so that all n are fast with probability `target`."""
    return target ** (1 / n)

def in_flight(qps, seconds):
    """Little's law: requests inside the system = arrival rate x time each one stays."""
    return qps * seconds

A request's p99 is set by its backends' p99.99 (Day 2 showed how to measure a p99 and its error bar).

What to do about it. The formula names the three levers.

  • Make n smaller. Batch by shard (above), cap hub lists (Day 2), sample friends (Day 3), or, best of all, precompute so the request reads one key (part 4).
  • Make p smaller with hedged requests. If a call has not answered by about its p95 time, send a copy to another replica and take whichever answers first. If the two are slow independently, a call is now slow with probability about p²: at 1% and 100 calls, the request is slow 1.0% of the time instead of 63.4%. In a simulation with an assumed read time (1 ms, or 50 ms with probability 1%), the share of slow requests fell from 16.8% to 0.21% (the simulation sends both copies at once, a simplification). The cost is the extra copies, roughly 5% more reads.
  • Stop waiting. Give the fan-out a deadline and rank with the lists that arrived. Mutual counts can be a little off; the eligibility check (part 6) cannot, so it is never skipped.

In one line. A request that waits for n calls is slow with probability 1 − (1 − p)ⁿ, so cut n, hedge to shrink p, or stop waiting; the slowest machine sets everyone's latency.

The math, step by step: 1 − (1 − p)ⁿ, a quick bound, and the per-call target

The formula. Assume each of the n calls is slow with probability p, independently of the others. "Request fast" means "call 1 fast and call 2 fast and … call n fast". For independent events the probability of all of them is the product: \((1-p)^n\). The request is slow otherwise: \(1 - (1-p)^n\). With p = 0.01 and n = 100: \(0.99^{100} = 0.366\), so 0.634.

A quick bound. The chance that at least one of several events happens is at most the sum of their chances (the union bound), so \(1 - (1-p)^n \le np\). For p = 0.005 and n = 10, 50, 100 the exact values are 4.9%, 22.2%, 39.4% against np = 5%, 25%, 50%: good while np is well below 1. A better approximation uses \(1-p \approx e^{-p}\), so \(1-(1-p)^n \approx 1 - e^{-np}\): once np reaches 1, most requests are slow.

The per-call target. We want \((1-p)^n \ge 0.99\). Take the n-th root of both sides: \(1-p \ge 0.99^{1/n}\). For n = 100 that is 0.9999: each call must be fast 99.99% of the time.

Hedging. A hedged call is slow only if both copies are slow: probability \(p \cdot p\) when they are independent. Put \(p^2 = 0.0001\) into the formula with n = 100: \(1 - 0.9999^{100} = 0.0100\).

What was shown. Waiting for all of n independent calls multiplies the chance of a slow request by roughly n while it is small, and drives it towards 1 once np nears 1.

2 · Hot keys

If every user makes one request, a person's list is read once per friend, and each read returns their whole list. So reads follow the degree, but bytes follow the degree squared. Measured: reads per list have median 15 and maximum 1,480; the top 1% of lists receive 11.1% of the reads but 69.1% of the bytes. The hottest list alone serves 1,480 × 1,480 × 8 bytes = 17.5 MB per round of requests, against 1.8 KB for a median list. A key that receives far more traffic than the rest is a hot key. Its shard saturates while the others idle, and adding shards does not help, because the key still lives on one shard. The fixes: copy hot lists to several shards and spread reads across the copies, cache them near the servers that compute candidates (the pinned cache above), or skip them (hub capping, Day 2). All three need the hot set, and the degree names it before any traffic arrives.

3 · Little's law: how many requests are in flight

The situation. To size thread pools, connection pools and memory, you need to know how many requests are inside the system at once.

The idea. In any stable system, the average number of items inside equals the rate at which they arrive times the average time each one stays: L = λW. A coffee shop where 2 customers arrive each minute and each stays 5 minutes, holds 10 customers on average. No assumption about how arrivals or service times vary is needed.

Use it. At the peak of 34,722 requests per second and an assumed 50 ms per request: 34,722 × 0.050 = 1,736 requests in flight. If each issues 200 friend-list reads in parallel, storage holds about 347,000 outstanding reads. If one server can hold 100 requests in flight, the fleet needs at least 18 servers before any headroom. And a slower tail raises W, which raises the concurrency the fleet must absorb.

Checked by measuring. A simulated single-server queue with random arrivals at rate 0.8 and random service at rate 1: measured arrival rate 0.8004, mean time inside 4.938, their product 3.952, and the time-average number inside, measured directly, 3.952.

In one line. In-flight requests = arrival rate × time in system; it turns a latency budget into a fleet size.

The math, step by step: why L = λW holds for any stable system

We compute one quantity, the total "customer-time" spent in the system, in two ways.

Small numbers first. Over 10 minutes, 20 customers arrive (λ = 2 per minute), and each stays 5 minutes (W = 5). Total customer-minutes: 20 × 5 = 100. Spread over 10 minutes, that is 10 customers inside on average: L = 10 = λW.

In general. Watch the system for a long time T. Let N(t) be the number of items inside at time t, and draw it as a curve.

  • Area by time. The area under the curve is \(\int_0^T N(t)\,dt\). By definition of the time-average L, this area is \(L \cdot T\).
  • Area by item. Each item raises the curve by 1 for exactly as long as it stays. So the area is also the sum of all stay times, \(\sum_i W_i\). About \(\lambda T\) items arrived, staying W on average, so the sum is \(\lambda T \cdot W\).

Set the two areas equal, \(L T = \lambda T W\), and divide by T: \(L = \lambda W\). Items still inside at the start or end of the window add an error that stays bounded while T grows, so it vanishes in the average.

What was shown. The law follows from counting the same area twice; it does not depend on how arrivals or service times are distributed, only on the system being stable.

4 · Fresh: precompute, or compute on request?

The situation. Computing two hops on request reads about 1,477 ids on average and 7,284 at the p99 on the week's graph, from about 15 of 64 shards. It is always fresh, but slow and fragile in the tail. The alternative: compute every user's candidates ahead of time, store them by user, and serve one key per request.

The idea: precompute as a self-join. Write the friendships as a table of pairs (x, v), both directions. Join the table with itself on the middle person v: every path x – v – y becomes one row (x, y). Count rows per pair and you have the mutual-friend count of every pair at once, the same count as Day 1, for everyone.

precompute.py · the batch two-hop self-join
def precompute_all(adj):
    """Batch two-hop: the self-join of the edge list with itself on the middle user."""
    m = defaultdict(Counter)
    for v in range(len(adj)):                  # v is the mutual friend
        for x in adj[v]:
            for y in adj[v]:
                if x != y:
                    m[x][y] += 1               # deg(v)·(deg(v)-1) rows for this v
    return m                                   # m[x][y] = |N(x) ∩ N(y)|, friends included

Use it on the past graph (the first 80,000 friendships): the join emits 9,519,454 rows, which group into 8,214,888 ordered pairs with at least one mutual friend; 8,091,284 of them are not yet friends, 809.1 candidates per user. The store keeps only each user's top few hundred for the ranker (Day 4), so the stored output is small even though the join is large. A distributed batch job splits the join by middle person, so each machine expands its own users.

5 · Incremental updates: when two people connect, whose suggestions change?

The situation. Rerunning a 9.5-million-row join after each new friendship is absurd. Which stored counts does one new friendship actually change?

Work it by hand. In the six-person example, Dev and Farid become friends. Before, Dev's only friend was Ben and Farid's only friend was Chloe. A count changes only where a new path through the new friendship appears:

new pathBen–Dev–FaridBen and Farid gain a mutual friend: Ben now sees Farid with 2 mutual friends (Chloe and Dev) instead of 1.
new pathChloe–Farid–DevChloe now sees Dev with 2 mutual friends instead of 1; Dev sees Chloe with 2.
unchangedYou EshaNo new path passes through them. Your list is still Esha (2), Dev (1), Farid (1).

So the people whose stored suggestions change are Dev and Farid themselves (they leave each other's lists and gain new counts) and their friends, Ben and Chloe. Nobody else. In general: when u and v connect, every friend of v gains a mutual friend with u, every friend of u gains one with v, and the people touched are u, v and their friends.

incremental.py · update mutual counts for one new friendship
def add_friendship(adj, m, u, v):
    """Update mutual counts m in place when u and v become friends. Returns the users touched."""
    for x in adj[u]:                           # new two-hop paths x - u - v
        m[x][v] += 1; m[v][x] += 1
    for y in adj[v]:                           # new two-hop paths u - v - y
        m[u][y] += 1; m[y][u] += 1
    adj[u].add(v); adj[v].add(u)
    return {u, v} | adj[u] | adj[v]

The math, step by step: exactly which counts one new friendship changes

We want every pair (x, y) whose mutual count changes when the friendship u–v is added.

Write the count as a sum over middle people. For each possible middle person w, the bracket \([w \in N(x)]\) is 1 if w is a friend of x and 0 otherwise. A mutual friend is a w with both brackets equal to 1:

\[ m(x,y) = \sum_{w} [\,w \in N(x)\,]\,[\,w \in N(y)\,] . \]

What the new friendship changes. Exactly two memberships: v joins \(N(u)\), and u joins \(N(v)\). A term of the sum can change only if one of its brackets is one of those two.

  • Bracket \([v \in N(x)]\) with x = u, w = v: the term becomes \([v \in N(y)]\), so \(m(u,y)\) rises by 1 for every friend y of v. These are the new paths u – v – y.
  • Symmetrically, \(m(v,x)\) rises by 1 for every friend x of u: the paths v – u – x.
  • The pair (u, v) itself would need v to be its own friend, which never happens, so \(m(u,v)\) does not change.

Count them. \(\deg(u) + \deg(v)\) pairs change by +1 each (degrees before the new friendship), stored in both directions. With Dev and Farid, 1 + 1 = 2 pairs: (Dev, Chloe) and (Farid, Ben).

The expected cost. A person at the end of a random new friendship is picked in proportion to their degree, so their expected degree is \(E[d^2]/E[d]\) (Day 2), not \(E[d]\). The expected update is therefore about \(2E[d^2]/E[d]\) counts.

What was shown. Only the rows of u, v and their friends change, by exactly \(\deg(u) + \deg(v)\) increments; every other stored suggestion stays exactly correct.

6 · Consistent enough: why the final check runs on every response

The situation. Updates travel through a queue to the shards that hold the touched rows, and the batch job rebuilds everything periodically. In between, a reader can see an old row. This is eventual consistency: if writes stop, every copy converges, but a read can return an old value.

How stale, measured. Take 2,000 users' top-10 lists at the end of the past graph and let the 20,000 future friendships happen without any update: 17.3% of those users now have at least one suggestion who is already their friend (2.0% of all suggestions). Blocks and privacy settings change the same way, and showing someone a person they blocked is a safety failure, not a ranking error.

The idea. Tolerate stale counts (a slightly wrong order) but never stale eligibility. The last step of every response re-checks the short list against the source of truth: the friend list, the block list in both directions, and privacy settings. It is ten or so lookups per request, cheap enough to run every time.

final_check.py · exact rules on every response, and a reason that reveals nothing hidden
def final_check(u, ranked, friends, blocked, opted_out, k=10):
    """Last step of every response: exact rules, read from the source of truth right now.
    friends[x] and blocked[x] are sets; opted_out holds users who asked never to be suggested."""
    out = []
    for v in ranked:
        if v == u or v in friends[u]:
            continue                           # never yourself, never a current friend
        if v in blocked[u] or u in blocked[v]:
            continue                           # blocked, in either direction
        if v in opted_out:
            continue                           # privacy: "do not suggest me"
        out.append(v)
        if len(out) == k:
            break
    return out

def shown_mutuals(u, v, friends, hides_list):
    """Mutual friends that may be NAMED in the reason ("Ben and Chloe are friends with Esha").
    Naming f reveals the friendship f-v, so skip f if f or v hides their friend list."""
    if v in hides_list:
        return []
    return sorted(f for f in friends[u] & friends[v] if f not in hides_list)

Use it on the six people. Your stored list is Esha, Dev, Farid. Farid blocks you: the check drops him, although the stored list still has him. Then you and Esha connect: the check drops her on your very next page load, before any update reaches the store. You never see a person you just befriended, which is the promise called read-your-writes.

In one line. Everything upstream may be stale or approximate; the final exact check on fresh data is what makes the rules hold on every response.

Unfriend. The same derivation with −1: \(m(u,y)\) falls for each friend y of v, and \(m(v,x)\) for each friend x of u; u and v become candidates of each other again. If only the top 10 is stored and one of them drops below the 11th, the new 10th was never stored, so the store must keep more than 10 (or the full counts) or recompute that user.

SQL. SELECT a.x, b.x AS y, COUNT(*) AS m FROM friends a JOIN friends b ON a.v = b.v AND a.x <> b.x GROUP BY a.x, b.x, then remove pairs that are already friends. It emits \(\sum_v d_v(d_v-1)\) rows before grouping.

Top 10 under increments. Counts only grow. A candidate outside the top 10 has count at most the 10th largest; if it was not incremented, its count is unchanged and the 10th did not fall, so it still cannot pass. After each increment, compare only the incremented candidate with the heap's smallest.

Shared slowness. \(0.005 + 0.995 \times (1 - 0.995^{100}) = 0.005 + 0.995 \times 0.3942 = 0.3973\). A hedge to another replica of the same slow tier does not remove the shared 0.5%.

Incremental only. Lost events and bugs accumulate silently and are never repaired. A periodic batch recomputes from the source of truth and resets the drift.

System Design · the product: rules people trust, goals traded off, the whole architecture

1 · The rules people must be able to trust

The situation. A ranking can be wrong on average and still be useful: a so-so suggestion costs a glance. Some mistakes are different. They are not "a bit less relevant"; they break the product or hurt someone. Those become rules that hold on every response, and the design checks them exactly, at the end, on fresh data (the final check above).

  • Never yourself. You are never in your own list.
  • Never a current friend. Suggesting someone you already know is a visible bug, and stale lists produce it (17.3% of users after one batch of new friendships).
  • Never a blocked person, in either direction. If you blocked Farid, or Farid blocked you, neither is ever suggested to the other. Blocking is often a safety tool; a single leak can do real harm.
  • Privacy. Respect the settings of the person being suggested, such as "do not suggest me". And the reason shown must not reveal what someone chose to hide: "Ben and Chloe are friends with Esha" reveals two friendships. If Chloe hides her friend list, the reason names only Ben (shown_mutuals above). The ranker may still use the full count; the display may not.

These rules are cheap to check and absolute, which is exactly why they sit in a small separate step instead of inside the model: the model can be retrained, approximated or replaced, and the rules still hold. Day 1 wrote them into the contract and its tests; here they hold at a billion users.

4 · Training–serving skew, and point-in-time features

The situation. The ranker's weights are valid only for features computed exactly as they were in training. Two things break that.

Try the obvious thing. To build a training row for a friendship formed last month, look up the pair's features in today's feature store. But today's mutual count already includes friendships formed after the one being predicted, some of them caused by it. That is the leak Day 4 measured with a random edge split, which inflated recall@10 from 0.0524 to 0.1421, 2.7 times, and here it is in production form.

The idea. Store every feature value with the time it became true, and build each training row from the values as of its label's time. That is LeetCode 981 again:

point_in_time.py · features as of the label's time, with the TimeMap from 981
store = TimeMap()                              # (key, value, time the value became true)
store.set("mutuals:You,Esha", 1, 100)          # Ben introduced them
store.set("mutuals:You,Esha", 2, 250)          # Chloe met Esha too
store.set("mutuals:You,Esha", 5, 900)          # three more, AFTER the label below

label_time = 300                               # You and Esha became friends at t = 300
store.get("mutuals:You,Esha", label_time)      # 2: what the model could have known then
store.get("mutuals:You,Esha", 1000)            # 5: "today's" value leaks the future

The second rule is one code path: the same function computes features for training and for serving, so a change cannot reach one and not the other. Computing a feature one way offline and another way online is training–serving skew; the model then sees inputs at serving time that it never saw in training, and its offline numbers no longer predict what users get.

In one line. Train on features as they were at the label's time, computed by the same code that serves them.

Solution

Removing boxes. No candidate generation: scoring a billion people per request. No ranker: hub-reached candidates crowd the list. No final check: a block or a new friendship leaks through a stale list. No graph store sharding or cache: the graph does not fit, and hub lists melt their shard. No impression log: the next model is trained only on what the old one chose to show.

Batch only. Lists are up to a day old: new friends stay suggested and new friends-of-friends do not appear until the next run. The final check still catches friends, blocks and privacy, so the product stays correct, only less fresh.

Online only. Reads per request: about 148,000 ids from about 181 shards, 41 GB/s at peak, and a tail set by the slowest shard.

ML · proving it helps: A/B tests

The situation

Offline, the learned ranker beats Adamic–Adar by 0.0080 recall@10 (95% interval 0.0052 to 0.0108, Day 4). Will people actually make more connections they value? Offline numbers come from a graph that grew without the new ranker. Only showing it to people answers the question.

Try the obvious thing

"Ship it, and compare this week with last week." Anything else that changed between the weeks, a holiday, a marketing push, an app release, is mixed into the difference, and nothing can separate it out.

The idea: randomize by user

Split users at random into control (old ranker) and treatment (new ranker). Because the split is random, the two groups are alike in everything except the ranker, on average, so a difference in outcome is caused by the ranker. Assign by a hash of the user id, so the same person always sees the same arm on every request and every device:

assign.py · sticky, independent assignment by hashing
def arm(user_id, experiment_id, treatment_share=0.5):
    """Same user and experiment -> same arm on every request; experiments are independent."""
    x = h64(h64(user_id) ^ h64(experiment_id + 0x5EED))
    return "treatment" if x < treatment_share * 2**64 else "control"

Decide before starting:

  • a primary metric per user, for example the share of users who accept at least one suggestion during the test;
  • guardrails that must not get worse: p95 latency of the request, block and report rates on suggested connections, requests left unanswered, notification opt-outs. A ranker that raises requests by pushing people towards strangers who then block them has failed.

How many users?

A small lift hides in noise unless the groups are large. The function below gives the users needed per arm to detect a relative lift with the usual settings (a 5% false-alarm rate and an 80% chance of catching a real effect):

sample_size.py · users per arm for a two-proportion test
def users_per_arm(p, lift, alpha=0.05, power=0.8):
    """Users per arm to detect p -> p*(1+lift) with a two-sided two-proportion z-test."""
    q = p * (1 + lift)
    z_a = NormalDist().inv_cdf(1 - alpha / 2)
    z_b = NormalDist().inv_cdf(power)
    pbar = (p + q) / 2
    n = (z_a * math.sqrt(2 * pbar * (1 - pbar)) + z_b * math.sqrt(p * (1 - p) + q * (1 - q))) ** 2
    return math.ceil(n / (q - p) ** 2)

The math, step by step: the users-per-arm formula

We want the number of users per arm, n, so that a real lift from p to q is detected most of the time.

The noise. In an arm of n users with true rate p, the observed share wobbles with standard deviation \(\sqrt{p(1-p)/n}\). The difference between two arms wobbles with standard deviation \(\sqrt{(p(1-p)+q(1-q))/n}\), adding the two variances.

The alarm threshold. If there is no effect, both arms have rate about \(\bar p = (p+q)/2\) and the difference has standard deviation \(\sqrt{2\bar p(1-\bar p)/n}\). We raise the alarm when the observed difference exceeds \(z_{1-\alpha/2}\) of these, where \(z_{0.975} = 1.96\) gives a 5% false-alarm rate.

Catching a real effect. If the true difference is \(q-p\), we want the observed difference above the threshold 80% of the time. That means the threshold must sit \(z_{0.8} = 0.84\) true standard deviations below \(q-p\):

\[ q - p = \frac{z_{1-\alpha/2}\sqrt{2\bar p(1-\bar p)} + z_{1-\beta}\sqrt{p(1-p)+q(1-q)}}{\sqrt n} . \]

Solve for n by squaring both sides and rearranging:

\[ n = \frac{\Big(z_{1-\alpha/2}\sqrt{2\bar p(1-\bar p)} + z_{1-\beta}\sqrt{p(1-p)+q(1-q)}\Big)^2}{(q-p)^2} . \]

Plug in. p = 0.10, a 2% relative lift, so q = 0.102 and \(\bar p = 0.101\): the numerator is \((1.96\sqrt{0.18160} + 0.84\sqrt{0.18160})^2 \approx 1.425\), the denominator \(0.002^2 = 4 \times 10^{-6}\), so n ≈ 356,000, the table's 356,335.

What was shown. The users needed grow like one over the square of the difference you want to detect.

Two ways the result can mislead

  • Novelty effects. New faces in the panel attract clicks at first simply because they are new, and the effect fades. Plot the treatment effect by day since each user's first exposure; if it shrinks, the early numbers overstate the long-run gain. Run until it flattens, or compare users who joined after the test began.
  • Interference. A friendship involves two people, who may be in different arms. If treatment users send more requests and control users accept them, the control arm's numbers rise too and the measured difference shrinks. Randomizing whole communities together (graph cluster randomization) reduces this, at the cost of fewer independent units and wider intervals.

In one line. Randomize by user with a sticky hash, fix one primary metric and the guardrails in advance, size the test from the lift you need, and watch for novelty and interference.

Problem variations
  • The primary metric is a mean (connections per user), not a proportion. What replaces p(1 − p)?
  • You test 20 metrics at a 5% level. How many "significant" results do you expect when nothing changed?

Solution

Means. Use the variance σ² of the per-user metric in each arm: \(n = (z_{1-\alpha/2} + z_{1-\beta})^2 \cdot 2\sigma^2/\delta^2\) for a difference δ in means. Heavy-tailed metrics such as connections per user (degrees, Day 2) have a large σ², so they are often capped or replaced by a proportion.

Twenty metrics. 20 × 0.05 = 1 false alarm expected. Fix one primary metric in advance, or lower the level for each (for example 0.05/20).

A/A. It checks assignment and the metric pipeline: about 5% of A/A tests should be "significant", the arms should match in size up to chance (a large imbalance means assignment or logging is broken), and the p-values of repeated A/A tests should be spread evenly between 0 and 1.

System Design · how to walk an interviewer through it

"Design People You May Know" is a classic interview problem, asked at companies such as Meta and LinkedIn. The design on these pages is hypothetical. The whole week fits into one answer if you take it in this order and say the numbers out loud.

  1. Restate and ask. Mutual friendship or follows? How many users, how many friends on average, how many requests per second, what latency, how fresh? Any signals beyond the graph (groups, city, contacts)? Write the answers down as labelled assumptions.
  2. State the rules that always hold. Never yourself, never a current friend, never a blocked person in either direction, respect privacy. Say they will be checked exactly at the end of every response.
  3. Give the simple baseline. Friends of friends ranked by mutual count, with why it works (most new friendships close a triangle) and its cost (the sum of your friends' friend counts).
  4. Estimate. 100 billion friendships, 1.6 TB, tens of thousands of requests per second, about 148,000 ids per request. Conclude: reading breaks first, not storage.
  5. Draw the funnel. Candidate generation → features → ranker → final check, with the graph store underneath and the impression log at the end.
  6. Go deep where the interviewer points. Storage: consistent hashing, hot lists, caching. Latency: fan-out and the tail, precompute versus online. Freshness: incremental updates and who they touch. Candidates: sampling, MinHash, random walks under a budget. Ranking: a time split, features, calibration.
  7. Say how you would know it works. Offline: recall@10 with error bars on a time split. Online: an A/B test by user, with one primary metric and guardrails on blocks and latency.
  8. Close with the risks. Feedback loops and exposure bias, hub write amplification, privacy of displayed reasons, and what you would build next.

In one line. Rules, baseline, estimate, funnel, depth on request, measurement, risks: in that order, every claim with a number.

What breaks next: the features themselves. Every feature this week was designed by hand: mutual friends weighted by 1/log of their degree, shared groups, degrees. Each captures one idea, and the gains came from adding the right idea. The next question is whether the ideas can be learned instead. In language, word2vec gives every word a vector, trained so that words appearing in similar contexts get similar vectors; nobody writes a feature for "is a city". The same trick applies to people: treat a random walk on the friendship graph as a sentence and each person as a word (DeepWalk, node2vec), and every user gets a vector whose closeness predicts who will connect, across groups and beyond two hops. Those user embeddings become both a candidate source (nearest neighbours in vector space) and features that replace much of the hand-made list, and the impression log becomes their training signal.
