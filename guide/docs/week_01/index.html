The problem, and the whole solution

R.1 · Foundations: what a model reads, and why we need a tokenizer

Before any algorithm, two questions: what does a language model actually take as input and produce as output, and why does that force us to build a tokenizer at all? This section answers both from the ground up and ends with the objective that R.2 writes down precisely.

1. What a language model reads and writes

The question. A model computes with numbers. Text is a string of characters. What exactly crosses the boundary between them?

The answer: integer ids. Fix a list of V pieces of text, called tokens, and number them 0 to V−1. That list is the vocabulary. A model never sees text. It sees a list of ids, and it produces, for the next position, one probability for each of the V ids.

A toy example. Take a vocabulary of V = 6 tokens:

id012345
tokenThe cat sat on the mat

The text The cat sat becomes the ids [0, 1, 2]. The model's job is to say which id comes next.

ids in: [0, 1, 2]"The", " cat", " sat"
↓ look up row 0, row 1, row 2 of the embedding table E (V × d)
three vectors of length dthe only thing the network ever sees
↓ the network mixes them into one vector h for the next position
scores z = h · Wᵀ, one per idW is the output table, also V × d
↓ softmax
V probabilities that sum to 1for example, " on" gets the highest
Both ends of the model are tables with one row per id. The middle never touches text.

The input end: the embedding table. The model owns a matrix E with V rows and d columns (d is the model width, for example 768). Row i is a learned vector for token i. "Embedding id 2" just means "read row 2". It is a table lookup, not a computation.

The output end: a softmax over V ids. The network turns its input into one vector h of length d. It scores every token by a dot product with that token's row of a second V × d table W: \(z_i = h \cdot W_i\). The softmax turns the V scores into probabilities:

\[ p(\text{next} = i) \;=\; \frac{e^{z_i}}{\sum_{j=0}^{V-1} e^{z_j}}, \qquad i = 0, \dots, V-1 \]

Worked by hand with V = 3 and scores z = (2, 1, 0): \(e^2 = 7.389\), \(e^1 = 2.718\), \(e^0 = 1\), sum 11.107, so the probabilities are 0.665, 0.245 and 0.090. Each is positive, and they add to 1 because every term is divided by the same sum.

Generating text is this step in a loop: pick an id from the probabilities, append it to the input, repeat. At the end, the ids are turned back into text. So the model needs two functions it cannot learn by itself: text → ids before it runs, and ids → text after. Those two functions are the tokenizer.

2. Why V must be fixed before training

The question. Why not let the vocabulary grow as new words show up?

Three reasons, each from the picture above.

  • (a) Each id owns learned parameters. Row i of E and row i of W are learned from the training examples in which token i appears. A token added after training has rows that no gradient ever touched: random numbers. The model has no idea what it means.
  • (b) The softmax needs a finite set to normalize over. The denominator sums over all V ids. An id outside 0..V−1 has no score, so its probability is 0 and the model can never produce it. Adding an id also changes the denominator, so every probability the model learned shifts.
  • (c) V sets the parameter count. The two tables each have one row per id, so their size in parameters is fixed by V:
\[ \underbrace{V \cdot d}_{\text{input table } E} \;+\; \underbrace{V \cdot d}_{\text{output table } W} \;=\; 2\,V d \]

With V = 50,000 and d = 768 that is 76.8 million, chosen once, before training. (Some models share one table for both ends, called weight tying, which halves this.) Doubling V doubles these tables, so V is a budget decision, not a detail.

The ids mean something only to the model that was trained with them. Row 1 was learned as " cat". Change the tokenizer so that id 1 means " dog", or so that " cat" is split into two ids, and the trained rows no longer match what they are fed. Changing the tokenizer means retraining the model.

3. Character, code point, grapheme, byte, subword

The question. If we must pick a fixed list of units, what units does text offer? "Character" sounds obvious, but it hides four different things. Definitions first:

  • Code point. Unicode gives every symbol a number, written U+ and hex: a is U+0061, न (Devanagari "na") is U+0928, 😀 is U+1F600. There are 1,114,112 possible code points, and about 150,000 are assigned. A Python str is a sequence of code points; len(s) counts them.
  • Mark. Some code points do not stand alone: they modify the code point before them. U+0301 adds an acute accent; U+093F is the Devanagari vowel sign "i". Unicode classes these as marks (categories Mn, Mc).
  • Grapheme (cluster). What a reader sees as one character: a base code point plus any marks or modifiers attached to it. Unicode defines the boundaries in UAX #29.
  • Byte. To store or send code points, they are written as bytes (numbers 0–255). UTF-8, the encoding used almost everywhere, writes each code point as 1 to 4 bytes.

The two é rows look identical on screen but are different code points and different bytes. A tokenizer that works on bytes sees two different strings. (Unicode normalization, NFC, converts the second into the first; whether to apply it is a design choice.)

UTF-8 in one paragraph. Code points below 128 (plain ASCII: English letters, digits, punctuation) take one byte, equal to the code point, so ASCII text is unchanged. Larger code points take 2, 3 or 4 bytes. The first byte's leading bits say how many bytes follow (110… two, 1110… three, 11110… four), and every following byte starts with 10. That is why Devanagari letters are 3 bytes and emoji 4, and why you can always find where a character starts. Day 1 builds and validates UTF-8 bit by bit.

Why tokenizers start from bytes. Bytes have two properties nothing else on the list has together:

  • Finite and small: exactly 256 symbols, fixed forever. New emoji, new scripts and new Unicode versions add code points, never bytes.
  • Total: every string, in every language, with any typo, has a UTF-8 byte sequence, and the bytes give the exact string back. A vocabulary that contains all 256 bytes can write anything.

What a subword token is. A byte-level tokenizer starts with the 256 single bytes as tokens and adds longer tokens: each new token is a byte string chosen by training because it is frequent, such as  the or ing. Nothing forces a token to stop at a character boundary. If e0 a4 is frequent in Hindi text, it can become a token, holding two of the three bytes of न:

e0 a4a8e0 a4 bf

A possible split of नि into three tokens. Red: tokens that hold part of a character. Neither is valid UTF-8 on its own; joined, the bytes are.

This is why decode must join bytes first and decode UTF-8 once at the end (R.6).

Now try each unit against R2 (total), R4 (short) and R5 (learnable).

Whole words. The first attempt: one token per word. Sequences are short. But the set of words has no end. Heaps' law says the number of distinct words in a text of n words grows like \(c\, n^{\beta}\) with β roughly 0.4–0.6: it keeps growing as you read more, without a ceiling (Day 1 measures it). Any fixed word list therefore misses words, and the classic fix is a special <UNK> ("unknown") id for every word not in the list, which breaks R1: the word is lost. On Alice, keeping every 10th document as held-out text, 4.8% of held-out words (135 of 2,810) never occur in the other 90% of the same book, for example birthday and anywhere. And 44% of the word types in the training part (1,071 of 2,435) occur exactly once, so their vectors would have one example each (fails R5).

Characters (code points). About 150,000 assigned code points, and the number grows with each Unicode version, so it is not fixed. Most are rare: a Chinese character seen twice gets a poor vector. Sequences are as long as the text has characters.

Bytes. 256 symbols, total, fixed. But sequences are long: one token per byte, so  the is 4 steps and नमस्ते is 18.

Subwords. Bytes plus a learned list of frequent byte strings. Frequent words get one token; rare words are spelled with smaller pieces, down to single bytes if needed. This keeps the totality of bytes and gets most of the shortness of words.

Why the details matter. "The children went to the market to buy fresh vegetables for dinner." is 13 tokens in English with GPT-2, GPT-4's cl100k_base and GPT-4o's o200k_base. Its Hindi translation is 90, 65 and 22 tokens: Hindi users paid up to 6.9× the price and got 6.9× less context, purely because of the tokenizer. 5. Why a bigger vocabulary gives shorter sequences

The question. We want short sequences (R4). How short can text get with V tokens, and why does a bigger V help?

The analogy: number bases. Write one million in different bases. Base 2 needs 20 digits (11110100001001000000). Base 10 needs 7 (1000000). Base 1000 needs 3, and you already use it: the commas in 1,000,000 mark base-1000 digits.

1000000

One million as three base-1000 digits. Each box is one "token" from an alphabet of 1,000 symbols (000 to 999).

A bigger alphabet means fewer symbols for the same value. How many fewer is a counting argument.

The bound, derived. With k digits in base b you can write \(b^k\) different values, no more: each position has b choices, and the choices multiply. To name any one of N values you need \(b^k \ge N\), so

\[ k \;\ge\; \log_b N \;=\; \frac{\log_2 N}{\log_2 b}. \]

\(\log_2 N\) is the number of bits needed to pick one value out of N, and \(\log_2 b\) is the number of bits one digit can carry. For one million, \(\log_2 10^6 = 19.93\): base 2 carries 1 bit per digit (20 digits), base 10 carries 3.32 (7 digits), base 1000 carries 9.97 (3 digits).

Tokens work the same way. A sequence of n tokens from a vocabulary of V can take at most \(V^n\) different values, so one token carries at most \(\log_2 V\) bits. Say a text carries H bits of information, meaning that even the best lossless code needs H bits to tell it apart from the alternatives (Day 3 defines this exactly as entropy). Because encode is lossless, its tokens must carry all H bits, so

\[ n \cdot \log_2 V \;\ge\; H \qquad\Longrightarrow\qquad n \;\ge\; \frac{H}{\log_2 V}. \]

Example: a passage carrying H = 2,000 bits needs at least 2,000 / 8 = 250 tokens with V = 256, and at least 2,000 / 16 = 125 with V = 65,536. The floor falls only like \(1 / \log_2 V\): squaring the vocabulary halves it.

Where the analogy stops. In a number base every digit string is used, and all digits are equally likely. Text is not like that, in two ways.

  • Tokens are not used equally. A token carries the full \(\log_2 V\) bits only if all V tokens are equally likely in every position. In real text  the is far more common than  quadrille, so each token carries less, and real sequences are longer than the floor.
  • Bytes are a wasteful starting point. A byte could carry 8 bits, but English uses a few dozen byte values, mostly in predictable orders, so each byte carries much less. A pure change of base from 256 to V = 3,208 symbols would shorten text by \(\log_2 3208 / 8 = 1.46\times\). Merging frequent byte strings removes the predictability as well, so the measured gain is much larger.

6. Why a bigger vocabulary can hurt: sharing vs identity

The question. If bigger V means shorter sequences, why not make every frequent word its own token?

Because of (a) in part 2: a token's vector is learned only from the examples that contain it. Compare two vocabularies for three related words:

Sharing (small V)
happy
unhappy
happiness

One vector for happ, trained by every occurrence of all three words. An unseen word like happily still reuses it.

Identity (large V)
happy
unhappy
happiness

Three independent vectors, each starting random and trained only by its own occurrences. Nothing tells the model they are related.

Shared pieces give generalization: many examples per vector, and new words built from known parts. Identity gives shorter sequences and a dedicated vector, but if the token is rare its vector stays close to its random start: the model ends up memorizing the few contexts it saw rather than learning what the token means. Day 2 derives how fast a vector's noise shrinks with its number of examples.

7. The design objective, derived

The question. What exactly should a tokenizer optimize?

The real goal. A tokenizer is good if the model trained with it is good. Measure the model in bits per byte: how many bits, on average, the model needs to predict each byte of held-out text (Day 3 explains why this is fair across tokenizers, whose tokens have different lengths). Compare tokenizers at a fixed compute budget C, since a shorter sequence also means less compute per byte. Then the goal is

\[ \begin{aligned} \min_{T}\quad & \mathrm{BPB}\bigl(\text{model trained with tokenizer } T \text{ under compute } C\bigr)\\ \text{s.t.}\quad & T \text{ is lossless (R1), total (R2) and deterministic (R3).} \end{aligned} \]

Why we cannot optimize it directly. Evaluating one candidate T means training a whole model. The search space of vocabularies is astronomically large. So we optimize a proxy that is cheap to compute from the training text alone and that tracks the parts of the real goal we understand:

  • Fewest tokens stands for compute and context: fewer tokens per byte means each unit of compute covers more text (part 5).
  • A budget K on new tokens stands for learnability and parameter cost: it caps the \(2Vd\) table size (part 2) and stops the vocabulary from filling with rare tokens (part 6).
  • Starting from the 256 bytes gives R1 and R2 for free (part 3).

R.2 states this proxy precisely: minimize the total number of tokens over the training corpus, with at most 256 + K tokens, each frequent enough to learn.

foundations.py · check the numbers in this section
import math

def softmax(z):
    m = max(z)                                   # subtract the max: same result, no overflow
    e = [math.exp(x - m) for x in z]
    s = sum(e)
    return [x / s for x in e]

def min_tokens(h_bits, V):
    return h_bits / math.log2(V)                 # n >= H / log2 V

def show(s):
    b = s.encode("utf-8")
    return f"{s!r}: {len(s)} code points, {len(b)} bytes: {b.hex(' ')}"

print([round(p, 3) for p in softmax([2, 1, 0])])   # [0.665, 0.245, 0.09]

Solution

Bytes. ñ is U+00F1, bytes c3 b1. 中 is U+4E2D, e4 b8 ad. 🇮🇳 is two code points, the regional indicators U+1F1EE and U+1F1F3, 8 bytes, one grapheme.

Parameters. \(2 \cdot (100{,}000 - 50{,}000) \cdot 4{,}096 = 409{,}600{,}000\): 409.6 million new parameters, all of which need training data.

Bound. \(2000 / \log_2 1024 = 2000/10 = 200\) tokens; \(2000 / 20 = 100\) tokens. A vocabulary 1,024 times larger only halves the floor.

Partial characters. e0 a4 (the first two bytes of न) is not valid UTF-8 alone. decode joins the bytes of all tokens first, so the full 3-byte sequence is back together before UTF-8 decoding.

R.2 · State it precisely

Name the objects, the objective and the constraints before any algorithm.

  • Base alphabet B: the 256 byte values. UTF-8 writes every string as bytes, so B alone already gives R1 and R2.
  • Corpus D: training text, cut into chunks (roughly words with their leading space), each chunk w occurring f(w) times. Merges never cross a chunk boundary.
  • Vocabulary V ⊇ B, and a segmentation sV(w) of each chunk into tokens.
\[ \begin{aligned} \min_{V}\quad & L(V) \;=\; \sum_{w \in D} f(w)\,\bigl|s_V(w)\bigr| && \text{total tokens}\\ \text{s.t.}\quad & |V| \le 256 + K && \text{budget: } K \text{ new tokens}\\ & c_t(D) \ge \tau \quad \forall\, t \in V && \text{every token learnable (R5)} \end{aligned} \]

Shorter is better (R4), but without the budget the answer is useless: every chunk becomes its own token. The two constraints are the trade-off: a bigger vocabulary shortens text but creates rare, poorly learned tokens. Day 2 measures this trade-off; Day 3 explains it with information theory.

BPE searches a restricted family: every new token is two existing tokens glued together, and segmenting a chunk means replaying the merges in order. Training then reduces to one question, asked K times: which pair do we merge next?

R.3 · What BPE does

Start with the 256 bytes as tokens. Count every adjacent pair of tokens in the training data. Merge the most frequent pair into a new token. Repeat until the vocabulary is full.
\[ L(\text{after merging } a\,b) \;=\; L(\text{before}) \;-\; r(a,b), \qquad r(a,b) = \text{non-overlapping occurrences, weighted by } f(w) \]

Why the most frequent pair? Merging a pair that occurs c times (without overlaps) shortens the corpus by exactly c tokens, so the most frequent pair is the best possible single step for the objective. That makes BPE a greedy algorithm. Day 2 shows it is not optimal over many steps, and why it is used anyway.

bytes 0–255→count adjacent pairs→merge the most frequent→new token 256, 257, …↺ repeat until V is full
Gain of one merge: if (a, b) occurs c times without overlap, the corpus gets exactly c tokens shorter.

R.4 · The algorithm

pseudocode
train(corpus, vocab_size):
    chunks ← split corpus with the pre-tokenization pattern; count each unique chunk
    write each chunk as a list of byte ids (0..255)
    merges ← []
    while 256 + len(merges) < vocab_size:
        count every adjacent pair in every chunk, weighted by the chunk's count
        (a, b) ← the most frequent pair (ties: the smaller pair)
        if its count < 2: stop                    # nothing worth merging
        new id ← 256 + len(merges); merges.append((a, b))
        in every chunk, replace each non-overlapping (a, b) with the new id, left to right
    return merges                                 # the ordered list IS the model

encode(text, merges):
    for each chunk: start from its bytes; repeatedly apply the EARLIEST-learned merge
    that occurs in it, until none does

decode(ids): join each token's bytes, then decode the bytes as UTF-8

Three things to notice. Overlaps: aaa has two aa pairs, but scanning left to right merges only the first. Ties are broken by the smaller pair, so the result is deterministic. Merges build on merges: aaab was never looked for; it appeared because aa and ab became tokens first.

Encoding uses the merge order, not frequencies: training applied merge 2 to text in which merges 0 and 1 had already happened, so encoding must too.

R.6 · The code

A complete, correct byte-level BPE tokenizer in about 50 lines. Day 4 makes training fast and Day 5 makes encoding fast; this version stays as the reference you test them against.

bpe.py · the complete simple tokenizer
from collections import Counter
import regex   # pip install regex: supports \p{L} (any letter) and \p{N} (any digit)

PATTERN = regex.compile(r"""'(?:[sdmt]|ll|ve|re)| ?\p{L}+| ?\p{N}+| ?[^\s\p{L}\p{N}]+|\s+(?!\S)|\s+""")

def unique_chunks(texts):
    counts = Counter()
    for text in texts:
        counts.update(c.encode("utf-8") for c in PATTERN.findall(text))
    return [list(c) for c in counts], list(counts.values())    # words, freqs

def merge(ids, pair, new_id):
    out, i = [], 0
    while i < len(ids):
        if i + 1 < len(ids) and ids[i] == pair[0] and ids[i + 1] == pair[1]:
            out.append(new_id); i += 2                          # consume both, emit one
        else:
            out.append(ids[i]); i += 1
    return out

def train(texts, vocab_size):
    words, freqs = unique_chunks(texts)
    merges = []
    while 256 + len(merges) < vocab_size:
        counts = Counter()
        for w, f in zip(words, freqs):
            for pair in zip(w, w[1:]):                          # every adjacent pair
                counts[pair] += f
        if not counts:
            break
        pair = min(counts, key=lambda p: (-counts[p], p))       # most frequent; ties → smaller pair
        if counts[pair] < 2:
            break
        new_id = 256 + len(merges)
        merges.append(pair)
        words = [merge(w, pair, new_id) for w in words]
    return merges

def encode(text, merges):
    ranks = {pair: 256 + i for i, pair in enumerate(merges)}    # id order = merge order
    out = []
    for chunk in PATTERN.findall(text):
        ids = list(chunk.encode("utf-8"))
        while len(ids) >= 2:
            pair = min(zip(ids, ids[1:]), key=lambda p: ranks.get(p, float("inf")))
            if pair not in ranks:
                break
            ids = merge(ids, pair, ranks[pair])
        out.extend(ids)
    return out

def decode(ids, merges):
    vocab = {i: bytes([i]) for i in range(256)}
    for i, (a, b) in enumerate(merges):
        vocab[256 + i] = vocab[a] + vocab[b]                    # each token's bytes
    return b"".join(vocab[i] for i in ids).decode("utf-8", errors="replace")

assert train(["aaabdaaabac"], 259) == [(97, 97), (97, 98), (256, 257)]
text = "The cat sat on the mat. मैं घर जा रहा हूँ 🙂"
assert decode(encode(text, train([text], 300)), train([text], 300)) == text

Two lines deserve a second look. zip(w, w[1:]) lines the list up against itself shifted by one, giving every adjacent pair. b"".join(...) joins bytes before decoding, because a token can hold part of a character: न is 3 bytes and can be split across two tokens.
