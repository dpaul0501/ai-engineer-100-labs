The problem, and the whole solution

R.1 · A model needs a fixed alphabet. Text doesn't have one.

A language model is a function from a sequence of ids to a probability for the next id. Both ends are fixed when the model is built: the input looks up one learned vector per id, and the output scores every id in a list of size V. Text is open-ended: any language, typos, emoji, code, names no one has seen. The tokenizer turns arbitrary text into ids from a fixed list and back. It is chosen once, before training, and every model trained with it is stuck with it.

the contract

train  : corpus, V → tokenizer     # learn the list of tokens from data

Why the details matter. "The children went to the market to buy fresh vegetables for dinner." is 13 tokens in English with GPT-2, GPT-4's cl100k_base and GPT-4o's o200k_base. Its Hindi translation is 90, 65 and 22 tokens: Hindi users paid up to 6.9× the price and got 6.9× less context, purely because of the tokenizer. By the end of the week you can explain each number.

R.2 · State it precisely

Name the objects, the objective and the constraints before any algorithm.

  • Base alphabet B: the 256 byte values. UTF-8 writes every string as bytes, so B alone already gives R1 and R2.
  • Corpus D: training text, cut into chunks (roughly words with their leading space), each chunk w occurring f(w) times. Merges never cross a chunk boundary.
  • Vocabulary V ⊇ B, and a segmentation sV(w) of each chunk into tokens.
\[ \begin{aligned} \min_{V}\quad & L(V) \;=\; \sum_{w \in D} f(w)\,\bigl|s_V(w)\bigr| && \text{total tokens}\\ \text{s.t.}\quad & |V| \le 256 + K && \text{budget: } K \text{ new tokens}\\ & c_t(D) \ge \tau \quad \forall\, t \in V && \text{every token learnable (R5)} \end{aligned} \]

Shorter is better (R4), but without the budget the answer is useless: every chunk becomes its own token. The two constraints are the trade-off: a bigger vocabulary shortens text but creates rare, poorly learned tokens. Day 2 measures this trade-off; Day 3 explains it with information theory.

BPE searches a restricted family: every new token is two existing tokens glued together, and segmenting a chunk means replaying the merges in order. Training then reduces to one question, asked K times: which pair do we merge next?

R.3 · What BPE does

Start with the 256 bytes as tokens. Count every adjacent pair of tokens in the training data. Merge the most frequent pair into a new token. Repeat until the vocabulary is full.
\[ L(\text{after merging } a\,b) \;=\; L(\text{before}) \;-\; r(a,b), \qquad r(a,b) = \text{non-overlapping occurrences, weighted by } f(w) \]

Why the most frequent pair? Merging a pair that occurs c times (without overlaps) shortens the corpus by exactly c tokens, so the most frequent pair is the best possible single step for the objective. That makes BPE a greedy algorithm. Day 2 shows it is not optimal over many steps, and why it is used anyway.

bytes 0–255→count adjacent pairs→merge the most frequent→new token 256, 257, …↺ repeat until V is full
Gain of one merge: if (a, b) occurs c times without overlap, the corpus gets exactly c tokens shorter.

R.4 · The algorithm

pseudocode
train(corpus, vocab_size):
    chunks ← split corpus with the pre-tokenization pattern; count each unique chunk
    write each chunk as a list of byte ids (0..255)
    merges ← []
    while 256 + len(merges) < vocab_size:
        count every adjacent pair in every chunk, weighted by the chunk's count
        (a, b) ← the most frequent pair (ties: the smaller pair)
        if its count < 2: stop                    # nothing worth merging
        new id ← 256 + len(merges); merges.append((a, b))
        in every chunk, replace each non-overlapping (a, b) with the new id, left to right
    return merges                                 # the ordered list IS the model

encode(text, merges):
    for each chunk: start from its bytes; repeatedly apply the EARLIEST-learned merge
    that occurs in it, until none does

decode(ids): join each token's bytes, then decode the bytes as UTF-8

R.5 · A worked example by hand

Train on the single chunk aaabdaaabac (11 bytes) with vocab size 259, so 3 merges. a = 97, b = 98.

step 1aaabdaaabac9 tokens. (aa, a) ×2 and (a, b) ×2 tie; (97, 98) is smaller → ab = 257
step 2aaabdaaabac7 tokens. (aa, ab) ×2 → aaab = 258
step 3aaabdaaabac5 tokens. Budget reached; every pair now occurs once

Filled = the pair about to merge; outlined = a token created by the previous merge.

Three things to notice. Overlaps: aaa has two aa pairs, but scanning left to right merges only the first. Ties are broken by the smaller pair, so the result is deterministic. Merges build on merges: aaab was never looked for; it appeared because aa and ab became tokens first.

Encoding new text with merges = [(97,97), (97,98), (256,257)]:

Encoding uses the merge order, not frequencies: training applied merge 2 to text in which merges 0 and 1 had already happened, so encoding must too.

R.6 · The code

A complete, correct byte-level BPE tokenizer in about 50 lines. Day 4 makes training fast and Day 5 makes encoding fast; this version stays as the reference you test them against.

bpe.py · the complete simple tokenizer
from collections import Counter
import regex   # pip install regex: supports \p{L} (any letter) and \p{N} (any digit)

PATTERN = regex.compile(r"""'(?:[sdmt]|ll|ve|re)| ?\p{L}+| ?\p{N}+| ?[^\s\p{L}\p{N}]+|\s+(?!\S)|\s+""")

def unique_chunks(texts):
    counts = Counter()
    for text in texts:
        counts.update(c.encode("utf-8") for c in PATTERN.findall(text))
    return [list(c) for c in counts], list(counts.values())    # words, freqs

def merge(ids, pair, new_id):
    out, i = [], 0
    while i < len(ids):
        if i + 1 < len(ids) and ids[i] == pair[0] and ids[i + 1] == pair[1]:
            out.append(new_id); i += 2                          # consume both, emit one
        else:
            out.append(ids[i]); i += 1
    return out

def train(texts, vocab_size):
    words, freqs = unique_chunks(texts)
    merges = []
    while 256 + len(merges) < vocab_size:
        counts = Counter()
        for w, f in zip(words, freqs):
            for pair in zip(w, w[1:]):                          # every adjacent pair
                counts[pair] += f
        if not counts:
            break
        pair = min(counts, key=lambda p: (-counts[p], p))       # most frequent; ties → smaller pair
        if counts[pair] < 2:
            break
        new_id = 256 + len(merges)
        merges.append(pair)
        words = [merge(w, pair, new_id) for w in words]
    return merges

def encode(text, merges):
    ranks = {pair: 256 + i for i, pair in enumerate(merges)}    # id order = merge order
    out = []
    for chunk in PATTERN.findall(text):
        ids = list(chunk.encode("utf-8"))
        while len(ids) >= 2:
            pair = min(zip(ids, ids[1:]), key=lambda p: ranks.get(p, float("inf")))
            if pair not in ranks:
                break
            ids = merge(ids, pair, ranks[pair])
        out.extend(ids)
    return out

def decode(ids, merges):
    vocab = {i: bytes([i]) for i in range(256)}
    for i, (a, b) in enumerate(merges):
        vocab[256 + i] = vocab[a] + vocab[b]                    # each token's bytes
    return b"".join(vocab[i] for i in ids).decode("utf-8", errors="replace")

assert train(["aaabdaaabac"], 259) == [(97, 97), (97, 98), (256, 257)]
text = "The cat sat on the mat. मैं घर जा रहा हूँ 🙂"
assert decode(encode(text, train([text], 300)), train([text], 300)) == text

Two lines deserve a second look. zip(w, w[1:]) lines the list up against itself shifted by one, giving every adjacent pair. b"".join(...) joins bytes before decoding, because a token can hold part of a character: न is 3 bytes and can be split across two tokens.
