What BPE optimizes, and how well

ML · length vs vocabulary vs learnability~1 h

The objective rewards a bigger vocabulary; learnability pulls the other way. A token's vector is learned from the places it appears, and like any average estimated from n samples, its noise shrinks only like 1/√n. A token seen 5 times has a vector that is mostly noise.

The first 744 new tokens buy 2.9× compression; the next 2,208 buy only 27% more, while most of them are rare and the train–test gap grows. On 130 KB of text the knee is near 1,000. On a corpus 10,000× larger the same curve bends much later, which is why production vocabularies are 50k–200k.

\[ \mathrm{SE}(\hat\mu) = \frac{\sigma}{\sqrt{n}} \quad\Rightarrow\quad \text{a token seen 100 times is } 10\times \text{ noisier than one seen 10{,}000 times} \]

The trade-off has a name: generalization (handle any input with pieces seen many times) versus identity (give each meaningful unit its own token). Too much identity gives rare, untrained tokens; too much generalization gives long sequences. The vocabulary size sets the dial; the training corpus decides whose words get identity.

Solution
sweep.py
from collections import Counter
docs = [d.strip() for d in open("data/alice.txt").read().split("<|endoftext|>") if d.strip()]
train_txt = "\n".join(d for i, d in enumerate(docs) if i % 10)
test_txt  = "\n".join(d for i, d in enumerate(docs) if i % 10 == 0)
for v in (256, 500, 1000, 2000, 4000):
    m = train([train_txt], v)
    used = Counter(encode(train_txt, m))
    rare = sum(1 for t in range(256, 256 + len(m)) if used[t] < 10)
    print(v, len(test_txt.encode()) / len(encode(test_txt, m)), rare / max(len(m), 1))

Splitting first matters because tokenizer training is a form of fitting: if held-out text is in the training set, its words get tokens and the held-out compression looks better than it will on new text. This is the same leakage rule as in any ML evaluation.

Algorithms · greedy, and when it fails~1 h

The gain identity. Replacing a non-overlapping a b with z turns two tokens into one and changes nothing else, so a merge with r replacements shortens the corpus by exactly r. Merging the most frequent pair is therefore the exact best single step. A greedy algorithm takes the best immediate step and never revisits it; it is optimal only when the problem has the greedy-choice property (some optimal solution starts with the greedy choice).

BPE doesn't have it. Corpus nan ×2, nab ×2, anan ×3 (24 characters), budget 2 merges. Counts: an 8, na 7, ab 2.

Greedy · 13 tokens
merge 1: a+n, gain 8 · merge 2: an+an, gain 3

Best plan · 12 tokens
merge 1: n+a, gain 7 · merge 2: na+n, gain 5
×2nan
×2nab
×3anan
Total gain: greedy 8 + 3 = 11; best 7 + 5 = 12. The bigger first step cut nan as n·an and destroyed the better second step.

Greedy's bigger first gain cut nan in the wrong place and left nothing good to merge next. Load the "greedy counterexample" preset in the simulator to watch it.

How bad can it get? Finding the best merge sequence is APX-complete (Kozma and Voderholzer, 2024): no polynomial algorithm gets arbitrarily close unless P = NP. The same paper proves greedy BPE always achieves between about 0.33 and 0.625 of the optimal compression gain in the worst case; Zouhar et al. (2023) found their bound to be about 0.37 in practice. On natural text, Zipf's shape means the big gains come first and later merges barely interact, so greedy does far better than its worst case.

def coinChange(coins, amount):                     # 322: dp[a] = fewest coins for a
    dp = [0] + [amount + 1] * amount
    for a in range(1, amount + 1):
        for c in coins:
            if c <= a:
                dp[a] = min(dp[a], dp[a - c] + 1)
    return dp[amount] if dp[amount] <= amount else -1
# coins [1, 3, 4], amount 6: greedy takes 4+1+1 (3 coins), optimal is 3+3 (2 coins)

def best_plan(words, k):                           # exhaustive search over k-merge plans
    best = None
    def rec(ws, plan):
        nonlocal best
        total = sum(len(w) * f for w, f in ws.items())
        pairs = {p for w in ws for p in zip(w, w[1:])}
        if len(plan) == k or not pairs:
            if best is None or total < best[0]: best = (total, plan)
            return
        for p in pairs:
            nxt = Counter()
            for w, f in ws.items():
                nxt[tuple(merge(list(w), p, f"<{len(plan)}>"))] += f
            rec(nxt, plan + [p])
    rec(Counter({tuple(w): f for w, f in words.items()}), [])
    return best
# best_plan({"nan": 2, "nab": 2, "anan": 3}, 2) → (12, [('n','a'), ('<0>','n')])

def min_tokens(s, vocab):                          # 139 variation: fewest tokens
    L, INF = max(map(len, vocab)), float("inf")
    dp, back = [0] + [INF] * len(s), [-1] * (len(s) + 1)
    for i in range(1, len(s) + 1):
        for j in range(max(0, i - L), i):
            if dp[j] + 1 < dp[i] and s[j:i] in vocab:
                dp[i], back[i] = dp[j] + 1, j
    out, i = [], len(s)
    while i:
        out.append(s[back[i]:i]); i = back[i]
    return out[::-1]

The brute force grows like (pairs)k, so it only works for tiny cases, which is the point: the problem is hard. And no, replay is not always shortest: with a 2,000-token vocabulary trained on Alice, 97 of 3,218 chunks have a shorter split. spoken encodes as sp|o|ken (3) though spoke|n (2) exists. Replay is still the right choice for a model: it is the split the model saw during training.

Design · choosing the vocabulary budget~1 h

The vocabulary size is paid for twice in the model: an input table of V × d parameters, and an output layer that scores all V tokens at every step (about 2Vd operations per token).

Share of parameters spent on the vocabulary
GPT-2 small · 50,257 × 768, tied31%
Llama 3 8B · 128,256 × 4,096, ×2 untied13%
38.6 M of 124 M parameters for GPT-2 small; 1.05 B of 8 B for Llama 3 8B. Small models pay most for a big vocabulary.

So the budget is a design decision with three inputs: how much text you have (how many tokens it can support at τ occurrences each), the model's size (what share of parameters you can spend), and the languages and domains you must serve.
