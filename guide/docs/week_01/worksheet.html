LEARNING CHECKS

Can you answer these without looking?

Answer each one aloud or on paper first, then open it. If an answer surprises you, go back to the day in brackets.

Learning checks
Answers
  1. The input layer has one learned vector per id and the output layer scores every id, so both are sized by V when the model is built. Changing the tokenizer changes what every id means: the model must be retrained.
  2. Minimize total tokens Σ f(w)·|sV(w)| (short, R4), subject to |V| ≤ 256 + K (a budget, without which every chunk becomes a token) and every token appearing at least τ times (learnable, R5). Keeping all 256 bytes gives lossless and total (R1, R2).
  3. Each non-overlapping replacement turns two tokens into one and changes nothing else, so the gain equals the number of replacements. In a run like aaaaa the count is 4 but only 2 replacements fit.
  4. An early merge changes which merges exist later: in nan ×2, nab ×2, anan ×3, greedy's first merge (gain 8) cuts nan badly and two merges give 13 tokens, while 7 then 5 gives 12. The optimum is APX-complete to find; greedy is within a constant factor, cheap, deterministic, and on Zipf-shaped text much better than its worst case.
  5. Tokenizing is lossless, so the text's information is fixed; bigger tokens carry more bits each. Bits per byte = bits per token × tokens per byte is comparable across tokenizers; per-token perplexity is not.
  6. Huffman has the greedy-choice property: some optimal tree has the two rarest symbols as deepest siblings (an exchange argument), and merging them leaves a smaller problem of the same kind. BPE's merges interact: one merge can destroy another's occurrences, so the exchange fails.
  7. Every live pair always has one heap entry whose count equals its true count. Then the first popped entry that matches counts is the true maximum; stale entries are skipped.
  8. Training applied each merge to text where all earlier merges had already happened; replaying the same order reproduces the splits the model was trained on. Frequencies belong to the training corpus, and longest match can give a different split.
  9. Hindi vowel signs are Unicode marks (\p{M}), not letters, so ?\p{L}+ stops at them and the marks become separate chunks that can never merge back. Including \p{M} in the word class (as o200k_base does) keeps words whole.
  10. Counting chunks parallelizes (map: count per shard; reduce: sum). The merge loop is sequential, since each merge depends on the previous counts; after deduplication it fits on one machine.
  11. Golden (tie-break and order), property round trip (per-token decoding, emoji, overlaps), differential fast vs simple (incremental bookkeeping), compatibility with tiktoken (pattern and rank order).
