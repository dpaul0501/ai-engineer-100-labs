Ship pymk on the week's graph

Everything from the week goes into one package: the lab's week_01/pymk/, its SPEC.md and its acceptance tests. The graph is the one every page measured: 10,000 users, 100,000 friendships, made by data/make_graph.py with seed 0. Work in the order spec → contract → test → code. Each work item says what to build, what "done" means, and gives hints.

Where we are in the design: this is the whole pipeline from the week reading, built small enough to run on a laptop and measured at every box.

spec + failing tests→exact baseline→workload→budgeted candidates→LSH source→ranker→serving: filter + cache→stretch: shards
Each box is one work item. The tests for each box are in tests/test_acceptance.py, one section per module.

Setup, from the lab folder: pip install -e ".[dev]", then pytest -q. Every test is red at the start. The first run writes data/edges.csv and data/users.csv. The numbers quoted under "done when" come from our own reference implementation on the same data and the same seeds, so a correct build should land close to them.

WI-1Spec and failing tests Delivery

Fill in every You write section of SPEC.md: the users and their failures, non-goals, your estimates (before any code), the decisions and the risks. Then write tests/test_mine.py, at least one test per module, each named after the bug it catches. (Day 1 design)

Done when a commit exists in which SPEC.md has an estimate in every row of section 6, and every test in test_mine.py and test_acceptance.py fails.

  • Start from the golden six-person graph of the week reading: YOU, friends B and C, candidates D, E, F, where E has two mutual friends. Write the expected output by hand before you read the acceptance test.
  • Good names say the bug: test_friend_never_suggested, test_tie_goes_to_smaller_id, test_block_applies_to_cached_ranking.
  • For a differential test, the slow and obviously right version is the matrix square: \((A^2)_{uv}\) counts the paths of length two from u to v.

WI-2The exact baseline and its properties DSA Delivery

Build graph.py (load, adjacency, temporal split, work) and exact.py (mutual_counts, top_k, suggest). Add Hypothesis properties to your own tests: symmetry \(m(u,v)=m(v,u)\); nothing ineligible is ever returned; counts equal \(A^2\) on random small graphs. (Reading R.3–R.4, Day 1)

Done when pytest -q -k "load or adjacency or split or work or golden or ties or never_self or mutual or top_k or suggest" is green and your three properties pass on at least 200 random graphs each.

  • Count with a dict while you walk the friends' lists. Do not build the set of candidates first and then intersect: that reads every list twice.
  • top_k with a size-k heap costs \(O(C\log k)\); sorting all C candidates costs \(O(C\log C)\). The ordering key is \((-m, v)\), which is also the tie-break rule.
  • temporal_split must sort by t. A test shuffles the edges first, so slicing by position fails it.

WI-3Workload report System Design ML

Measure W(u) for every user and plot its distribution in buckets. Time exact.suggest for every user and report p50, p95 and p99 with metrics.percentile. Find the slowest user and explain the time from the degrees of their friends. (Reading R.5, Day 2)

Done when your W numbers match the week's exactly (they are deterministic: mean 1,477, median 1,023, p99 7,284, max 51,806), your report plots time against W, and your SPEC row "p50/p95/p99 time" has a measured value next to your estimate with the difference explained.

  • Use time.perf_counter() around one call, run each user once to warm up first, and keep every sample; percentiles need the samples, not a running mean.
  • The test checks \(\sum_u W(u)=\sum_f \deg(f)^2\). Prove it before you run it: each f is counted once by each of its \(\deg(f)\) friends.

Reference implementation, 200 users. The median Jaccard similarity of N(u) and N(v) over exact top-10 pairs is 0.017 (mean 0.031): two or three mutual friends out of a union of dozens.

  • Hash all num_perm functions at once: an outer product of the coefficients and the items, then a minimum along one axis.
  • Test with scattered ids, not range(100): a linear hash on consecutive integers is far from a random permutation.
  • Read the table as a lesson, not a failure: LSH finds sets that are similar as wholes, and mutual-friend candidates are not. Think about where a Jaccard-based source would help (for example, users with no mutual friends yet).

WI-6The ranker, with error bars ML

Build rank.py: the eight features, build_dataset, the loss and its gradient, and LogisticRegression in plain NumPy. Train on features from the first 60% of friendships with labels from the next 20%; test on features from the first 80% with labels from the last 20%. Report AUC for each single feature and for the model, with bootstrap 95% intervals, and recall@10 of each user's future friends for common neighbours and for the model. (Day 5)

Done when the tests in the rank.py section pass and your table is close to ours, including the paired difference in recall@10 with its interval.

Why these AUCs are lower than Day 5's. Here each future friend is paired with one non-friend candidate of the same user, so the AUC asks "does the model rank this user's future friend above another of this user's candidates?". Day 5 pools every candidate pair across all users (AUC 0.620 for common neighbours, 0.805 for Adamic–Adar, 0.832 for logistic regression); pooling lets degree differences between users help, which a within-user comparison removes. Both are correct; report which one you computed.

WI-7Serving: the final filter and the cache System Design Delivery

Build serve.py: an LRUCache and PYMKService. The cache stores each user's ranking; the eligibility filter (self, friends, blocks in either direction, opt-outs) runs on every response. add_friendship invalidates exactly the users whose counts can change. Plug in your ranker with rank.make_scorer. Report p50 and p95 of recommend with a cold cache and with a warm one. (Days 3 and 5)

Done when the tests in the serve.py section pass, your own tests show that a block, an opt-out and a new friendship each take effect on the very next response, and your report gives cold and warm percentiles. On our machine the warm p95 was about 400 times lower than the cold one; the ratio, not the milliseconds, is what to compare.

  • Cache the ranking, never the filtered answer: a filtered answer goes stale the moment someone blocks or opts out.
  • The affected set of a new friendship u–v is \(\{u,v\}\cup N(u)\cup N(v)\). Prove it from \(m(w,x)=|N(w)\cap N(x)|\) before you code it (learning check 8).
  • Copy the graph in the constructor. A service that mutates its caller's adjacency lists breaks every measurement that follows.

WI-8Stretch: simulated sharding System Design DSA

Build shard.py: a consistent-hash ring with virtual nodes over a stable hash, and shards_touched. Measure the mean number of shards one request fans out to for 16, 64 and 256 shards, and the share of users that move when a 17th shard joins, against mod-N. Then turn the fan-out into a tail: with a 1% chance that any one RPC is slow, what share of requests waits on a slow one? (Days 2–3)

Done when PYMK_STRETCH=1 pytest -q -k stretch is green and your table is close to ours: 10.0, 15.5 and 18.2 shards per request for 16, 64 and 256 shards; adding a 17th shard moves 0.062 of users (1/17 = 0.059), where mod-N moves 0.941.

  • Python's hash() of a string changes between processes. Use hashlib.blake2b, or your ring changes every time you restart.
  • A request touches at most min(S, deg(u)) shards; with mean degree 20, more shards stop adding RPCs quickly.
Work items
LEARNING CHECKS

Can you answer these without looking?

Answer each one aloud or on paper first, then open the answers. If an answer surprises you, go back to the day in brackets.

Learning checks
Answers
  1. \(C(u)=N(N(u))\setminus N(u)\setminus\{u\}\): friends of friends who are not already friends and not u. \(m(u,v)=|N(u)\cap N(v)|\). With A the 0/1 adjacency matrix, \((A^2)_{uv}=\sum_w A_{uw}A_{wv}\); a term is 1 exactly when w is a friend of both, so the sum counts the common friends.
  2. The exact algorithm reads the friend list of each of your friends, so it touches \(W(u)=\sum_{f\in N(u)}\deg(f)\) entries; your own degree only sets how many lists. Friends are reached by following edges, and edges lead to high-degree people more often: the mean degree of a friend is 73.8 against a mean degree of 20 on the week's graph. If degrees of neighbours are uncorrelated, \(\mathbb{E}[W(u)]=d_u\,\mathbb{E}[d^2]/\mathbb{E}[d]\). Measured: mean W 1,477, p99 7,284, max 51,806. Adding the size-k heap, one request costs \(O(W(u)+|C(u)|\log k)\).
  3. Hash: put the larger list in a hash set and probe it with each element of the smaller one, \(O(\min(a,b))\) expected; best when the sets are already in memory as hash sets. Sorted merge: walk both sorted lists with two pointers, \(O(a+b)\); best when both are sorted and of similar size. Galloping: for each element of the smaller sorted list, search forward in the larger one by doubling and then binary search, \(O(a\log(b/a))\); best when \(a\ll b\), for example a user with 20 friends against a hub with 1,480.
  4. Triadic closure: two people with a common friend are more likely to become friends, so friendships close triangles. On the temporal split, 10,645 of the 20,000 future friendships (53.2%) have at least one mutual friend in the past graph. A candidate generator that only proposes friends of friends can therefore recall at most 53.2% of future friendships, however good its ranker. The rest need other sources: groups, similar friend sets, random walks.
  5. Pick an edge uniformly and then one of its two ends. A user v is picked with probability \(d_v/\sum_w d_w=d_v/(n\,\mathbb{E}[d])\). So \(\mathbb{E}[\text{deg of a random friend}]=\sum_v d_v\cdot d_v/(n\,\mathbb{E}[d])=\mathbb{E}[d^2]/\mathbb{E}[d]\). Then \(\mathbb{E}[d^2]/\mathbb{E}[d]-\mathbb{E}[d]=(\mathbb{E}[d^2]-\mathbb{E}[d]^2)/\mathbb{E}[d]=\operatorname{Var}(d)/\mathbb{E}[d]\ge 0\), with equality exactly when every degree is the same. Measured: 73.8 against 20.
  6. The request is fast only if all n RPCs are fast: \(0.99^n\). So the share that waits on a slow one is \(1-0.99^n\): 0.096 for n = 10, 0.165 for n = 18 (the mean fan-out at 256 shards), 0.634 for n = 100. The tail of one server becomes the median experience of a request with large fan-out.
  7. With mod-N, key k stays put only if \(k \bmod N = k \bmod (N+1)\). Over a full cycle of \(N(N+1)\) keys this holds for exactly the N keys with \(k \bmod N(N+1)\lt N\), a share of \(1/(N+1)\); so \(N/(N+1)\) of keys move (0.941 measured at N = 16). On a consistent-hash ring, a new node takes over only the arcs just before its own points; every other key keeps its owner. With enough virtual nodes the new node owns about \(1/(N+1)\) of the ring, so about \(K/(N+1)\) keys move, all of them to the new node (0.062 measured, against 0.059).
  8. Adding u–v changes exactly two sets: v joins N(u) and u joins N(v). Every other friend set is unchanged. Take a pair (w, x) with \(m(w,x)=|N(w)\cap N(x)|\). If neither w nor x is u or v, both sets are unchanged, so m(w, x) is unchanged. If w = u, the intersection \(N(u)\cap N(x)\) gains v exactly when \(v\in N(x)\), that is, \(x\in N(v)\). If w = v, it gains u exactly when \(x\in N(u)\). So the changed counts are m(u, x) for x in N(v) and m(v, x) for x in N(u), each up by one. The users whose candidate lists change are therefore u, v (their own counts, and they stop being candidates for each other), every friend of v (u gained a mutual friend with them) and every friend of u: \(\{u,v\}\cup N(u)\cup N(v)\), and nobody else.
  9. Let \(Z=N(u)\cap N(v)\), \(|Z|=m\), \(d=|N(u)\). Sampling s friends uniformly without replacement, each friend is in the sample with probability s/d. count = \(\sum_{f\in Z}\mathbf{1}[f\text{ sampled}]\), so \(\mathbb{E}[\text{count}]=m\,s/d\) by linearity, and \(\mathbb{E}[(d/s)\,\text{count}]=m\). The count is hypergeometric: \(\operatorname{Var}=s\,\tfrac{m}{d}\,(1-\tfrac{m}{d})\,\tfrac{d-s}{d-1}\), so \(\operatorname{Var}(\hat m)=(d/s)^2\) times that. For d = 10, s = 3, m = 4: 0.560 and 6.22, as the acceptance test checks. Note the factor \((d-s)/(d-1)\): sampling every friend gives zero variance.
  10. Under a random permutation of \(A\cup B\), the smallest element of the union is equally likely to be any of its \(|A\cup B|\) elements. Both minima agree exactly when that element is in \(A\cap B\): probability \(|A\cap B|/|A\cup B|=J\). Mutual-friend candidates have tiny J (median 0.017 over exact top-10 pairs: two or three mutual friends out of a union of dozens), so with r = 2 a band matches with probability about \(J^2\), and even 64 bands rarely fire. A Bloom filter stores bits, not elements: it answers "is x in the set?" with false positives and no false negatives, at rate \((1-e^{-kn/m})^k\). It cannot list the elements of a set, so it cannot intersect two of them; use it for "already friends", "already shown" or "blocked" checks.
  11. A mutual friend w with \(\deg(w)\) friends is a common friend of about \(\deg(w)^2/2\) pairs, so being one of them says little about any one pair. Adamic–Adar weights w by \(1/\log\deg(w)\); resource allocation by \(1/\deg(w)\). In this graph a triadic-closure step from u picks a friend f with probability \(1/d_u\) and then v with probability \(1/d_f\), so it lands on v with probability \(\sum_{f\in Z}1/(d_u d_f)\): resource allocation divided by \(d_u\), which is why it is the best single feature (AUC 0.726, against 0.590 for common neighbours). Logistic loss for one example: \(L=-[y\log\sigma(z)+(1-y)\log(1-\sigma(z))]\), \(z=w^\top x+b\). Since \(\sigma'(z)=\sigma(z)(1-\sigma(z))\), \(\partial L/\partial z=\sigma(z)-y\), so \(\nabla_w L=(\sigma(z)-y)\,x\). The Hessian \(X^\top S X/n\) with \(S=\operatorname{diag}(\sigma(1-\sigma))\) is positive semidefinite, so the loss is convex and gradient descent reaches the global minimum.
  12. The cache holds a ranking computed earlier. Since then someone may have blocked, opted out or become a friend. Those are hard constraints, so they are checked at read time, on every response, at a cost of \(O(k)\) plus the skipped entries. Approximate candidates may miss good people; the filter guarantees nothing ineligible is ever shown. A random split puts friendships from after the predicted one into the feature graph: they create the very mutual friends that "predict" it, so the offline AUC is too high. The product predicts the future from the past, so the test must do the same.
