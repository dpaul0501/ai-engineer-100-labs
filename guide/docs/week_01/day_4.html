DAY 4 · FAST TRAININGMLDSADelivery

Count once, then update only what each merge changes

The main-reading trainer recounts every pair after every merge: O(merges × corpus). Today you make it about 60× faster on Alice without changing a single output, and build the tests that prove it.

ML · counts are sufficient statistics

A sufficient statistic is a summary of the data that loses nothing the estimator needs. The mean and count are sufficient for fitting a Gaussian's mean; n-gram counts are sufficient for fitting an n-gram model (you will use this in the next chapter). For BPE training, the counter of unique chunks is sufficient: every step of the trainer reads only words and freqs, never the order of the text.

156,630 bytes of text37,404 chunks, in order
↓ count unique chunks (order discarded)
3,218 unique chunks × counts21,171 bytes: everything training needs
↓ train
the same merges
The 7.4× reduction is free: it loses nothing the trainer uses. On web-scale text the ratio is far larger.

Three consequences: deduplication is lossless for training; counting can be split across machines and summed (Day 5); and shuffling the corpus cannot change the tokenizer.

Problem variations
  • Remove pre-tokenization (merges may cross words). Is the chunk counter still sufficient? What is?
  • You train on a 10% sample. Which merges are most likely to change, and why?
Solution

unique_chunks is the only function that reads texts; everything after it reads words and freqs, and every count is a sum of f over chunks, which doesn't depend on order. Shuffling changes neither, so merges are identical (the dictionary's iteration order differs, but ties are broken by the pair, not by order). Without pre-tokenization each document is one long chunk; the counter of whole documents is still sufficient, but it is almost as large as the corpus, so the saving disappears. With a 10% sample, the late, low-count merges change first: their counts are small, so sampling noise (about √n) is large relative to the gaps between them.

Algorithms · heap, lazy deletion, inverted index

The key observation: a merge only changes its neighbours

xaby  →  xZy
removed:(x, a)(a, b)(b, y) added:(x, Z)(Z, y)
Every other pair in the chunk is untouched, and chunks without (a, b) are untouched entirely.

So instead of recounting, keep four structures and update them locally:

counts · hash mappair → total count. O(1) get and add
where · inverted indexpair → chunks containing it. Visit only those
heap · binary min-heap(−count, pair): the max in O(log H); ties pop the smaller pair
words · unique chunkseach a list of ids, with its frequency
loop pop heap → stale? skip → merge the chunks in where[pair] → for each: remove old pairs, rewrite, add new pairs → push changed counts

Lazy deletion. A heap can't find and update an entry without an O(n) scan, so when a count changes we push a new entry and leave the old one. On pop, compare with counts: if they differ, the entry is stale; drop it and pop again. It is correct because every live pair always has one entry with its exact count.

bpe.py · fast trainer
import heapq
from collections import Counter, defaultdict

def train(texts, vocab_size):
    words, freqs = unique_chunks(texts)
    counts, where = Counter(), defaultdict(set)
    for wi, w in enumerate(words):
        for pair in zip(w, w[1:]):
            counts[pair] += freqs[wi]
            where[pair].add(wi)
    heap = [(-c, p) for p, c in counts.items()]
    heapq.heapify(heap)                         # O(P), faster than P pushes

    merges = []
    while 256 + len(merges) < vocab_size and heap:
        neg, pair = heapq.heappop(heap)
        if counts.get(pair, 0) != -neg:
            continue                            # stale: the true count is already in the heap
        if -neg < 2:
            break
        new_id = 256 + len(merges)
        merges.append(pair)

        delta = Counter()
        for wi in list(where[pair]):            # copy: where[pair] shrinks inside the loop
            old, f = words[wi], freqs[wi]
            new = merge(old, pair, new_id)
            words[wi] = new
            for p in zip(old, old[1:]):         # 1. remove the old pairs
                delta[p] -= f
                where[p].discard(wi)
            for p in zip(new, new[1:]):         # 2. add the new pairs
                delta[p] += f
                where[p].add(wi)
        for p, d in delta.items():              # 3. apply net changes; push new counts
            if d:
                counts[p] += d
                if counts[p] > 0:
                    heapq.heappush(heap, (-counts[p], p))
        del counts[pair], where[pair]           # the merged pair can never occur again
    return merges

Problem variations
  • Linked-list trainer: store each chunk as a doubly linked list and index pair → positions, not chunks. Each merge then costs O(1) pointer edits per occurrence, and since every merge removes a node, total work is O(S log S). Implement it and keep the differential test green.
  • Bucket queue: replace the heap with count → set of pairs (the All O`one idea). When is it faster?
  • Indexed heap with decrease-key: no stale entries. Compare memory and time.
  • Prove the stale check never skips the true maximum.
Solutions

def topKFrequent(words, k):                      # 692: O(n log k)
    c = Counter(words)
    return [w for _, w in heapq.nsmallest(k, ((-n, w) for w, n in c.items()))]

class StockPrice:                                # 2034: lazy deletion, twice
    def __init__(self):
        self.price, self.latest, self.mx, self.mn = {}, 0, [], []
    def update(self, timestamp, price):
        self.price[timestamp] = price
        self.latest = max(self.latest, timestamp)
        heapq.heappush(self.mx, (-price, timestamp))
        heapq.heappush(self.mn, (price, timestamp))
    def current(self):
        return self.price[self.latest]
    def maximum(self):
        while -self.mx[0][0] != self.price[self.mx[0][1]]:   # stale: price was corrected
            heapq.heappop(self.mx)
        return -self.mx[0][0]
    def minimum(self):
        while self.mn[0][0] != self.price[self.mn[0][1]]:
            heapq.heappop(self.mn)
        return self.mn[0][0]

Stale check proof. Invariant: for every pair with count c > 0, the heap holds an entry (−c, pair). It holds after heapify, and every count change pushes the new value. A popped entry that matches counts has the smallest −count in the heap, and every live pair has an entry with its true count, so no live pair has a larger count. Ties go to the smaller pair because the tuples compare the pair next.

Design · contracts and tests

Write the invariants before the code; each becomes a test that exists, and fails, before the implementation.

contracts.py
class Tokenizer(Protocol):
    vocab_size: int
    def encode(self, text: str) -> list[int]: ...
    def decode(self, ids: Sequence[int]) -> str: ...

# I1  decode(encode(x)) == x                  for every str x
# I2  0 <= id < vocab_size                    for every id from encode
# I3  encode(x) is identical across runs and machines
# I4  train(D, V) is identical across runs    (fixed tie-break)
# I5  load(save(t)) encodes exactly like t

File format decisions: store merges in order (the vocabulary is derived from them), the pattern (same merges with another pattern give other tokens), a format_version (refuse unknown files instead of mis-encoding), and integers, not byte strings (they round-trip through JSON exactly). Mutation testing checks the tests: plant a bug and confirm some test fails.

Solution
tests/test_bpe.py
from hypothesis import given, settings, strategies as st

MERGES = train([open("data/alice.txt").read()], 500)

def test_golden():
    assert train(["aaabdaaabac"], 259) == [(97, 97), (97, 98), (256, 257)]

@given(st.text())
def test_round_trip_any_text(s):
    assert decode(encode(s, MERGES), MERGES) == s

@settings(max_examples=200)
@given(st.text(min_size=1), st.integers(257, 400))
def test_fast_trainer_matches_simple(s, v):
    assert train([s], v) == train_simple([s], v)

"Decode each token separately" is caught by the round trip as soon as Hypothesis generates a non-ASCII character split across tokens. "Overlapping merge" is caught by the golden test (aaa). The reversed tie-break is caught by the golden test at step 2. For the regex upgrade: a golden encoding test on a fixed multilingual string.
