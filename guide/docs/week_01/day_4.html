DAY 4 · FAST TRAININGMLDSADelivery

Count once, then update only what each merge changes

The main-reading trainer recounts every pair after every merge, so its cost is (number of merges) × (size of the corpus). Today you make it about 60× faster on Alice without changing a single output. Three ideas do it. The ML block shows that the trainer needs only the chunk counts, not the text. The Algorithms block teaches how to keep the maximum of a set whose values keep changing, and how to find the few chunks a merge touches. The Design block builds the tests that prove the fast trainer is the same trainer.

ML · sufficient statistics

The question

Alice is 156,630 bytes. Does the trainer need all of it, in order? Or is there a smaller summary from which it would produce exactly the same merges?

First attempt

Keep the text and rescan it. Every merge then reads all 37,404 chunks again, most of them duplicates: the chunk ␣the appears 1,477 times and is scanned 1,477 times per merge, always with the same result.

Definitions

A statistic is any function T(D) of the data D: its length, its mean, a table of counts. In statistics, T is sufficient for a parameter θ when, once you know T(D), the rest of D tells you nothing more about θ:

\[ P\big(D \mid T(D) = t;\ \theta\big)\ \text{does not depend on } \theta . \]

An equivalent test, the Fisher–Neyman factorization: T is sufficient exactly when the likelihood splits into a part that sees the data only through T and a part that does not see θ at all.

\[ p(D;\theta) = g\big(T(D),\,\theta\big)\; h(D). \]

Example. Flip a coin with heads-probability θ, n times, and get k heads. The likelihood of one particular sequence is \( \theta^{k}(1-\theta)^{n-k} \). It depends on the sequence only through k (and n), so take \( g = \theta^k(1-\theta)^{n-k} \) and \( h = 1 \). The order of the flips carries no information about θ, and the best estimate \( \hat\theta = k/n \) uses only the count. In the same way, the sum and the count are sufficient for the mean of a Gaussian with known variance.

BPE training has no θ: it is a deterministic procedure A. The same idea applies in a simpler form. Call T sufficient for A when \( A(D) = F(T(D)) \) for some function F: any two corpora with the same T produce the same output.

The claim and its proof

Claim. Let T(D) be the counter of chunks: each distinct chunk produced by the split pattern, with the number of times it occurs. Then T is sufficient for BPE training.

Proof, by induction on the number of merges. Write the trainer's state after t merges as \( S_t \): the list of unique chunks, each rewritten by the merges so far, with its frequency.

  • Base. \( S_0 \) is the chunk counter itself, so it is a function of T.
  • Step. Suppose \( S_t \) is a function of T. The count of a pair p is \( \sum_w f_w \cdot \mathrm{occ}_p(w) \), a sum over unique chunks w of frequency × occurrences. Addition does not care about order, so the counts are a function of \( S_t \). The chosen pair is the largest count, ties broken by the smaller pair: a function of the counts, not of the order in which a dictionary lists them. Each chunk is then rewritten on its own by merge. So the next merge and \( S_{t+1} \) are functions of \( S_t \), hence of T.

The proof needs one fact from the split: merges never cross chunk boundaries, so what sits between chunks, and in what order, never enters a count. ∎

Cost

Building the counter is one pass over the text: O(N) time for N bytes, O(S) space for S bytes of unique chunks. From then on every pass costs O(S) instead of O(N).

The 7.4× reduction is free: by the proof it loses nothing the trainer uses. On web-scale text the ratio is far larger, because common chunks repeat millions of times.

The shuffle test agrees: split Alice into its 723 documents, shuffle them, and train to vocabulary 2,000. The merges are identical to the unshuffled run.

Where BPE uses it

unique_chunks is the first line of every trainer on this page, and every structure in the Algorithms block indexes unique chunks, not positions in the text. Three consequences follow from the proof. Replacing the text by its chunk counter loses nothing. Counting can be split across machines and the counters summed (Day 5). Shuffling the corpus cannot change the tokenizer. Note what the proof does not say: removing duplicate documents changes the counts, so it can change the merges.

Practice
  • Write the induction above for your own trainer, line by line: which variable holds \( S_t \), and which line uses anything else?
  • Test it: shuffle alice.txt's documents, retrain, and compare merges.
  • Use the factorization to show that the count table of all (previous token, next token) pairs is sufficient for a bigram model's probabilities.
Problem variations
  • Remove pre-tokenization (merges may cross words). Is the chunk counter still sufficient? What is?
  • You train on a 10% sample. Which merges are most likely to change, and why?
  • Is the set of unique chunks, without counts, sufficient? Give a counterexample with two distinct chunks.
Solution

unique_chunks is the only function that reads texts; everything after it reads words and freqs, and every count is a sum of f over chunks, which does not depend on order. Shuffling changes neither, so the merges are identical (the dictionary's iteration order differs, but ties are broken by the pair, not by order).

Without pre-tokenization each document is one long chunk. The counter of whole documents is still sufficient, but it is almost as large as the corpus, so the saving disappears.

With a 10% sample, the late, low-count merges change first: their counts are small, so sampling noise (about \( \sqrt{n} \) for a count n) is large relative to the gaps between them.

The set without counts is not sufficient: the corpora ␣ab␣ab␣ab␣cd and ␣ab␣cd␣cd␣cd have the same set of chunks, {␣ab, ␣cd}, but the first merge is (␣, a) in one and (␣, c) in the other. For the bigram model: the likelihood is \( \prod_{a,b} P(b\mid a)^{n_{ab}} \), which depends on the text only through the counts \( n_{ab} \), so take h = 1.

Algorithms · the maximum of a changing set

The fast trainer rests on one subproblem that appears all over computer science: keep the maximum of a set whose values keep changing. This block teaches it as a subject in its own right (the binary heap, four ways to change priorities, related problems), then adds the inverted index and puts the trainer together.

1 · The question

Keep a set of keys, each with a value. Support two operations, many times each, in any order:

  • update(key, v): set the key's value (value 0 removes it);
  • max(): return the key with the largest value; on a tie, the smallest key.

In BPE the keys are pairs and the values are their counts. After merging aa in aaabdaaabac, the pair (a, a) drops from 4 to 0, (aa, a) appears with count 2, (d, a) drops to 0, and so on. Then we ask for the maximum again. On Alice, training to vocabulary 2,000 asks for the maximum 1,744 times and, after the initial 665 inserts, makes 15,419 updates, about 9 per merge.

The two simple structures sit at opposite ends: no order (cheap updates, slow max) and full order (fast max, slow updates). A heap keeps a partial order, which is enough to know the max and cheap to repair.

2 · The binary heap, from first principles

Shape. A complete binary tree has every level full except possibly the last, and the last level is filled from the left. Number its nodes level by level, left to right, starting at 0, and store node i at a[i]. No pointers are needed:

\[ \text{children of } i:\ 2i+1,\ 2i+2 \qquad\qquad \text{parent of } i:\ \lfloor (i-1)/2 \rfloor . \]

Why these formulas hold. Level d holds \( 2^d \) nodes, at indices \( 2^d-1 \) to \( 2^{d+1}-2 \). If node i is the j-th node on level d, so \( i = 2^d - 1 + j \), its children are the (2j)-th and (2j+1)-th nodes on level d+1, at index \( 2^{d+1} - 1 + 2j = 2i+1 \) and the one after it. The parent formula inverts this.

index:   0  1  2  3  4  5
a:     [ 2, 5, 3, 9, 6, 8 ]

              2 (0)
            /       \
         5 (1)       3 (2)
        /    \       /
     9 (3)  6 (4)  8 (5)
A min-heap of six values. Each parent is ≤ its children. Siblings are not ordered: 5 is above 3's subtree but larger than 3.

The heap invariant (for a min-heap): every node is at most each of its children, \( a[\lfloor (i-1)/2 \rfloor] \le a[i] \) for all i ≥ 1. Along any path from the root downwards the values never decrease, so the root is the minimum.

Height. Levels 0 to d−1 hold \( 2^d - 1 \) nodes, so if level d is used then \( n \ge 2^d \). The height of a complete tree with n nodes is therefore \( \lfloor \log_2 n \rfloor \). Every operation below walks one path, so this bounds its cost.

Push: sift up. Append the new value as the next leaf (the tree stays complete). It may be smaller than its parent. While it is, swap it with the parent.

push 12539681Append at index 6. Parent (6−1)//2 = 2 holds 3 > 1 → swap.
step 12519683Now at index 2. Parent 0 holds 2 > 1 → swap.
step 21529683At the root: stop. 2 swaps = the height of a 7-node tree.
Filled = the value being moved. The array is the tree, read level by level.

Why sift-up is correct. Invariant during the loop: every parent–child edge is in order except possibly the edge between the moving value x and its parent. It holds at the start, since only the new leaf's edge is new. Now let x < its parent p, and swap them. p moves down into x's old slot. Before the swap, p was ≤ everything in its subtree, which includes the children of that slot and x's sibling. So p is in order with its new children, and x < p ≤ sibling, so x is in order with its new children. The only edge that can still fail is x with its new parent: the invariant holds one level up. The loop stops at the root or when that edge is in order, and then every edge is in order.

Pop: sift down. The minimum is a[0]. Swap it with the last leaf, remove it from the end (the tree stays complete), and repair the root: while the moving value is larger than its smaller child, swap it with that child.

pop352968Return 1; the last leaf 3 moves to the root. Children 5 and 2; the smaller is 2 < 3 → swap.
step 1253968At index 2. Only child is index 5, holding 8 ≥ 3 → stop.

Why sift-down is correct. Invariant: every edge is in order except possibly the edges from the moving value x down to its children. Let c be the smaller child and x > c; swap them. Now c is the parent of x and of the other child s: c < x, and c ≤ s because we picked the smaller child. c's new parent is the value that sat in x's slot before x arrived there; that value was c's parent, so it is ≤ c. Only x's edges to its new children can fail. Choosing the smaller child is what makes this work: swapping with the larger one would put it above a smaller sibling.

Cost. Each swap moves one level, so sift-up makes at most \( \lfloor\log_2 n\rfloor \) swaps (one comparison each) and sift-down at most \( \lfloor\log_2 n\rfloor \) swaps (two comparisons each). Push and pop are O(log n) time and O(1) extra space. Peeking at the minimum is O(1).

Heapify: build a heap from n values in O(n). Pushing n values one at a time costs up to \( \sum_{i\le n} \lfloor\log_2 i\rfloor = \Theta(n\log n) \) swaps in the worst case. Bottom-up is faster. Every leaf is already a one-node heap, and the leaves are the indices from \( \lfloor n/2 \rfloor \) on. Sift down each internal node, from index \( \lfloor n/2\rfloor - 1 \) back to 0. When node i is processed, both of its subtrees are already heaps (their roots have larger indices), which is exactly the situation sift-down repairs. Example, [9, 6, 8, 2, 5, 3]: index 2 swaps 8 with 3; index 1 swaps 6 with 2; index 0 swaps 9 with 2 and then with 5, giving [2, 5, 3, 6, 9, 8].

Why heapify is O(n). Sift-down from a node of height h (distance to the deepest leaf below it) makes at most h swaps. A complete tree has at most \( \lceil n/2^{h+1} \rceil \) nodes of height h: half the nodes are leaves, a quarter sit just above them, and so on. So the total number of swaps is

\[ \sum_{h=0}^{\lfloor \log_2 n\rfloor} \Big\lceil \frac{n}{2^{h+1}} \Big\rceil\, h \;\le\; \frac{n}{2}\sum_{h\ge 0}\frac{h}{2^{h}} \;+\; \sum_{h=0}^{\lfloor\log_2 n\rfloor} h \;=\; \frac{n}{2}\cdot 2 + O(\log^2 n) \;=\; n + O(\log^2 n). \]

The series comes from the geometric series: differentiate \( \sum_{h\ge0} x^h = \frac{1}{1-x} \) to get \( \sum h x^{h-1} = \frac{1}{(1-x)^2} \), multiply by x: \( \sum h x^h = \frac{x}{(1-x)^2} \), which is 2 at \( x = \tfrac12 \). The intuition: most nodes are near the bottom. Heapify gives those many nodes short walks (down to a nearby leaf); repeated pushing gives them the long walks (up to the root).

Confirm by measuring. On 100,000 values, heapify makes 1.88 comparisons per value on random input and 2.00 on descending input. Repeated pushing makes 2.28 per value on random input (a random new value rarely climbs far) but 14.69 on descending input, where every new value climbs to the root.

heap.py · a binary min-heap from scratch
def sift_up(a, i):
    while i > 0:
        parent = (i - 1) // 2
        if not a[i] < a[parent]:
            return                                  # invariant restored
        a[i], a[parent] = a[parent], a[i]
        i = parent

def sift_down(a, i):
    n = len(a)
    while True:
        left, right, small = 2 * i + 1, 2 * i + 2, i
        if left < n and a[left] < a[small]:
            small = left
        if right < n and a[right] < a[small]:
            small = right
        if small == i:
            return                                  # both children are >= a[i]
        a[i], a[small] = a[small], a[i]
        i = small

def push(a, x):
    a.append(x)                                     # new last leaf keeps the tree complete
    sift_up(a, len(a) - 1)

def pop(a):
    a[0], a[-1] = a[-1], a[0]                       # move the minimum to the end
    smallest = a.pop()
    if a:
        sift_down(a, 0)
    return smallest

def heapify(a):
    for i in range(len(a) // 2 - 1, -1, -1):        # last internal node down to the root
        sift_down(a, i)

Python's heapq provides these functions (heappush, heappop, heapify) on a plain list, in C. It is a min-heap only. For a max-heap, store the negated priority. Entries can be tuples, which Python compares element by element: (-count, pair) puts the largest count first, and among equal counts the smaller pair, because the second element decides. That is exactly BPE's tie-break, and it holds no matter in which order the entries were pushed, so training is deterministic. For example, (-2, (97, 98)) pops before (-2, (98, 99)). Two cautions: every element of the tuple must be comparable (a dict as the last element raises on a tie), and if you want ties broken by insertion order instead, put a running counter second: (priority, seq, item).

3 · Changing priorities: four designs

The question. A heap can change only the root or a new leaf. To change the count of some pair in the middle of the array, you first need to know where it is, and a plain heap does not know: finding it is an O(n) scan. There are four standard ways out. To compare them fairly, each is written below against the same interface, update(key, v) and peek(), which returns (key, value) of the maximum.

(a) Lazy deletion. Do not find the old entry; push a new one with the new value, and leave the old one where it is. When you read the top, compare it with the current value: if they differ, the entry is stale; pop it and look again.

Invariant. For every live key k with current value v(k) > 0, the heap holds at least one entry \( (-v(k), k) \) with exactly that value. It holds after the initial build, and every update pushes the new value.

Why the first matching entry is the true maximum. Let the top entry be \( (-v, k) \) with \( v = v(k) \), so it is not stale. Take any live key j. By the invariant the heap holds \( (-v(j), j) \), and the top is the smallest tuple in the heap, so \( (-v, k) \le (-v(j), j) \). That means \( v \ge v(j) \), and if \( v = v(j) \) then \( k \le j \). So k is the maximum, with the right tie-break. Discarding a stale entry is safe: its key either is dead or, by the invariant, has another entry with its current value. That same argument shows a common extra step is unnecessary: some implementations push the current value again when they discard a stale entry. The invariant says that entry already exists, so the re-push only adds a duplicate. On Alice it raises the total pushes from 11,198 to 16,128.

Cost. Let U be the number of updates and H the heap's size. Each update is one push, O(log H). Each entry is popped at most once, so the stale pops, summed over the whole run, are at most the number of pushes: they add O(log H) per update, amortized. The price is memory: H grows to the initial size plus U, not to the number of live keys. If that matters, rebuild with heapify on the live entries whenever H exceeds twice the live count. The rebuild costs O(live), and at least that many pushes happened since the last one, so it adds O(1) per update.

Measured on Alice (vocabulary 2,000): 6,276 pops, of which 4,532 (72%) were stale. The heap grows from 665 entries to a peak of 6,338, while the number of live pairs at the start of a merge never exceeds 3,739.

queues.py · (a) lazy deletion
class LazyHeap:
    """(a) Lazy deletion: push on every change, skip stale entries when reading."""
    def __init__(self):
        self.value, self.heap = {}, []
    def update(self, key, v):
        self.value[key] = v
        if v > 0:
            heapq.heappush(self.heap, (-v, key))
    def peek(self):
        while self.heap:
            neg, key = self.heap[0]
            if self.value.get(key, 0) == -neg:
                return key, -neg
            heapq.heappop(self.heap)                # stale: drop it, never re-push
        return None

(b) Indexed heap. Keep the heap of keys and also a position map pos[key] = the key's index in the array. Now update can go straight to the key, change its value, and sift it up (if it became better) or down (if it became worse). Invariant: pos[keys[i]] == i for every i, plus the heap order. Every swap must update pos for both keys, or the map goes out of date. Removing a key: swap it with the last leaf, drop it, and sift the moved key in whichever direction it needs.

Cost. O(log n) per update and removal, where n is the number of live keys; O(1) peek; O(n) memory, and no stale entries ever. The price is more code and more work per swap (two dictionary writes). This is the "decrease-key" heap that textbook Dijkstra and Prim use. On Alice it holds at most 3,739 entries, against 6,338 for the lazy heap, and gives the same 1,744 merges.

queues.py · (b) indexed max-heap
class IndexedMaxHeap:
    """(b) A heap of keys plus pos[key] = index, so any key can be found and moved."""
    def __init__(self):
        self.keys, self.pos, self.value = [], {}, {}
    def _above(self, i, j):                         # should keys[i] sit above keys[j]?
        a, b = self.keys[i], self.keys[j]
        return (-self.value[a], a) < (-self.value[b], b)   # larger value; ties: smaller key
    def _swap(self, i, j):
        ks = self.keys
        ks[i], ks[j] = ks[j], ks[i]
        self.pos[ks[i]], self.pos[ks[j]] = i, j
    def _up(self, i):
        while i > 0 and self._above(i, (i - 1) // 2):
            self._swap(i, (i - 1) // 2)
            i = (i - 1) // 2
    def _down(self, i):
        n = len(self.keys)
        while True:
            best = i
            for c in (2 * i + 1, 2 * i + 2):
                if c < n and self._above(c, best):
                    best = c
            if best == i:
                return
            self._swap(i, best)
            i = best
    def update(self, key, v):
        if key in self.pos:
            if v <= 0:
                self._remove(key)
                return
            self.value[key] = v
            i = self.pos[key]
            self._up(i)
            self._down(self.pos[key])               # only one of the two moves it
        elif v > 0:
            self.value[key] = v
            self.keys.append(key)
            self.pos[key] = len(self.keys) - 1
            self._up(len(self.keys) - 1)
    def _remove(self, key):
        i, last = self.pos[key], len(self.keys) - 1
        self._swap(i, last)
        self.keys.pop()
        del self.pos[key], self.value[key]
        if i < last:                                # the moved key may need to go either way
            self._up(i)
            self._down(self.pos[self.keys[i]])
    def peek(self):
        if not self.keys:
            return None
        k = self.keys[0]
        return k, self.value[k]

(c) A balanced search tree or sorted container. Keep all (-value, key) tuples in sorted order, in a balanced binary search tree (AVL, red–black) or a sorted container. An update deletes the old tuple and inserts the new one, O(log n) each; the maximum is the first element. What you gain over a heap is order: the top k, the k-th largest, or "all pairs with count ≥ c" in O(log n + output). Python has no built-in balanced tree; the sortedcontainers package provides SortedList.

queues.py · (c) sorted container
class SortedQueue:
    """(c) A sorted container of (-value, key): every operation O(log n), plus ordered iteration."""
    def __init__(self):
        from sortedcontainers import SortedList   # pip install sortedcontainers
        self.items, self.value = SortedList(), {}
    def update(self, key, v):
        old = self.value.pop(key, 0)
        if old > 0:
            self.items.remove((-old, key))
        if v > 0:
            self.value[key] = v
            self.items.add((-v, key))
    def peek(self):
        if not self.items:
            return None
        neg, key = self.items[0]
        return key, -neg

(d) Bucket queue. When values are small non-negative integers, keep an array of buckets, bucket[v] = the set of keys with value v, and a pointer top to the highest non-empty bucket. An update moves a key between two sets in O(1). peek walks top down past empty buckets. In general the pointer can also move up, and its total movement is at most the largest value C plus the total size of the increases.

In BPE the maximum never rises, so the pointer only moves down. Proof: let the merged pair (a, b) have count c, the current maximum. Pairs that do not contain the new token Z only lose occurrences. Every occurrence of a pair that contains Z contains one occurrence of Z, and there are at most c of those, so each such pair has count ≤ c. Every count after the merge is ≤ c. On Alice the maximum falls from 3,978 to 4, so the pointer moves fewer than 4,000 steps in the whole run. The catch is the tie-break: the smallest key in the top bucket takes a scan of the bucket, on average 42 keys and at most 287 on Alice. A min-heap or sorted set per bucket would remove the scan.

queues.py · (d) bucket queue
class BucketQueue:
    """(d) value -> set of keys, and a pointer to the highest non-empty bucket."""
    def __init__(self):
        self.bucket, self.value, self.top = defaultdict(set), {}, 0
    def update(self, key, v):
        old = self.value.pop(key, 0)
        if old > 0:
            self.bucket[old].discard(key)
        if v > 0:
            self.value[key] = v
            self.bucket[v].add(key)
            self.top = max(self.top, v)
    def peek(self):
        while self.top > 0 and not self.bucket[self.top]:
            self.top -= 1                           # in BPE the max never rises, so this pointer only falls
        if self.top == 0:
            return None
        return min(self.bucket[self.top]), self.top # tie-break: smallest pair in the bucket

4 · The inverted index: visit only what changes

The question. After choosing the pair (a, b), which chunks must change, and which counts?

First attempt. Rewrite and recount all 3,218 unique chunks per merge. That is what the simple trainer does: 1,744 merges × 3,218 chunks = 5,612,192 chunk visits, almost all of which change nothing.

The key observation: a merge only changes its neighbours.

xaby  →  xZy
removed:(x, a)(a, b)(b, y) added:(x, Z)(Z, y)
Every other pair in the chunk is untouched, and chunks without (a, b) are untouched entirely.

So we need, for each pair, the list of chunks that contain it. An inverted index maps each item to the places where it occurs; a search engine maps each word to the documents that contain it. Here where[p] is the set of chunk ids that contain pair p. A merge visits only where[(a, b)].

Invariant. Chunk w is in where[p] exactly when p occurs in w's current tokens. It holds after the initial pass. When a chunk is rewritten, the trainer removes it from where of every old pair and adds it to where of every new pair, which restores the invariant for that chunk. Chunks not rewritten did not change, so their entries stay correct.

Total work. Let \( A_k \) be the number of chunks containing the k-th merged pair. A visited chunk contains the pair at least once, so the merge shortens it by at least one token. A chunk of \( \ell \) bytes can be shortened at most \( \ell - 1 \) times, so over the whole run

\[ \sum_k A_k \;\le\; \sum_{\text{unique chunks } w} (\ell_w - 1) \;=\; S - (\text{number of unique chunks}) \;=\; 21{,}171 - 3{,}218 \;=\; 17{,}953 . \]

No matter how many merges you ask for, the total number of chunk visits is bounded by the size of the unique chunks. Each visit costs O(L) for a chunk of length L, plus a queue update per changed pair.

Confirm by measuring. The fast trainer visits 14,013 chunks in total, under the bound of 17,953 and 400× fewer than 5,612,192. The first five merges touch 164, 145, 74, 128 and 309 chunks; the last five touch 2, 1, 1, 1 and 2. That is Zipf again: frequent pairs live in many chunks, rare pairs in few.

5 · Putting it together: the fast trainer

The trainer keeps four structures and updates them locally:

counts · hash mappair → total count. O(1) get and add
where · inverted indexpair → chunks containing it. Visit only those
heap · binary min-heap(−count, pair) with lazy deletion: the max in O(log H); ties pop the smaller pair
words · unique chunkseach a list of ids, with its frequency
loop pop heap → stale? skip → merge the chunks in where[pair] → for each: remove old pairs, rewrite, add new pairs → push changed counts
bpe.py · fast trainer
import heapq
from collections import Counter, defaultdict

def train(texts, vocab_size):
    words, freqs = unique_chunks(texts)
    counts, where = Counter(), defaultdict(set)
    for wi, w in enumerate(words):
        for pair in zip(w, w[1:]):
            counts[pair] += freqs[wi]
            where[pair].add(wi)
    heap = [(-c, p) for p, c in counts.items()]
    heapq.heapify(heap)                         # O(P), faster than P pushes

    merges = []
    while 256 + len(merges) < vocab_size and heap:
        neg, pair = heapq.heappop(heap)
        if counts.get(pair, 0) != -neg:
            continue                            # stale: the true count is already in the heap
        if -neg < 2:
            break
        new_id = 256 + len(merges)
        merges.append(pair)

        delta = Counter()
        for wi in list(where[pair]):            # copy: where[pair] shrinks inside the loop
            old, f = words[wi], freqs[wi]
            new = merge(old, pair, new_id)
            words[wi] = new
            for p in zip(old, old[1:]):         # 1. remove the old pairs
                delta[p] -= f
                where[p].discard(wi)
            for p in zip(new, new[1:]):         # 2. add the new pairs
                delta[p] += f
                where[p].add(wi)
        for p, d in delta.items():              # 3. apply net changes; push new counts
            if d:
                counts[p] += d
                if counts[p] > 0:
                    heapq.heappush(heap, (-counts[p], p))
        del counts[pair], where[pair]           # the merged pair can never occur again
    return merges

The changes for each merge are collected in delta first and applied once, so a pair that loses an occurrence in one chunk and gains one in another gets one push, not two. Where BPE uses it. Every merge asks for the most frequent pair (the maximum of a changing set, part 3) and then changes a few counts (the inverted index, part 4). Heapify builds the first heap in O(P) for P distinct pairs. The tuple (-count, pair) is the tie-break rule of the specification, written as a sort key.

6 · The same pattern in other problems

Kth largest in a stream (703). Values arrive one at a time; after each, report the k-th largest so far. Sorting each time is O(n log n) per value. Instead keep the k largest in a min-heap of size k. Invariant: the heap holds exactly the k largest values seen. When a value arrives, push it and, if the heap has k+1 entries, pop the smallest; whichever value leaves is not among the k largest. The root is the smallest of the k largest, which is the answer. O(log k) per value, O(k) space.

Median of a stream (295). The median is in the middle, so no single heap exposes it. Keep the smaller half in a max-heap lo and the larger half in a min-heap hi, with two invariants: every value in lo is ≤ every value in hi, and len(lo) equals len(hi) or exceeds it by one. Then the median is the top of lo, or the average of both tops. To add x: push it into lo, move the largest of lo to hi (that keeps the ordering invariant, since the moved value is the largest of lo ∪ {x}), and if hi is now larger, move its smallest back. O(log n) per add, O(1) per median.

Sliding window maximum (239). Report the maximum of every window of k consecutive values. Rescanning each window is O(nk). A lazy heap works in O(n log n): entries whose index has left the window are stale. Better, a monotonic deque: keep the indices of values that could still become a window maximum, with values strictly decreasing from front to back. If an older value is ≤ a newer one, it can never be a maximum again, because the newer value is at least as large and stays in the window longer; so pop it from the back. The front is the current maximum; pop it from the front when it leaves the window. Amortized proof: each index is appended once and removed at most once, so the whole run makes at most 2n deque operations, O(n) in total and O(1) amortized per value, with O(k) space. The deque beats the heap here because values leave in arrival order; in BPE they leave in no particular order, so the heap is needed.

Stock price fluctuation (2034). Prices arrive with timestamps and earlier prices may be corrected; report the latest, the maximum and the minimum. This is lazy deletion again, in two heaps: a corrected price leaves a stale entry, recognized because it no longer matches price[timestamp]. The invariant and proof are those of part 3.

Seat reservation manager (1845). Always hand out the smallest free seat: a plain min-heap of free seats. A sorted list is already a valid heap, so initialization needs no work.

def topKFrequent(words, k):                      # 692: O(n log k)
    c = Counter(words)
    return [w for _, w in heapq.nsmallest(k, ((-n, w) for w, n in c.items()))]

class KthLargest:                                # 703: size-k min-heap
    def __init__(self, k, nums):
        self.k, self.h = k, []
        for x in nums:
            self.add(x)
    def add(self, val):
        heapq.heappush(self.h, val)
        if len(self.h) > self.k:
            heapq.heappop(self.h)                # drop the smallest; the k largest remain
        return self.h[0]                         # the smallest of the k largest

class MedianFinder:                              # 295: two heaps
    def __init__(self):
        self.lo, self.hi = [], []                # lo: max-heap (negated), hi: min-heap
    def addNum(self, num):
        heapq.heappush(self.lo, -num)
        heapq.heappush(self.hi, -heapq.heappop(self.lo))   # largest of lo moves up
        if len(self.hi) > len(self.lo):
            heapq.heappush(self.lo, -heapq.heappop(self.hi))
    def findMedian(self):
        if len(self.lo) > len(self.hi):
            return float(-self.lo[0])
        return (-self.lo[0] + self.hi[0]) / 2

def maxSlidingWindow(nums, k):                   # 239: monotonic deque, O(n)
    dq, out = deque(), []                        # indices; their values strictly decrease
    for i, x in enumerate(nums):
        while dq and nums[dq[-1]] <= x:
            dq.pop()                             # can never be a maximum again
        dq.append(i)
        if dq[0] <= i - k:
            dq.popleft()                         # left the window
        if i >= k - 1:
            out.append(nums[dq[0]])
    return out

class StockPrice:                                # 2034: lazy deletion, twice
    def __init__(self):
        self.price, self.latest, self.mx, self.mn = {}, 0, [], []
    def update(self, timestamp, price):
        self.price[timestamp] = price
        self.latest = max(self.latest, timestamp)
        heapq.heappush(self.mx, (-price, timestamp))
        heapq.heappush(self.mn, (price, timestamp))
    def current(self):
        return self.price[self.latest]
    def maximum(self):
        while -self.mx[0][0] != self.price[self.mx[0][1]]:   # stale: price was corrected
            heapq.heappop(self.mx)
        return -self.mx[0][0]
    def minimum(self):
        while self.mn[0][0] != self.price[self.mn[0][1]]:
            heapq.heappop(self.mn)
        return self.mn[0][0]

class SeatManager:                               # 1845: the smallest free seat
    def __init__(self, n):
        self.free = list(range(1, n + 1))        # already a valid min-heap
    def reserve(self):
        return heapq.heappop(self.free)
    def unreserve(self, seatNumber):
        heapq.heappush(self.free, seatNumber)
train_pq · the fast trainer with any of the four queues
def train_pq(texts, vocab_size, queue):
    words, freqs = unique_chunks(texts)
    counts, where = Counter(), defaultdict(set)
    for wi, w in enumerate(words):
        for pair in zip(w, w[1:]):
            counts[pair] += freqs[wi]
            where[pair].add(wi)
    for p, c in counts.items():
        queue.update(p, c)

    merges = []
    while 256 + len(merges) < vocab_size:
        top = queue.peek()
        if top is None or top[1] < 2:
            break
        pair, new_id = top[0], 256 + len(merges)
        merges.append(pair)
        delta = Counter()
        for wi in list(where[pair]):
            old, f = words[wi], freqs[wi]
            new = merge(old, pair, new_id)
            words[wi] = new
            for p in zip(old, old[1:]):
                delta[p] -= f
                where[p].discard(wi)
            for p in zip(new, new[1:]):
                delta[p] += f
                where[p].add(wi)
        for p, d in delta.items():
            if d:
                counts[p] += d
                queue.update(p, counts[p])          # counts[pair] reaches 0 here: removed
        del counts[pair], where[pair]
    return merges

d-ary heap. The height is \( \log_d n \). Push compares once per level: O(logd n). Pop compares with all d children per level: O(d logd n). With many more updates (pushes or sift-ups) than pops, a larger d such as 4 or 8 helps; this is why Dijkstra on dense graphs is sometimes run with a d-ary heap.

Per-bucket heaps. Each peek pops stale keys from the top bucket's heap; each stale key is popped once, so peek is O(log b) amortized for bucket size b, and an update is an O(log b) push.

Duplicate entries. Two identical tuples (-v, k) are both valid when k's value is v. Whichever pops first is returned; after the merge the pair's count is 0, so the second becomes stale and is skipped.

Design · contracts and tests

The question

The fast trainer is about 40 lines of bookkeeping. How do you know it is the same trainer as the simple one, on every input, and stays so as the code changes?

First attempt

Train on Alice and look at the first merges. That checks one input, and a bookkeeping bug that only fires when a chunk contains the merged pair twice, or when a count returns to an earlier value, can pass it.

The key idea: every test needs an oracle

A test compares the code's output with an oracle: something that tells you the right answer. Kinds of test differ in where the oracle comes from, and that decides which bugs each can see and which it is blind to. Write the invariants first; each becomes a test that exists, and fails, before the implementation.

contracts.py
from typing import Protocol, Sequence

class Tokenizer(Protocol):
    vocab_size: int
    def encode(self, text: str) -> list[int]: ...
    def decode(self, ids: Sequence[int]) -> str: ...

# I1  decode(encode(x)) == x                  for every str x
# I2  0 <= id < vocab_size                    for every id from encode
# I3  encode(x) is identical across runs and machines
# I4  train(D, V) is identical across runs    (fixed tie-break)
# I5  load(save(t)) encodes exactly like t

The four kinds cover each other's blind spots, which is why you want all of them. Mutation testing checks the tests themselves: plant a bug and confirm that some test fails. If none does, a test is missing.

File format decisions follow the same contracts. Store the merges in order (the vocabulary is derived from them), the pattern (the same merges with another pattern give other tokens, so I3 would break), a format_version (refuse unknown files instead of mis-encoding them, I5), and integers, not byte strings (they round-trip through JSON exactly).

Where BPE uses it

The differential test is what lets you optimize at all: every queue in the Algorithms block was accepted only after it produced the simple trainer's merges. The golden test pins the tie-break that the tuple (-count, pair) implements.

MERGES = train([open("data/alice.txt").read()], 500)

def test_round_trip_any_text(s):
