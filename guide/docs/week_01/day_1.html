DAY 1 · COMMON FRIENDSDSASystemsML

Common friends: intersect two friend lists

Where we are. The reading gave each candidate a naive score: the number of mutual friends. Open Esha's profile and the app says "2 mutual friends: Ben and Chloe". Behind that line is one small question asked billions of times a day: which ids appear in both your friend list and hers? That is the intersection of two lists. Today starts with one pair and grows: five ways to intersect two lists, measured on the week's data; then every candidate for one user at once; then, as an advanced part, lists too large for one machine.

By hand. Your friends are Ben and Chloe. Esha's friends are Ben and Chloe. Walk your list and ask, for each name, "is this one in Esha's list?" Ben: yes. Chloe: yes. Two mutual friends. For Dev (friends: Ben) the same walk gives Ben only: one. For Farid (friends: Chloe): Chloe only: one.

Six people make this trivial. On the week's data (10,000 users, 100,000 friendships) a typical list has 15 friends, the mean is 20, and the five largest have 793, 1,108, 1,117, 1,132 and 1,480. Those few long lists, the hubs, decide which method wins.

DSA · one pair, five ways to intersect

A small sorted example to count steps on: A = [3, 9, 14, 20] and B = [1, 3, 4, 7, 9, 12, 15, 20, 22, 30]. The answer is [3, 9, 20]. Write a for the shorter length and b for the longer.

1 · The obvious attempt: compare everything with everything

For each id in A, scan B until you find it. That is up to a × b = 4 × 10 = 40 comparisons; stopping at the first match, the code below makes 25. It needs nothing from the input (any order, any container), which is its only virtue.

code/day_1/intersect.py · nested loops
def intersect_nested(a, b):
    """Any two lists. Compare every x in a with the members of b: up to |a|*|b| comparisons."""
    out, ops = [], 0
    for x in a:
        for y in b:
            ops += 1
            if x == y:
                out.append(x)
                break                      # ids are distinct: x cannot match again
    return sorted(out), ops

Every function in this file returns the common ids and the number of operations it used, so the measurements below can count work as well as time it. On the week's data the nested loops make 720 comparisons for a typical pair and 11,021 when one side is a hub.

2 · A hash set: one lookup per id

The idea. Keep one list as a hash set, where "is Ben in here?" takes one step on average. Walk the shorter list and look each id up in the longer one: a lookups. In the example, 4 lookups instead of 25 comparisons. If the set does not exist yet, building it costs one insert per id, so the total is \(O(a + b)\) time; if it is already stored, the pair costs only \(O(a)\).

code/day_1/intersect.py · hash set
def intersect_hash(a, b_set):
    """a: any list; b_set: the other list, already a hash set. One lookup per x in a.
    Call it with the SHORTER list as a."""
    out = [x for x in a if x in b_set]
    return sorted(out), len(a)

The catch is memory. A Python set for the largest list (1,480 ids) takes 131,288 bytes for its table alone; the same ids as a sorted array of 4-byte integers take 5,920 bytes. Keeping every list as a hash set costs about 22 times the memory of keeping it as an array.

3 · Both lists sorted: merge with two pointers

The idea. If both lists are sorted, put a finger at the start of each. If A's finger points at the smaller id, that id cannot be in B (everything left in B is bigger), so move A's finger. If B's is smaller, move B's. If they are equal, write it down and move both.

8–920vs1520skip 15; equal: output 20. A is used up: stop after 9 steps (the lengths add to 14)
code/day_1/intersect.py · two-pointer merge
def intersect_merge(a, b):
    """a, b sorted, no repeats. Two pointers; each step moves at least one: <= |a| + |b| steps."""
    i = j = ops = 0
    out = []
    while i < len(a) and j < len(b):
        ops += 1
        if a[i] < b[j]:
            i += 1                         # a[i] is below everything left in b: not shared
        elif a[i] > b[j]:
            j += 1
        else:
            out.append(a[i]); i += 1; j += 1
    return out, ops

Every step moves at least one finger, so the merge takes at most \(a + b\) steps. It needs no extra memory beyond the two arrays, and it reads both front to back, which suits arrays in memory, compressed lists on disk and streams alike. The price: on a small list against a hub it walks through almost all of the hub's list to find a handful of matches.

4 · Very different sizes: binary search, then galloping

Binary search. When one list is tiny and the other huge, look each id of the short list up in the long one by halving: about \(\log_2 b\) comparisons each, so \(a \log_2 b\) in all. Against the 1,480-id list that is about 11 comparisons per id instead of walking 1,480 entries.

Galloping. Binary search forgets where the last search ended. Galloping remembers: from where the finger stopped, leap 1, 2, 4, 8 … places ahead until you pass the id, then binary-search the last leap. For 9 in the example, starting at position 2: look at 4 (too small), 7 (too small), 12 (past it), then search between 7 and 12 and find 9. The cost is about \(a \log_2(b/a)\): close to the merge when the sizes are equal, close to binary search when they are far apart. In the example the merge took 9 steps, binary search 20 and galloping 14; the small example favours the merge, the hubs do not.

code/day_1/intersect.py · binary search and galloping
def lower_bound(b, x, lo, hi):
    """Smallest i in [lo, hi) with b[i] >= x (hi if none), and the comparisons used."""
    ops = 0
    while lo < hi:
        mid = (lo + hi) // 2
        ops += 1
        if b[mid] < x:
            lo = mid + 1
        else:
            hi = mid
    return lo, ops

def intersect_binary(a, b):
    """a short and sorted, b long and sorted. Binary-search each x of a in all of b:
    about |a| * log2|b| comparisons."""
    out, ops = [], 0
    for x in a:
        i, c = lower_bound(b, x, 0, len(b))
        ops += c + 1
        if i < len(b) and b[i] == x:
            out.append(x)
    return out, ops

def intersect_gallop(a, b):
    """a short and sorted, b long and sorted. From where the last search stopped, leap
    1, 2, 4, 8 ... places until past x, then binary-search that last leap:
    about |a| * log2(|b| / |a|) comparisons."""
    out, ops, j = [], 0, 0
    for x in a:
        lo, step = j, 1
        hi = j
        while hi < len(b):
            ops += 1
            if b[hi] >= x:
                break
            lo = hi + 1                    # b[hi] < x: the answer lies beyond hi
            hi += step
            step *= 2
        j, c = lower_bound(b, x, lo, min(hi, len(b)))
        ops += c + 1
        if j == len(b):
            break                          # everything left in a is bigger than all of b
        if b[j] == x:
            out.append(x); j += 1
    return out, ops

5 · Dense ids: bitsets and popcount

The idea. Number the users 0 to n − 1 and store each friend list as n bits: bit x is 1 when x is a friend. You are bits 1 and 2 (Ben, Chloe): 000110 read right to left; Esha is the same, 000110. AND the two bit strings and count the 1s that survive (a popcount, one machine instruction per 64-bit word): 2. The work is \(n/64\) words whatever the list sizes: 157 words for 10,000 users.

code/day_1/intersect.py · bitsets
def to_bits(ids):
    """A friend list as one big integer: bit x is 1 when x is a friend."""
    bits = 0
    for x in ids:
        bits |= 1 << x
    return bits

def intersect_bits(a_bits, b_bits, n):
    """Ids 0..n-1. AND the two bitsets, then count the 1s (popcount): n/64 machine words."""
    both = a_bits & b_bits
    out = [x for x in range(n) if both >> x & 1] if both else []
    return out, (n + 63) // 64

def count_bits(a_bits, b_bits):
    """Only the number of mutual friends: AND, then popcount."""
    return (a_bits & b_bits).bit_count()

The catch is again memory. A bitset costs \(n/8\) bytes per user however few friends they have: 1,250 bytes each here, 12,500,000 bytes for all 10,000 users, against 800,000 bytes for every list as 4-byte arrays (15.6 times more). With a billion users one bitset would be 125 MB. Bitsets pay inside a small, dense id range: one community, one company, one block of a matrix.

Interview takeaway
  • Say first: "Build a hash set from one list and probe it with the other: \(O(a + b)\) time, \(O(\min(a, b))\) extra space if I build the set from the shorter one. If the sets are already stored, probe with the shorter list: \(O(\min(a, b))\)."
  • "What if both are sorted?" Two pointers, \(O(a + b)\) time, \(O(1)\) extra space. Prove it with the invariant in the math below.
  • "What if one list is huge?" Binary search each id of the small one: \(O(a \log b)\). Galloping if you do not know the sizes in advance.
  • "Memory is tight?" Sorted arrays and the merge; a hash set costs many times the array (22 times here).
  • "Ids are small and dense, and you do this for many pairs?" Bitsets: AND plus popcount, \(n/64\) words per pair.
  • "Duplicates?" (LeetCode 350) A count map instead of a set, or the merge emitting a match once per matched pair.

In one line. Hash set by default; two pointers when sorted and memory matters; binary search or galloping when one side is huge; bitsets when ids are dense.

The math, step by step: why the merge is correct, what galloping costs, and why nothing can do much better

Write a for the shorter length and b for the longer, and \(A_i\), \(B_j\) for the ids under the two fingers.

The merge is correct. Both lists are sorted with no repeats. Two facts stay true before every step. (P): everything already passed in either list, \(A[{:}i]\) and \(B[{:}j]\), is smaller than both \(A_i\) and \(B_j\). (Q): the output so far is exactly what \(A[{:}i]\) and \(B[{:}j]\) have in common. Both hold at the start, when nothing has been passed. Take a step where \(A_i < B_j\). Everything passed in B is below \(A_i\) by (P), and everything not yet passed in B is at least \(B_j > A_i\). So \(A_i\) is nowhere in B, and moving past it without output keeps (Q); (P) still holds because \(A_i < B_j\). The case \(A_i > B_j\) is the mirror image. If \(A_i = B_j\), outputting it and moving both keeps (Q), and (P) holds because both lists strictly increase. When one list runs out, (P) says nothing left in the other can match, so the output is the whole intersection. Each step moves a finger, so there are at most \(a + b\) steps.

What galloping costs. Take one id of the short list, and say its search moves the finger past \(g\) positions of B. The leaps probe 1, 3, 7, 15 … places ahead; passing \(g\) places takes about \(\log_2(g+1)\) probes plus one that overshoots, and the binary search of the last leap costs about as many again. So that id costs at most about \(2\log_2(g_i + 1) + 4\) comparisons. The finger only moves forward, so all the jumps together are at most b: \(\sum_i g_i \le b\). The logarithm curves downward, so the average of logs is at most the log of the average (Jensen's inequality):

\[ \sum_{i=1}^{a} \log_2(g_i + 1) \;\le\; a \log_2\!\Big(\frac{1}{a}\sum_i (g_i + 1)\Big) \;\le\; a \log_2\!\Big(\frac{b}{a} + 1\Big). \]

So galloping takes at most about \(2a\log_2(b/a+1) + 4a\) comparisons. When \(b \approx a\) that is a constant times a, like the merge. When b is far larger it approaches \(2a \log_2 b\), twice a binary search per id: which is why, against a hub with only 13 ids on the other side, plain binary search came out slightly ahead.

No comparison method can do much better. Think about inputs where the two lists share nothing. To answer "nothing in common", a method must know, for each id of A, which two neighbouring ids of B it falls between (otherwise another input with the same comparison results would put it equal to one of them). That fixes the full interleaving of the two lists, and there are \(\binom{a+b}{a}\) interleavings. Each comparison has two outcomes, so c comparisons tell at most \(2^c\) interleavings apart:

\[ c \;\ge\; \log_2 \binom{a+b}{a} \;\ge\; \log_2\Big(\frac{a+b}{a}\Big)^{a} \;\ge\; a\log_2\frac{b}{a}. \]

The middle step uses \(\binom{N}{a} = \prod_{i=0}^{a-1}\frac{N-i}{a-i}\), where each factor is at least \(N/a\).

What this shows. The merge is correct and costs at most \(a + b\); galloping costs at most about \(2a\log_2(b/a+1) + 4a\); every comparison method needs at least \(a\log_2(b/a)\). Galloping is within a constant factor of the best possible for every pair of sizes.

DSA · from one pair to one user

7 · Count every candidate in one pass

The situation. The profile line needs one pair. The suggestion list for You needs a count for everyone who shares at least one friend with you, so it can rank them.

The obvious attempt. Intersect your list with every other user's list: 9,999 intersections per user, nearly all of them empty. A little better: intersect only with friends of friends, since nobody else can share a friend with you. On the week's data that is 1,191 people per user on average, and with hash lookups over the shorter list it costs 19,714 lookups per user.

The idea. Turn it around. Each of your friends vouches for each of their friends: when you read Ben's list, every person on it gets one more mutual friend with you. Keep a dictionary of counts. For You: Ben's list adds 1 to Dev and Esha (and to Chloe and You, who are skipped); Chloe's list adds 1 to Esha and Farid. Result: Esha 2, Dev 1, Farid 1, after reading 4 + 4 = 8 entries.

code/day_1/one_user.py · counts with a dictionary
def mutual_counts(friends, u):
    """For every friend of a friend of u (not u, not already a friend): how many mutual friends.
    Reads each friend's list once, so the cost is the sum of u's friends' list lengths."""
    counts = {}
    for f in friends[u]:                   # each friend f of u ...
        for v in friends[f]:               # ... vouches for each of f's friends
            if v != u and v not in friends[u]:
                counts[v] = counts.get(v, 0) + 1
    return counts

def cost(friends, u):
    """Entries read by mutual_counts: the sum of the friends' list lengths."""
    return sum(len(friends[f]) for f in friends[u])

Interview takeaway
  • "For one pair, intersect. For one user's whole candidate list, count: read each friend's list once into a hash map, \(O(\sum_{f} d_f)\) where \(d_f\) is friend f's list length."
  • Follow-up "who is expensive?": users whose friends have long lists, not users with many friends. The cost is set by your friends' lengths.

In one line. Many intersections with one shared side collapse into one counting pass over your friends' lists.

The math, step by step: why the total is the sum of squared lengths

Write \(d_f\) for the length of f's list. User u's pass reads \(\sum_{f \in \text{friends}(u)} d_f\) entries. Add this over every user u:

\[ \sum_u \sum_{f \in \text{friends}(u)} d_f \;=\; \sum_f d_f \cdot \#\{u : f \in \text{friends}(u)\} \;=\; \sum_f d_f \cdot d_f \;=\; \sum_f d_f^2 . \]

The middle step swaps the order of the sums: list f is read once for each person who has f as a friend, and those are exactly f's \(d_f\) friends.

Why the tail sets the bill. With n users and mean length \(\bar d\), \(\sum_f d_f^2 = n(\bar d^2 + \sigma^2)\), where \(\sigma^2\) is the variance of the lengths. If everyone had exactly 20 friends the total would be \(10{,}000 \times 20^2 = 4{,}000{,}000\). The measured 14,768,324 means \(\sigma^2 = 1{,}476.8 - 400 = 1{,}076.8\): the spread of lengths, driven by the hubs, costs 2.7 times more than the average itself.

The bridge to scale. Suppose a billion users with 300 friends each. One user's pass reads about 300 × 300 = 90,000 entries; all users together about \(10^9 \times 90{,}000 = 9 \times 10^{13}\). The lists alone hold \(10^9 \times 300 = 3 \times 10^{11}\) ids, 2.4 TB at 8 bytes each. They no longer fit on one machine, and the rest of the day is about what changes when they do not.

Systems · advanced · two machines, one pair

8 · Ship the smaller list

The situation. Lists are spread over machines by user id. Your list is on machine A, Esha's on machine B, and the profile page needs your mutual-friend count.

The obvious attempt. Fetch both lists to the web server and intersect there. That moves both lists every time, and if one belongs to a hub, it moves the big one.

The idea. Move the smaller list to where the larger one lives, intersect there (hash set or merge, as above), and send back only the answer. A median user (15 friends) against the 1,480-id hub, at 4 bytes an id:

PlanBytes moved
ship the hub's list to the user's machine1,480 × 4 = 5,920
ship the user's list to the hub's machine, return a 4-byte count15 × 4 + 4 = 64

That is 92 times fewer bytes. With hypothetical sizes of 300 and 5,000 friends and 8-byte ids, it is 2,400 + 8 bytes against 40,000. The same rule, applied to whole tables, is the "broadcast the small side" choice of a distributed join: send the small table to every machine holding pieces of the big one. When both lists are long (two hubs, 1,132 and 1,480 ids: 4,528 bytes for the smaller), the next step is to send a summary instead of a list. A MinHash signature of 64 numbers is 64 × 8 = 512 bytes, at the price of an estimate (section 10).

Interview takeaway
  • "Move the computation to the data: ship the smaller list, return a count." State the bytes.
  • Follow-up "both lists are huge": a compact summary (a MinHash signature for overlap, a Bloom filter for membership) trades exactness for bytes.
Systems · advanced · every pair at once as a batch job

9 · Mutual friends for all pairs, MapReduce-style

The situation. Instead of counting on demand, precompute every user's mutual-friend counts overnight on many machines. Day 1's counting pass says "each friend vouches for each of their friends". Turned into a batch job it says: user u is a mutual friend of every two people on u's list.

map: each user's list→every pair on it, with a 1→shuffle: route by pair→reduce: add the 1s
Map runs on the machine holding each list. The shuffle sends every record across the network to the reducer that owns its pair. The reducer's sum for (x, y) is the number of users who have both x and y as friends: their mutual-friend count.

By hand. Ben's list is You, Chloe, Dev, Esha, so his map emits six pairs: (You, Chloe), (You, Dev), (You, Esha), (Chloe, Dev), (Chloe, Esha), (Dev, Esha). Chloe's list is You, Ben, Esha, Farid: six more, including (You, Esha) again. You and Esha each emit (Ben, Chloe); Dev and Farid, with one friend each, emit nothing. In all, 14 records reduce to 12 distinct pairs, and (You, Esha) sums to 2. Pairs that are already friends, such as (Ben, Chloe), are dropped at the end.

code/day_1/mapreduce.py · the job, simulated in one process
# Mutual-friend counts for ALL pairs as a MapReduce-style job, simulated in one process.
# Map: each user's friend list -> every pair of those friends, with a 1 ("u is a mutual friend of x and y").
# Shuffle: route each pair to the reducer that owns it (hash of the pair).
# Reduce: add up the 1s per pair = the number of mutual friends.
from itertools import combinations

def map_user(u, friend_list):
    for x, y in combinations(sorted(friend_list), 2):
        yield (x, y), 1

def shuffle(records, reducers):
    parts = [{} for _ in range(reducers)]
    for key, val in records:
        parts[hash(key) % reducers].setdefault(key, []).append(val)
    return parts

def reduce_sum(part):
    return {key: sum(vals) for key, vals in part.items()}

def run_job(friends, reducers=4, mapper=map_user):
    emitted = []
    for u, fl in friends.items():
        emitted.extend(mapper(u, fl))
    out = {}
    for part in shuffle(emitted, reducers):
        out.update(reduce_sum(part))
    return out, len(emitted)

How one hub explodes the job. The shuffle size is \(\sum_u d_u(d_u - 1)/2\), half the sum of squared lengths (14,768,324 here) less a small term: the same quantity as the counting pass, now paid in network bytes. A single map task is 10,423 times the median one, so the whole job waits for the hub's mapper (a straggler). The reducers are fine: routing by a hash of the pair, the busiest of 100 reducers got 1.018 times the average load. Routing by the first user of the pair instead (to get each user's list on one reducer) gave 1.49. Now suppose one account with a million friends: it alone emits \(10^6 \times (10^6 - 1)/2 \approx 5 \times 10^{11}\) records, about 8 TB at 16 bytes a record, all from one map task.

Interview takeaway
  • "Map each friend list to all pairs of its friends with a 1, shuffle by pair, reduce by summing. The shuffle is \(\sum d^2/2\), so the heavy tail, not the mean, sets the cost."
  • Follow-ups: "one mapper never finishes" (a hub: cap or sample its fan-out); "most of the output is never shown" (emit only for users you will serve, keep top-k per user in the reducer); "a reducer is overloaded" (route by a hash of the pair, not by user).
The math, step by step: what the job emits, and why its answer is the mutual-friend count

Correctness. The reducer for pair (x, y) receives one 1 from each user u whose list contains both x and y. A user whose list contains both is a friend of x and of y: a mutual friend. So the sum is \(|\text{friends}(x) \cap \text{friends}(y)|\), exactly the intersection of section 1, computed for every pair at once.

Size. A list of length d has \(\binom{d}{2} = d(d-1)/2\) pairs, so the job emits

\[ \sum_u \frac{d_u(d_u - 1)}{2} \;=\; \frac{1}{2}\Big(\sum_u d_u^2 - \sum_u d_u\Big) \;=\; \frac{14{,}768{,}324 - 200{,}000}{2} \;=\; 7{,}284{,}162 . \]

(\(\sum_u d_u = 200{,}000\) because every friendship appears on two lists.) It is the counting pass of section 7 for every user, halved because each unordered pair is emitted once.

Emitting only for wanted users. If T is the set of users to serve, the mapper of u emits, for each friend x of u in T, the pairs (x, y) for the other \(d_u - 1\) friends y. That is \(\sum_u |\text{friends}(u) \cap T|\,(d_u - 1)\) records, and each x in T still receives one 1 from every mutual friend, so its counts are exact.

ML · advanced · estimating overlap: MinHash and LSH

10 · MinHash: a short signature that remembers overlap

The situation. Two long lists on different machines, or millions of pairs to compare: we want each list's overlap with others from something much shorter than the list.

A measure that fits. Shared friends divided by everyone either person knows is the Jaccard similarity, J, from 0 to 1. You (Ben, Chloe) and Esha (Ben, Chloe): \(J = 2/2 = 1\). You and Dev (Ben): one shared out of two people in all, \(J = 1/2\). Knowing J and the two lengths gives the mutual count back: \(m = J(|A| + |B|)/(1 + J)\).

The idea. Shuffle all users into one random order. For each person, note which of their friends comes first. Two people get the same "first friend" exactly when the first person in the order, among everyone either of them knows, is someone they both know. By hand for You and Dev: among Ben and Chloe, each comes first with chance one half. Ben first: your first friend is Ben and Dev's is Ben: they agree. Chloe first: yours is Chloe and Dev's is Ben: they differ. They agree half the time, and \(J = 1/2\). The chance that the first friends agree is exactly J.

Repeat with k independent orders: each person's k first friends form their signature, k numbers however long the list. The share of positions where two signatures agree estimates J. A hash function stands in for each order (friend x's position is mix64(x ^ seed)), so no order is ever stored.

code/day_1/minhash.py · signatures and the estimates
import random
from collections import defaultdict

MASK = (1 << 64) - 1

def mix64(x):
    """splitmix64 finalizer: nearby ids get unrelated 64-bit values (stands in for a random order)."""
    x = (x + 0x9E3779B97F4A7C15) & MASK
    x = ((x ^ (x >> 30)) * 0xBF58476D1CE4E5B9) & MASK
    x = ((x ^ (x >> 27)) * 0x94D049BB133111EB) & MASK
    return x ^ (x >> 31)

def make_seeds(k, seed=0):
    rng = random.Random(seed)
    return [rng.getrandbits(64) for _ in range(k)]

def signature(friend_list, seeds):
    """For each of the k random orders, the friend that comes first (its hash value)."""
    return [min(mix64(x ^ s) for x in friend_list) for s in seeds]

def jaccard(a, b):
    """Shared friends / everyone either knows."""
    return len(a & b) / len(a | b)

def estimate_jaccard(sig_a, sig_b):
    return sum(x == y for x, y in zip(sig_a, sig_b)) / len(sig_a)

def estimate_mutual(j, len_a, len_b):
    """|A & B| from J: J = m / (|A| + |B| - m)  =>  m = J (|A| + |B|) / (1 + J)."""
    return j * (len_a + len_b) / (1 + j)

The math, step by step: why the first friends agree with probability J, and how noisy the estimate is

Step 1: list it out once. Take A = {1, 2, 3} and B = {2, 3, 4}. They share 2 and 3, and together contain 1, 2, 3, 4, so \(J = 2/4\). Order 1, 2, 3, 4 at random. If 2 or 3 comes first among them, it is the first member of both sets: agree. If 1 comes first, A's first is 1 and B's is not: differ. If 4 comes first, the same the other way. Each of the four is first with chance 1/4, so they agree with chance 2/4 = J.

Step 2: the general argument. Write the min-hash of a set as \(h_\pi(A) = \min_{x \in A} \pi(x)\), the position of its earliest member under the order π. Let \(x^{*}\) be the earliest element of \(A \cup B\). By symmetry each element of \(A \cup B\) is equally likely to be \(x^{*}\), with chance \(1/|A \cup B|\).

  • If \(x^{*}\) is in both sets, it comes before every other member of each, so both min-hashes equal \(\pi(x^{*})\): they agree.
  • If \(x^{*}\) is only in A, then \(h_\pi(A) = \pi(x^{*})\) is smaller than the position of every member of B: they differ. "Only in B" is the same.

So they agree exactly when \(x^{*} \in A \cap B\), which has probability \(|A \cap B|/|A \cup B| = J\).

Step 3: the estimate and its noise. With k independent orders, let \(Z_i = 1\) if the i-th min-hashes agree. Each \(Z_i\) is 1 with probability J, independently, so its variance is \(J(1-J)\). The estimate is their average:

\[ \hat J = \frac1k \sum_{i=1}^k Z_i, \qquad \mathbb E[\hat J] = J, \qquad \operatorname{Var}(\hat J) = \frac{1}{k^2}\cdot k \cdot J(1-J) = \frac{J(1-J)}{k} . \]

The typical error is the square root, \(\sqrt{J(1-J)/k}\). At \(J = 0.1\) and \(k = 100\) that is \(\sqrt{0.09/100} = 0.03\). Halving it costs four times the hashes, as the table shows.

Step 4: back to a count. \(J = m/(|A| + |B| - m)\) where m is the mutual count. Solve for m: \(J(|A| + |B|) - Jm = m\), so \(m = J(|A| + |B|)/(1 + J)\). An error in \(\hat J\) is multiplied by about \((|A| + |B|)/(1+J)^2\), which is why long lists turn a small error in J into a large one in the count.

What was proved. One random order makes two min-hashes agree with probability exactly J; averaging k orders gives an unbiased estimate with variance \(J(1-J)/k\).

11 · LSH: find high-overlap pairs without comparing all pairs

The situation. Signatures make one comparison cheap, but 10,000 users still make about 50 million pairs, and a billion users about \(5 \times 10^{17}\). We want only the high-overlap pairs, found by putting people into buckets instead of comparing them.

The idea. Cut each signature of k numbers into b bands of r numbers. For each band, put every user into a bucket labelled by that band's r numbers. Two users become a candidate pair if they share a bucket in at least one band. Matching a whole band is unlikely unless two people overlap a lot (a narrow door), and b bands give them many chances (many doors). This is locality-sensitive hashing (LSH). A pair agrees on one band with probability \(J^r\), so it becomes a candidate with probability \(1 - (1 - J^r)^b\), an S-shaped curve whose step sits near \((1/b)^{1/r}\).

code/day_1/minhash.py · banding and the S-curve
def lsh_candidates(sigs, r, b):
    """Cut each signature into b bands of r values. Two users are a candidate pair if they agree
    on a whole band. Returns (candidate pairs, pairs emitted by the buckets before de-duplication)."""
    pairs, emitted = set(), 0
    for band in range(b):
        buckets = defaultdict(list)
        for u, sig in sigs.items():
            buckets[tuple(sig[band * r:(band + 1) * r])].append(u)
        for members in buckets.values():
            emitted += len(members) * (len(members) - 1) // 2
            for i, x in enumerate(members):
                for y in members[i + 1:]:
                    pairs.add((min(x, y), max(x, y)))
    return pairs, emitted

def s_curve(j, r, b):
    """P(a pair with Jaccard j becomes a candidate) = 1 - (1 - j^r)^b."""
    return 1 - (1 - j ** r) ** b

Interview takeaway
  • "MinHash makes overlap cheap to compare: k numbers per user, error \(\sqrt{J(1-J)/k}\). LSH banding finds high-overlap pairs by bucketing: choose r and b to place the step at the similarity you care about, then check candidates exactly."
  • Follow-ups: "how big should k be?" (from the error you can tolerate at the J you care about); "a huge bucket" (one hub with a small hash puts all its friends together: cap bucket size); "lists change" (a new friend updates a signature in k steps by keeping the smaller hash; a removed friend forces a recompute).

In one line. A random order's first friend agrees with probability J, so k orders give a fixed-size signature; banding turns "find similar pairs" into "find people in the same bucket".

The math, step by step: the S-curve and where its step is

Step 1: one position. By the MinHash result, one signature position agrees with probability J, and positions use independent hashes.

Step 2: one band. A band agrees only if all r of its positions agree: \(J^r\). With \(r = 2\) and \(J = 0.1\), that is 0.01.

Step 3: all bands. The pair is missed only if every one of the b bands fails, each with probability \(1 - J^r\), independently:

\[ P(\text{candidate}) = 1 - (1 - J^r)^b . \]

With \(r = 2\), \(b = 50\), \(J = 0.1\): \(1 - 0.99^{50} = 1 - 0.605 = 0.395\), the value in the chart.

Step 4: where the step is. Try \(J^r = 1/b\): the probability is \(1 - (1 - 1/b)^b \approx 1 - 1/e \approx 0.63\). To find the steepest point, differentiate \(f(J) = 1 - (1 - J^r)^b\):

\[ f'(J) = b\,r\,J^{r-1}(1 - J^r)^{b-1} . \]

Set the derivative of \(\ln f'\) to zero:

\[ \frac{r-1}{J} - \frac{(b-1)\,r\,J^{r-1}}{1 - J^r} = 0 \;\Rightarrow\; J^r = \frac{r-1}{rb-1} . \]

For large b, \((r-1)/(rb-1) \approx (1 - 1/r)/b\), the same size as \(1/b\): the step is near \((1/b)^{1/r}\).

Step 5: the two errors. A pair well below the step becomes a candidate with probability about \(b\,J^r\) (since \(1 - (1-x)^b \approx bx\) for small x). A pair above it is missed with probability \((1 - J^r)^b\). With \(r = 2\), \(b = 50\): a pair at \(J = 0.02\) slips through with chance about \(50 \times 0.0004 = 0.02\); a pair at \(J = 0.3\) is missed with chance \(0.91^{50} \approx 0.009\).

What was proved. Banding catches a pair of similarity J with probability \(1 - (1 - J^r)^b\); more rows sharpen the step, more bands move it left.

A solution, with the sorted follow-up
code/day_1/lc349.py
def intersection(nums1, nums2):
    """Hash set: build a set from one array, probe it with the distinct values of the other.
    O(n + m) time, O(min(n, m)) extra space if we build the set from the shorter one."""
    if len(nums1) > len(nums2):
        nums1, nums2 = nums2, nums1
    small = set(nums1)
    return [x for x in set(nums2) if x in small]

def intersection_sorted(nums1, nums2):
    """Follow-up "what if both are sorted?": two pointers, O(1) extra space besides the answer."""
    i = j = 0
    out = []
    while i < len(nums1) and j < len(nums2):
        if nums1[i] < nums2[j]:
            i += 1
        elif nums1[i] > nums2[j]:
            j += 1
        else:
            if not out or out[-1] != nums1[i]:   # skip repeats: each value once
                out.append(nums1[i])
            i += 1; j += 1
    return out

The output must hold each value once, so the hash version probes with the distinct values of the longer array, and the merge skips a value equal to the last one written.
