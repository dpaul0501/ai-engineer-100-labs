DAY 1 · TEXT AS DATAMLDSAAI

What text looks like to a counter

BPE only ever counts things. Today: how text is distributed (ML), how to count it correctly and fast (algorithms), and how to cut it into the pieces that get counted (design).

ML · Zipf's law and the long tail

In natural language, the word of frequency rank r appears roughly in proportion to 1/rs with s near 1: a straight line on a log–log plot. A few words are everywhere; most words are rare. On Alice in Wonderland (37,404 words, 3,218 distinct):

Share of Alice covered by its most frequent words
top 10 words26%
top 10064%
top 1,00091%
Meanwhile 1,479 words (46% of the distinct words) appear exactly once: the long tail.

This shape is why BPE works. A small vocabulary already covers most of the text, so the first merges buy a lot of compression. The long tail can never get its own tokens (there is no data to learn them from), so rare words must be built from shared pieces.

Practice
  • Count the words of alice.txt (lower-case, letters and apostrophes), sort the counts, and plot log rank against log frequency.
  • Fit a straight line by least squares and report the slope.
Problem variations
  • Repeat on Hindi text and on Python code. Is the slope steeper or flatter, and why?
  • Heaps' law: plot the number of distinct words against corpus size as you read more of the book. How fast does the vocabulary grow?
  • Do the same for chunks (the pattern's output) instead of words. How do leading spaces change the picture?
Solution
zipf.py
import math, re
from collections import Counter

def zipf_slope(words):
    freqs = sorted(Counter(words).values(), reverse=True)
    xs = [math.log(r) for r in range(1, len(freqs) + 1)]
    ys = [math.log(f) for f in freqs]
    mx, my = sum(xs) / len(xs), sum(ys) / len(ys)
    return sum((x - mx) * (y - my) for x, y in zip(xs, ys)) / sum((x - mx) ** 2 for x in xs)

words = [w.lower() for w in re.findall(r"[A-Za-z']+", open("data/alice.txt").read())]
print(zipf_slope(words))    # -1.23 on alice.txt

A slope of −1.23 means frequency falls a little faster than 1/r. The fit is dominated by the long tail of words seen once or twice, which form the flat steps at the bottom right of the plot; fitting only the top 1,000 ranks gives −1.12, closer to the classic −1.

Algorithms · UTF-8, hash maps, sliding windows

UTF-8: the 256-symbol alphabet

UTF-8 writes each Unicode character as 1–4 bytes. The first byte says how many follow:

Hash maps and counters

A hash map stores key → value with average O(1) get and set. Python's Counter is one whose missing keys read as 0. Keys must be immutable: the tuple (97, 116) works as a pair key, a list doesn't.

The size-2 sliding window

A window of size k over a list of length n has n − k + 1 positions; with k = 2 they are the adjacent pairs, zip(w, w[1:]). Windows overlap: [a, a, a] has two (a, a) windows, but only one merge fits.

393 · 187 · BPE variation
def validUtf8(data):                              # 393
    need = 0                                      # continuation bytes still expected
    for b in data:
        b &= 0xFF
        if need:
            if b >> 6 != 0b10: return False
            need -= 1
        elif b >> 7 == 0: continue
        elif b >> 5 == 0b110: need = 1
        elif b >> 4 == 0b1110: need = 2
        elif b >> 3 == 0b11110: need = 3
        else: return False
    return need == 0

def findRepeatedDnaSequences(s):                  # 187
    seen = Counter(s[i:i + 10] for i in range(len(s) - 9))
    return [k for k, c in seen.items() if c > 1]

def most_frequent_pair(ids):                      # the BPE variation
    c = Counter(zip(ids, ids[1:]))
    return min(c, key=lambda p: (-c[p], p)) if c else None

assert most_frequent_pair([1, 2, 1, 2, 3, 3]) == (1, 2)

All three are O(n) time. 187 uses O(n) space for the window strings; rolling a 20-bit hash of the 10 letters makes each window O(1).

Design · the pre-tokenization pattern

Before BPE counts anything, a regular expression cuts text into chunks, and merges never cross a chunk boundary. Without it, BPE learns accidental tokens like t␣s (the end of one word, the start of the next) and separate tokens for dog., dog, and dog!.

GPT-2 pre-tokenization pattern
'(?:[sdmt]|ll|ve|re)| ?\p{L}+| ?\p{N}+| ?[^\s\p{L}\p{N}]+|\s+(?!\S)|\s+      # GPT-2
PieceMatchesDecision
'(?:[sdmt]|ll|ve|re)'s 'llContractions become shared pieces
?\p{L}+ catA word keeps its leading space: one token per word, not two
?\p{N}+ 2024Digits never merge with letters, but any length is allowed
?[^\s\p{L}\p{N}]+{" !!Punctuation runs
\s+(?!\S), \s+whitespaceLeaves the last space for the next word

\p{L} is "any letter". Unicode also has marks (\p{M}), characters that attach to the one before: Hindi vowel signs like ा and ै, combining accents. GPT-2's pattern leaves them out, so it cuts most Hindi words in two, and BPE can never merge them back. That alone explains part of the 90-token Hindi sentence. o200k_base includes \p{M} and caps digit groups at 3 (\p{N}{1,3}, as cl100k_base also does).

Solution
pattern with marks and digit groups
PATTERN = regex.compile(r"""'(?:[sdmt]|ll|ve|re)| ?[\p{L}\p{M}]+| ?\p{N}{1,3}| ?[^\s\p{L}\p{M}\p{N}]+|\s+(?!\S)|\s+""")
PATTERN.findall("मैं घर जा रहा हूँ, I paid 12345 rupees!")
# ['मैं', ' घर', ' जा', ' रहा', ' हूँ', ',', ' I', ' paid', ' 123', '45', ' rupees', '!']

Two edits: add \p{M} to the letter class (and to the excluded set of the punctuation rule, or marks would also match there), and cap digits with {1,3}. Note that 12345 becomes 123 + 45, grouped from the left; some designs group from the right to match thousands separators.
