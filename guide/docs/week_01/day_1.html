Algorithms · storing, walking, counting, intersecting, top-k

1 · Storing the friendships

The situation. suggest asks two questions over and over. "Who are this person's friends?" is asked once for You and once for each of your friends. "Is this person already your friend?" is asked for every person the loops arrive at. The storage has to make both fast, on 10,000 users today and on far more later.

The obvious thing: a table. Make one row and one column per person, and tick the cell where two people are friends. For the six people that is 36 cells with 14 ticks (each friendship is ticked twice, once in each person's row). "Is Dev your friend?" is one look at one cell. But "who are Farid's friends?" means reading all six cells of Farid's row to find one tick. On the week's graph a row has 10,000 cells and about 20 ticks, so 99.8% of the table says "not friends". The whole table is 100 million cells: 100 MB at one byte per cell. The same counting on such a table, scanning rows, took 3.2 ms per user against 0.26 ms with lists of sets, because it read 178,700 cells per request to find 1,143 entries that mattered.

The idea: write down only the ticks. Give each person a list of their friends, nothing else. This is called an adjacency list (two people who are friends are adjacent). Each friendship appears in two lists, so the six people need 14 entries and the week's graph 200,000. There are two good ways to keep each list:

  • As a hash set (Python's set): "is Dev in Ben's list?" is answered in one step on average, and adding a friend is cheap. This is what the reading used.
  • As a sorted array of ids: compact, and "is Dev in the list?" is a binary search.

Take the sorted-array choice to its end and you get CSR (compressed sparse row). Glue all the sorted lists together, in user order, into one long array indices. A second array indptr says where each person's run starts. Your friends are the run from indptr[You] up to indptr[Ben], Ben's run starts where yours ends, and so on. For the six people:

pymk/graph.py · CSR
from bisect import bisect_left

def build_csr(n, edges):
    """Compressed sparse row form of an undirected graph:
    the friends of u are indices[indptr[u]:indptr[u + 1]], sorted ascending."""
    deg = [0] * n
    for u, v in edges:
        deg[u] += 1; deg[v] += 1
    indptr = [0] * (n + 1)
    for u in range(n):
        indptr[u + 1] = indptr[u] + deg[u]             # prefix sums: where each row starts
    fill = indptr[:-1]                                 # a copy: next free slot in each row
    indices = [0] * indptr[n]
    for u, v in edges:                                 # each edge is written into both rows
        indices[fill[u]] = v; fill[u] += 1
        indices[fill[v]] = u; fill[v] += 1
    for u in range(n):
        indices[indptr[u]:indptr[u + 1]] = sorted(indices[indptr[u]:indptr[u + 1]])
    return indptr, indices

def neighbors(indptr, indices, u):                     # O(1) to find, O(deg u) to read
    return indices[indptr[u]:indptr[u + 1]]

def is_friend(indptr, indices, u, v):                  # binary search in u's row: O(log deg u)
    lo, hi = indptr[u], indptr[u + 1]
    i = bisect_left(indices, v, lo, hi)
    return i < hi and indices[i] == v

CSR is 14 times smaller than even a table of single bits, and 22 times smaller than Python sets. The sets buy speed: on 200,000 random pairs, "is v a friend of u?" took 94 ns with a set and 553 ns with a pure-Python binary search on CSR. At a billion users the gap stops being a detail: the bit table alone would be 125 petabytes, while CSR stays proportional to the number of friendships.

When to use which. Lists of hash sets when the graph changes often and you check membership a lot. CSR for a read-mostly snapshot: rows are contiguous, so reading a friend list is one sweep through memory, and it is the smallest. The table only for small, dense graphs, where most pairs are connected. In an interview, say "adjacency list", say why the matrix fails (memory grows with the square of the users, and listing friends costs a full row), and mention CSR for a compact snapshot.

In one line. Store only the friendships that exist; a table stores every pair that doesn't.

The math, step by step: how big each layout is, and why the CSR build is correct

Counting the entries. First, how many entries does an adjacency list have? In the six-person graph, the friend counts are You 2, Ben 4, Chloe 4, Dev 1, Esha 2, Farid 1. They add up to 14, which is twice the 7 friendships. That is no accident: each friendship adds one entry to each of its two people's lists. Now in symbols. Write n for the number of users, \(|E|\) for the number of friendships, and \(d_u\) for the number of friends of user u (we call it the degree of u). Each friendship adds 1 to exactly two degrees, so

\[ \sum_{u} d_u = 2|E| . \]

This is the handshake lemma. For the week's graph, \(2 \times 100{,}000 = 200{,}000\) entries.

Memory of each layout. The table has one cell per ordered pair: \(n^2\) cells, whatever \(|E|\) is. At one bit per cell that is \(n^2/8\) bytes; for \(n = 10{,}000\), \(10^8/8 = 12.5\) million bytes. CSR has \(n + 1\) offsets and \(2|E|\) ids. With 8-byte offsets and b-byte ids it takes \(8(n+1) + 2|E|\,b\) bytes; for the week's graph with \(b = 4\), \(8 \times 10{,}001 + 200{,}000 \times 4 = 80{,}008 + 800{,}000\) bytes, the 0.88 MB measured.

The fraction of ticks. Of the \(n^2\) cells, \(2|E|\) are ticked: \(200{,}000 / 10^8 = 0.2\%\). So 99.8% of the table records "not friends".

The running totals. User u's run in indices starts after all earlier users' runs, so its start is the sum of their degrees:

\[ \texttt{indptr}[0] = 0, \qquad \texttt{indptr}[u+1] = \texttt{indptr}[u] + d_u, \qquad \texttt{indptr}[n] = \textstyle\sum_u d_u = 2|E| . \]

With the six degrees 2, 4, 4, 1, 2, 1 this gives 0, 2, 6, 10, 11, 13, 14, the array in the figure.

Why build_csr puts every entry in the right run. The code sets a cursor fill[u] = indptr[u] for each user. Each friendship (u, v) writes v at fill[u] and moves that cursor one step, and writes u at fill[v] and moves that one. User u takes part in exactly \(d_u\) friendships, so their run receives exactly \(d_u\) writes, at positions indptr[u], indptr[u] + 1, …, indptr[u] + d_u − 1. The last of these is indptr[u+1] − 1, so the writes fill the run exactly and never spill into the next one. Sorting each run afterwards makes binary search valid. (This is a counting sort, keyed by user.)

2 · Walking the graph: breadth-first search

The situation. "Friends of friends" means "people two steps away". To find them, the code walks: from You to each friend, and from each friend to each of their friends.

The obvious thing: follow every step. From You, step to Ben and to Chloe; from each, step to all their friends. That gives 8 two-step walks: You → Ben → {You, Chloe, Dev, Esha} and You → Chloe → {You, Ben, Esha, Farid}. Only three of them reach someone new, Dev, Esha and Farid, and Esha is reached twice. You is reached twice too, and Ben and Chloe each once. On the week's graph a user has 1,477 two-step walks on average. Keep walking further and it never ends: Ben → Chloe → Ben → Chloe … goes round forever. To walk the whole graph, you have to remember who you have already seen.

The idea: visit in rings, and mark people when you first see them. Start at You. Ring 1 is everyone one step away. Ring 2 is everyone one step from ring 1 who has not been seen yet. Keep a queue, first in, first out, so that ring 1 is finished before ring 2 starts. Each person gets a label, their ring number, the moment they are first seen, and nobody is added twice. This is breadth-first search (BFS). The ring number is the person's distance from you: the fewest steps it takes to reach them.

pymk/graph.py · BFS
from collections import deque

def bfs(adj, s, max_depth=None):
    """dist[v] = fewest hops from s to v, for every v within max_depth hops of s."""
    dist = {s: 0}
    queue = deque([s])
    while queue:
        x = queue.popleft()
        if max_depth is not None and dist[x] == max_depth:
            continue                                   # reached the limit: do not expand x
        for y in adj[x]:
            if y not in dist:                          # mark on discovery: y enters the queue once
                dist[y] = dist[x] + 1
                queue.append(y)
    return dist

def components(adj):
    """Number of connected components and a component label for every vertex."""
    label, c = [-1] * len(adj), 0
    for s in range(len(adj)):
        if label[s] == -1:
            for v in bfs(adj, s):
                label[v] = c
            c += 1
    return c, label

When to use it. BFS when you need distances, "fewest steps", or everyone within L steps (a depth-limited search, the max_depth argument). Swap the queue for a stack and you get depth-first search, which reaches the same people but does not give distances; for "can I get from A to B?" either works. Interviewers listen for two things: mark a person when you first see them, not when you take them from the queue, or they enter the queue many times; and the cost is proportional to users plus friendships.

In one line. suggest is a two-step BFS that counts how often it arrives at each person instead of marking them once.

The math, step by step: BFS labels are true distances, and what a two-step walk costs

Three claims, each proved in turn. Write \(\ell(v)\) for the label BFS gives v, and \(\mathrm{dist}(s, v)\) for the true fewest number of steps from the start s to v.

(a) The queue stays in order. We want: labels in the queue, front to back, never go down, and the last is at most the first plus 1. Check it on the trace: after taking Ben the queue is Chloe (1), Dev (2), Esha (2). In general: it holds at the start, with only s. Each step removes the front, with label ℓ, and appends people with label ℓ + 1. The labels left behind are all at least ℓ, and the old back label was at most ℓ + 1, so the order is kept and the spread is still at most 1. Consequence: people leave the queue in order of their labels.

(b) A label is never too small. Each label is the length of a real walk from s (follow the chain of who discovered whom back to s), and a walk is at least as long as the shortest one. So \(\ell(v) \ge \mathrm{dist}(s, v)\).

(c) A label is never too large. Suppose some person has a label that is too large. Among all such people, pick one, v, closest to s, at true distance k. Let x be the person just before v on a shortest path, so \(\mathrm{dist}(s, x) = k - 1\); x is closer than v, so by the choice of v its label is right: \(\ell(x) = k - 1\). When x left the queue, either v had not been seen, and then it got label \(k\); or v had been seen from some x′ that left the queue earlier, so by (a) \(\ell(x') \le \ell(x) = k-1\) and \(\ell(v) = \ell(x') + 1 \le k\). Either way \(\ell(v) \le k\), which contradicts "too large". With (b), every label equals the true distance.

Cost. Each person enters and leaves the queue once. When a person leaves, their friend list is read once, and the lists together have \(\sum_x d_x = 2|E|\) entries (the handshake lemma). So BFS costs O(\(n + |E|\)) time and O(n) memory for the labels and the queue. People never seen are in another component; starting a fresh BFS from each unlabelled person finds all components.

A two-step walk. Stopping at depth 2 means expanding only You (read \(d_u\) entries) and your friends (read each friend's list). Write \(W(u)\) for the total length of your friends' lists. Then

\[ \text{entries read} = d_u + \sum_{f \text{ a friend of } u} d_f = d_u + W(u). \]

For You: \(d = 2\), and Ben and Chloe have 4 friends each, so \(2 + 8 = 10\) entries. This is exactly the work of suggest, whose inner loop reads \(W(u)\) entries.

What this shows. BFS labels everyone with their true distance, in time proportional to users plus friendships; and a two-step search costs your friend count plus the sum of your friends' friend counts.

3 · Counting with a hash map

The situation. The two-step walk arrives at Esha twice, once through Ben and once through Chloe. Each arrival is one mutual friend. We need to turn arrivals into counts.

The obvious things. One: write every arrival in a list, sort it, and count runs of equal names. That sorts 1,477 arrivals on average to count them. Two: keep an array with one counter per user and add 1 on each arrival. For six people that is fine. At a billion users it means preparing a billion counters, and then scanning them for the non-zero ones, to record about 1,500 arrivals.

The idea: a counter that only has room for the people you reach. A hash map (Python's dict, or Counter) stores a key and its count at a slot chosen by a hash of the key, so finding or adding a key takes one step on average, and its size follows the number of keys stored, not the number of users. pymk/exact.py · mutual counts
from collections import Counter

def mutual_counts(adj, u):
    """count[v] = |N(u) & N(v)| for every v that shares a friend with u.
    (u itself and u's friends can appear; the caller filters them.)"""
    count = Counter()
    for f in adj[u]:
        for v in adj[f]:                               # v is a friend of f, so f is a mutual friend
            count[v] += 1
    return count

Measured on the week's graph. Counting for all 10,000 users took 3.4 s: 0.34 ms per user, 232 ns per arrival. A user's loops make 1,477 arrivals on average, landing on 1,191 different people on average (median 888, at most 8,271). Most candidates are reached through just one mutual friend.

What the number means. The work is the number of arrivals, and the number of arrivals is the sum of your friends' friend counts. It does not depend on how many friends you have, but on how many they have. Keep that in mind; it is where the week goes next.

In one line. A hash map counts in one step per arrival and only remembers the people actually reached.

The math, step by step: why a hash map is one step on average, and why the count is the mutual-friend count

What a lookup costs. A hash table has M slots and puts key x at slot h(x), where h is a hash function. Two keys can land in the same slot (a collision); a lookup for x then has to look past the other keys in x's slot. How many are there? Model h as sending every key to a random slot, independently. Say the table holds K keys. Each other key lands in x's slot with probability 1/M, and there are K − 1 other keys, so the expected number of keys sharing the slot is

\[ \sum_{y \ne x} P\big(h(y) = h(x)\big) = \frac{K - 1}{M} < \alpha, \qquad \alpha = \frac{K}{M}. \]

The ratio α is the load factor. With 1,000 keys in 2,000 slots, α = 0.5: a lookup inspects its slot plus, on average, less than half of one other key. So a lookup or insert is O(1 + α) on average.

Keeping α small. The table doubles M when it gets full and copies every key across. One copy is expensive, but they are rare. After K inserts the copies have moved at most \(K + K/2 + K/4 + \dots < 2K\) keys in total, so each insert pays for at most two copies: O(1) per insert, averaged over the whole run ("amortized").

Why the count is right. The loops do count[v] += 1 once for each pair (friend f of u, friend v of f). So after the loops, count[v] is the number of friends f of u who have v as a friend. Friendship goes both ways, so "v is a friend of f" is the same as "f is a friend of v". Writing \(N(u)\) for the set of u's friends:

\[ \texttt{count}[v] = \big|\{ f : f \in N(u) \text{ and } f \in N(v) \}\big| = |N(u) \cap N(v)| . \]

That is the number of mutual friends, which we write \(m(u, v)\).

The same count as a matrix product. Put the table of section 1 into a matrix A, with \(A_{uf} = 1\) if u and f are friends and 0 otherwise. The entry \((A^2)_{uv} = \sum_f A_{uf} A_{fv}\) adds 1 for each f that is a friend of both, so \((A^2)_{uv} = m(u, v)\). For You and Esha: \(A_{\text{You},f} A_{f,\text{Esha}}\) is 1 for f = Ben and Chloe and 0 for everyone else, giving 2. This independent definition is what the differential test in the Delivery block checks against.

Cost. \(W(u) = \sum_{f \in N(u)} d_f\) updates at O(1) on average each, plus \(d_u\) to read your own list: O(\(d_u + W(u)\)) time, and memory for at most \(\min(W(u), n)\) keys.

What this shows. The counter holds exactly the mutual-friend count for every person reached, in time proportional to the number of arrivals.

4 · Comparing two friend lists: set intersection, three ways

The situation. You open Esha's profile and the app says "2 mutual friends: Ben and Chloe". That is one pair, not a ranking. The job is to find the people who are in both your friend list and hers: the intersection of two lists. Take a bigger example, with sorted ids: A = [3, 9, 14, 20] and B = [1, 3, 4, 7, 9, 12, 15, 20, 22, 30]. The answer is [3, 9, 20].

The obvious thing: compare everything with everything. For each id in A, scan all of B: 4 × 10 = 40 comparisons here. A user with 20 friends against the most popular user on the week's graph (a hub), who has 1,480, is 29,600 comparisons to find a handful of matches.

Way 1 · Hash: look each one up. If the larger list is a hash set, go through the smaller list and ask "is this one in the set?". That is one lookup per element of the smaller list: 4 lookups for the example. Go through the smaller list; going through the larger one would cost its length instead.

Way 2 · Merge: walk two sorted lists together. Put a finger at the start of each list. If A's finger points at the smaller number, that number cannot be in B (everything left in B is bigger), so move A's finger. If B's is smaller, move B's. If they are equal, write it down and move both.

1–23vs1→3vs31 < 3: move B's finger. Then equal: output 3
3–59vs479skip 4 and 7 in B; equal: output 9
6–714vs1215skip 12; then 14 < 15, so 14 is not in B: move A's finger
8–920vs1520skip 15; equal: output 20. A is used up: stop after 9 steps (the lengths add to 14)

Every step moves a finger, so merging takes at most the two lengths added together, and it reads both lists front to back, which memory handles best.

Way 3 · Gallop: leap through the long list. When one list is far longer, merging walks through nearly all of it to find a few matches. Instead, for each id in the short list, leap ahead in the long list from where you last stopped, doubling the leap each time (1, 2, 4, 8 places), until you overshoot; then binary-search the last leap. For 9 in the example, starting at position 2: look at 4 (too small), 7 (too small), 12 (past it), then search between 7 and 12 and find 9. The cost grows with the short list's length times the logarithm of how much longer the other one is.

pymk/sets.py · intersection three ways
from bisect import bisect_left

def intersect_hash(a, b):
    """a, b: hash sets. Expected O(min(|a|, |b|)) probes."""
    if len(a) > len(b):
        a, b = b, a                                    # loop over the smaller set
    return [x for x in a if x in b]

def intersect_merge(a, b):
    """a, b: sorted lists of distinct ids. At most |a| + |b| steps."""
    i = j = 0
    out = []
    while i < len(a) and j < len(b):
        if a[i] < b[j]:
            i += 1                                     # a[i] is smaller than all of b[j:], so not in b
        elif a[i] > b[j]:
            j += 1
        else:
            out.append(a[i]); i += 1; j += 1
    return out

def gallop(b, x, lo):
    """Smallest i >= lo with b[i] >= x (len(b) if none), in O(log(i - lo + 2)) comparisons."""
    hi, step = lo, 1
    while hi < len(b) and b[hi] < x:
        lo = hi + 1                                    # the answer is past hi
        hi += step
        step *= 2                                      # probe lo, lo+1, lo+3, lo+7, ...
    return bisect_left(b, x, lo, min(hi, len(b)))      # binary search the last gap

def intersect_gallop(a, b):
    """a, b: sorted lists of distinct ids. O(a log(b/a + 1)) for a = the smaller size."""
    if len(a) > len(b):
        a, b = b, a
    out, j = [], 0
    for x in a:
        j = gallop(b, x, j)                            # b[:j] < x: never look there again
        if j == len(b):
            break
        if b[j] == x:
            out.append(x); j += 1
    return out

The math, step by step: why merging is correct, what galloping costs, and why nothing can do much better

Write a for the shorter length and b for the longer, and \(A_i\), \(B_j\) for the elements under the two fingers.

Merge is correct. Both lists are sorted with no repeats. We show two facts stay true before every step. (P): everything already passed in either list, \(A[{:}i]\) and \(B[{:}j]\), is smaller than both \(A_i\) and \(B_j\). (Q): the output so far is exactly what \(A[{:}i]\) and \(B[{:}j]\) have in common. Both hold at the start, when nothing has been passed. Now take a step where \(A_i < B_j\). Everything passed in B is below \(A_i\) by (P), and everything not yet passed in B is at least \(B_j > A_i\). So \(A_i\) is nowhere in B, and moving past it without output keeps (Q); (P) still holds because \(A_i < B_j\). The case \(A_i > B_j\) is the mirror image. If \(A_i = B_j\), outputting it and moving both keeps (Q), and (P) holds because both lists strictly increase. When A runs out, (P) says nothing in A is in the unpassed part of B, so the common elements are exactly those found, which is (Q). Each step moves a finger, so there are at most \(a + b\) steps.

What galloping costs. Look at one element of the short list, and say its search moves the finger past \(g\) positions of B. The leaps probe 1, 3, 7, 15, … places ahead; to pass \(g\) places takes about \(\log_2(g+1)\) probes, plus one that overshoots, and the binary search of the last leap costs about as many again. So each element costs at most \(2\log_2(g_i + 1) + 4\) comparisons, where \(g_i\) is that element's jump. In the example, the search for 9 moves the finger past 4 and 7, so \(g = 2\) and it costs at most \(2\log_2 3 + 4 \approx 7.2\) comparisons. The finger only moves forward, so all the jumps together are at most b: \(\sum_i g_i \le b\). To bound the sum for any jumps, use the fact that the logarithm curves downward (it is concave), so the average of logs is at most the log of the average (Jensen's inequality):

\[ \sum_{i=1}^{a} \log_2(g_i + 1) \;\le\; a \log_2\!\Big(\frac{1}{a}\sum_i (g_i + 1)\Big) \;\le\; a \log_2\!\Big(\frac{b}{a} + 1\Big). \]

So galloping takes at most \(2a\log_2(b/a + 1) + 4a\) comparisons. When \(b \approx a\) that is a constant times a, like merging. When b is much larger than a it approaches \(a \log_2 b\), like a binary search per element. The measured counts stayed under this bound in every group.

No comparison method can do much better. Think about inputs where the two lists share nothing. To answer "nothing in common" correctly, a method must know, for each element of A, which two neighbouring elements of B it falls between. (If it did not, some other input with the same comparison results would put that element equal to one in B, and the answer would be wrong.) Knowing that for every element fixes the full interleaving of the two lists, and there are \(\binom{a+b}{a}\) possible interleavings. Each comparison has two outcomes, so c comparisons can tell at most \(2^c\) interleavings apart. Hence

\[ c \;\ge\; \log_2 \binom{a+b}{a} \;\ge\; \log_2\Big(\frac{a+b}{a}\Big)^{a} \;\ge\; a\log_2\frac{b}{a}. \]

The middle step uses \(\binom{N}{a} = \prod_{i=0}^{a-1}\frac{N-i}{a-i}\), where each factor is at least N/a.

What this shows. Merging is correct and costs at most \(a + b\); galloping costs at most \(2a\log_2(b/a+1) + 4a\); and any comparison method needs at least \(a\log_2(b/a)\), so galloping is within a constant factor of the best possible.

5 · Picking the best ten: top-k, three ways

The situation. A user has, on average, 1,191 candidates with counts (at most 8,271). The app shows ten. "Best" means most mutual friends, and for ties, the smaller id.

Way 1, the obvious thing · Sort them all. Sort every candidate, keep the first ten. It is correct, and in Python it took 483 µs per user on the week's graph. Most of that work puts thousands of candidates in an order nobody will see.

Way 2 · Keep a small pile of the best so far. Walk through the candidates once, keeping only the ten best seen so far, arranged so that the worst of the ten is always on top. Each new candidate is compared with that worst one. If it is not better, throw it away: one comparison. If it is better, it replaces the worst, and the pile reorders itself. The structure that keeps the smallest item on top and reorders in a few steps is a binary heap; Python's is heapq. Most candidates arrive, lose to the worst of the ten, and leave after one comparison.

Way 3 · Quickselect. Pick a random candidate as a pivot and split the rest into "better than the pivot" and "worse". If ten or more are better, the answer is among them: repeat there. If fewer, they are all in the answer, along with the pivot: keep them and look for the rest among the worse ones. Each round throws away a big share of the candidates. At the end, sort just the ten.

pymk/topk.py · three ways
import heapq
import random

def topk_sort(count, k):
    """O(C log C): sort every candidate, keep the first k."""
    return sorted(count, key=lambda v: (-count[v], v))[:k]

def topk_heap(count, k):
    """O(C log k) time, O(k) space: keep the k best seen so far in a min-heap."""
    heap = []                                          # items (m, -v); the root is the worst kept
    for v, m in count.items():
        item = (m, -v)
        if len(heap) < k:
            heapq.heappush(heap, item)
        elif item > heap[0]:                           # better than the worst kept: replace it
            heapq.heapreplace(heap, item)
    return [-nv for m, nv in sorted(heap, reverse=True)]

def topk_quickselect(count, k, seed=0):
    """O(C + k log k) expected: select the k best keys, then sort only those."""
    rng = random.Random(seed)
    keys = [(-m, v) for v, m in count.items()]         # distinct keys; smaller is better
    best = []
    while k > 0 and keys:
        p = rng.choice(keys)
        less = [x for x in keys if x < p]
        if len(less) >= k:
            keys = less                                # all k answers are below the pivot
        else:
            best += less + [p]                         # all of these are answers
            k -= len(less) + 1
            keys = [x for x in keys if x > p]
    return [v for _, v in sorted(best)]

The math, step by step: the cost of sorting, why the heap is correct and how often it changes, and quickselect's average

Write C for the number of candidates and k for how many we keep. Order candidates by the key (−m, id): smaller keys are better, and no two keys are equal because ids differ.

Sorting needs about C log₂ C comparisons. A comparison sort must be able to produce any of the C! orders of the candidates, and each comparison splits the possibilities in two, so it needs at least \(\log_2 C!\) comparisons. By Stirling's formula that is about \(C\log_2 C - 1.44\,C\). For the largest candidate set, C = 8,271, \(\log_2 C \approx 13.0\), so about 11.6 comparisons per candidate, against \(\log_2 10 \approx 3.3\) for a heap of ten.

The heap is correct. Claim: after looking at the first i candidates, the heap holds exactly the best \(\min(i, k)\) of them. It is true while the heap is filling. Suppose it is true and the heap is full. Its top, r, is the k-th best of the first i. A new candidate x that is worse than r is beaten by k candidates already seen, so it is not in the top k of the first i + 1, and leaving the heap unchanged is right. If x beats r, the new top k is the old top k with r replaced by x, which is exactly what the code does.

How often the heap changes. In a random order, when is the i-th candidate put in? Exactly when it is among the best k of the first i. Every one of those i is equally likely to be any rank, so for i > k this happens with probability k/i. Try it with k = 10: the 20th candidate goes in with probability 10/20 = 1/2, the 1,000th with probability 1/100. Adding these up, the expected number of insertions is

\[ k + \sum_{i=k+1}^{C} \frac{k}{i} \;\approx\; k\Big(1 + \ln\frac{C}{k}\Big). \]

For C = 1,191 and k = 10 that is \(10(1 + \ln 119.1) \approx 57.8\); averaged over the week's users it predicts 54.0, and 53.6 was measured. Each insertion costs O(log k), every other candidate one comparison, so the total is about C + (a few dozen) × log k.

Quickselect averages a constant per candidate. One round over s keys costs at most 2s comparisons (the code makes two passes). Call a round good if the pivot's rank lands in the middle half, between s/4 and 3s/4. A random pivot is good with probability 1/2, so on average it takes two rounds to get one, and after a good round at most 3s/4 keys remain. So shrinking from s keys to 3s/4 costs at most 2 × 2s = 4s comparisons on average. Adding the shrinking sizes,

\[ E[\text{comparisons}] \;\le\; 4C\Big(1 + \tfrac34 + \big(\tfrac34\big)^2 + \cdots\Big) = 4C \cdot \frac{1}{1 - 3/4} = 16\,C, \]

plus k log k to sort the answer. The measured 4.27 per candidate is well under 16. The worst case, a bad pivot every round, costs C², and random pivots make it vanishingly unlikely.

What this shows. Sorting pays about log₂ C per candidate; a size-k heap is correct and, in random order, changes only about k(1 + ln(C/k)) times; quickselect costs at most 16 comparisons per candidate on average.

1 · More mutual friends, more likely friends?

The situation. The reading found that 53% of new friendships had at least one mutual friend. suggest goes further: it assumes two mutual friends beat one, and five beat two. Is that true?

The obvious thing: count new friendships by their number of mutual friends. Split the week's friendships by when they formed: the first 80,000 are the past, the last 20,000 the future. For each future friendship, count its mutual friends in the past graph. 9,355 had none, 7,057 had one, and only 2,042 had two. Read that way, having no mutual friends is the best sign of all. That is wrong, and the reason is the most useful idea in this block: it ignores how many pairs had the chance. In the past graph, 45.9 million non-friend pairs have no mutual friend; only 343,961 have two. A count of successes means nothing without the count of chances.

The idea: successes divided by chances. For each number of mutual friends m, take all the pairs who were not friends in the past and had m mutual friends (the chances), and see what share of them became friends in the future (the successes):

\[ \hat p_m = \frac{\text{pairs with } m \text{ mutual friends that became friends}}{\text{all non-friend pairs with } m \text{ mutual friends}} . \]
pymk/closure.py · the closure curve
from collections import Counter

def closure_curve(n, past, future):
    """N[m]: non-friend pairs with m mutual friends in the past graph.
    F[m]: how many of those pairs became friends in the future."""
    adj = [set() for _ in range(n)]
    for u, v in past:
        adj[u].add(v); adj[v].add(u)
    fut = {(min(u, v), max(u, v)) for u, v in future}
    N, F = Counter(), Counter()
    for u in range(n):
        count = Counter()
        for f in adj[u]:
            for v in adj[f]:
                if v > u and v not in adj[u]:          # each unordered pair once, non-friends only
                    count[v] += 1
        for v, m in count.items():
            N[m] += 1
            F[m] += (u, v) in fut
    N[0] = n * (n - 1) // 2 - len(past) - sum(N.values())   # every other non-friend pair has m = 0
    F[0] = len(fut) - sum(F.values())
    return N, F

The math, step by step: why successes over chances is the right estimate, and how sure we are

The model. We pretend each pair in a row is a coin flip: it becomes a friendship with the same unknown chance p, independently of the others. Write N for the number of pairs in the row and F for how many became friends. For the row m = 2, N = 343,961 and F = 2,042.

The most likely p. The probability of exactly the outcomes we saw is \(p\) for each success and \(1 - p\) for each failure, multiplied together. This is the likelihood, and taking logs turns the product into a sum:

\[ L(p) = p^{F}(1-p)^{N-F}, \qquad \log L(p) = F\log p + (N-F)\log(1-p). \]

The best p is the one that makes what we saw most probable (the maximum-likelihood estimate). At the top of the curve the slope is zero, so differentiate and set it to zero:

\[ \frac{F}{p} - \frac{N-F}{1-p} = 0 \;\Longrightarrow\; F(1-p) = (N-F)\,p \;\Longrightarrow\; F = Np \;\Longrightarrow\; \hat p = \frac{F}{N}. \]

The second derivative, \(-F/p^2 - (N-F)/(1-p)^2\), is negative, so this is a maximum. For m = 2: \(\hat p = 2{,}042 / 343{,}961 = 0.00594\), the 0.594% in the table. So the obvious estimate, successes over chances, is also the most likely one.

How far off can it be? F is a sum of N coin flips, each 1 with chance p. One flip has mean p and variance \(p(1-p)\); for independent flips both add up, so \(E[F] = Np\) and \(\mathrm{Var}(F) = Np(1-p)\). Dividing by N:

\[ E[\hat p] = p, \qquad \mathrm{Var}(\hat p) = \frac{p(1-p)}{N^2} \cdot N = \frac{p(1-p)}{N}, \qquad \mathrm{SE} = \sqrt{\frac{\hat p(1-\hat p)}{N}} . \]

The estimate is right on average (unbiased), and its typical error, the standard error SE, shrinks like \(1/\sqrt{N}\). For m = 2: \(\sqrt{0.00594 \times 0.99406 / 343{,}961} = 0.000131\). When there are plenty of successes and failures (here at least 24 successes in every row), \(\hat p\) is close to normally distributed, so \(\hat p \pm 1.96\,\mathrm{SE}\) is an approximate 95% interval: \(0.00594 \pm 0.00026\), the 0.568–0.619% in the table.

Cost of the measurement. Listing every pair is \(10{,}000 \times 9{,}999 / 2 \approx 50\) million pairs. Instead the code runs the two-step count from every user u, keeping only v > u so each pair is seen once, which touches only the 4 million pairs with at least one mutual friend. The m = 0 row is everything else: \(N_0 = \binom{n}{2} - (\text{past friendships}) - \sum_{m \ge 1} N_m\). The whole curve took 3.2 s.

What this shows. Successes over chances is the maximum-likelihood estimate of each row's chance; it is unbiased, and its 95% interval is about ±1.96 standard errors, which is narrow when the row has many pairs.

2 · Why it works: friendships close triangles

The situation. Why would a mutual friend predict a friendship? Because friends introduce friends: if Ben is your friend and Esha's friend, you and Esha are likely to meet. Then the graph should be full of triangles, three people who are all friends with each other.

The obvious thing: count triangles. The week's graph has 71,976 of them. Is that a lot? On its own the number cannot say: a bigger or denser graph has more triangles by chance alone. It has to be compared with the number of chances to form a triangle.

The idea: of all pairs of your friends, what share are friends with each other? That share is the clustering coefficient of a person. Take Ben: his four friends are You, Chloe, Dev and Esha. They make six pairs. Two of those pairs are friends (You–Chloe and Chloe–Esha), so Ben's clustering is 2/6 = 1/3. You have two friends, Ben and Chloe, and they are friends with each other, so your clustering is 1/1 = 1.

\[ C_v = \frac{\text{pairs of } v\text{'s friends who are friends with each other}}{\text{all pairs of } v\text{'s friends}} \]

It is defined for anyone with at least two friends. To know whether a value is high, compare it with a graph wired with no tendency to close triangles: the same number of friendships placed completely at random, or, stricter, every person keeping their friend count but with friendships shuffled at random (the configuration model).

pymk/closure.py · clustering
def clustering(adj):
    """Local clustering C_v for every v with degree >= 2, and the global transitivity."""
    local, closed, wedges = {}, 0, 0
    for v, nv in enumerate(adj):
        d = len(nv)
        if d < 2:
            continue                                   # no pair of friends, C_v undefined
        t = sum(len(nv & adj[x]) for x in nv) // 2     # each friend-friend edge is seen from both ends
        local[v] = t / (d * (d - 1) / 2)
        closed += t                                    # closed wedges centred at v
        wedges += d * (d - 1) // 2                     # all wedges centred at v
    return local, closed / wedges

The math, step by step: triangles, pairs of friends, and what a random graph would give

Naming the pieces. A pair of v's friends, {x, y}, forms a path x – v – y; call it a wedge at v. Ben has four friends, so he has 4 × 3 / 2 = 6 wedges. In general, choosing 2 of \(d_v\) friends gives \(\binom{d_v}{2} = d_v(d_v - 1)/2\) wedges. A wedge is closed if x and y are friends too, and then x, v, y form a triangle. Write \(T_v\) for the closed wedges at v. Then

\[ C_v = \frac{T_v}{\binom{d_v}{2}} . \]

Each triangle is counted three times. The six-person graph has two triangles, {You, Ben, Chloe} and {Ben, Chloe, Esha}. Closed wedges: You 1, Ben 2, Chloe 2, Esha 1, total 6 = 3 × 2. In general, a triangle {x, y, z} is a closed wedge at each of its three corners, and each closed wedge belongs to exactly one triangle. So \(\sum_v T_v = 3 \times (\text{number of triangles})\).

The pooled share is a weighted average. The pooled share (also called transitivity) is all closed wedges over all wedges: \(\sum_v T_v / \sum_v \binom{d_v}{2}\). In the six-person graph that is 6 / 14 ≈ 0.43, while the average of the four defined \(C_v\) is (1 + 1/3 + 1/3 + 1)/4 ≈ 0.67. Why they differ: put \(w_v = \binom{d_v}{2}\), so \(T_v = w_v C_v\), and

\[ \frac{\sum_v T_v}{\sum_v w_v} = \frac{\sum_v w_v\, C_v}{\sum_v w_v}, \]

an average of the \(C_v\) in which person v has weight \(w_v\), which grows like the square of their friend count. Ben and Chloe have 6 wedges each, You and Esha 1 each, so Ben's and Chloe's 1/3 dominate.

What a random graph gives. In the random graph where each of the \(\binom{n}{2}\) pairs is a friendship independently with chance p, look at any wedge x – v – y. Whether x–y is a friendship is independent of the two friendships we already know about, so the wedge is closed with chance exactly p. So the expected clustering is p for every person. To compare fairly, give the random graph the same number of friendships:

\[ p = \frac{|E|}{\binom{n}{2}} = \frac{100{,}000}{10{,}000 \times 9{,}999 / 2} = \frac{200{,}000}{99{,}990{,}000} \approx 0.0020 . \]

That random graph also gets the friend counts wrong (nearly everyone has about 20). The shuffled graph keeps every person's friend count, so popular people share some friends by chance; that baseline was measured, not derived.

Cost. For each user v and each friend x, the size of the intersection of their friend lists is the number of triangles on the friendship v–x; with hash sets each costs the shorter list's length (Algorithms 4). Each friend-friend link at v is seen from both of its ends, hence the // 2 in the code. Day 2 studies triangle counting properly.

What this shows. Clustering is the share of closed wedges; the pooled share weights popular people heavily; and a random graph with the same density would have clustering of about 0.002, 55 times below the week's graph.

3 · Why sorting by mutual friends is the right first rule

The table showed that, on average, the chance of a friendship rises with the number of mutual friends. If that chance depends only on the count, then showing the ten candidates with the most mutual friends gives the most expected new friendships of any ten you could show. Ties can go either way without losing anything, so the function picks one rule (smaller id first) and sticks to it. The rule stops being the best possible when its assumption breaks, and each way it breaks is a later day's work: the chance depends on more than the count (the 25-times spread inside m = 1 above; Day 4 learns a better score), candidates with no mutual friend are invisible (46.8% of future friendships; Day 3), and what the app shows changes what people do, which changes next month's data (feedback loops, Day 4).

The math, step by step: an exchange argument shows the top ten by count is the best ten

The assumption. The chance that u accepts a suggestion v is \(g(m_v)\), where \(m_v\) is their mutual-friend count and g never goes down as m goes up.

The expected number accepted. For a set S of k suggestions, let \(X_v\) be 1 if v is accepted and 0 if not. The expected total is the sum of the expected parts (this holds even if the acceptances depend on each other):

\[ E\Big[\sum_{v \in S} X_v\Big] = \sum_{v \in S} E[X_v] = \sum_{v \in S} g(m_v). \]

Swapping never hurts. Take any set S of k that is not a top-k set. Then some v in S and some w outside it have \(m_w > m_v\). Swap them. The total changes by \(g(m_w) - g(m_v)\), which is at least 0 because g never goes down. Each swap brings one more top-k member into S, so after at most k swaps S is a top-k set, and its total is at least what we started with.

What this shows. Under the assumption, no set of k suggestions beats the k with the most mutual friends; any tie-break is equally good, so the contract can choose one for determinism.

Solution

Six-person graph. You: 1 (one pair, Ben–Chloe, friends). Ben: 2/6 (You–Chloe and Chloe–Esha). Chloe: 2/6 (You–Ben and Ben–Esha). Esha: 1 (Ben–Chloe). Dev and Farid have one friend each, so clustering is undefined. Average (1 + 1/3 + 1/3 + 1)/4 ≈ 0.67; pooled 6/14 ≈ 0.43.

Pooled share = 1. If every wedge is closed, then any two people two steps apart would have a closed wedge between them, making them one step apart. So nobody is exactly two steps from anyone, and hence nobody is further either (a shortest path of length 2 or more starts with two steps to someone two away). So each connected piece has everyone friends with everyone. The converse is immediate.

Wilson interval. Squaring gives a quadratic in p: \((1 + z^2/N)p^2 - (2\hat p + z^2/N)p + \hat p^2 = 0\) with z = 1.96. Its two roots are the interval. It never leaves [0, 1], which the ±1.96 SE interval can.

Without logs. \(L'(p) = p^{F-1}(1-p)^{N-F-1}\,[F(1-p) - (N-F)p]\). For \(0 < p < 1\) the first two factors are positive, so \(L'\) has the sign of \(F - Np\): positive below F/N, negative above. The maximum is at \(\hat p = F/N\).

Both measurement functions are tested against brute force: clustering on hand-checked graphs, closure_curve against listing every pair on 30 random graphs.

Delivery · the contract and its tests

The situation

This week, suggest will be rewritten again and again: made cheaper on Day 2, approximated on Day 3, re-ranked by a model on Day 4, split across machines on Day 5. Every new version has to be compared with the right answer. So we need to say exactly what the right answer is, and check it automatically.

The obvious thing

Run it for one user and look at the output. Ten plausible ids with plausible counts look the same whether ties go to the smaller id or the larger, whether a blocked person was removed before or after taking the top ten, and whether an existing friend slipped in. Looking has no oracle: nothing tells you what the output should have been.

The idea: write down the promises, then test each one

A contract says what a function promises for every valid input, in rules precise enough that each one can become a check. For suggest:

The function below is the reading's suggest with the contract written into it: it returns each person with their count, checks the edge cases, and filters inside the loop, before ranking.

pymk/exact.py · suggest, with its contract
import heapq
from collections import Counter

def suggest(adj, u, k=10, blocked=frozenset()):
    """The exact baseline. Returns up to k pairs (v, m), best first, where
    m = |N(u) & N(v)| >= 1 and v is eligible: v != u, v not already u's friend,
    v not in blocked (users u blocked or who blocked u, and users who opted out).
    Order: m descending, then v ascending, so the output is deterministic."""
    if not 0 <= u < len(adj):
        raise KeyError(u)
    if k <= 0:
        return []
    direct = adj[u]
    count = Counter()
    for f in direct:
        for v in adj[f]:
            if v != u and v not in direct and v not in blocked:   # filter before ranking
                count[v] += 1
    best = heapq.nsmallest(k, count, key=lambda v: (-count[v], v))
    return [(v, count[v]) for v in best]

Three kinds of test, three kinds of oracle

Tests differ by where they get the right answer from, and that decides which bugs each one can see.

  • A golden test uses an answer worked out by hand on a tiny input. On the six-person graph, You must get Esha (2), Dev (1), Farid (1); with k = 2, Esha and Dev; with Esha blocked and k = 1, Dev. Precise, but it sees only what that one graph exercises.
  • A property test checks rules that must hold for every input, on hundreds of random small graphs: never yourself, a friend or a blocked person; the documented order; no duplicates; the count from u to v equals the count from v to u; the top 3 is the start of the top 10; shuffling the friendships changes nothing. It needs no answers, only rules.
  • A differential test compares with a separate implementation of the definition. Here that is the matrix product of Algorithms 3: the mutual-friend count for u and v is entry (u, v) of \(A^2\), computed with NumPy on small random graphs.
tests/test_exact.py · golden, property and differential checks
import random
import numpy as np

# Each check takes the implementation under test: check_golden(suggest).
def graph_from(n, edges):
    adj = [set() for _ in range(n)]
    for u, v in edges:
        if u != v:
            adj[u].add(v); adj[v].add(u)
    return adj

# The six-person example: You 0, Ben 1, Chloe 2, Dev 3, Esha 4, Farid 5.
GOLDEN = [(0, 1), (0, 2), (1, 2), (1, 3), (1, 4), (2, 4), (2, 5)]

def check_golden(suggest):
    adj = graph_from(6, GOLDEN)
    assert suggest(adj, 0, k=10) == [(4, 2), (3, 1), (5, 1)]   # You: Esha (2), Dev (1), Farid (1)
    assert suggest(adj, 0, k=2) == [(4, 2), (3, 1)]            # Dev and Farid tie: smaller id first
    assert suggest(adj, 0, k=1, blocked={4}) == [(3, 1)]       # a blocked Esha does not use up a slot
    assert suggest(adj, 3, k=10) == [(0, 1), (2, 1), (4, 1)]   # Dev: You, Chloe, Esha, all via Ben
    assert suggest(adj, 1, k=10) == [(5, 1)]                   # Ben: everyone else is already a friend
    assert suggest(adj, 0, k=0) == []

def random_graph(rng):
    n = rng.randint(2, 14)
    edges = [(rng.randrange(n), rng.randrange(n)) for _ in range(rng.randint(0, 3 * n))]
    return n, edges

def check_properties(suggest, trials=300, seed=1):
    rng = random.Random(seed)
    for _ in range(trials):
        n, edges = random_graph(rng)
        adj = graph_from(n, edges)
        u = rng.randrange(n)
        blocked = {v for v in range(n) if rng.random() < 0.2}
        out = suggest(adj, u, k=n, blocked=blocked)
        vs = [v for v, _ in out]
        assert len(vs) == len(set(vs))                                   # no duplicates
        assert out == sorted(out, key=lambda p: (-p[1], p[0]))           # documented order
        for v, m in out:
            assert v != u and v not in adj[u] and v not in blocked      # eligibility
            assert m >= 1
            assert dict(suggest(adj, v, k=n)).get(u) == m               # symmetry m(u,v) = m(v,u)
        k = rng.randint(1, 4)
        assert suggest(adj, u, k=k, blocked=blocked) == out[:k]         # top-k is a prefix
        shuffled = edges[:]; rng.shuffle(shuffled)
        assert suggest(graph_from(n, shuffled), u, k=n, blocked=blocked) == out   # deterministic

def check_against_matrix(suggest, trials=200, seed=2):
    """Differential test: the oracle is the matrix definition m(u, v) = (A @ A)[u, v]."""
    rng = random.Random(seed)
    for _ in range(trials):
        n, edges = random_graph(rng)
        adj = graph_from(n, edges)
        A = np.zeros((n, n), dtype=np.int64)
        for x in range(n):
            for y in adj[x]:
                A[x, y] = 1
        M = A @ A
        for u in range(n):
            want = [(v, int(M[u, v])) for v in range(n)
                    if v != u and A[u, v] == 0 and M[u, v] > 0]
            want.sort(key=lambda p: (-p[1], p[0]))
            assert suggest(adj, u, k=n) == want

Solution

The update property. After adding u–v, u's friends are the old friends plus v, so v is now a friend and not eligible. For another candidate w, its own friend list is unchanged (it gains u only if w = v), so the new count is the old count plus 1 if v is one of w's friends, and unchanged otherwise. Day 5 builds incremental updates on this rule.

A bug all three miss. One example: returning m as a float (2.0 instead of 2). Python's == treats them as equal. A type check (all(type(m) is int …)) catches it. Checks based on equality inherit the blind spots of equality.

Fair ties. Break ties by a hash of the pair, such as sha256(f"{seed}:{u}:{v}"): deterministic for a given seed, unrelated to when someone joined, and reshuffled by changing the seed. Python's built-in hash of strings changes between runs unless PYTHONHASHSEED is set, so it is not deterministic across processes.

A read budget. The never-suggested rules, the order rule on whatever is returned, and determinism for a given budget must not change. The counts and the set of candidates may be approximate, and the response should say so. Day 3 writes this as the budget for candidate sources.

Broken input. Check that every friendship appears in both lists once, where the graph is built or loaded, not on every request: it costs one pass over the friendships. On failure, refuse to load; a silently wrong count is worse than a batch job that stops.

The tests themselves are in the block above; under pytest they run as def test_golden(): check_golden(suggest) and so on.
