DAY 3 · INFORMATIONMLDSAAI

Tokenization moves information around; it never creates or destroys it

ML · entropy and bits per byte

An event of probability p carries −log₂ p bits of surprise. Entropy is the average surprise (left, below): largest (log₂ V) when all outcomes are equally likely, 0 when one is certain. Shannon's source coding theorem says no lossless code averages fewer than H bits per symbol, and the best codes give each symbol about −log₂ p bits: frequent things get short codes. BPE follows that rule with substrings: frequent strings become one token.

Because tokenizing is lossless, it can't change how much information text contains. It only moves it:

\[ H(p) = -\sum_x p(x)\log_2 p(x) \qquad\qquad \underbrace{\frac{\text{bits}}{\text{byte}}}_{\text{invariant}} \;=\; \underbrace{\frac{\text{bits}}{\text{token}}}_{\uparrow\ \text{as } V \uparrow} \times \underbrace{\frac{\text{tokens}}{\text{byte}}}_{\downarrow\ \text{as } V \uparrow} \]

So never compare tokenizers, or models with different tokenizers, by per-token perplexity; compare bits per byte: total −log₂ q over the text, divided by its bytes.

A unigram model ignores context, yet with bigger tokens it needs barely half the bits per byte (4.66 → 2.45), and at 2.45 it beats gzip (2.61) on the same book. A token like Alice already contains the dependencies between its letters: tokenization moves modeling work into the vocabulary. Efficiency (entropy ÷ log₂ V) peaks in the middle and falls once the vocabulary fills with rare tokens.

The minimum description length view adds the missing term: total cost = bits for the text + bits to write down the vocabulary. BPE replaces the second term with a hard budget; the Unigram LM tokenizer (SentencePiece) comes closer, pruning tokens that hurt likelihood least.

Solutions
entropy.py
import math
def entropy(counts):
    n = sum(counts)
    return -sum(c / n * math.log2(c / n) for c in counts if c)
entropy([1] * 6)             # 2.585 bits (= log2 6)
entropy([5, 1, 1, 1, 1, 1])  # 2.161 bits

def unigram_bits_per_byte(train_txt, test_txt, merges):
    tr, te = encode(train_txt, merges), encode(test_txt, merges)
    c, n, V = Counter(tr), len(tr), 256 + len(merges)
    bits = -sum(math.log2((c[t] + 1) / (n + V)) for t in te)   # add-one smoothing
    return bits / len(test_txt.encode())

Proof: bits/byte = (bits/token) · (tokens/byte), because tokens cancel. On Alice, gzip 2.61, xz 2.32, bz2 2.05 bits per byte. The comparison favours BPE slightly, because the compressors pay to store their dictionary inside the output and the unigram model's vocabulary is not counted: exactly the term MDL adds back. For the hosted models you need bits per byte, or at least tokens per byte for each tokenizer on the same text.

Algorithms · Huffman, a greedy that is optimal

Yesterday greedy failed. Huffman coding is the classic case where it provably works. Put every symbol in a min-heap by frequency; repeatedly pop the two rarest, join them under a new node whose frequency is their sum, and push it back. The path from the root to a symbol (0 = left, 1 = right) is its codeword.

Why greedy is optimal here: an exchange argument. In some optimal tree the two rarest symbols are siblings at the deepest level (if not, swap them there; the average length can't go up). Merging them reduces the problem to one fewer symbol with the same structure, so by induction greedy is optimal.

BPE versus Huffman. Both exploit frequency. Huffman keeps the symbols fixed and gives frequent ones shorter codewords; BPE keeps codewords fixed-size (one id each) and gives frequent strings bigger symbols.

Solution
huffman.py
import heapq
def huffman(freqs):
    if len(freqs) == 1:
        return {s: "0" for s in freqs}
    heap = [(f, i, {s: ""}) for i, (s, f) in enumerate(freqs.items())]   # i breaks ties
    heapq.heapify(heap); i = len(heap)
    while len(heap) > 1:
        f1, _, a = heapq.heappop(heap); f2, _, b = heapq.heappop(heap)
        merged = {s: "0" + c for s, c in a.items()} | {s: "1" + c for s, c in b.items()}
        heapq.heappush(heap, (f1 + f2, i, merged)); i += 1
    return heap[0][2]

On Alice's letters and spaces (28 symbols): Huffman averages 4.134 bits per symbol, the entropy is 4.088, and a fixed-length code needs 5. Huffman is always within 1 bit of the entropy. The counter i in the tuple is the tie-break: without it, two equal frequencies would compare the dictionaries and fail.

Design · evaluating a tokenizer

An evaluation plan decides which tokenizer ships. It needs:

  • Fertility: tokens per word (or per byte) for every language and domain you serve. Report the worst case, not just the average.
  • Paired comparisons: the same sentences in each language (a parallel set like FLORES+), with ratios per sentence and a bootstrap interval.
  • Held-out text the tokenizer never saw.
  • Under-trained tokens: how many appear fewer than τ times in the model's training data.
  • Bits per byte of a small model trained with each tokenizer, plus tasks known to be sensitive: arithmetic, spelling, code.
Practice
  • Write a one-page plan to choose between cl100k_base and o200k_base for a product used in English, Hindi and Tamil.
Problem variations
  • The budget allows training only one small model. Which measurements do you drop?
  • Code-heavy traffic: which extra test set and metric do you add?
Solution outline
  1. Data: FLORES+ devtest for the three languages (same 1,012 sentences each), plus a sample of real product traffic, held out.
  2. Fertility: tokens per sentence for each tokenizer and language; the ratio to English per sentence, with a bootstrap 95% interval; the paired difference between the two tokenizers, bootstrapped per sentence.
  3. Cost: convert fertility into price and context-window use at expected traffic.
  4. Decision rule: pick the tokenizer whose worst-language ratio is lowest, unless its English fertility is worse by more than an agreed margin.

Why paired: the sentences differ hugely in length, and pairing removes that variation, so the interval reflects the tokenizers rather than the sentences.
