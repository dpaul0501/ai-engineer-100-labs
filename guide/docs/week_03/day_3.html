DAY 3 · INFORMATIONMLDSAAI

How many bits does text need, and how close can a code get?

A tokenizer is a code: it rewrites bytes as a sequence of ids, and the model then pays some number of bits for each id. Today answers three questions in order. How much information is in a piece of text (entropy, and how to estimate it from a sample)? What is the shortest code a symbol-by-symbol scheme can reach, and how do you build it (prefix codes and Huffman's algorithm, with a full proof)? And when you compare two tokenizers on a test set, how sure can you be of the difference (the bootstrap)?

ML · information from first principles

1 · Surprise: how much does one outcome tell you?

The question. A friend rolls a fair 8-sided die and tells you the result. Another flips a fair coin and tells you the result. The first message tells you more. How much more, as a number?

First attempt. Measure information by the number of possible outcomes: 8 for the die, 2 for the coin. This breaks as soon as you combine messages. The coin and the die together have 2 × 8 = 16 outcomes, but hearing two independent messages should give you the information of the first plus the information of the second, not their product. A measure of information should add, and counting outcomes multiplies.

The key idea, derived. Write I(p) for the information (the surprise) of learning that an event of probability p happened. We ask for three properties:

  • Rarer events are more surprising: I decreases as p grows, and a certain event (p = 1) carries none: I(1) = 0.
  • Independent events add. If A and B are independent, P(A and B) = pq, so we need \( I(pq) = I(p) + I(q) \).
  • A unit: a fair coin flip carries 1 bit, \( I(1/2) = 1 \).

The second property is the important one. A function that turns products into sums is a logarithm: set \( g(t) = I(2^{-t}) \); then \( g(s + t) = I(2^{-s}2^{-t}) = g(s) + g(t) \), so g is additive, and an additive function that is monotone must be linear, \( g(t) = c\,t \). The unit fixes \( c = g(1) = I(1/2) = 1 \). So \( I(2^{-t}) = t \), that is:

\[ I(p) = -\log_2 p = \log_2 \frac{1}{p} \ \text{bits} \]

Check it on the examples. The coin: \( -\log_2 \tfrac12 = 1 \) bit. One face of the 8-sided die: \( -\log_2 \tfrac18 = 3 \) bits. Both together: \( -\log_2 \tfrac1{16} = 4 = 1 + 3 \). A bit has a concrete meaning: it is one yes/no question that halves the possibilities. Finding one face out of 8 takes exactly three halvings:

8 faces→ "is it 1–4?" →4 left→ "is it 1–2?" →2 left→ "is it 1?" →1 face
Three yes/no answers identify one of 8 equally likely outcomes, so the outcome carries 3 bits. An outcome of probability p carries log₂(1/p) bits, also when that number is not a whole number.

2 · Entropy: the average surprise

The question. A source emits symbols x with probabilities p(x), such as letters of English. How much information does one symbol carry on average?

The key idea. Average the surprise over the outcomes, weighting each by how often it happens. That average is the entropy:

\[ H(p) = \sum_x p(x)\, I(p(x)) = -\sum_x p(x)\log_2 p(x) \qquad (0 \log 0 = 0) \]

Two dice, worked by hand. A fair six-sided die: every face has surprise log₂ 6, so H = log₂ 6 = 2.585 bits. A loaded die with probabilities ½, ⅒, ⅒, ⅒, ⅒, ⅒: the likely face carries 1 bit, each rare face log₂ 10 = 3.32 bits, so H = ½ · 1 + 5 · ⅒ · 3.32 = 2.161 bits. The loaded die is more predictable, so it carries less information per roll.

Why the uniform distribution has the most entropy, two outcomes first. With probabilities p and 1 − p,

\[ h(p) = -p\log_2 p - (1-p)\log_2(1-p), \qquad h'(p) = \log_2\frac{1-p}{p}, \qquad h''(p) = -\frac{1}{p(1-p)\ln 2} < 0 . \]

The derivative is zero only at p = ½, and the second derivative is negative everywhere, so h is concave with its single maximum h(½) = 1 bit. At the ends h(0) = h(1) = 0: a certain outcome tells you nothing.

The general bound. With n possible outcomes, \( 0 \le H(p) \le \log_2 n \), with equality on the right exactly when p is uniform. The proof uses Gibbs' inequality, derived in part 4 below.

3 · Shannon's source coding theorem: entropy is the price of a lossless code

The question. You must send a long stream of symbols as bits and the receiver must recover it exactly. Give each symbol a binary codeword. What is the smallest possible average number of bits per symbol?

Statement. For a source with entropy H:

  • Lower bound. No uniquely decodable code has average length below H bits per symbol.
  • Achievability. There is a prefix code with average length below H + 1. Coding blocks of k symbols at a time brings the cost per symbol below H + 1/k, because a block of k independent symbols has entropy kH, so its code costs below kH + 1 bits.

Intuition. The ideal codeword for x has length −log₂ p(x), its surprise: frequent symbols get short codewords, rare ones long codewords, and the average of the ideal lengths is exactly H. You cannot make every codeword short, because short codewords are scarce: there are only two codewords of length 1, four of length 2, and using one of them rules out every longer codeword that starts with it. The Algorithms block below turns this scarcity into an inequality (Kraft) and proves both halves of the theorem.

BPE follows the same rule with a twist: instead of shorter codewords for frequent symbols, it makes frequent strings into single symbols.

4 · Cross-entropy: what a model's loss measures

The question. We never know the true distribution p of text. A model gives its own estimate q. If we build the code from q and use it on text that really comes from p, what does it cost?

The key idea. The ideal code for q spends −log₂ q(x) bits on x. Averaged over what actually occurs:

\[ H(p, q) = -\sum_x p(x)\log_2 q(x) = H(p) + \underbrace{\sum_x p(x)\log_2\frac{p(x)}{q(x)}}_{D(p\,\|\,q)} \]

The extra term D(p‖q) is the Kullback–Leibler divergence: the bits wasted per symbol because the model is wrong.

Why it is never negative (Gibbs' inequality). Use \( \ln t \le t - 1 \) for every t > 0 (the line t − 1 is tangent to the concave ln at t = 1), with equality only at t = 1. Summing over the x with p(x) > 0:

\[ -D(p\,\|\,q)\ln 2 = \sum_x p(x)\ln\frac{q(x)}{p(x)} \le \sum_x p(x)\Big(\frac{q(x)}{p(x)} - 1\Big) = \sum_x q(x) - 1 \le 0 . \]

So \( H(p, q) \ge H(p) \), with equality only when q = p. Taking q uniform over the n outcomes gives \( H(p, q) = \log_2 n \), so \( H(p) \le \log_2 n \): the general bound from part 2.

Why a model's loss is a code length. A language model is trained to minimise the average of −ln q(next token | context) over the training tokens. That is a cross-entropy in nats (natural log); divide by ln 2 to get bits. An arithmetic coder driven by the model compresses text to within a couple of bits of the total −log₂ q, so a lower loss is literally a shorter file. Perplexity is the same number on another scale: 2 to the power of the cross-entropy in bits, the size of a uniform choice that would be equally surprising.

5 · Bits per byte: the number that survives a change of tokenizer

The question. Model A uses a byte-level tokenizer; model B uses BPE with 2,000 tokens. Both are tested on the same text. Which predicts the text better?

First attempt: compare per-token perplexity. This is wrong, because the two models predict different things. A predicts one byte at a time; B predicts tokens that hold about 3.4 bytes each. A larger token is harder to guess, so B's per-token loss is higher even if B is the better model.

The key idea, derived. Let the test text have N bytes. A tokenizer turns it into T tokens, and the model pays a total of B = Σ −log₂ q(token) bits. Tokenization is lossless (the bytes can be recovered from the tokens), so those B bits are a code for the bytes themselves. Any two tokenizers' totals are therefore code lengths for the same object, and can be compared. Divide by the bytes, which do not depend on the tokenizer, and factor through the tokens:

\[ \underbrace{\frac{B}{N}}_{\text{bits/byte: comparable}} \;=\; \underbrace{\frac{B}{T}}_{\text{bits/token}\ \uparrow\ \text{as } V \uparrow} \times \underbrace{\frac{T}{N}}_{\text{tokens/byte}\ \downarrow\ \text{as } V \uparrow} \]

The tokens cancel. Per-token numbers move with the tokenizer; their product does not depend on how the text was cut up, only on how well the text was predicted.

Efficiency is token entropy ÷ log₂ V, the fraction of the maximum entropy (part 2) the token distribution reaches. It peaks in the middle and falls once the vocabulary fills with rare tokens.

The minimum description length (MDL) view adds the missing term: total cost = bits for the text + bits to write down the vocabulary. BPE replaces the second term with a hard budget; the Unigram LM tokenizer (SentencePiece) comes closer, pruning tokens that hurt likelihood least.

6 · Estimating entropy from a sample

The question. You have N characters of text and want the entropy of the letter distribution that produced them. You never see p, only counts.

First attempt: the plug-in estimator. Estimate each probability by its frequency in the sample, \( \hat p(x) = n_x / N \) (this is the maximum-likelihood estimate), and plug it into the formula: \( \hat H = H(\hat p) \). It is consistent (correct as N → ∞) but on small samples it is biased low: on average it reports less entropy than there is. Two reasons:

  • Unseen symbols. A symbol that never appears in the sample gets \( \hat p = 0 \) and contributes nothing, although its true surprise is large.
  • The sample fits itself. By Gibbs' inequality (part 4), the sample's own frequencies \( \hat p \) give the shortest code for the sample: \( H(\hat p) \le H(\hat p, p) \). The right-hand side is linear in \( \hat p \) and \( \mathbb{E}[\hat p] = p \), so \( \mathbb{E}[H(\hat p, p)] = H(p) \). Taking expectations, \( \mathbb{E}[\hat H] \le H(p) \). (The same conclusion follows from Jensen's inequality, since H is concave.) The estimator learns the noise in the sample and mistakes it for structure.

The key idea: estimate the bias and add it back. Work in nats (natural log) and write \( \hat p_x = p_x + \delta_x \), where \( \delta_x \) is the sampling error. Expand \( f(t) = -t \ln t \) to second order around each \( p_x \): \( f'(t) = -\ln t - 1 \), \( f''(t) = -1/t \), so

\[ H(\hat p) \approx H(p) + \sum_x f'(p_x)\,\delta_x - \sum_x \frac{\delta_x^2}{2p_x} . \]

The linear term has mean zero, because \( \mathbb{E}[\delta_x] = 0 \). The count \( n_x \) is binomial, so \( \mathbb{E}[\delta_x^2] = \operatorname{Var}(\hat p_x) = p_x(1-p_x)/N \). Over the m symbols with \( p_x > 0 \):

\[ \mathbb{E}[H(\hat p)] - H(p) \approx -\sum_x \frac{p_x(1-p_x)}{2Np_x} = -\frac{\sum_x (1-p_x)}{2N} = -\frac{m-1}{2N}\ \text{nats} = -\frac{m-1}{2N\ln 2}\ \text{bits}. \]

The Miller–Madow estimator adds this back, using the number of observed symbols for m because the true number is unknown:

\[ \hat H_{\text{MM}} = \hat H_{\text{plug-in}} + \frac{m - 1}{2N} \ \text{nats} \;=\; \hat H_{\text{plug-in, bits}} + \frac{m - 1}{2N \ln 2}\ \text{bits}. \]

Take care with the units: the correction is in nats, so dividing by ln 2 (multiplying by 1.443) converts it to bits. Forgetting this under-corrects by about 30%.

Cost. Both estimators count the sample once, O(N) time, and sum over the distinct symbols, O(m) time and space.

Confirm by measuring. Alice's letters and spaces, lowercased (28 symbols: 26 letters, the space, and one accented letter that occurs once), have entropy 4.088 bits over the full 137,958 characters. Draw random samples of size N from the text and average each estimator over 2,000 samples:

Where BPE uses it. Every count-based number about a tokenizer is a plug-in estimate. The token-entropy column above is computed from token counts; at a large vocabulary many tokens are seen only a few times, so that column (and the efficiency built on it) is biased low, and the bias grows with V for a fixed amount of text. The same effect makes rare tokens look better estimated than they are (Day 2).

Solutions
entropy.py
import math
from collections import Counter

def entropy(counts):
    """Entropy in bits of the distribution given by a list of counts."""
    n = sum(counts)
    return -sum(c / n * math.log2(c / n) for c in counts if c)

def cross_entropy(p, q):
    """Average code length in bits when data from p is coded with a code built for q."""
    return -sum(p[x] * math.log2(q[x]) for x in p if p[x])

entropy([1] * 6)             # 2.585 bits (= log2 6)
entropy([5, 1, 1, 1, 1, 1])  # 2.161 bits
unigram.py · uses encode() from the week reading R.6
def unigram_bits_per_byte(train_txt, test_txt, merges):
    tr, te = encode(train_txt, merges), encode(test_txt, merges)
    c, n, V = Counter(tr), len(tr), 256 + len(merges)
    bits = -sum(math.log2((c[t] + 1) / (n + V)) for t in te)   # add-one smoothing
    bits_per_token = bits / len(te)
    tokens_per_byte = len(te) / len(test_txt.encode())
    return bits_per_token * tokens_per_byte                     # = bits / bytes
estimators.py
def plugin_entropy(sample):
    """Maximum-likelihood ("plug-in") estimate in bits: entropy of the sample's own frequencies."""
    return entropy(list(Counter(sample).values()))

def miller_madow(sample):
    """Plug-in plus the first-order bias correction (m - 1) / (2N) nats, converted to bits."""
    m, N = len(set(sample)), len(sample)
    return plugin_entropy(sample) + (m - 1) / (2 * N * math.log(2))

Bits per byte: \( \frac{B}{N} = \frac{B}{T}\cdot\frac{T}{N} \) because T cancels; it is an identity, true for any tokenizer. For the divergences, D(p‖q) = H(p, q) − H(p) = 0.168 bits and D(q‖p) = 0.143 bits: not symmetric. The first is the waste when text from p is coded with q's code, the second the reverse. On Alice, gzip 2.61, xz 2.32, bz2 2.05 bits per byte. The comparison favours BPE slightly, because the compressors pay to store their dictionary inside the output and the unigram model's vocabulary is not counted: exactly the term MDL adds back. For the hosted models you need bits per byte, or at least tokens per byte for each tokenizer on the same text.

Algorithms · optimal prefix codes

1 · Prefix codes: decoding without separators

The question. Give each symbol a binary codeword so that the concatenation of codewords, with no separators, can be split back into symbols in exactly one way, and the average length is small.

First attempt. A fixed-length code: with n symbols, every codeword has ⌈log₂ n⌉ bits. Decoding is easy (cut every 5 bits for 28 symbols), but frequent and rare symbols cost the same. So try variable lengths, say a = 0, b = 01, c = 10. The string 010 now reads as a c (0 | 10) or as b a (01 | 0). Variable lengths alone are ambiguous.

The key idea. A prefix code (also called prefix-free) is one in which no codeword is a prefix of another. Draw the codewords as paths in a binary tree, 0 = left, 1 = right: the code tree. Prefix-free means every codeword ends at a leaf, never at a node that lies on the way to another codeword. Decoding is then a walk: start at the root, follow one edge per bit, and when you reach a leaf, output its symbol and jump back to the root. At a leaf there is no choice to make, so the split is unique, and the decoder never needs to look ahead.

In the bad example, 0 (a) is a prefix of 01 (b), so a sits on the path to b. The cost of a code for symbol counts fi and codeword lengths ℓi is the total number of bits, \( L = \sum_i f_i \ell_i \), which is the sum of f × depth over the leaves of its code tree.

2 · The Kraft inequality: short codewords are scarce

The question. Which lists of lengths ℓ1, …, ℓn can be the codeword lengths of a prefix code? Lengths 1, 1, 2 cannot: the two length-1 codewords 0 and 1 leave no room for a third.

Statement. A prefix code with lengths ℓi exists if and only if

\[ \sum_{i=1}^{n} 2^{-\ell_i} \le 1 . \]

Proof (only if). Let L = max ℓi and picture the complete binary tree of depth L, which has 2L leaves at the bottom. A codeword at depth ℓi is the root of a subtree containing 2L−ℓi of those bottom leaves: all the length-L strings that start with it. Because the code is prefix-free, no codeword lies inside another's subtree, so these sets of bottom leaves are disjoint. Disjoint subsets of 2L leaves have sizes summing to at most 2L:

\[ \sum_i 2^{L-\ell_i} \le 2^L \quad\Longrightarrow\quad \sum_i 2^{-\ell_i} \le 1 . \]

Proof (if). Sort the lengths ascending and give codewords out in order, each time taking the leftmost free node at the required depth and marking its whole subtree used. Before placing codeword j, the used part of the bottom level is \( \sum_{i<j} 2^{L-\ell_i} < 2^L \) (strictly, because codeword j's own share is still unspent). Each earlier codeword is no deeper than ℓj, so it covers a whole number of depth-ℓj subtrees, and taking leftmost nodes keeps the used region a left-aligned block of them. So a free node exists at depth ℓj. This construction is exactly canonical Huffman coding (below): it needs only the lengths.

Example: lengths 1, 2, 3, 4, 4 give ½ + ¼ + ⅛ + 1⁄16 + 1⁄16 = 1, so the tree is full (every internal node has two children). Lengths 1, 1, 2 give 1¼ > 1: impossible, as seen above.

3 · Both halves of the source coding theorem

Lower bound: every prefix code has \( L/N \ge H \). Let pi = fi/N and define \( K = \sum_i 2^{-\ell_i} \le 1 \) (Kraft) and the distribution \( q_i = 2^{-\ell_i}/K \). Then \( \ell_i = -\log_2 q_i - \log_2 K \), and the average length is

\[ \bar\ell = \sum_i p_i \ell_i = H(p, q) - \log_2 K \;\ge\; H(p) - \log_2 K \;\ge\; H(p), \]

using Gibbs' inequality (ML block, part 4) for the first step and \( K \le 1 \) for the second.

Upper bound: some prefix code has \( \bar\ell < H + 1 \). Use the Shannon code lengths \( \ell_i = \lceil -\log_2 p_i \rceil \), the surprise rounded up. They satisfy Kraft, because \( \ell_i \ge -\log_2 p_i \) means \( 2^{-\ell_i} \le p_i \), and \( \sum_i p_i = 1 \). So a prefix code with these lengths exists, and since \( \lceil t \rceil < t + 1 \),

\[ \bar\ell = \sum_i p_i \lceil -\log_2 p_i \rceil < \sum_i p_i(-\log_2 p_i + 1) = H + 1 . \]

The best prefix code is at least as good as the Shannon code, so it too lands in [H, H + 1). Shannon's code is not optimal itself, as the example below shows. Huffman's algorithm finds the optimum.

4 · Huffman's algorithm

The question. Given counts f1, …, fn, find the prefix code (the code tree) that minimises \( L = \sum_i f_i \ell_i \).

First attempts. Trying every tree is hopeless: the number of full binary trees with n labelled leaves grows faster than exponentially. Rounding surprises up (Shannon's code) is fast but can waste close to a bit per symbol.

The key idea. The two rarest symbols should be the two deepest leaves, side by side. Once they are siblings, they behave like one symbol whose count is their sum. So: repeatedly take the two smallest counts, join them under a new node whose count is their sum, and put that node back. When one node is left, it is the root. Keep the counts in a min-heap so "take the smallest" is fast.

5 · Why Huffman is optimal

The proof has the two parts every greedy proof needs (Day 2): the greedy choice is safe (Lemma 1), and after making it, what remains is a smaller copy of the same problem (Lemma 2). Then induction.

A fact first. In an optimal tree every internal node has two children. If a node had one child, you could delete it and lift its subtree up a level, shortening every codeword below it and keeping the code prefix-free. So the deepest leaf of an optimal tree always has a sibling, which is also a leaf.

Lemma 1 (the rarest two can be deepest siblings). Let x and y be the two symbols with the smallest counts. Some optimal tree has x and y as sibling leaves at the maximum depth.

Proof, by exchange. Take any optimal tree T, and let b, c be sibling leaves at the maximum depth (they exist by the fact above). Then \( f_x \le f_b \) (x is a rarest symbol) and \( d_x \le d_b \) (b is at the maximum depth). Swap the positions of x and b. Only those two terms of the cost change:

\[ L(T_{\text{swap}}) - L(T) = \big(f_x d_b + f_b d_x\big) - \big(f_x d_x + f_b d_b\big) = -\,(f_b - f_x)(d_b - d_x) \;\le\; 0, \]

because both brackets are non-negative. The swap does not increase the cost, and T was optimal, so the new tree is optimal too. Swap y with c the same way (\( f_y \le f_c \), \( d_y \le d_c \)). The result is an optimal tree with x and y as deepest siblings. ∎

Lemma 2 (merging gives the same problem, one symbol smaller). Replace x and y by one new symbol z with \( f_z = f_x + f_y \). For any tree T′ on the new alphabet, expanding the leaf z into an internal node with children x and y gives a tree T on the original alphabet, and conversely collapsing sibling leaves x, y of a tree T gives T′. In both directions

\[ L(T) = L(T') + f_x + f_y , \]

because x and y sit at depth \( d_z + 1 \): \( f_x(d_z + 1) + f_y(d_z + 1) = f_z d_z + f_x + f_y \), and every other leaf keeps its depth. In the example, merging d and e into z (count 5) leaves counts 10, 6, 4, 5, whose Huffman tree costs 49 bits, and 49 + 3 + 2 = 54.

Theorem. Huffman's tree is optimal, by induction on the number of symbols n.

  • Base, n = 2. Each symbol gets one bit, and no prefix code can do better (a 0-bit codeword cannot distinguish two symbols).
  • Step. Huffman merges the rarest x, y into z and then runs on the n − 1 symbols, building H′, which is optimal for the smaller problem by the induction hypothesis. Its final tree is H′ with z expanded, so \( L(H) = L(H') + f_x + f_y \) (Lemma 2). Take the optimal tree T* from Lemma 1, where x, y are siblings, and collapse them: \( L(T^*) = L(T^{*\prime}) + f_x + f_y \ge L(H') + f_x + f_y = L(H) \), since H′ is optimal and T*′ is just some tree on the same n − 1 symbols. So H costs no more than an optimal tree: it is optimal. ∎

Combined with part 3: \( H \le \bar\ell_{\text{Huffman}} < H + 1 \), where H is the entropy of the counts. The lower bound holds for every prefix code; the upper bound holds because Huffman is at least as good as Shannon's code.

6 · Cost

  • With a heap: O(n log n) time. Building the heap from n counts is O(n) (Day 4 proves it). Each of the n − 1 merges does two pops and one push, each O(log n) because the heap holds at most n items. Computing every depth afterwards is one pass over the 2n − 1 nodes, O(n). Space: O(n) for the nodes.
  • Writing codewords out costs O(Σ ℓi) extra, the total length of the strings. That is O(n log n) for balanced counts but O(n²) when the counts grow like Fibonacci numbers, which make the tree a long chain. The dictionary-merging huffman() in the solution pays this cost; huffman_lengths() does not.
  • Already-sorted counts: O(n), no heap. Keep two FIFO queues: the sorted leaves, and the merged nodes in the order they are created. The merged counts come out in non-decreasing order. Proof: at merge k + 1, every item in the pool either was in the pool at merge k and was not popped, so it is at least as large as both items popped then, or is the node created at merge k, which is their sum and also at least as large. So both items popped at merge k + 1 are at least as large as those popped at merge k, and so is their sum. Each queue therefore stays sorted, the smallest item is at the front of one of the two queues, and each pop is O(1). Total O(n) after sorting, O(n log n) including the sort.

8 · Where BPE uses it, and where BPE differs

Both exploit frequency, in opposite directions. Huffman keeps the symbols fixed and gives frequent ones shorter codewords; BPE keeps codewords fixed-size (one id each) and gives frequent strings bigger symbols. The model then plays the Huffman role: a well-trained model spends about −log₂ q bits per token, which is what bits per byte measures.

The proof is also where the two part ways. Huffman's merges do not interact: joining x and y leaves every other count unchanged, so the remaining problem is the same problem with one symbol fewer (Lemma 2), and the exchange in Lemma 1 touches only two terms of the cost. BPE's merges do interact: merging the pair (a, b) consumes occurrences of (b, c) and creates new pairs such as (ab, c), so after a merge the remaining problem has different counts, and the best first merge can make later merges worse. There is no Lemma 2 for BPE, which is why its greedy is not optimal (Day 2's counterexample).

Solutions
huffman.py
import heapq
def huffman(freqs):
    if len(freqs) == 1:
        return {s: "0" for s in freqs}
    heap = [(f, i, {s: ""}) for i, (s, f) in enumerate(freqs.items())]   # i breaks ties
    heapq.heapify(heap); i = len(heap)
    while len(heap) > 1:
        f1, _, a = heapq.heappop(heap); f2, _, b = heapq.heappop(heap)
        merged = {s: "0" + c for s, c in a.items()} | {s: "1" + c for s, c in b.items()}
        heapq.heappush(heap, (f1 + f2, i, merged)); i += 1
    return heap[0][2]

On Alice's letters and spaces (28 symbols): Huffman averages 4.134 bits per symbol, the entropy is 4.088, and a fixed-length code needs 5. The counter i in the tuple is the tie-break: without it, two equal counts would compare the dictionaries and fail. This version copies dictionaries at every merge, so it does O(Σ ℓi) extra work. The next version records parents instead and stays O(n log n), with an O(n) two-queue variant for sorted counts.

huffman_lengths.py
def depths(parent):
    """Node i's parent is parent[i] > i; the last node is the root. Returns every node's depth."""
    d = [0] * len(parent)
    for i in range(len(parent) - 2, -1, -1):    # parents before children
        d[i] = d[parent[i]] + 1
    return d

def huffman_lengths(freqs):
    """Code length per symbol. O(n log n): n - 1 rounds of two pops and one push."""
    syms = list(freqs)
    if len(syms) == 1:
        return {syms[0]: 1}
    heap = [(f, i) for i, f in enumerate(freqs.values())]
    heapq.heapify(heap)                          # O(n)
    parent = [None] * len(syms)
    while len(heap) > 1:
        f1, a = heapq.heappop(heap)
        f2, b = heapq.heappop(heap)
        parent.append(None)                      # new internal node
        parent[a] = parent[b] = len(parent) - 1
        heapq.heappush(heap, (f1 + f2, len(parent) - 1))
    d = depths(parent)
    return {s: d[i] for i, s in enumerate(syms)}

def huffman_lengths_sorted(fs):
    """Same lengths in O(n) when fs is already sorted ascending: two FIFO queues, no heap."""
    if len(fs) == 1:
        return [1]
    leaves = deque((f, i) for i, f in enumerate(fs))
    merged = deque()                             # merged weights arrive in ascending order
    parent = [None] * len(fs)
    def pop_min():
        if not merged or (leaves and leaves[0][0] <= merged[0][0]):
            return leaves.popleft()
        return merged.popleft()
    while len(leaves) + len(merged) > 1:
        f1, a = pop_min()
        f2, b = pop_min()
        parent.append(None)
        parent[a] = parent[b] = len(parent) - 1
        merged.append((f1 + f2, len(parent) - 1))
    return depths(parent)[:len(fs)]
canonical.py
def canonical_codes(lengths):
    """Rebuild a prefix code from code lengths alone (the decoder needs only the lengths)."""
    assert sum(2 ** -l for l in lengths.values()) <= 1, "lengths violate Kraft"
    code, prev, out = 0, 0, {}
    for s, l in sorted(lengths.items(), key=lambda kv: (kv[1], kv[0])):
        code <<= l - prev                        # move down to depth l in the code tree
        out[s] = format(code, f"0{l}b")
        code += 1                                # next free node at this depth
        prev = l
    return out

def decode(bits, codes):
    back, out, cur = {c: s for s, c in codes.items()}, [], ""
    for b in bits:
        cur += b
        if cur in back:                          # prefix-free: the first match is the only one
            out.append(back[cur]); cur = ""
    assert cur == "", "trailing bits"
    return out

Canonical Huffman sorts symbols by (length, symbol) and counts upward in binary, appending a 0 each time the length grows. That is the "if" half of the Kraft proof: each codeword takes the leftmost free node at its depth. A decoder needs only the 28 lengths, not the tree. For the chain question, Fibonacci-like counts (1, 1, 2, 3, 5, 8) do it: each merged node is no larger than the count two places further on, so it is picked again in the very next merge.

leetcode_1046_1167.py
def last_stone_weight(stones):                   # LeetCode 1046
    heap = [-s for s in stones]                  # heapq is a min-heap: negate for max
    heapq.heapify(heap)
    while len(heap) > 1:
        y = -heapq.heappop(heap)                 # heaviest
        x = -heapq.heappop(heap)                 # second heaviest
        if y != x:
            heapq.heappush(heap, -(y - x))
    return -heap[0] if heap else 0

def connect_sticks(sticks):                      # LeetCode 1167: this is Huffman's cost
    heap = list(sticks)
    heapq.heapify(heap)
    cost = 0
    while len(heap) > 1:
        a = heapq.heappop(heap)
        b = heapq.heappop(heap)
        cost += a + b                            # every merge pays the merged weight
        heapq.heappush(heap, a + b)
    return cost

For 1167, every merged stick's length is added once per merge above it, so the total cost is Σ (length × depth) of the merge tree: Huffman's objective. Both run in O(n log n).

Design · evaluating a tokenizer, with error bars

1 · What to measure

An evaluation plan decides which tokenizer ships. It needs:

  • Fertility: tokens per word (or its inverse, bytes per token) for every language and domain you serve. A language with high fertility costs more per request and fits less text in the context window. Report the worst case, not just the average.
  • Held-out text the tokenizer never saw. Measuring on training text flatters the tokenizer, because its merges were chosen to fit that text (Day 2).
  • Bits per byte of a small model trained with each tokenizer (ML block, part 5), plus tasks known to be sensitive: arithmetic, spelling, code.
  • Paired comparisons: the same sentences in each language (a parallel set like FLORES+), and the same documents for each tokenizer.
  • Under-trained tokens: how many appear fewer than τ times in the model's training data.
  • Error bars on every number. The rest of this block builds them.

2 · Error bars: the question

The question. Hold out every 10th document of Alice (73 documents, 16,362 bytes) and train BPE with 1,000 tokens on the other 650. On the held-out documents it packs 2.913 bytes into each token. With a different 73 documents, the number would change. By how much? Without that, "2.913" cannot be compared with anything.

First attempt: treat every token as an independent sample. The held-out set has 5,616 tokens; compute the spread of bytes per token across them and divide by √5,616. This interval is too narrow. Tokens inside one document are not independent: a document about the Queen repeats Queen, a chapter of dialogue is full of short tokens, a poem has its own rhythm. Ten more tokens from the same document tell you much less than ten tokens from a new document. The unit that is (roughly) independent is the document.

3 · The bootstrap, from first principles

Definitions. We have a sample of D documents, assumed drawn independently from the population of text we care about, and a statistic computed from them, here \( \theta = \sum_d \text{bytes}_d \,/\, \sum_d \text{tokens}_d \) (total bytes over total tokens). Its sampling distribution is the spread of θ over many independent samples of D documents. We cannot draw new samples. The bootstrap's idea is to use the sample as a stand-in for the population:

73 held-out documentseach reduced to (bytes, tokens): tokenize once
↓ draw 73 documents with replacement (some twice, some not at all)
one resample → θ*Σ bytes ÷ Σ tokens over the drawn documents
↓ repeat B = 10,000 times
10,000 values of θ*sort them; the 2.5th and 97.5th percentiles bound the 95% interval

Why it works. If the documents are independent draws, the sample's empirical distribution (each document with probability 1/D) approximates the true distribution of documents, and better as D grows. Drawing D documents with replacement from it is a simulation of "collect a new sample of D documents", so the spread of θ* around θ approximates the spread of θ around the true value. The percentile interval takes the middle 95% of the sorted θ*. Two conditions matter: the resampled units must be independent (hence documents, not tokens), and the statistic should be smooth in the data (sums and ratios of sums are; a maximum is not).

Why resampling tokens is wrong, measured. A bootstrap over the 5,616 individual tokens gives a 95% interval of width 0.084 bytes per token. The document bootstrap gives 0.235, 2.8 times wider. The token-level interval treats correlated tokens as fresh information and claims a precision the data do not have.

Cost. Tokenize each held-out document once and store (bytes, tokens): O(total text). Each resample then costs O(D), so the bootstrap is O(B · D) time and O(B) space for the replicates (sorted in O(B log B)). Never re-tokenize inside the loop.

4 · Paired comparison of two tokenizers

The question. BPE with 2,000 tokens packs 3.416 bytes per token on the same held-out documents. Is it really more compact than BPE 1,000 at 2.913, and by how much?

First attempt: two separate intervals. Bootstrap each tokenizer independently and subtract. That treats the two numbers as if they came from different documents. But they come from the same documents, and documents differ a lot (per-document bytes per token ranges from 1.57 to 3.73 for BPE 1,000): a resample heavy in long-worded documents raises both numbers. Independent resampling counts this shared variation twice.

The key idea. Resample document indices once per round, compute both statistics on that same resample, and record the difference \( \theta^*_B - \theta^*_A \). The interval of the differences is the paired interval. Why it is narrower:

\[ \operatorname{Var}(\theta_B - \theta_A) = \operatorname{Var}(\theta_A) + \operatorname{Var}(\theta_B) - 2\operatorname{Cov}(\theta_A, \theta_B) . \]

When the two tokenizers move together across documents, the covariance is large and cancels most of the variance. Independent resampling sets that covariance to zero.

Confirm by measuring. 73 held-out documents (every 10th of 723), BPE trained on the other 650 at 1,000 and 2,000 tokens, B = 10,000 resamples, percentile 95% intervals:

QuantityPoint estimate95% intervalWidth
bytes per token, BPE 1,0002.913[2.784, 3.019]0.235
bytes per token, BPE 2,0003.416[3.225, 3.558]0.333
difference, paired bootstrap0.502[0.429, 0.564]0.135
difference, independent resamples (wrong)0.502[0.282, 0.697]0.415

The two tokenizers' bootstrap replicates have correlation 0.954, so pairing makes the interval for the difference about three times narrower. The paired interval excludes 0 by a wide margin, and BPE 2,000 packs more bytes per token on 71 of the 73 documents. Conclusion: on this kind of text the 2,000-token vocabulary is about 0.50 bytes per token (17%) more compact, and we are confident of that to within about ±0.07.

Two cautions. The interval describes variation over documents like these (one English novel); it says nothing about other languages or domains, which need their own held-out sets. And more bytes per token is not automatically better: Day 2 explains what a larger vocabulary costs.

Where BPE uses it. Every tokenizer decision in this week is a comparison of two numbers measured on the same text: two vocabulary sizes, two split patterns, two tokenizers for a new language. Pair them, resample documents, and report the interval for the difference.

bootstrap.py
import random

def paired_bootstrap(rows, B=10_000, seed=0):
    """rows: one (bytes, tokens_A, tokens_B) per held-out document.
    Resamples documents, never tokens. Returns sorted replicates of
    bytes/token for A, for B, and of the paired difference B - A."""
    rng, D = random.Random(seed), len(rows)
    ra, rb, rd = [], [], []
    for _ in range(B):
        s = [rows[rng.randrange(D)] for _ in range(D)]   # D documents, with replacement
        nbytes = sum(r[0] for r in s)
        a = nbytes / sum(r[1] for r in s)
        b = nbytes / sum(r[2] for r in s)                # same documents for both tokenizers
        ra.append(a); rb.append(b); rd.append(b - a)
    return sorted(ra), sorted(rb), sorted(rd)

def percentile_ci(reps, level=0.95):
    """Percentile interval from sorted bootstrap replicates."""
    k = int(len(reps) * (1 - level) / 2)
    return reps[k], reps[len(reps) - 1 - k]

The statistic is total bytes over total tokens of the resampled documents, so long documents count in proportion to their length. Rerunning with 20 different seeds, the lower end of the paired interval ranges from 0.415 to 0.451 with 100 resamples, from 0.426 to 0.442 with 1,000, and from 0.428 to 0.433 with 10,000: use thousands of resamples before trusting the second decimal. For bits per byte, store (bytes, bits) per document. For chapters, resample whole chapters: always resample the largest unit that is independent.

Plan outline for cl100k_base against o200k_base:

  1. Data: FLORES+ devtest for the three languages (same 1,012 sentences each), plus a sample of real product traffic, held out.
  2. Fertility: tokens per sentence for each tokenizer and language; the ratio to English per sentence, with a bootstrap 95% interval; the paired difference between the two tokenizers, bootstrapped per sentence.
  3. Cost: convert fertility into price and context-window use at expected traffic.
  4. Decision rule: pick the tokenizer whose worst-language ratio is lowest, unless its English fertility is worse by more than an agreed margin.

Why paired: the sentences differ hugely in length, and pairing removes that variation, so the interval reflects the tokenizers rather than the sentences.
