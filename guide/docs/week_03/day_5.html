DAY 5 · ENCODING AND SERVINGMLDSAAISys

From a trained merge list to a production tokenizer

Training produced a merge list. Today covers what happens after: how a model goes wrong because of its tokenizer, how to encode a chunk fast, how to count when the data is too big to count exactly, and how to train and serve a tokenizer at scale.

ML · failure modes and their mechanisms

The question

Some model failures have nothing to do with the network. They come from how the text was cut into tokens. Why does each one happen, mechanically, and what is the fix?

The first principle behind most of them

An embedding row is a vector of numbers, one row per token id. It changes only when its token appears in the model's training data: each appearance contributes one gradient update. On Day 2 we derived that a token seen \(n\) times has an embedding whose noise falls like \(1/\sqrt{n}\). When \(n\) is near zero, the row carries almost no signal. It stays close to its random initial value, minus whatever weight decay removed. The model has never learned what it means.

The tokenizer and the model are trained on different data, at different times. The tokenizer decides which tokens exist (from its corpus). The model decides what they mean (from its corpus). Every failure below is a mismatch between those two, or between the token boundary and the boundary the user cares about.

The failure modes

  • Token tax. What you see: the same sentence costs many more tokens in some languages. The week reading measured 6.9× more tokens for Hindi than English with GPT-2's tokenizer. Why: merges are chosen by frequency in the tokenizer's corpus. A script with little text there contributes few pairs to the counts, so few merges are learned for it, and its text stays close to raw bytes (Devanagari is 3 bytes per code point in UTF-8). Cost to the user: more money per request (billing is per token), less text in a fixed context window, more decoding steps per word. Fix: rebalance the tokenizer's training mix by language (see Design).
  • Glitch tokens. What you see: SolidGoldMagikarp is a single GPT-2 token, and the model behaved strangely on it (refusing to repeat it, or answering with an unrelated word). Why: the string was frequent in the tokenizer's corpus (a Reddit username), so it earned a merge. It was nearly absent from the model's training data, so \(n \approx 0\) and its row never moved from initialization. Fix: train the tokenizer on the same mixture as the model, and check for such rows before release.
  • Under-trained intermediate tokens. What you see: tokens that are in the vocabulary but are almost never produced by the encoder. Why: BPE learns a long token through shorter ones. Once the longer merge exists, the encoder applies it, so the shorter token is used only where the longer one does not fit. Measured on Alice with a 2,000-token vocabulary: of the 1,744 learned tokens, 122 are never emitted when encoding Alice itself, and 437 are emitted at most 4 times. Those rows get \(n \le 4\) updates from this text. Fix: find them (smallest embedding norms, or zero counts when encoding the training data; Land and Bartolo 2024 do this for real models) and prune or retrain.
  • Streaming decode prints �. What you see: a chat interface shows � (U+FFFD, the replacement character) mid-word, then the right text. Why: byte-level tokens are byte strings, not characters. A token can end inside a multi-byte character. In the Alice vocabulary, one learned token is b"\xe2\x80": the first two of the three bytes of the curly apostrophe ’ (U+2019). Decoding that token alone with errors="replace" produces �. Fix: an incremental decoder that holds back an incomplete tail until the next token completes it (code below).
  • Spelling and counting letters. The model never sees the letters inside strawberry; it sees one or two ids. "How many r's?" asks about something it observed only indirectly.
  • Prompt boundaries. A prompt ending mid-word ("https:") is split differently from the same text in training, where the colon was usually merged with the characters after it. "Token healing" backs up one token and constrains the next one to start with the removed text.
  • Digits. GPT-2 merges digit strings however the counts fell, so 1234 and 1235 can split differently. Later split patterns cap digit groups at 3, which gives arithmetic a consistent unit.

BPE-dropout: making the model see more than one split

The question. Deterministic BPE gives each word exactly one split. A typo ( unhapiness) produces a split the model has never seen. How can the model learn that different splits mean the same text?

The key idea. While the model trains, encode each chunk with randomness: at every step, each candidate merge is skipped with probability \(p\). The lowest-rank surviving merge is applied. The model then sees a word's pieces as well as its usual split.

Why it is safe. Each step still merges two adjacent tokens into the token whose bytes are their concatenation, so the decoded bytes never change: the encoding stays lossless. With \(p = 0\) it is ordinary BPE. With \(p = 1\) no merge survives and it returns bytes.

Cost. One random draw per candidate per step: the same O(\(L \cdot R\)) as the simple encoder (Algorithms, below). It is used only while training the model. At inference, encode deterministically.

Measured. With \(p = 0.3\) and the 2,000-token Alice vocabulary, unhappiness encodes as un|ha|pp|iness deterministically. Over seeds 0 to 4, dropout gave that split three times, un|ha|pp|in|es|s once and un|ha|pp|in|ess once.

Solution
bpe.py · BPE-dropout
def encode_dropout(data, ranks, p, rng):
    ids = list(data)
    while len(ids) >= 2:
        cands = [(ranks[q], q) for q in zip(ids, ids[1:]) if q in ranks and rng.random() >= p]
        if not cands:
            break
        r, pair = min(cands)
        ids = merge(ids, pair, r)
    return ids

merge is the function from the week reading. Every step joins two neighbours, so b"".join(vocab[t] for t in out) equals the input for every seed; the tests check this.

stream.py · streaming decode without �
import codecs

class StreamDecoder:
    """Turn token ids into text as they arrive, never printing a half character."""
    def __init__(self, vocab):                   # vocab: id -> bytes
        self.vocab = vocab
        self.dec = codecs.getincrementaldecoder("utf-8")(errors="replace")
    def feed(self, token_id):
        return self.dec.decode(self.vocab[token_id])   # holds back an incomplete tail
    def close(self):
        return self.dec.decode(b"", final=True)        # a truncated tail becomes one U+FFFD

The incremental decoder keeps the bytes of an incomplete UTF-8 sequence until the next call. Feeding b"\xe2\x80" returns an empty string; feeding b"\x99s" next returns ’s. Only a stream that ends mid-character yields �, at close().

Algorithms · the fast encoder and the LRU cache

The question

Given a chunk of \(L\) byte ids and a merge list where each merge has a rank (its position in the list, which is also the id of the token it creates), produce exactly the tokens the training rule implies: repeatedly apply the lowest-rank merge present, left to right, until no merge applies.

First attempt: replay the merges, O(L · R)

The week reading's encoder scans the whole chunk for the lowest-rank adjacent pair, rebuilds the list with every occurrence merged, and repeats. One round costs O(\(L\)): one scan, one rebuild. The number of rounds is \(R\), the number of distinct merges that apply to this chunk. So a chunk costs O(\(L \cdot R\)).

For a normal chunk this is fine: rabbit has \(L = 7\) and a few rounds. It breaks on long chunks with no spaces (URLs, base64, minified code, other scripts). Both factors grow together: a longer chunk contains more distinct pairs, so more merges apply. To stand in for such an input, feed the first 10,000 bytes of alice.txt to the encoder as one chunk, whitespace kept and no pattern split (2,000-token vocabulary): the simple encoder needs 951 rounds, each rescanning thousands of tokens.

The key idea: a linked list to splice, a heap to choose

Two operations repeat: "find the lowest-rank pair" and "replace two neighbours by one token". Give each its own structure.

Doubly linked list. Each token is a node holding four things: its token id, the index of the previous live node, the index of the next live node, and an alive flag. Merging node \(i\) with its right neighbour \(j\) means: set ids[i] to the new token, mark \(j\) dead, and point \(i\)'s next at \(j\)'s next (and that node's prev back at \(i\)). That is three pointer writes, O(1), whatever the chunk length. In an array the same removal shifts every later element: O(\(L\)). The code stores the list as parallel arrays prev, nxt, alive indexed by original position, which avoids allocating node objects.

Min-heap of (rank, position). For every adjacent pair that is in the merge list, push the entry (rank, position of its left node). The heap's minimum is the next merge to apply. Ties on rank pop by position, so occurrences of the same merge come out left to right.

Lazy invalidation. A merge changes the neighbourhood of \(i\): the pairs (prev, \(i\)) and (\(i\), next) are new, and old entries that mention \(i\) or \(j\) now describe pairs that no longer exist. Instead of finding and deleting those entries (a binary heap cannot do that cheaply; Day 4 compares the options), leave them in the heap and check each entry when it is popped. An entry \((r, i)\) is valid exactly when \(i\) is alive, \(i\) has a next node \(j\), and the pair (ids[i], ids[j]) has rank \(r\). Invalid entries are skipped. After a merge, push at most two entries: the two new neighbouring pairs, if they are in the merge list.

Worked example

Merges: aa = 256 (rank 256), ab = 257, aa+ab = 258. Chunk: aaab, positions 0 to 3.

starta·0⇄a·1⇄a·2⇄b·3Heap: (256, 0) (256, 1) (257, 2). Three adjacent pairs, all in the merge list.
pop 1aa·0⇄a·2⇄b·3(256, 0) valid. Node 0 absorbs node 1; node 1 is dead. New pair (aa, a) is not a merge: push nothing.
pop 2aa·0⇄a·2⇄b·3(256, 1) stale: node 1 is dead. Skip. This is the overlap rule: aaa gives aa, a, as in the simple encoder.
pop 3aa·0⇄ab·2(257, 2) valid. Node 2 absorbs node 3. New pair (aa, ab) has rank 258: push (258, 0).
pop 4aaab·0(258, 0) valid. One token. The heap is empty: done.
a·0 means token a in the node at position 0. Four pops, three merges, one stale entry skipped. Walking nxt from position 0 reads the output: [258].

Why it gives the same output as the simple encoder

The simple encoder processes ranks in increasing order: for the lowest rank present, it merges all its non-overlapping occurrences left to right, then looks again. We show the fast encoder does the same, by induction over the merges it applies.

  1. Invariant: the heap holds a valid entry for every current mergeable pair. True at the start (all pairs pushed). A merge creates only two new adjacent pairs, and both are pushed. Every other adjacent pair is unchanged, and its entry is still in the heap.
  2. A merge never creates a pair of lower or equal rank. The new pairs contain the new token \(r\). A merge involving token \(r\) can only have been learned after token \(r\) existed, so its rank is greater than \(r\). Hence once the minimum rank in the heap is \(r\), every occurrence of rank \(r\) that will ever exist is already present.
  3. Same order within a rank. Equal ranks pop by position, so occurrences of rank \(r\) are processed left to right. When two occurrences overlap (aaa), the left one merges first and the right one's entry becomes stale because its node died: exactly the simple encoder's left-to-right, non-overlapping rule.
  4. Stale entries are harmless. A popped entry is applied only if it passes the validity check, which describes a pair that exists now with the rank the entry claims. A rank identifies one pair, so a valid entry is a correct merge.

So the fast encoder applies the same merges at the same places in the same order, and its output is identical. The differential test in the solutions checks this on every Alice chunk and on 3,000 random strings.

Cost

Pushes: at most \(L - 1\) at the start, and at most 2 per merge. A merge removes one node, so there are at most \(L - 1\) merges, and at most \(3L\) pushes in total. Pops: each push is popped at most once, so at most \(3L\) pops. Each heap operation costs O(\(\log L\)) because the heap never holds more than \(3L\) entries. Splices are O(1). Total: O(\(L \log L\)) time, O(\(L\)) space for the arrays and the heap. The rank lookups are hash-map lookups, expected O(1) (Day 1).

The LRU cache (146)

The question. Natural text repeats: the is encoded thousands of times. Store each chunk's encoding so a repeat costs one lookup. Memory is bounded, so keep at most \(C\) entries, and when full, evict the least recently used one. Both get and put must be O(1).

First attempt. A hash map from chunk to (tokens, last-used time). Lookups are O(1), but eviction must scan all \(C\) entries for the oldest time: O(\(C\)). A list kept in recency order has the opposite problem: moving an entry to the front needs to find it first, O(\(C\)).

The key idea. Use both, linked to each other. A doubly linked list holds the entries in recency order, most recent at the head. A hash map sends each key to its list node. get: look up the node in the map (O(1)), unlink it (O(1), it knows its neighbours), and relink it at the head (O(1)). put: the same, and if the size exceeds \(C\), unlink the tail node and delete its key from the map. Two sentinel nodes, a fixed head and tail, mean every real node always has both neighbours, so there are no empty-list special cases.

Why it is correct. Invariant: the list order is the order of last use, and the map contains exactly the keys in the list. Each operation moves the touched key to the head and touches nothing else, so the order of the others is unchanged; the tail is therefore the least recently used key. Eviction removes it from both structures at once, so the invariant holds.

Cost. O(1) expected per operation (the map is the only "expected" part). Space O(\(C\)): one node plus one map entry per key.

Measured on Alice, encoding its 37,404 chunks in order (3,218 distinct): an LRU cache of 256 entries hits 71.9% of lookups, 1,024 entries hit 86.8%, 4,096 entries hit 91.4%. The last number is the ceiling: the cache is larger than the number of distinct chunks, so only the 3,218 first sightings miss (1 − 3,218 / 37,404 = 0.914).

Where BPE uses it. Production encoders put a lookup in front of the merge loop: Hugging Face tokenizers keeps a bounded cache of word encodings in its BPE model, and tiktoken first checks whether the whole chunk is itself a token. A cache must be bounded: an attacker (or a log file) can send millions of distinct chunks.

146 · LRU cache
class Node:
    __slots__ = ("key", "val", "prev", "next")
    def __init__(self, key=0, val=0):
        self.key, self.val, self.prev, self.next = key, val, None, None

class LRUCache:
    def __init__(self, capacity):
        self.cap, self.map = capacity, {}
        self.head, self.tail = Node(), Node()            # sentinels: no edge cases
        self.head.next, self.tail.prev = self.tail, self.head
    def _remove(self, n):
        n.prev.next, n.next.prev = n.next, n.prev
    def _push_front(self, n):
        n.prev, n.next = self.head, self.head.next
        self.head.next.prev = n; self.head.next = n
    def get(self, key):
        if key not in self.map: return -1
        n = self.map[key]; self._remove(n); self._push_front(n)
        return n.val
    def put(self, key, value):
        if key in self.map: self._remove(self.map[key])
        n = Node(key, value); self.map[key] = n; self._push_front(n)
        if len(self.map) > self.cap:
            lru = self.tail.prev; self._remove(lru); del self.map[lru.key]
bpe.py · O(L log L) encoder
def encode_chunk_fast(data, ranks):                  # ranks: pair -> new id (= rank order)
    ids = list(data); n = len(ids)
    if n < 2: return ids
    prev = list(range(-1, n - 1)); nxt = list(range(1, n + 1)); nxt[-1] = -1
    alive = [True] * n
    heap = [(ranks[(ids[i], ids[i + 1])], i) for i in range(n - 1) if (ids[i], ids[i + 1]) in ranks]
    heapq.heapify(heap)
    while heap:
        r, i = heapq.heappop(heap)
        j = nxt[i]
        if not alive[i] or j == -1 or ranks.get((ids[i], ids[j])) != r:
            continue                                     # stale entry
        ids[i] = r; alive[j] = False                     # i absorbs j
        nxt[i] = nxt[j]
        if nxt[j] != -1: prev[nxt[j]] = i
        for a in (prev[i], i):                           # the two new neighbouring pairs
            if a != -1 and nxt[a] != -1 and (ids[a], ids[nxt[a]]) in ranks:
                heapq.heappush(heap, (ranks[(ids[a], ids[nxt[a]])], a))
    out, i = [], 0
    while i != -1:
        out.append(ids[i]); i = nxt[i]
    return out

The order argument in one line: equal ranks pop left to right (the position is the second tuple field), and a newly created pair always has a higher rank than the merge that created it, because its token was learned later.

Algorithms · streams and scale: counting what you cannot store

The question

BPE's first step is "find the most frequent adjacent pair". On Alice that is easy: 119,226 pair occurrences, 665 distinct pairs, one Counter. On a 10 TB corpus, the objects we count (chunks, or pairs over a large vocabulary) number in the billions, and one exact counter per distinct object does not fit in memory. Can we find the most frequent items in one pass over a stream, with memory that does not grow with the number of distinct items, and say exactly how wrong the counts can be?

Definitions. A stream is a sequence \(x_1, \dots, x_n\) read once, in order. The frequency \(f(x)\) is how many times \(x\) occurs, so \(\sum_x f(x) = n\). A heavy hitter for threshold \(1/k\) is an item with \(f(x) > n/k\). There can be fewer than \(k\) of them, since \(k\) items each above \(n/k\) would sum to more than \(n\).

First attempt. A hash map of exact counts: O(1) per item, but memory O(number of distinct items), which is the problem. Sampling a fraction of the stream and counting the sample saves memory but gives no worst-case guarantee. The algorithms below give guarantees that hold for every stream.

(a) Majority vote: Boyer–Moore (169) and its n/3 version (229)

The question. One value occurs more than \(n/2\) times. Find it with O(1) memory.

The idea. Keep one candidate and a count. For each item: if the count is 0, the item becomes the candidate. If the item equals the candidate, add 1; otherwise subtract 1.

Why it is correct: cancellation. Each time the count goes down, pair the arriving item with one stored copy of the candidate. The two are different values, and both are now "cancelled". At any moment the items read so far split into (i) cancelled pairs, each holding two different values, and (ii) count uncancelled copies of the candidate. Let \(m\) be the majority value, \(f(m) > n/2\). A pair contains at most one copy of \(m\), and there are at most \(n/2\) pairs. If \(m\) were not the final candidate, every copy of \(m\) would sit in a pair, so \(f(m) \le n/2\): a contradiction. So the final candidate is \(m\). If the input might have no majority, a second pass counts the candidate to check.

Extending to \(n/3\) (229). Keep two candidates with two counts. An item that matches neither, when both counts are positive, decrements both: it cancels together with one copy of each candidate, so each cancellation removes three different values. There are at most \(n/3\) such rounds, and each removes at most one copy of any value. A value with \(f > n/3\) therefore keeps \(f - n/3 > 0\) copies, so it must be a final candidate. Candidates can be false, so a second pass checks both.

Cost. O(\(n\)) time, O(1) space (O(1) per candidate).

(b) Misra–Gries: the same cancellation with k − 1 counters

The algorithm. Keep at most \(k - 1\) (item, counter) entries. For each arriving \(x\): if \(x\) has a counter, add 1. Else if fewer than \(k - 1\) counters exist, give \(x\) a counter of 1. Else decrement every counter by 1, delete counters that reach 0, and drop \(x\). The estimate \(\hat f(x)\) is \(x\)'s counter, or 0. With \(k = 2\) this is exactly Boyer–Moore.

Worked example, \(k = 3\) (two counters), stream a b a c a b d a, \(n = 8\):

a b aa:2b:1Two counters, room for both.
ca:1b:0cDecrement round 1. Full, c is new: a, b, c each lose one copy (3 = \(k\) distinct items).
a ba:2b:1a increments; b takes the free counter.
da:1b:0dDecrement round 2.
aa:2End. True counts: a 4, b 2, c 1, d 1. Estimates: a 2, others 0. Every error is at most \(D = 2 \le n/k = 2.67\).

Why every estimate is within \(n/k\): proof. Let \(D\) be the number of decrement rounds. In one round, the dropped arrival and the \(k - 1\) stored items each lose one unit of count: \(k\) units, from \(k\) distinct items. Counters only grow by 1 per arrival, so at the end the counters sum to \(n - kD\). That sum is at least 0, so

\[ D \le \frac{n}{k}. \]

Now fix an item \(x\). Its counter is increased only by its own arrivals, so \(\hat f(x) \le f(x)\). It falls short of \(f(x)\) only in decrement rounds, and each round takes at most one unit from \(x\): either \(x\) is the dropped arrival, or \(x\) holds a counter and loses 1, never both, because an arrival that already has a counter is incremented, not dropped. So

\[ f(x) - \frac{n}{k} \;\le\; f(x) - D \;\le\; \hat f(x) \;\le\; f(x). \]

Consequence. Every item with \(f(x) > n/k\) has \(\hat f(x) > 0\), so it holds a counter at the end: the \(k - 1\) counters contain every heavy hitter. A second pass over the data with exact counts for these \(k - 1\) items removes the false ones.

Cost. Space: \(k - 1\) counters. Time: O(1) per increment, O(\(k\)) per decrement round; since there are at most \(n/k\) rounds, the total decrement work is O(\(n\)), so O(1) amortized per item.

(c) Space-Saving: overestimate instead of underestimate

The algorithm (Metwally, Agrawal and El Abbadi, 2005). Keep \(k\) (item, count, error) entries. For each arriving \(x\): if \(x\) is stored, add 1 to its count. Else if fewer than \(k\) entries exist, store \(x\) with count 1, error 0. Else find the entry \(y\) with the smallest count \(m\), replace \(y\) by \(x\), and set count \(m + 1\), error \(m\). Misra–Gries throws information away; Space-Saving hands the evicted count to the newcomer.

Worked example, \(k = 3\), the same stream a b a c a b d a: after a b a c a b the entries are a:3, b:2, c:1, all exact. d arrives with the table full; the minimum is c:1, so d takes it over with count 2, error 1. The final a makes a:4. Result: a 4 (true 4), b 2 (true 2), d 2 with error 1 (true 1).

Why it is correct: proof by induction on the stream. Let \(\mu\) be the smallest stored count once the table is full. We show three facts hold after every step:

  1. the stored counts sum to \(n\) (each arrival adds exactly 1 to some count, including a takeover: \(m \to m + 1\));
  2. for a stored \(x\): \(f(x) \le \hat c(x) \le f(x) + \text{err}(x)\), and \(\text{err}(x) \le \mu\);
  3. for an item not stored: \(f(x) \le \mu\).

\(\mu\) never decreases, since counts only grow and a takeover raises the minimum entry from \(m\) to \(m + 1\). An arrival of a stored \(x\) raises \(f\) and \(\hat c\) together, which keeps (2). When the table is full and an unstored \(x\) arrives, (3) says \(f(x) \le m\) before the arrival; afterwards \(f(x)\) is at most \(m + 1 = \hat c(x)\), and \(\hat c(x) - f(x) \le m = \text{err}(x) \le \mu\). The evicted \(y\) had \(f(y) \le \hat c(y) = m \le \mu\), which is (3) for \(y\). Fact (1) and \(k\) counts give \(\mu \le n/k\). Together:

\[ f(x) \;\le\; \hat c(x) \;\le\; f(x) + \mu \;\le\; f(x) + \frac{n}{k}. \]

Every item with \(f(x) > \mu\) is stored (by fact 3), and the stored error field gives a per-item bound that is usually much tighter than \(n/k\). The two algorithms are known to be equivalent (Agarwal et al., Mergeable Summaries, 2012): subtract the smallest Space-Saving count (with \(k\) counters) from every Space-Saving count, drop the non-positive ones, and you get exactly the Misra–Gries counters (with \(k - 1\)). The tests check this on 300 random streams. So Misra–Gries underestimates by at most \(\mu\), Space-Saving overestimates by at most \(\mu\); on Alice the largest Misra–Gries underestimate on the top 20 equals the Space-Saving minimum counter for every \(k\) we tried.

Cost. \(k\) entries. With a dictionary and a linear scan for the minimum (the code below), a takeover costs O(\(k\)). The paper's "stream summary" (a linked list of buckets, one per distinct count, each holding a linked list of items) makes every step O(1), because a count only ever moves to the next bucket.

(d) Count-Min sketch: hashing, with a probabilistic bound

The question. Misra–Gries and Space-Saving answer well only for heavy items. Can we estimate \(f(x)\) for any \(x\), with error at most \(\varepsilon n\), using memory independent of the number of distinct items?

The structure (Cormode and Muthukrishnan, 2005). A table of \(d\) rows and \(w\) columns of counters, all 0, and one hash function per row, \(h_j\) mapping items to columns \(0 \dots w - 1\). To add \(x\): for every row \(j\), add 1 to \(C[j][h_j(x)]\). To estimate: \(\hat f(x) = \min_j C[j][h_j(x)]\).

Worked example, \(d = 2\), \(w = 4\), stream a a b c a, hashes chosen by hand: row 1 sends a→0, b→1, c→0; row 2 sends a→2, b→2, c→3.

col 0col 1col 2col 3
row 14 (a×3 + c)1 (b)00
row 2004 (a×3 + b)1 (c)

\(\hat f(a) = \min(4, 4) = 4\), true 3: a collides in both rows. \(\hat f(b) = \min(1, 4) = 1\) and \(\hat f(c) = \min(4, 1) = 1\), both exact: each collides in one row, and the other row rescues it. That is why we take the minimum over independent rows.

Why it is correct: the \((\varepsilon, \delta)\) bound. Every cell that \(x\) touches contains all \(f(x)\) of \(x\)'s arrivals plus whatever else hashed there, so each row overestimates and \(\hat f(x) \ge f(x)\). Fix a row \(j\) and define its error

\[ X_j = C[j][h_j(x)] - f(x) = \sum_{y \ne x} f(y)\, \mathbf{1}[h_j(y) = h_j(x)]. \]

Choose \(h_j\) at random from a universal family: for any two different items, \(P(h_j(y) = h_j(x)) \le 1/w\). By linearity of expectation,

\[ \mathbb{E}[X_j] \le \sum_{y \ne x} f(y) \cdot \frac{1}{w} \le \frac{n}{w}. \]

\(X_j\) is non-negative, so Markov's inequality, \(P(X \ge a) \le \mathbb{E}[X]/a\), applies with \(a = e \cdot n/w\):

\[ P\!\left(X_j \ge \frac{e\,n}{w}\right) \le \frac{n/w}{e\,n/w} = \frac{1}{e}. \]

The rows use independent hash functions, so the minimum is large only if every row is large:

\[ P\!\left(\hat f(x) - f(x) \ge \frac{e\,n}{w}\right) = \prod_{j=1}^{d} P\!\left(X_j \ge \frac{e\,n}{w}\right) \le e^{-d}. \]

Now pick the sizes. With \(w = \lceil e/\varepsilon \rceil\) we get \(e\,n/w \le \varepsilon n\). With \(d = \lceil \ln(1/\delta) \rceil\) we get \(e^{-d} \le \delta\). So

\[ f(x) \;\le\; \hat f(x) \;\le\; f(x) + \varepsilon n \quad \text{with probability at least } 1 - \delta. \]

Cost. \(w \cdot d = \lceil e/\varepsilon \rceil \lceil \ln(1/\delta) \rceil\) counters, independent of the number of distinct items. \(d\) hash evaluations per add and per query. The hash used below, \(h(x) = ((a x + b) \bmod p) \bmod w\) with \(p\) a prime and \(a \ne 0\), \(b\) random, is the classic universal family (CLRS, universal hashing). Two sketches with the same hash functions add cell by cell, so a sketch per shard merges into the sketch of the whole corpus. Unlike Misra–Gries, Count-Min also supports decrements.

(e) Reservoir sampling: a uniform sample from a stream of unknown length

The question. Keep a uniformly random sample of \(k\) items from a stream whose length \(n\) is not known in advance, using O(\(k\)) memory. (Sampling documents for the tokenizer's training set is this problem.)

First attempt. Store everything, then sample: O(\(n\)) memory. Keep each item with a fixed probability \(q\): the sample size is random, and \(q\) needs \(n\).

Algorithm R. Keep the first \(k\) items. For the \(i\)-th item with \(i > k\): draw \(j\) uniformly from \(\{0, \dots, i - 1\}\); if \(j < k\), replace slot \(j\) by the item. So item \(i\) enters with probability \(k/i\), and evicts a uniformly chosen slot.

Why it is correct: induction. Claim: after \(i \ge k\) items, every one of them is in the reservoir with probability \(k/i\). Base \(i = k\): all are kept, probability \(1 = k/k\). Step from \(i\) to \(i + 1\): the new item enters with probability \(k/(i+1)\), as required. An old item is in the reservoir with probability \(k/i\) by the hypothesis. It is evicted only if the new item enters and picks its slot: probability \(\frac{k}{i+1} \cdot \frac{1}{k} = \frac{1}{i+1}\). So it survives with probability \(\frac{i}{i+1}\), and

\[ P(\text{old item kept after } i+1) = \frac{k}{i} \cdot \frac{i}{i+1} = \frac{k}{i+1}. \]

Example with \(k = 1\) and three items: item 3 is kept with probability \(1/3\); item 1 survives with probability \(1 \cdot \frac12 \cdot \frac23 = \frac13\).

Cost. O(1) per item (one random draw), O(\(k\)) memory. 382 Linked List Random Node is \(k = 1\) over a list whose length is unknown. 398 Random Pick Index is \(k = 1\) over the sub-stream of indices whose value equals the target.

Does an approximate top pair pick the same merge?

Let \(p_1\) be the true top pair and \(p_2\) the runner-up, with gap \(g = f(p_1) - f(p_2)\). Suppose every estimate satisfies \(f \le \hat f \le f + \text{err}\). Then \(\hat f(p_1) \ge f(p_1)\), and every other pair has \(\hat f(q) \le f(q) + \text{err} \le f(p_2) + \text{err}\). So if \(g > \text{err}\), the approximate argmax is \(p_1\): the same merge. If \(g \le \text{err}\), the summary may pick another pair.

On Alice, \(g = 3{,}978 - 3{,}686 = 292\). Space-Saving guarantees err \(\le n/k\), so the first merge is guaranteed once \(k \ge 409\) (\(119{,}226 / 292 = 408.3\)); with \(k\) = 50, 100, 200 the guarantee does not cover it, although the measured top pair was right in all three. Count-Min with \(\varepsilon = 0.001\) (\(\varepsilon n = 119 < 292\)) guarantees it with probability at least 0.99.

For the rest of training the answer is mostly no. We recorded the gap \(g_t\) and the total pair count \(n_t\) at each of the 1,744 merges of the Alice trainer. Only 9 merges have \(g_t > 0.001\, n_t\), and 7 of those are among the first 10. In 1,510 of the 1,744 merges, the top two counts are exactly tied (\(g_t = 0\)): late merges are decided by the tie-break rule, and any counting error can flip them. There is a second obstacle: after each merge the pair counts change, so a one-pass summary of the original stream does not describe step 2. Approximate counting can choose the first few merges and can shrink the input; it cannot replace the exact merge loop.

Where BPE uses it

Not inside the merge loop, as measured above. Before it: a Count-Min pass over a huge corpus finds the chunks that occur at least \(T\) times (it never underestimates, so no frequent chunk is lost), and only those get exact counters. Reservoir sampling draws a fixed-size uniform sample of documents per language for the tokenizer's training set. Both are covered in the Design block.

169 and 229 · majority vote
def majority_element(nums):                      # 169: some value occurs more than n/2 times
    cand, count = None, 0
    for x in nums:
        if count == 0:
            cand = x                             # everything before has cancelled out
        count += 1 if x == cand else -1          # a different value cancels one copy
    return cand

def majority_element_ii(nums):                   # 229: all values occurring more than n/3 times
    c1, n1, c2, n2 = None, 0, None, 0
    for x in nums:
        if x == c1: n1 += 1
        elif x == c2: n2 += 1
        elif n1 == 0: c1, n1 = x, 1
        elif n2 == 0: c2, n2 = x, 1
        else: n1 -= 1; n2 -= 1                   # x, c1, c2: three distinct values cancel
    return [c for c in (c1, c2) if c is not None and nums.count(c) > len(nums) // 3]
stream.py · Misra–Gries
def misra_gries(stream, k):
    """k-1 counters. For every x: true(x) - n/k <= cnt.get(x, 0) <= true(x)."""
    cnt = {}
    for x in stream:
        if x in cnt:
            cnt[x] += 1
        elif len(cnt) < k - 1:
            cnt[x] = 1
        else:                                    # x plus k-1 stored items: k distinct, cancel one each
            for y in list(cnt):
                cnt[y] -= 1
                if cnt[y] == 0:
                    del cnt[y]
    return cnt
stream.py · Space-Saving
def space_saving(stream, k):
    """k counters. For a stored x: true(x) <= cnt[x] <= true(x) + err[x], err[x] <= min counter <= n/k."""
    cnt, err = {}, {}
    for x in stream:
        if x in cnt:
            cnt[x] += 1
        elif len(cnt) < k:
            cnt[x], err[x] = 1, 0
        else:
            y = min(cnt, key=cnt.get)            # O(k) here; the "stream summary" bucket list makes it O(1)
            m = cnt.pop(y); del err[y]
            cnt[x], err[x] = m + 1, m            # x inherits y's count, so it may be over by m
    return cnt, err
stream.py · Count-Min sketch
P = (1 << 61) - 1                                # a prime larger than any key

class CountMin:
    def __init__(self, eps, delta, seed=0):
        self.w = math.ceil(math.e / eps)         # error <= eps * n ...
        self.d = math.ceil(math.log(1 / delta))  # ... with probability >= 1 - delta
        rng = random.Random(seed)
        self.ab = [(rng.randrange(1, P), rng.randrange(P)) for _ in range(self.d)]
        self.rows = [[0] * self.w for _ in range(self.d)]
    def _cols(self, x):                          # x: a non-negative integer key
        return [((a * x + b) % P) % self.w for a, b in self.ab]
    def add(self, x, c=1):
        for row, col in zip(self.rows, self._cols(x)):
            row[col] += c
    def estimate(self, x):                       # never below the true count
        return min(row[col] for row, col in zip(self.rows, self._cols(x)))
    def merge(self, other):                      # same seed => same hashes: add cell by cell
        for r1, r2 in zip(self.rows, other.rows):
            for i, v in enumerate(r2):
                r1[i] += v
stream.py · reservoir sampling (algorithm R)
def reservoir_sample(stream, k, rng):
    res = []
    for i, x in enumerate(stream, start=1):      # x is the i-th item
        if i <= k:
            res.append(x)
        else:
            j = rng.randrange(i)                 # uniform in 0 .. i-1
            if j < k:                            # probability k / i
                res[j] = x                       # evicts a uniformly chosen slot
    return res
382 · Linked List Random Node
class Solution:                                  # 382 Linked List Random Node (reservoir, k = 1)
    def __init__(self, head):
        self.head = head
    def getRandom(self):
        chosen, i, node = None, 0, self.head
        while node:
            i += 1
            if random.randrange(i) == 0:         # keep the i-th node with probability 1/i
                chosen = node.val
            node = node.next
        return chosen
398 · Random Pick Index
class Solution:                                  # 398 Random Pick Index
    def __init__(self, nums):
        self.nums = nums
    def pick(self, target):
        chosen, seen = -1, 0
        for i, x in enumerate(self.nums):
            if x == target:
                seen += 1
                if random.randrange(seen) == 0:  # reservoir over the matching indices only
                    chosen = i
        return chosen

Design · training on terabytes, serving at scale

Prompt: train a tokenizer on a 10 TB multilingual corpus, then serve encoding for an API handling 50,000 requests per second.

Training: what parallelizes and what does not

Map: count chunks per shard. Each worker reads one shard, splits it with the pattern, and counts chunks. Chunk counts are a sufficient statistic for training (Day 4): the merge loop never needs the raw text again. Reduce: sum the counters. Addition is associative and commutative, so the shard counters can be combined in any order or in a tree. This is word count, the classic MapReduce job. Then drop chunks seen fewer than a few times.

The merge loop is sequential. Merge \(t\) is the argmax of the pair counts after merge \(t - 1\) has been applied. Each merge changes the counts of the pairs around it, so merge \(t\) cannot be chosen before merge \(t - 1\) is known. Distributing it would need a global synchronization per merge, 200,000 of them for a 200k vocabulary. After deduplication the chunk counter is small enough for one machine, so the loop runs there.

Where sketches and sampling fit

  • Pruning before exact counting. If the unique chunks of a shard do not fit in memory, first build a Count-Min sketch per shard, merge them by addition, and keep exact counters only for chunks whose estimate is at least the pruning threshold \(T\). Count-Min never underestimates, so no chunk with true count \(\ge T\) is lost; the cost is a few false positives, which the exact pass then counts correctly.
  • Top chunks per shard. Space-Saving or Misra–Gries summaries are mergeable, so per-shard summaries combine into a summary of the corpus with the same kind of guarantee: useful for monitoring what dominates the data.
  • The training mix. Reservoir sampling draws a fixed number of documents per language from a stream of unknown length, which sets the language balance of the tokenizer's corpus. That balance decides the token tax (ML block).
  • Not the merge loop. On Alice, 1,510 of 1,744 merges were exact ties and only 9 had a gap above \(0.001\,n_t\). Approximate counts would change the merge list.

Serving a tokenizer

  • Determinism. The same text must always give the same ids: no dropout at inference, a fixed tie-break, and the regex and Unicode versions pinned (a new Unicode version can reclassify characters and change the split).
  • The tokenizer is part of the model's contract. Token ids index the embedding table. Ship the merges file with the model, store its SHA-256 in the model config, and refuse to start on a mismatch.
  • Caching. A bounded LRU cache of chunk encodings, as in 146. On Alice, 1,024 entries already hit 87% of chunks. Bound it: unique strings (logs, base64) would otherwise exhaust memory.
  • Throughput. Tokenize in the API layer, before the GPU queue: the token count is needed for routing, rate limits and billing. Use compiled code (tiktoken and tokenizers are in Rust) and the O(\(L \log L\)) encoder so that a long chunk cannot stall a worker.

count.py · map and reduce
from collections import Counter
from multiprocessing import Pool

def map_shard(lines):                            # PATTERN: the split regex from the week reading
    return Counter(c for line in lines for c in PATTERN.findall(line))

def reduce_counts(counters):
    total = Counter()
    for c in counters:
        total.update(c)
    return total

if __name__ == "__main__":                       # required where workers are spawned (macOS, Windows)
    lines = open("data/alice.txt").read().splitlines()
    with Pool(4) as pool:
        total = reduce_counts(pool.map(map_shard, [lines[i::4] for i in range(4)]))
    assert total == map_shard(lines)             # same counter as one pass

The __main__ guard matters: on macOS and Windows, worker processes re-import the script, and without the guard each worker would start its own pool.

Fleet sizing: if one core encodes \(t\) tokens/s on real traffic (measure it; the cache hit rate dominates), the fleet needs \(5 \times 10^7 / t\) cores, plus headroom for peaks (×2) and failures (+1 zone). Mismatch detection: the model's config stores the SHA-256 of the merges file; the server hashes the tokenizer it loads and refuses to start on a difference.
